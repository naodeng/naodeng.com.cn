Testing every email address is not thorough; it is a way to run out of time. The useful question is which inputs share the same rule and which one breaks away.

Equivalence Partitioning groups inputs expected to behave the same, then selects representatives that cover valid, invalid, empty, and conditional classes.

The Equivalence Partitioning Skill is useful when a team needs a structured review of valid and invalid classes, empty values, type, format, business rule, and representative selection. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

## Equivalence Partitioning Skill: what it is for

A practical standard for this Skill is simple: A good partition follows behavior, not syntax alone. Two strings may share a format but belong to different business classes when one is an active owner and the other is unknown.

Use it when the team needs a repeatable review of valid and invalid classes, empty values, type, format, business rule, and representative selection—especially when several evidence sources disagree or a handoff must explain what remains unverified.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Input rules | Type, format, allowed values, optionality, and business conditions | Keep separate rules separate |
| Behavior oracle | Expected result, error, empty set, or normalization | A class needs an observable outcome |
| Dependencies | Fields whose valid class changes with another field | Record conditional partitions |

Use a request like this:

```text

Task: design input classes for a search API that accepts date range, status, owner, and free-text filters
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.
```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Partition map | Class definition, representative, and source rule | Valid, invalid, or conditional |
| Coverage choice | Values selected and values deliberately omitted | Reason |
| Gap | Class with no oracle or ambiguous behavior | Clarification action |

Do not write “passed” without a run record, query result, or source artifact. A good partition follows behavior, not syntax alone. Two strings may share a format but belong to different business classes when one is an active owner and the other is unknown.

## Run one focused pass

Start with a bounded pass—design input classes for a search API that accepts date range, status, owner, and free-text filters. For a date filter, create classes for omitted dates, valid same-day ranges, reversed ranges, future ranges, invalid time zones, and ranges beyond retention. Choose one representative for each, then add boundary values where the class changes.

The handoff should preserve the input version, time window, evidence index, owner, and next validation action. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, keep the output limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.

A richer input changes the answer here because valid and invalid classes, empty values, type, format, business rule, and representative selection must be tied to evidence rather than inferred from a familiar pattern.

## Common traps

1. Grouping by data type while ignoring business behavior.
2. Choosing one valid example and calling the class covered.
3. Missing conditional classes created by account or state.

## Two practical questions

### Do partitions replace boundary tests?

No. Partitions reduce the space; boundary testing chooses values where behavior changes.

### What if two classes look identical?

Keep one only when the source and observable behavior are identical; otherwise record the uncertainty.

The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
