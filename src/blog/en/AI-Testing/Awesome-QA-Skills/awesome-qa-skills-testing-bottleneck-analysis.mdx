A testing bottleneck is not always a slow test. It may be a shared environment, a review queue, missing data, a specialist handoff, or a capacity rule that no dashboard captures.

## Why this Skill is needed

The Testing Bottleneck Analysis Skill examines wait queues, dependencies, capacity, handoffs, and evidence for testing constraints. It converts a delay complaint into an evidence-bounded improvement path.

## What the Skill does

The output should identify the next measurable constraint, not just the longest-looking queue.

Use this Skill to review why testing work waits, where flow stops, and what evidence can distinguish demand, capacity, dependency, or handoff constraints. It does not invent root causes or approve a process change.

A useful finding names the queue, dependency, capacity or handoff signal, time window, evidence state, priority, owner, close condition, and smallest validation.

Use it when test work is repeatedly waiting for environments, data, reviews, specialists, or CI capacity and the team needs a decision-ready diagnosis.

## What it does not do

The Testing Bottleneck Analysis Skill can organize queue, dependency, capacity, and handoff evidence and propose the next check. It does not replace:

- Confirmation of rules, scope, and risk by the accountable domain owner.
- A real environment, account, dataset, log, or run record; static analysis does not become runtime evidence by itself.
- Authorization for release, compliance, production actions, or residual-risk acceptance.
- A Human decision when supplied sources conflict.

## What it checks

The goal is not simply to find the longest queue. Identify where work waits and whether the available events distinguish queue time, service time, dependency, or handoff delay. Start with a matrix based on the source Skill's output contract:

| Focus | Question before analysis | Handoff output |
| --- | --- | --- |
| Stage and constraint | Which queue, dependency, capacity, or handoff has a wait | Related event, source, and evidence state |
| Impact scope | Which releases, validation scope, or risks are affected | Affected work and priority rationale |
| Validation plan | Smallest change that distinguishes candidate causes | Comparison window, measures, and stop condition |
| Decision boundary | Which capacity or process choices need owner approval | Decision maker, authority, and residual risk |

If a row has only a conventional expectation and no source or validation method, keep it open instead of turning it into a pass.

## Audit inputs before you start

Before analysis, assign one of six evidence states to each input. Missing or conflicting timestamps limit causal claims, but do not automatically prove a process failure.

| State | Meaning | How this Skill should handle it |
| --- | --- | --- |
| known | Directly supported by the supplied material | Keep the source, version, and time with the judgment |
| missing | Needed for this pass but not supplied | Name the smallest evidence action and limit the conclusion |
| conflicting | Sources disagree | Show both sources and route the conflict to an owner |
| stale | Present but outside the relevant version or time window | Mark freshness; old evidence is not current proof |
| out_of_scope | Related but excluded from this pass | Keep the boundary explicit |
| assumptions | Temporarily adopted to continue analysis | State how and when the assumption will be checked |

Keep the input version, scope, environment, evidence locations, and accountable owner together. Without a run record, deliver analysis, design, or a validation plan—not an execution pass.

## From problem to structured Finding

Connect the source, scope, evidence state, analysis, owner, action, close condition, and validation before writing the conclusion. The case below keeps this Skill’s identifier and domain context.

### Keep the decision layers separate

Keep facts, evidence-backed inferences, recommendations, and Human decisions separate in the report:

| Layer | How to write it | Application here |
| --- | --- | --- |
| Fact | What the supplied material directly shows | Cite the source, version, input, or run record for the focus |
| Evidence-backed Inference | What several facts support together | Show the inference chain and retain uncertainty |
| Recommendation | The smallest next action | Name the evidence, review, execution, or regression path |
| Human Decision | What an accountable person must decide | Leave scope, risk acceptance, resources, and release meaning to the owner |

## A complete case

The checkout release example below uses a wait for staging and security review to show how a timeline becomes a testable hypothesis. Keep missing, conflicting, or assumed material visible.

### Input

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Flow evidence | Arrival, wait, service, handoff, queue, and completion timestamps | Keep missing timestamps explicit |
| Dependencies | Environment, data, approval, service, and specialist constraints | Separate observed dependency from assumption |
| Capacity | Workers, environments, review slots, windows, and utilization | Do not infer saturation from complaints |
| Decision boundary | Owner, experiment, stop condition, and change authority | Human decides the trade-off |

Use a request like this:

~~~text
Use the testing-bottleneck-analysis Skill.

Task: Diagnose why checkout release validation waits two days for a shared staging environment and a security review.
Inputs: [queue timestamps, environment bookings, review handoffs, capacity, blocked reasons, release calendar]
Scope: [last four releases]
Constraints: [do not invent root cause or promise throughput improvement]

Separate wait queue, dependency, capacity, handoff, and evidence findings. Give priority, owner, close condition, and a measurable next action.
~~~

### Analysis

Separate arrival, queue, service, handoff, and completion time. Compare releases only when event definitions, time windows, and scope are comparable; without them, the cause remains unverified.

### Finding

#### Focused example: Separate staging scarcity from security-review handoff

Suppose the example timestamps show a release waiting for staging while security review begins only after a manual handoff. Environment capacity and handoff sequence are separate candidate causes and need separate checks; a long queue alone does not prove that staging capacity is insufficient.

## Turn the hypotheses into comparable experiments

Choose the smallest change that distinguishes the hypotheses. Keep the current security review and release gates; change handoff order only if the responsible owners confirm that parallel work is allowed. Change one condition at a time and record other changes that could affect the wait.

| Hypothesis | Smallest validation | Observation and boundary |
| --- | --- | --- |
| Staging capacity is insufficient | Within authorized scope, add an isolated environment slot and compare booking waits for similar release windows | Check both environment wait and total cycle time; differences in workload, test scope, or release timing limit attribution |
| Security review is delayed by handoff order | If policy permits, let reviewers assess the same evidence pack while the environment is prepared | Compare review start/end and total wait; do not skip a required review or count preparation as approval |
| Test execution time is the actual delay | Separate queue time from service time, then analyze slow steps independently | Route to runtime optimization only when service time is a substantial part of the delay; queue length is not test duration |
| Capacity or event data is missing | Capture arrival, ready, actual start, completion, and blocked-reason times | Keep the cause unassessed until the timeline can be reviewed; do not fill unknowns by adding staff |

Before comparing, define each timestamp and timezone and fix the release scope and observation window. Retain the raw events, calculation rules, experiment conditions, stop conditions, and unexplained differences. A diagnosis can propose a change; it cannot prove root cause, throughput gain, or release readiness before validation.

#### Example finding: turn one problem into a handoff

Follow the handoff example above. Suppose the summary shows that review starts after manual handoff, but supplies no full booking or service timestamps. Record the gap like this:

| Field | Example record |
| --- | --- |
| Source and scope | Booking, review handoff, and CI timeline for the last four checkout releases; use the supplied versions |
| Finding | The timeline shows review after manual environment handoff but lacks stage-level wait and service time, so the primary constraint is unknown |
| Evidence state | If only summary durations are supplied and arrival/start events are missing, mark cause `missing` / `unassessed`; do not infer saturation |
| Impact and priority | The gap may extend release validation; rank it by affected release scope and the risk being investigated |
| Owner and open decision | The pipeline owner supplies the timeline; the security owner confirms whether review preparation may happen in parallel |
| Action and close condition | Validate timestamp definitions, then run one authorized experiment; close only when the changed wait stage and remaining confounders are visible |
| Validation | Compare booking, review start/end, environment-ready, and validation-complete records for similar windows; retain raw events and calculations |

This record names the remaining question, its owner, and a check that can change the diagnosis.

### Decision

The accountable owner confirms the decision question and risk trade-off; the Skill does not make that choice.

### Validation

Before closing the finding, run the stated validation and retain the raw artifact. Without an execution record, the status remains unverified.

## How a Finding enters the next stage

### Handoff output

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Constraint finding | Observed queue, dependency, capacity, or handoff issue | Source and evidence state |
| Impact | How delay affects validation or risk | Priority and scope |
| Experiment | Smallest change that distinguishes hypotheses | Expected observation |
| Decision boundary | What requires Human capacity or process choice | Owner and residual risk |

Every conclusion should point to a source, evidence state, and next action. If evidence is missing, use pending, blocked, unassessed, or NOT_SCORED instead of filling the gap with confidence.

### Next-stage route

Route each gap to the owner who can provide evidence or authorize a process change:

| Gap | Next owner | Handoff goal |
| --- | --- | --- |
| Arrival, start, or completion times are missing | CI, environment, or review-system owner | Define the events and how they link to a release |
| Queue and service time are mixed together | Flow owner and analyst | Calculate wait and processing time by stage and show uncovered intervals |
| Handoff sequence may add delay | Security review and release owners | Confirm whether parallel preparation is allowed while retaining required approvals |
| More environment capacity or staff is proposed | Authorized engineering manager | Decide on capacity, scope, and review date from the evidence |

Later conclusions remain bounded by the evidence state; the diagnosis does not authorize a process or capacity change.

## How to prepare better input

Provide a fixed release window, queue and service timestamps, blocked reasons, dependency map, capacity schedule, handoff ownership, and the decision the analysis supports. Missing timestamps remain unassessed.

Keep input versions, scope, observation window, event definitions, evidence locations, assumptions, and the Human decision boundary in the handoff, plus the smallest validation action.

## Common traps

1. Calling the longest queue the bottleneck without checking downstream wait or service time.
2. Using utilization or complaints as proof of capacity saturation.
3. Changing process before defining a small experiment and success evidence.

## FAQ

### Does this Skill automatically recommend more people?

No. It identifies evidence and trade-offs; capacity changes are a Human planning decision.

### What if timestamps are incomplete?

Return a bounded diagnosis, mark causal findings unassessed, and request the smallest missing event timestamps.

The Skill is most useful when attached to one real project artifact and kept with its source evidence. Start narrow, validate the uncertain part, and expand only when evidence supports it.
