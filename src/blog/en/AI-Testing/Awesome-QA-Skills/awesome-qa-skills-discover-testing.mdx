When you inherit an unfamiliar project or receive a vague testing request, it is easy to pick a Skill and start too soon. First understand the goal, project entry points, dependencies, environment, risks, and existing tests; then choose the capability that fits the work.

discover-testing supports this exploration and routing. It inventories relevant QA Skills, project materials, and information gaps. If the goal itself is unclear, ask a clarifying question before routing. Whether a Skill is installed or available in the current host requires evidence from the current environment or inventory; a directory in a repository does not prove availability.

## Start with the goal and project context

State the desired outcome, current phase, scope, and anything that must not be touched. Then inspect repository entry points, dependencies, test structure, environment, and relevant documentation. Separate observed facts from inferences and questions. Do not use internal memory in place of project material.

You can start with a request like this:

~~~text
Use discover-testing to explore this testing task.

Goal: [problem to solve or expected deliverable]
Project material: [repository, requirements, tests, run records, and versions]
Scope: [included and excluded journeys]
Constraints: [environment, data, permissions, time, and compliance]

First check whether the goal is clear and the material is accessible.
List known facts, risks, gaps, and relevant Skills, then select one primary Skill.
Suggest one helper only when it is genuinely needed, and state the handoff input.
Do not treat a Skill in the repository as installed in the current host.
~~~

When the goal is unclear, a focused question is more useful than a long list of recommendations. Ask about missing information that would change the route: is the task to design tests, import old cases, retrieve existing cases, or review a change?

## Choose one primary Skill, then decide whether a helper is needed

Route by user intent and available material, not keywords alone. Start with one primary Skill. Add at most one helper only when a distinct step falls outside the primary Skill’s scope.

For example, when searching a test asset library, test-case-retrieval can find candidates. A person then selects the intended records. If selected legacy cases need migration, hand them to test-case-importer. Search candidates do not become import authorization or an import list automatically. When the request is to guide or review Red, Green, and Refactor, consider tdd-quality-workflow instead of routing it as ordinary test design.

The routing result should explain why the Skill was selected, which inputs are missing, what evidence is needed next, and what has not been executed. If there is no explicit evidence of host installation or capability, mark availability as unknown.

## Use AI to explore, then check its sources

AI can quickly organize repository entry points, test directories, and candidate workflows, and split a broad request into open questions. Each factual claim should trace to an accessible file, a user-provided record, or a named source. Do not use internal model memory, conversation logs, or unreviewable conclusions as user-facing evidence.

| Output | What to verify |
| --- | --- |
| Task goal | Is it clear enough to route, or should it be clarified? |
| Project facts | Is there a file, version, or run record behind each one? |
| Risks and gaps | Which are source-backed and which remain inferences? |
| Skill route | Does the primary Skill fit, and is a helper necessary? |
| Next step | Are inputs, handoff, and execution permissions clear? |

Exploration is a bounded assessment. It does not mean tests ran or authorize project actions.

### Can the Skill recommend several options?

It can list candidates for comparison, but routing should settle on one primary Skill. Add at most one helper when there is a separate, well-defined handoff.

### What if I cannot find installation evidence?

Keep host availability as UNKNOWN and check the current tool or installation inventory. Repository source, a website details page, and local installation are different kinds of evidence.

### Can retrieved cases be imported automatically?

No. A person should confirm the candidate records, provenance, and target before proceeding to import preview and confirmation.
