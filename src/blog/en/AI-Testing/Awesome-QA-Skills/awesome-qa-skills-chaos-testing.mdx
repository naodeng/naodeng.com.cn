Chaos testing is a controlled failure experiment built around an explicit hypothesis. Before anyone proposes injection, the design needs a measurable steady state, a bounded blast radius, sourced stop conditions, and an owner for rollback.

## Why this Skill is needed

Chaos Testing designs controlled failure experiments that connect a hypothesis to steady-state signals, blast radius, stop conditions, and recovery evidence.

## What the Skill does

The Chaos Testing Skill is useful when a team needs a structured review of hypothesis, steady state, failure injection, blast radius, guardrail, recovery, and learning.

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) organizes Skills by language and testing stage. The [series overview](https://inaodeng.com/en/blog/ai-testing/introduction_of_awesome_qa_skills/) explains the shared installation model; this guide stays with Chaos Testing.

A practical standard for this Skill is simple: A good chaos test is boringly specific. It knows the steady state, the first signal that matters, the maximum blast radius, and the exact condition that stops the experiment.

Use it when the team needs a repeatable review of hypothesis, steady state, failure injection, blast radius, guardrail, recovery, and learning—especially when several evidence sources disagree or a handoff must explain what remains unverified.

## What it does not do

The Chaos Testing Skill can prepare and review the experiment design. It does not authorize fault injection, access real dependencies, or replace:

- Confirmation of rules, scope, and risk by the accountable domain owner.
- A real environment, account, dataset, log, or run record; static analysis does not become runtime evidence by itself.
- Authorization for release, compliance, production actions, or residual-risk acceptance.
- A Human decision when supplied sources conflict.

## What it checks

The value of this Skill is not another keyword list. It connects each focus area to an observable input, a judgment, and a way to close the loop. Start with a small matrix based on the source Skill's output contract:

| Focus | Question before analysis | Handoff output |
| --- | --- | --- |
| Hypothesis and steady state | What must remain true, over which sourced window, compared with which baseline or control | A falsifiable hypothesis |
| Injection and blast radius | Fault, target, duration, traffic or instance fraction, dependencies, isolation, and exclusions | A bounded experiment card |
| Stop and rollback | Measurable stop rule, monitoring cadence, stop owner, and recovery action | Readiness blockers and owner |
| Before/during/after evidence | Functional, data, and recovery signals compared with the baseline and control | Evidence status and residual risk |

If a row has only a conventional expectation and no source or validation method, keep it open instead of turning it into a pass.

## Audit inputs before you start

Before designing a fault-injection scenario, classify the input into six evidence states. A gap is not automatically a failure, but it must not disappear inside the conclusion.

| State | Meaning | How this Skill should handle it |
| --- | --- | --- |
| known | Directly supported by the supplied material | Keep the source, version, and time with the judgment |
| missing | Needed for this pass but not supplied | Name the smallest evidence action and limit the conclusion |
| conflicting | Sources disagree | Show both sources and route the conflict to an owner |
| stale | Present but outside the relevant version or time window | Mark freshness; old evidence is not current proof |
| out_of_scope | Related but excluded from this pass | Keep the boundary explicit |
| assumptions | Temporarily adopted to continue analysis | State how and when the assumption will be checked |

Keep the input version, scope, environment, evidence locations, and accountable owner together. Without a run record, deliver analysis, design, or a validation plan—not an execution pass.

## From problem to structured Finding

Connect the source, scope, evidence state, analysis, owner, action, close condition, and validation before writing the conclusion. The case below keeps this Skill’s identifier and domain context.

### Keep the decision layers separate

For each chaos finding, do not compress four different kinds of language into “recommended to pass”:

| Layer | How to write it | Application here |
| --- | --- | --- |
| Fact | What the supplied material directly shows | Cite the source, version, input, or run record for the focus |
| Evidence-backed Inference | What several facts support together | Show the inference chain and retain uncertainty |
| Recommendation | The smallest next action | Name the evidence, review, execution, or regression path |
| Human Decision | What an accountable person must decide | Leave scope, risk acceptance, resources, and release meaning to the owner |

## A complete case

This case follows Input, Analysis, Finding, Decision, and Validation. When material is incomplete, keep missing, conflicting, or assumptions visible instead of turning them into a pass.

### Input

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Experiment hypothesis | Expected degradation, user impact, and recovery condition | Do not start with an unbounded failure |
| Guardrails | Traffic scope, abort threshold, permissions, and communication plan | Name the person who can stop the experiment |
| Signals | Latency, errors, fallback rate, business conversion, and recovery logs | Define baseline before injection |

Use a request like this:

```text
Use the chaos-testing Skill.

Task: test whether a recommendation service keeps checkout usable when its feature store becomes unavailable
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.
```

### Analysis

Treat this as a design-only example: a sample brief asks whether recommendations can tolerate a feature-store timeout and excludes checkout from the experiment. The brief supplies no target fraction, duration, baseline, measurable stop threshold, test environment, or rollback owner. Mark those inputs `missing`; do not substitute a convenient percentage. Execution readiness stays blocked until an accountable owner supplies the values and authorizes an isolated, reversible test. A later run would compare sourced recommendation and checkout invariants before, during, and after the fault against the stated baseline or control. This article records no run or result.

The handoff should preserve the input version, time window, evidence index, owner, and next validation action. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

### Finding

#### Example finding: turn one problem into a handoff

The field example below shows the recording pattern; it is not an execution result.

Use the source prompt's `CHS-##` contract for each finding. This example records missing execution-readiness evidence; it is not a claim that a system failed.

| `CHS-01` field | Bounded example |
| --- | --- |
| Object/rule and source | Recommendation path; sample brief and its version must be attached |
| Trigger/applicability | Feature-store timeout; target and excluded checkout path must be confirmed |
| Expected concern/rationale | Safe recommendation behavior and checkout isolation, as stated by the sample objective |
| Evidence state | `missing`: fraction, duration, baseline, stop threshold, environment, and rollback owner are not supplied |
| Impact/priority and owner | Not scored from this brief; service owner and experiment stop owner need confirmation |
| Close condition | Approved scope, sourced thresholds, monitor cadence, stop owner, and rollback/recovery steps are reviewable |
| Validation method | Review the card, then run only in the authorized isolated environment and retain before/during/after artifacts; no execution is claimed here |

The point is to let the next person walk from the finding back to the source and run an action that can change the decision.

### Decision

The accountable owner confirms the decision question and risk trade-off; the Skill does not make that choice.

### Validation

Before closing the finding, run the stated validation and retain the raw artifact. Without an execution record, the status remains unverified.

## How a Finding enters the next stage

### Handoff output

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Hypothesis/control | Sourced invariant and baseline or control group | Design status |
| Injection/boundary | Fault, target, duration, exposure, dependencies, and exclusions | Scope and authorization |
| Stop/recovery | Threshold, cadence, stop owner, rollback, and recovery evidence | Readiness blockers |
| Learning | What the before/during/after evidence supports or leaves unknown | Owner and next action |

Do not write “passed” without a run record and raw evidence. A design card is preparation, not an experiment result.

### Next-stage route

At minimum, hand off the source, evidence state, owner, close condition, and validation action; the next-stage conclusion remains bounded by the evidence state.

## How to prepare better input

If the first request contains only a one-line goal, keep the output limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.

A richer input changes the answer here because hypothesis, steady state, failure injection, blast radius, guardrail, recovery, and learning must be tied to evidence rather than inferred from a familiar pattern.

## Common traps

1. Injecting failure without a steady-state baseline.
2. Expanding blast radius because the first metric looks fine.
3. Calling recovery complete before user and business signals return.

## FAQ

### Can chaos experiments run in production?

Only with explicit authorization, guardrails, communication, and a reversible failure mechanism.

### What if no business metric is available?

State the gap and use the smallest reliable proxy; do not claim user impact is known.

The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
