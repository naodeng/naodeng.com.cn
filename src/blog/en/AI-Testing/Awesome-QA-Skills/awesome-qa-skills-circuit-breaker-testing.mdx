A circuit breaker that opens quickly but never probes recovery is just a permanent outage with better terminology.

Circuit Breaker Testing validates failure thresholds, open and half-open transitions, fallback behavior, probe traffic, and recovery without causing a retry storm.

The Circuit Breaker Testing Skill is useful when a team needs a structured review of failure threshold, state transition, fallback, probe request, reset timing, and downstream protection. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) organizes Skills by language and testing stage. The [series overview](https://inaodeng.com/en/blog/ai-testing/introduction_of_awesome_qa_skills/) explains the shared installation model; this guide stays with Circuit Breaker Testing.

## Circuit Breaker Testing Skill: what it is for

A practical standard for this Skill is simple: A useful breaker test follows state, traffic, and user behavior together. It checks that open state protects the dependency, half-open state limits probes, and recovery does not turn into a sudden surge.

Use it when the team needs a repeatable review of failure threshold, state transition, fallback, probe request, reset timing, and downstream protection—especially when several evidence sources disagree or a handoff must explain what remains unverified.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Breaker policy | Failure count or rate, open duration, half-open probes, and reset rule | Keep time windows explicit |
| Dependency behavior | Timeout, 5xx, slow response, recovery, and partial failure | Different failures may have different classification |
| Fallback contract | Cache, default result, queue, or user message | Verify the fallback is safe for the journey |

Use a request like this:

```text
Use the circuit-breaker-testing Skill.

Task: test a recommendation dependency protected by a circuit breaker during a regional timeout event
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.
```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| State trace | Closed, open, half-open, and reset transitions | Trigger and timestamp |
| Fallback result | User and downstream behavior while open | Safe, degraded, or unsafe |
| Recovery finding | Probe, storm, stuck-open, or premature-close issue | Repair action |

Do not write “passed” without a run record, query result, or source artifact. A useful breaker test follows state, traffic, and user behavior together. It checks that open state protects the dependency, half-open state limits probes, and recovery does not turn into a sudden surge.

## Run one focused pass

Start with a bounded pass—test a recommendation dependency protected by a circuit breaker during a regional timeout event. Inject slow responses until the breaker opens, send normal traffic while it is open, then restore the dependency and observe half-open probes. Record fallback rate, probe count, transition timestamps, and the first request that safely returned to normal.

The handoff should preserve the input version, time window, evidence index, owner, and next validation action. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, keep the output limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.

A richer input changes the answer here because failure threshold, state transition, fallback, probe request, reset timing, and downstream protection must be tied to evidence rather than inferred from a familiar pattern.

## Common traps

1. Testing only the open transition.
2. Letting every request probe during half-open.
3. Treating fallback success as dependency recovery.

## Two practical questions

### Should a circuit breaker be tested with real traffic?

Use a controlled environment or approved traffic slice; the point is observable state transitions, not uncontrolled disruption.

### What if fallback data is stale?

Record freshness and user impact as part of the fallback contract; stale is not automatically safe.

The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
