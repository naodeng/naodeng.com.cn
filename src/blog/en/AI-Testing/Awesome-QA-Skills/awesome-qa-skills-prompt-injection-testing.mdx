Prompt Injection Testing checks whether untrusted text can override an application's instruction hierarchy, expose protected data, or cause an unauthorized tool action. The work is a defensive test plan for an authorized environment; it is not permission to target real systems or sensitive data.

## Define trust boundaries and safe scope first

Collect the system prompt, trusted and untrusted sources, retrieval paths, tool permissions, sensitive asset categories, security policy, and prohibited actions. If any are missing, record assumptions and open questions before proposing cases. Use safe placeholder data and a sandbox or mock.

| Input source | Test question | Evidence to retain |
| --- | --- | --- |
| Direct user input | Does untrusted text change higher-priority instructions or exceed the task? | Input ID, prompt version, response and refusal state |
| Retrieved document or web page | Can embedded instructions cross the source boundary? | Source ID, retrieval trace, generated action |
| Tool output | Can a result steer a later call outside its permission? | Tool response, next-call arguments, authorization result |
| Multi-turn context | Does a rejected instruction persist into a later turn? | Turn IDs, memory state, later tool calls |

## Check refusal and side effects together

Build an attack corpus for direct and indirect injection, instruction hierarchy, data exposure, tool abuse, encoding obfuscation, multi-turn persistence, and detection or recovery. Each case should state the authorized preconditions, stimulus, expected behavior, and required evidence.

A refusal is not sufficient if the application still performs a write or sends data. In a mock or authorized sandbox, record whether a blocked request leaves state unchanged, whether a tool call was attempted, and how the system explains the stop. Do not include real credentials or sensitive target details in test inputs.

## Prioritize findings without overstating them

Rank confirmed risks using the project's impact scale. Keep a hypothesis separate from observed behavior, and list what remains untested. A useful handoff contains the threat model, attack-case IDs, security assertions, evidence, mitigation ideas, and regression cases. The Skill structures verification; it does not certify that the whole application is secure.

For model behavior and task quality, see [LLM Testing](/en/qaskills/llm-testing/). For tool permission and side-effect checks, see [Agent Tool Call Testing](/en/qaskills/agent-tool-testing/); broader controls are covered by [Security Testing](/en/qaskills/security-testing/).
