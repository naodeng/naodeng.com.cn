Agent Memory Testing reviews what an assistant stores, retrieves, updates, and forgets across users and sessions. A useful result follows each memory item back to its source and policy; the final answer alone cannot show which version was retrieved.

## Keep a traceable memory record

For each supplied item, preserve the tenant and user scope, memory ID, content version, source, write time, expiry, and consent, withdrawal, or deletion status. Link the retrieved item and its provenance to the response so a reviewer can inspect the same evidence.

## Compare retrieval across scope and time

Use the project’s actual consistency window and preference precedence rules. Compare the visible memory set for the same query across two tenants, and keep an authorized retrieval as a control. Check whether an update exposes stale content, whether an expired item still appears, and whether retrieval after withdrawal or deletion follows the supplied policy.

Do not assume last-write-wins or invent a retention period. If precedence, expiry, deletion propagation, or the expected consistency window is missing, leave that judgment open.

## Follow one item through update and deletion review

The following is an illustrative isolated-environment scenario; expected behavior must still come from the project's policy. Use two synthetic preference values to follow one memory item from write through deletion:

| Stage | Check | Evidence to retain |
| --- | --- | --- |
| Write | Create a memory in an authorized test tenant | Tenant and user scope, memory ID, source, version, write time, consent state, and expiry policy |
| Update | Change the test preference from A to B, then query within the policy's consistency window | Update event, returned memory ID and version, retrieval result, and provenance |
| Delete | Submit an authorized deletion request and inspect the stores named by policy | Deletion request ID, checks for each storage scope, completion state, and time |

If the old value is still retrieved after an update, compare it with the policy's propagation window and version rules. An empty result from one query does not prove that every store has been cleared. If backup or propagation policy is missing, limit the conclusion to the scopes that were checked. Missing retrieval traces, deletion scope, or authorization evidence means “insufficient evidence” or “needs confirmation”; this plan is not proof of execution.

## Trace deletion through the real storage scope

Compare the deletion request with evidence for the index, cache, and backup scope that the project actually uses. A missing propagation or backup-retention policy limits the conclusion; absence from one search result does not prove erasure from every store.

## Distinguish memory lifecycle from access permission

Memory testing follows stored state over time: provenance, freshness, tenant isolation, retention, and forgetting. Agent Permission Testing: https://inaodeng.com/en/qaskills/agent-permission-testing/ evaluates whether a principal may perform a particular read or tool action. Both can matter, but one result does not establish the other.

## Record an AMT-## finding

Capture the object or rule, source, trigger or applicability, expected concern, evidence state, impact and priority, owner role, close condition, and validation method. Keep confirmed facts, inferences, candidate checks, and Human decisions distinct.

## Keep validation isolated

Review supplied policies, memory records, retrieval traces, and deletion evidence as static material. If further validation is needed, propose the smallest authorized check using masked data, mocks, or an isolated environment. Do not claim execution or complete deletion without the relevant evidence.

## FAQ

**Does one empty retrieval prove that a memory was deleted?** No. It shows only that this query returned no result through the current retrieval path. Check the indexes, caches, and other stores named by the actual architecture and policy, and retain evidence for each scope.

**Will invoking the Skill inspect a live account automatically?** This review uses supplied materials. Any runtime validation needs prior authorization and an isolated environment with redacted data or mocks.
