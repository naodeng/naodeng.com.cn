Observability starts with a question an operator must answer during a failure: which user flow is affected, where did it break, and what evidence can narrow the cause? This Skill reviews whether the telemetry design can answer that question before implementation.

## When this Skill helps

Use Observability Design Review for logging, metrics, traces, context propagation, SLO and SLI definitions, alerts, sampling, retention, privacy, and cost. It reviews supplied designs and produces OBS-## findings. It does not query production signals, run probes, assess an incident, or declare system health.

## Review workflow

Start by naming the service boundary, business flow, environment, version, and time window. Classify each input as known, missing, conflicting, stale, out_of_scope, or assumptions. Then trace a failure path across the signals that should explain it.

| Signal area | Questions to answer |
| --- | --- |
| Logs | Which event and fields identify the object and outcome? Are sensitive values masked? |
| Metrics | Are units, dimensions, cardinality, and aggregation semantics explicit? |
| Traces | Do spans preserve context across service and asynchronous boundaries? |
| Alerts | What condition triggers the alert, who responds, and what action follows? |
| Operations | Are sampling, retention, access, and cost constraints stated? |

Do not fill in missing SLOs, thresholds, retention periods, or sample rates from platform defaults. Record the source and evidence state for each conclusion.

## Worked example

Suppose a supplied checkout design shows a gateway request ID, a payment-provider request ID, and an order-worker event, but does not explain how those identifiers join. An OBS finding should name the affected checkout path, show which design sections were reviewed, describe the correlation gap, and give a safe validation action such as checking a masked synthetic request across the planned spans.

A second finding might show an alert rule with no response owner or runbook action. The handoff should ask the team to define the action and validate it in an isolated environment. These are examples of review findings, not claims about a live service.

## What to hand off

Each OBS-## should identify the signal and covered object, source and evidence status, expected fields or semantics, gap and impact, detection action, owner role, close condition, and validation method. Keep design facts, evidence-backed inferences, recommendations, and Human decisions separate. If runtime identity, time, environment, or raw signals are missing, mark runtime conclusions unverified or unassessed.

## Boundaries

A dashboard proves that a view was designed; it does not prove that an alert fires or that a service is healthy. Do not choose SLOs, incident severity, sample rates, retention, or cost budgets for the owner. Keep production data out of a design-only review.
