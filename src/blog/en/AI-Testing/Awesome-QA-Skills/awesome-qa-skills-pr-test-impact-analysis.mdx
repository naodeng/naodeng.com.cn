The files changed by a PR do not directly tell you which behaviors are affected. A shared function can reach several business entry points; choosing tests by directory can miss consumers elsewhere in the call chain.

pr-test-impact-analysis uses the actual changes to map affected behavior, dependencies, and test scope. Judgments should trace to evidence instead of filenames alone. When risk is high but impact evidence is weak, expand the review or preserve uncertainty.

## Build a traceable impact chain from the diff

Provide exact base/head commits, the complete diff, requirements or interface contracts, relevant consumers, and existing test mappings. Record the chain:

**Changed symbol → consumer → behavior obligation → test ID, level, and revision**

For example, a change to order validation may affect an API, a background job, and a UI flow. Find the consumer paths, confirm the expected behavior for each, and map them to unit, API, end-to-end, or regression tests. A filename containing “order” does not prove that all relevant tests are covered.

If the repository lacks call graphs or test mappings, return candidate paths with explicit gaps and a minimal validation action. High-risk changes, shared interfaces, historical defects, and weak evidence call for a wider scope. Both selected and excluded checks need a rationale.

## A prediction is not a run result

Prediction statuses describe the expected relationship between a test and the current change. Run statuses describe whether execution happened and what it returned. Keep these separate.

| Prediction | Meaning | Example run status |
| --- | --- | --- |
| PREDICTED_PASS | Current analysis expects the test to pass | RUN_PASS: a matching run record passed |
| PREDICTED_FAIL | Current analysis expects failure or a finding | RUN_FAIL: a real run record failed |
| UNCERTAIN | Available evidence cannot predict the result | NOT_RUN or UNKNOWN: no run or status is unknown |

A prediction is not a test result. A command or CI record, matching revision, and actual outcome are needed for run status. A green result from an older revision is not evidence for the new diff.

## Use AI to trace impact while preserving sources

AI can read the diff, search call relationships, and organize candidate tests. The reviewer should confirm that each path points to a symbol, dependency, or contract, and that test ID, level, and revision match.

~~~text
Use pr-test-impact-analysis to assess this PR's test impact.

Versions and scope: [base/head, file scope, included and excluded paths]
Code evidence: [complete diff and relevant symbols]
Project basis: [requirements, contracts, consumers, test mappings, and past defects]
Constraints: [environment, time, and permissions]

Trace “changed symbol → consumer → behavior obligation → test ID/level/revision.”
Cite a source for each judgment; do not infer from filenames alone.
Assign PREDICTED_PASS, PREDICTED_FAIL, or UNCERTAIN, and keep predictions
separate from actual run status.
~~~

When a PR changes, recompute affected paths from the new diff. Keep the tests and judgments that changed, those that stayed the same, and those that need review. Old conclusions do not become new evidence automatically.

### Can I propose scope without test mappings?

Yes, as candidate paths with the evidence gap and validation method stated. In a high-risk area, weak evidence usually means expanding the check, not shrinking it.

### Is PREDICTED_PASS the same as a passing test?

No. It is an analysis prediction. RUN_PASS requires a real run record for the relevant revision.

### Which risks need human confirmation?

Owners should confirm scope trade-offs, excluded areas, residual risk, and release decisions. The Skill organizes evidence and options; it does not approve risk for the team.
