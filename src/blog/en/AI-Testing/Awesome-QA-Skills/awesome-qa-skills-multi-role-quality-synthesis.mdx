The same release can present four different risk pictures to product, QA, engineering, and operations. Synthesis is not stapling reports together; it resolves evidence conflicts into shared decision language.

The Multi-role Quality Synthesis Skill aligns perspectives, assumptions, and unresolved risks so cross-functional teams can decide without pretending disagreement does not exist.

The membership-upgrade example shows how Product, QA, Engineering, and UX findings can be synthesized while preserving each source, evidence limit, and unresolved decision.

## How synthesis receives reports across one delivery workflow

The Product, QA, UX, and Technical articles use the same development stages, but each has a different focus. Multi-role synthesis receives reports from the same stage, records sources, classifies facts, merges equivalent findings, and preserves conflicts. It does not create an averaged opinion.

| Development stage | Inputs to synthesis | Synthesis output |
| --- | --- | --- |
| Requirements analysis | Product rules, QA testability, technical constraints, UX task evidence | Shared facts, input gaps, role disagreements, and questions to resolve |
| Test strategy | Coverage priorities, technical risks, experience paths, and project constraints | Separate quality facts from project constraints and retain each source's trade-offs |
| Test strategy review | Role views on scope, exit criteria, and downgrade risk | Agreement, conflict severity, blockers, and action sources |
| Code review | Product impact, QA static findings, technical diff observations, and UI impact | Merge only equivalent findings; retain code identity and evidence limits |
| Test case writing | Business rules, testable entry points, technical failure modes, and UX states | Relevant agreement, gaps, and conditions that still need an owner |
| Test case review | Executability, coverage, observability, and user paths | Separate facts, risks, and recommendations; do not report recommendations as run results |
| Test reporting | Command results, product impact, runtime signals, and UX observations | Align run identity and scope; preserve verified, not_run, and blocked states |
| Test report review | Role conclusions, evidence, project requirements, and residual risk | Shared facts, disagreements, decision options, approver, and information gaps |

Here, delivery means handing off a synthesis report; it does not mean release approval. A nearing project date cannot turn an unrun QA case into a completed one, and a Product view cannot override high-risk evidence in a technical report.

## Keep inputs from different roles mergeable

When combining Product, QA, UX, and Technical perspectives, preserve disagreements so the quality conclusion remains actionable.

| Role | Focus | Evidence to include | Decision it does not make for another role |
| --- | --- | --- | --- |
| Product | User tasks, conversion, and business rules | Funnel, acceptance record, user feedback | Whether to change scope or goals |
| QA | Coverage, gaps, and residual risk | Cases, run records, defects | Whether to accept insufficient test evidence |
| Engineering | Stability, dependencies, and recovery | Logs, metrics, traces, rollback records | Whether to accept a technical trade-off |
| UX | Task flow, states, accessibility, and recovery | Prototype, screenshots, recordings, reproduction steps | Whether to accept an experience trade-off |

Project Delivery Perspective can separately provide scope, dependencies, dates, and owners. Treat those as project constraints, not as a quality-role report. First check whether each input has a source, time window, and clear object of observation.

## Separate shared facts from conflicting judgments

Suppose a payment callback passed in staging. Product may focus on conversion, QA on exception coverage, and Engineering on production configuration differences. One fact can support different judgments.

| Synthesis section | How to write it | Example |
| --- | --- | --- |
| Shared fact | Evidence every role can point to | Staging payment callback passed; build is build-42 |
| Conflicting judgments | Keep each role's observation and impact separate | QA has no timeout case; Engineering found the rollback window insufficient |
| Decision needed | List options, risk, approver, and due time | Release after reducing scope, pending Product approval |

Do not compress disagreement into “overall risk is manageable.” Decision-makers need to see the risk of each option and the evidence still missing.

## Membership upgrade example: from four reports to one decision-ready output

The following inputs are hypothetical and show how the six articles can connect in a real workflow. Replace source_id, version, environment, and evidence links with project material in actual use. Register project delivery constraints separately from role reports.

| source_id | Source type | Stage | Observation and evidence |
| --- | --- | --- | --- |
| PROD-42 | Product | test-report-review | PRD-42 says benefits should appear immediately after payment succeeds, but does not define the user experience when a callback takes more than 10 seconds |
| QA-42 | QA | test-report-review | RUN-42 exercised only the successful callback; timeout and duplicate submission are marked not_run |
| TECH-42 | Engineering | test-report-review | PR-42's callback client has no timeout configuration; the code observation is from commit abc123 and runtime behavior is unverified |
| UX-42 | UX | test-report-review | REC-42 shows no progress explanation while waiting in iPhone Safari, but covers only one device and one path |

Register the project constraint separately:

| source_id | Source type | Stage | Constraint and evidence |
| --- | --- | --- | --- |
| DELIVERY-42 | Project constraint, not a quality report | test-report-review | The delivery calendar sets a review for Friday at 18:00; the payment provider committed to a sandbox callback by Thursday at 12:00 |

The synthesis should separate the material into four layers rather than conclude that “most roles think it is ready”:

| Synthesis area | Example wording | Source |
| --- | --- | --- |
| Quality fact | One successful callback has a run record; timeout and duplicate submission have not been run | QA-42 |
| Technical finding | No timeout configuration was seen in code; this static observation does not prove that production will time out | TECH-42 |
| Experience finding | One recording shows insufficient waiting feedback, with limited device and path coverage | UX-42 |
| Project constraint | A decision meeting is scheduled for Friday and the sandbox callback has an external commitment time | DELIVERY-42 |
| Disagreement and decision | Confirm whether Product accepts the scheduled review; QA and Technical inputs call for timeout evidence first, and no approver is recorded | PROD-42, QA-42, TECH-42, DELIVERY-42 |

A handoff record can use this structure so Project Delivery Perspective does not need to rebuild source attribution:

```yaml
stage: test-report-review
common_facts:
  - id: FACT-01
    statement: One successful callback has a run record
    sources: [QA-42]
role_observations:
  - source_id: TECH-42
    finding: No timeout configuration was seen in the callback client
    evidence: Code observation from commit abc123
    status: static_observation
  - source_id: UX-42
    finding: Waiting state lacks a progress explanation
    evidence: REC-42
    status: limited_observation
conflicts:
  - topic: Whether the review can proceed on schedule
    sources: [PROD-42, QA-42, TECH-42]
    unresolved_reason: Timeout and duplicate-submission evidence is missing
decision_options:
  - option: Review after reducing scope
    approver: pending
    required_evidence: [timeout callback result, rollback criteria]
status: pending
```

The statuses static_observation and limited_observation are deliberate. Synthesis can organize them, but cannot promote them to verified or release-approved. The summary can be short, but stage coverage, quality facts, project constraints, agreement, disagreement, blockers, actions, and sources must remain. The Skill does not vote or invent an approver.

```text
Version and environment: [requirement / build / environment]
Inputs: [file paths or links]
Scope: [included and excluded journeys]
Constraints: [time, data, permissions, compliance]

Register each source and keep shared facts, role observations, project constraints, conflicts, decision options, and missing evidence separate. Preserve verified, static_observation, limited_observation, not_run, and blocked states. Do not invent approval or turn a role recommendation into a release decision.
```

## Synthesis preserves conflicts and routes decisions

A multi-role summary does not need one forced conclusion. Separate common facts, conflicting observations, and pending decisions so the accountable owner can choose with the evidence visible.

## Who should use this Skill

Teams preparing a cross-functional test report review can use it to combine Product, QA, Engineering, and UX reports without flattening their boundaries. Delivery leads can then track owners and dates against the same source-linked record.

## Review a synthesis before handoff

| Review item | What to retain | If missing |
| --- | --- | --- |
| Stage and scope | Same-stage reports, versions, and included journeys | List the sources or stages still missing |
| Source identity | source_id, source link, observation window, and owner | Keep the claim unverified until it can be traced |
| Shared facts and conflicts | Facts, role-specific views, impact, and disagreement | Do not replace them with a consensus phrase |
| Project constraints | Scope, dependencies, date, and delivery owner | Keep them separate from quality conclusions |
| Decision record | Options, evidence needed, approver, and due time | Leave the decision pending |

## Common questions

### Must a synthesis report have only one conclusion?

No. Keeping common facts, conflicting views, and pending decisions separate makes the accountable owner's choice traceable.

### What if one role has no input?

Mark the role absent or label any proxy analysis. List questions for that role; do not invent its observations.

### Who makes the final decision?

An authorized Product, release, or Technical owner approves an option. The Skill makes the evidence and risk visible.

### Can a release proceed without agreement?

The team can discuss it, but must list unresolved risks, the accepter, and the due time. Without those, there is no auditable release decision.

Run a synthesis on reports from the same stage and retain source IDs, inputs, output, and review notes. The examples provide structure; project evidence must come from the project.
