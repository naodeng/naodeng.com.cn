A diagram can be complete enough to present and still omit the boundary that will fail in production. Technical design review is where those omissions become questions before they become code.

The Technical Design Quality Review Skill reviews ADRs, component designs, data flows, and non-functional constraints before implementation. It produces TD-## findings and validation preparation without reviewing unsupplied code or approving an architecture.

The review should expose assumptions that the first implementation or validation must make explicit.

## Technical Design Quality Review Skill: what it is for

Use this Skill to inspect boundaries, dependencies, failure modes, data consistency, security, performance, observability, compatibility, maintainability, and verification readiness in a supplied design.

A good finding names the design topic, source evidence, impact, priority, gap action, owner, decision question, and validation method.

Use it when an architecture note, ADR, component design, or technical proposal needs an implementation-readiness pass while important details remain uncertain.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Design material | ADR, diagrams, interfaces, data flow, constraints, and success criteria | List unsupplied design areas |
| Version and scope | Revision, components, environments, traffic, data, and compatibility boundary | Do not infer from names |
| Risk topics | Dependencies, failures, security, performance, observability, and maintenance | Assess topics separately |
| Verification readiness | Test ideas, metrics, fixtures, owners, and safe environment | Keep unverified claims open |

Use a request like this:

~~~text
Use the technical-design-quality-review Skill.\n\nTask: Review a design for a multi-tenant invoice export service before implementation.\nInputs: [ADR, data flow, API contract, tenant boundary, storage plan, threat notes, observability plan]\nScope: [export jobs, object storage, customer access]\nConstraints: [no code or production probe supplied]\n\nProduce TD-## findings across boundaries, dependencies, failures, data, security, performance, observability, compatibility, maintainability, and verification readiness. Keep design claims separate from runtime evidence.
~~~

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Design finding | The topic, source, impact, and priority | TD ID and evidence |
| Gap action | What must be clarified or added | Owner and decision question |
| Validation preparation | Smallest check for the design claim | Environment and evidence |
| Human boundary | What remains an architecture or risk decision | Not an approval |

Every conclusion should point to a source, evidence state, and next action. If evidence is missing, use pending, blocked, unassessed, or NOT_SCORED instead of filling the gap with confidence.

## Focused example: Review tenant isolation in an export design

The design stores export files under a tenant-prefixed path but does not specify how download authorization checks the tenant ID. The Skill should record the boundary and trace it to API, storage, and audit evidence, then request a safe validation. It should not infer isolation from the path name or approve the design.

The review assesses the supplied design and prepares validation. It cannot prove implementation compatibility, security, capacity, latency, or release readiness.

## Improve the first result with better baseline input

Provide the current design revision, scope, interfaces, dependency assumptions, data classification, non-functional objectives, observability plan, and intended validation environment. Missing design material stays unassessed.

A useful handoff includes input versions, scope, time window, evidence index, assumptions, Human decision boundary, and the smallest validation action.

## Common traps

1. Checking that a diagram exists without checking boundaries, failure handling, or recovery.
2. Treating “supports high concurrency” or “has monitoring” as a verification criterion.
3. Turning a recommendation into an approved architecture or release conclusion.

## Two practical questions

### Can this Skill review code?

Only code supplied as design evidence can be referenced. It must not claim to have reviewed unsupplied implementation.

### Does a clean design review mean the build will pass?

No. Build, compatibility, security, and performance still need their own execution evidence.

The Skill is most useful when attached to one real project artifact and kept with its source evidence. Start narrow, validate the uncertain part, and expand only when evidence supports it.
