Authentication testing follows the proof of a user's identity through challenges, sessions, recovery, expiry, and revocation. It asks which state the service should recognize after each event and what evidence would establish that state. Identity verification is separate from deciding what an authenticated user may do.

## Why this Skill is needed

A successful login screen says little about what happens to an earlier session after logout, whether an expired link can create a new session, or how a recovery route relates to multi-factor authentication. Those questions depend on the product's rules; familiar security conventions are not a substitute for supplied policy.

## What the Skill does

The Authentication Testing Skill organizes evidence-bounded scenarios around credentials, identity states, failure paths, and lifecycle. It can prepare reviewable validation candidates from redacted requirements, token metadata, session records, audit events, and existing reports.

## Model state transitions, not just login forms

Use the states supported by the supplied authentication mechanisms. A password, email link, MFA challenge, federated assertion, or recovery token can have different rules, so do not invent which methods are mandatory or how long they remain valid.

| Event or state | Evidence to compare | Question to resolve from policy |
| --- | --- | --- |
| Unauthenticated → challenged | Challenge issued, recipient or factor, request context | Which mechanism and trigger apply? |
| Challenged → authenticated | Server-side state and newly issued session or token metadata | What counts as a completed challenge? |
| Authenticated → expired, locked, or revoked | Current session state and validity of earlier credentials | Which event ends or restricts this identity? |
| Recovery → authenticated | Recovery proof, replacement credential, notification, audit event | Which controls apply to recovery and how does recovery close? |

The source Skill also calls for creation, rotation, expiry, revocation, and replay rules. Compare the service's authentication state, token issuance, and old-credential validity after each supplied event. Keep authentication separate from authorization: a valid identity does not prove that a payout change or other resource action is permitted.

## Audit the evidence before modeling a risk

The Prompt requires six input states. For authentication, the gaps often concern a policy, state transition, or evidence source.

| State | Example | How to handle it |
| --- | --- | --- |
| known | A versioned requirement defines an MFA challenge before changing a payout account | Cite the requirement and its effective version |
| missing | Token lifetime, link reuse, or logout behavior is unspecified | Leave the expected result unresolved |
| conflicting | UI copy and server policy describe different expiry rules | Keep both sources and route the conflict to an owner |
| stale | A prior token report refers to a superseded identity service | Do not treat it as current lifecycle evidence |
| out_of_scope | Authorization to change another user's payout account is excluded | Keep the authorization question separate |
| assumptions | A draft assumes a recovery link can be issued in a test fixture | Name the owner and validation needed to retain the assumption |

Separate redacted identity state and token metadata from secret credential values. A login screenshot alone does not establish server-side authentication state or that an earlier credential stopped working.

## Example: passwordless login with step-up MFA

Consider a design request for passwordless login using an email link, followed by step-up MFA before a payout-account change. The request does not specify link lifetime, single-use behavior, device binding, lock thresholds, or what logout revokes. These remain policy questions; this example does not assert a vulnerability or describe an executed test.

### AUT-01 candidate: replay of an email authentication link

Use this candidate only if the supplied requirement says that the link is single-use or otherwise defines replay behavior.

| Finding field | Example record |
| --- | --- |
| Object and applicability | Email authentication link; applies only when a source defines its recipient, expiry, reuse, and any device-binding rules |
| Preconditions and stimulus | An approved isolated test identity and a policy-backed issued link; a separate session attempts reuse after the first accepted use. This is a proposed scenario, not an action taken by the Skill. |
| Expected concern and evidence | If the contract is single-use, determine whether reuse can create another authenticated state or session. Compare server-side state, redacted token metadata, prior-session validity, and audit events; do not infer a bypass from a missing log. |
| Source and evidence state | The example request supplies no policy, service log, or run record; mark **UNASSESSED** until those inputs exist |
| Impact, priority, and owner | Assess impact from the protected account action and product scope; leave priority pending evidence. Route to the authentication or security test owner. |
| Stop condition | Stop and escalate if the policy conflicts, a production identity or personal credential enters scope, or an unexpected authenticated state is observed. |
| Validation and close condition | A separately authorized executor may validate the rule in an isolated environment without exposing credential values. Close only when the expected transition, evidence source, owner, and residual risk are reviewable. |

The Skill does not log in, call real APIs, read credentials, or execute this candidate. Its result is a proposed validation with explicit conditions, not proof that link replay is possible or prevented.

## Keep account recovery and enumeration in scope

Recovery can issue or replace credentials, change sessions, and notify an identity owner. Model which state changes are expected after recovery and whether earlier sessions or tokens remain valid; use only the supplied policy to decide. If the recovery contract is absent, record the transition as missing.

If requirements define different responses for existing and non-existing accounts, compare the documented response and timing evidence. Keep an enumeration concern as a risk candidate until evidence shows disclosure; do not label it a confirmed vulnerability from a conventional expectation alone.

## Hand off the lifecycle evidence

For each candidate, pass the source rule, applicability, preconditions, trigger, expected concern, evidence state, impact and priority rationale, owner, stop condition, close condition, and validation method. Keep facts, evidence-backed inferences, candidate recommendations, and Human decisions distinct. Risk acceptance, exceptions, and release judgment stay with an accountable person.

## Prepare useful input

Provide the authentication mechanisms in scope, roles, identity states, relevant policy versions, environment boundaries, redacted token/session metadata, audit evidence, and known gaps. Exclude real credential values. If input is incomplete, return a bounded model and name the smallest policy or artifact needed to continue.

## Common mistakes

1. Treating authentication as a substitute for authorization.
2. Assuming token lifetime, MFA policy, replay behavior, or lock thresholds without a source.
3. Testing only the first login and ignoring expiry, revocation, recovery, or prior sessions.
4. Calling a candidate or static review a confirmed exploit—or claiming security from a missing finding.

## FAQ

### Does authentication testing decide whether a user may change a payout account?

No. Authentication establishes identity; authorization and transaction policy determine which actions that identity may perform.

### What if email-link expiry or reuse rules are missing?

Keep expected behavior unresolved, mark the related item unassessed, and request the policy owner and smallest source needed before treating it as a test oracle.
