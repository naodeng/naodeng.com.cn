A language model can answer the same question differently without being wrong. It can also change one eligibility decision while keeping the prose almost identical.

LLM Consistency Testing defines which parts of an output must remain stable, which variation is acceptable, and what repeated evidence can show drift.

The LLM Consistency Testing Skill is useful when a team needs a structured review of semantic invariants, structured fields, acceptable variation, repetition, version, and drift. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

## LLM Consistency Testing Skill: what it is for

A practical standard for this Skill is simple: A good consistency test begins with invariants. It does not demand identical prose, but it does demand that a deadline, exclusion, amount, or required field cannot change silently.

Use it when the team needs a repeatable review of semantic invariants, structured fields, acceptable variation, repetition, version, and drift—especially when several evidence sources disagree or a handoff must explain what remains unverified.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Consistency contract | Stable facts, required fields, allowed wording variation, and threshold | Do not compare raw strings as meaning |
| Replay setup | Prompt, document, model version, retrieval context, temperature, and run count | Record every variable that can drift |
| Oracle | Fact extraction, schema validation, semantic comparison, and human review | Define what counts as a material change |

Use a request like this:

```text
Use the llm-consistency-testing Skill.

Task: test a policy summarizer that must preserve deadlines, exclusions, and source references across repeated runs
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.
```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Stable fact result | Facts preserved, omitted, changed, or invented | Source and run IDs |
| Variation judgment | Acceptable wording or material behavior drift | Threshold and rationale |
| Regression action | Prompt, model, retrieval, evaluator, or review change | Owner and next replay |

Do not write “passed” without a run record, query result, or source artifact. A good consistency test begins with invariants. It does not demand identical prose, but it does demand that a deadline, exclusion, amount, or required field cannot change silently.

## Run one focused pass

Start with a bounded pass—test a policy summarizer that must preserve deadlines, exclusions, and source references across repeated runs. Run the same policy document 20 times and compare extracted deadlines, exceptions, and source spans. Allow sentence order to vary; flag a run that moves a 30-day deadline to 60 days or drops the exclusion for contractors.

The handoff should preserve the input version, time window, evidence index, owner, and next validation action. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, keep the output limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.

A richer input changes the answer here because semantic invariants, structured fields, acceptable variation, repetition, version, and drift must be tied to evidence rather than inferred from a familiar pattern.

## Common traps

1. Using exact string equality as the only oracle.
2. Changing model, prompt, and retrieval at once.
3. Treating low variance as correctness.

## Two practical questions

### How many replays are enough?

Choose a count that matches risk and cost, then state the confidence limitation; there is no universal number.

### Can human review replace automated comparison?

It can judge meaning, but stable fields and formatting still benefit from deterministic checks.

The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
