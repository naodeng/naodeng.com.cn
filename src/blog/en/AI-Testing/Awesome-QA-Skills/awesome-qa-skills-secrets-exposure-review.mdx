A secret can leak without ever appearing in source control. Configuration snapshots, debug logs, crash reports, build output, and copied environment files all create different exposure paths.

## Why this Skill is needed

The Secrets-Exposure Review Skill builds an evidence-bounded view of where secrets live, how they flow, what logs expose, which configuration boundaries matter, and whether rotation evidence exists.

## What the Skill does

The review should make the next safe check obvious without increasing exposure.

Use this Skill to review a service or pipeline with redacted material. It identifies exposure concerns and validation actions; it does not log in, call real APIs, read credentials, or declare a system secure.

A good finding names the secret class, location or flow, exposure trigger, evidence state, impact, priority, owner, close condition, and isolated validation method.

Use it when a credential moves from local development to CI, a logging change is proposed, a security incident needs a bounded review, or rotation readiness is unclear.

## What it does not do

The Secrets-Exposure Review Skill can organize material, evidence, and next actions for Exposure location. It does not replace:

- Confirmation of rules, scope, and risk by the accountable domain owner.
- A real environment, account, dataset, log, or run record; static analysis does not become runtime evidence by itself.
- Authorization for release, compliance, production actions, or residual-risk acceptance.
- A Human decision when supplied sources conflict.

## What it checks

The value of this Skill is not another keyword list. It connects each focus area to an observable input, a judgment, and a way to close the loop. Start with a small matrix based on the source Skill's output contract:

| Focus | Question before analysis | Handoff output |
| --- | --- | --- |
| Exposure location | Where a secret may be stored or emitted | Redacted source and evidence state |
| Flow finding | How the secret moves through configuration or runtime | Trigger and boundary |
| Rotation readiness | What proves safe replacement and rollback | Runbook, owner, or gap |
| Validation action | Safe isolated check that reduces uncertainty | No real credential access |

If a row has only a conventional expectation and no source or validation method, keep it open instead of turning it into a pass.

## Audit inputs before you start

Before analyzing Exposure location, classify the input into six evidence states. A gap is not automatically a failure, but it must not disappear inside the conclusion.

| State | Meaning | How this Skill should handle it |
| --- | --- | --- |
| known | Directly supported by the supplied material | Keep the source, version, and time with the judgment |
| missing | Needed for this pass but not supplied | Name the smallest evidence action and limit the conclusion |
| conflicting | Sources disagree | Show both sources and route the conflict to an owner |
| stale | Present but outside the relevant version or time window | Mark freshness; old evidence is not current proof |
| out_of_scope | Related but excluded from this pass | Keep the boundary explicit |
| assumptions | Temporarily adopted to continue analysis | State how and when the assumption will be checked |

Keep the input version, scope, environment, evidence locations, and accountable owner together. Without a run record, deliver analysis, design, or a validation plan—not an execution pass.

## From problem to structured Finding

Connect the source, scope, evidence state, analysis, owner, action, close condition, and validation before writing the conclusion. The case below keeps this Skill’s identifier and domain context.

### Keep the decision layers separate

For Exposure location, do not compress four different kinds of language into “recommended to pass”:

| Layer | How to write it | Application here |
| --- | --- | --- |
| Fact | What the supplied material directly shows | Cite the source, version, input, or run record for the focus |
| Evidence-backed Inference | What several facts support together | Show the inference chain and retain uncertainty |
| Recommendation | The smallest next action | Name the evidence, review, execution, or regression path |
| Human Decision | What an accountable person must decide | Leave scope, risk acceptance, resources, and release meaning to the owner |

## A complete case

This case follows Input, Analysis, Finding, Decision, and Validation. When material is incomplete, keep missing, conflicting, or assumptions visible instead of turning them into a pass.

### Input

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Scope and version | Service, repository, pipeline, environment, and change revision | Mark unknown boundaries |
| Redacted material | Config templates, log samples, deployment manifests, and secret references | Never attach real values |
| Secret flow | Creation, injection, use, logging, error handling, and revocation path | Separate facts from assumptions |
| Rotation evidence | Owner, cadence, dependency impact, dry-run, and rollback material | Keep readiness unassessed without proof |

Use a request like this:

~~~text
Use the secrets-exposure-review Skill.

Task: Review whether a payment service can expose API credentials through CI logs, exception traces, or deployment configuration during a logging change.
Inputs: [redacted manifests, log samples, pipeline steps, secret references, rotation runbook]
Scope: [staging and CI, no real credentials]
Constraints: [do not call APIs or read secret values]

Separate known exposure evidence, assumptions, candidate validation, impact, owner, close condition, and security decision boundary.
~~~

### Analysis

Use the input, matrix, and evidence state to form the judgment before writing the Finding; keep missing material as a gap.

### Finding

#### Focused example: Review a logging change without copying credentials

A new exception logger records request headers in CI failure output. The Skill should flag the possible authorization-header exposure, ask whether headers are masked before persistence, and propose a synthetic-token test in an isolated pipeline. It should not ask for a production token or call the payment provider.

The review classifies supplied redacted evidence and proposes safe validation. It cannot prove absence of secrets, exploit success, remediation completion, or a security pass.

#### Example finding: turn one problem into a handoff

The field example below shows the recording pattern; it is not an execution result.

If the supplied material cannot prove that Exposure location meets its contract, write the finding like this. It does not invent the missing rule or turn missing evidence into a failure.

| Field | Example wording |
| --- | --- |
| Source and scope | Record the requirement, version, environment, and the concrete object for Exposure location |
| Finding | The condition or result for Exposure location is not yet traceable to evidence |
| Evidence state | missing / assumptions; use conflicting when sources disagree |
| Impact and priority | Name the affected user, journey, or delivery decision without inflating severity |
| Owner and Human decision | Ask the product, engineering, security, or test owner to confirm the rule and trade-off |
| Action and close condition | Add the smallest missing evidence; close only when source, judgment, and owner can be reviewed |
| Validation | Name one repeatable check, query, or run and retain the raw artifact |

The point is to let the next person walk from the finding back to the source and run an action that can change the decision.

### Decision

The accountable owner confirms the decision question and risk trade-off; the Skill does not make that choice.

### Validation

Before closing the finding, run the stated validation and retain the raw artifact. Without an execution record, the status remains unverified.

## How a Finding enters the next stage

### Handoff output

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Exposure location | Where a secret may be stored or emitted | Redacted source and evidence state |
| Flow finding | How the secret moves through configuration or runtime | Trigger and boundary |
| Rotation readiness | What proves safe replacement and rollback | Runbook, owner, or gap |
| Validation action | Safe isolated check that reduces uncertainty | No real credential access |

Every conclusion should point to a source, evidence state, and next action. If evidence is missing, use pending, blocked, unassessed, or NOT_SCORED instead of filling the gap with confidence.

### Next-stage route

At minimum, hand off the source, evidence state, owner, close condition, and validation action; the next-stage conclusion remains bounded by the evidence state.

## How to prepare better input

Provide redacted config, log samples, pipeline steps, secret reference names, environment boundaries, rotation owner, and the intended validation environment. Keep real values outside the prompt and repository.

A useful handoff includes input versions, scope, time window, evidence index, assumptions, Human decision boundary, and the smallest validation action.

## Common traps

1. Searching for literal values and concluding the system is safe when derived or logged forms remain.
2. Treating a rotation document as proof that every consumer can reload the new secret.
3. Requesting real credentials to make the review complete.

## FAQ

### Can I paste a real token for a more accurate review?

No. Use redacted values or synthetic tokens. Real credentials increase exposure and are outside this Skill's contract.

### Does a clean static scan prove rotation is ready?

No. Rotation also needs consumer reload, revocation, rollback, and evidence from a safe validation path.

The Skill is most useful when attached to one real project artifact and kept with its source evidence. Start narrow, validate the uncertain part, and expand only when evidence supports it.
