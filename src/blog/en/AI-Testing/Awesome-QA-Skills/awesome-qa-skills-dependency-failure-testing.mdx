A service rarely fails in one clean way. It can answer slowly, return old data, close the connection after a write, or fail only for one region.

Dependency Failure Testing checks how a system classifies, contains, exposes, and recovers from failures in services, databases, queues, and external providers.

The Dependency Failure Testing Skill is useful when a team needs a structured review of timeout, slow response, error, stale data, partial write, retry, fallback, and recovery. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) organizes Skills by language and testing stage. The [series overview](https://inaodeng.com/en/blog/ai-testing/introduction_of_awesome_qa_skills/) explains the shared installation model; this guide stays with Dependency Failure Testing.

## Dependency Failure Testing Skill: what it is for

A practical standard for this Skill is simple: A good dependency test starts at the business effect. It asks whether an order may be paid without inventory, whether a reservation can be duplicated, and which record proves the final state.

Use it when the team needs a repeatable review of timeout, slow response, error, stale data, partial write, retry, fallback, and recovery—especially when several evidence sources disagree or a handoff must explain what remains unverified.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Dependency contract | Timeout, error, consistency, retry, and fallback rules | Separate provider behavior from client assumptions |
| Business state | Order, reservation, payment, and compensation states | Track partial writes |
| Evidence | Request ID, provider trace, local state, retry count, and user message | Unknown write status needs explicit handling |

Use a request like this:

```text
Use the dependency-failure-testing Skill.

Task: test inventory reservation when the inventory service times out after receiving the reservation request
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.
```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Failure classification | Transient, permanent, partial, stale, or unknown | Evidence basis |
| Containment action | Retry, queue, compensate, fallback, or stop | Side-effect guardrail |
| Recovery check | State reconciliation and user-visible outcome | Owner and next evidence |

Do not write “passed” without a run record, query result, or source artifact. A good dependency test starts at the business effect. It asks whether an order may be paid without inventory, whether a reservation can be duplicated, and which record proves the final state.

## Run one focused pass

Start with a bounded pass—test inventory reservation when the inventory service times out after receiving the reservation request. Make inventory respond after the client timeout but before the retry. The expected result is one reservation or a clear reconciliation state, not a second reservation hidden behind a successful retry.

The handoff should preserve the input version, time window, evidence index, owner, and next validation action. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, keep the output limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.

A richer input changes the answer here because timeout, slow response, error, stale data, partial write, retry, fallback, and recovery must be tied to evidence rather than inferred from a familiar pattern.

## Common traps

1. Testing only 5xx responses.
2. Retrying a write without classifying its original state.
3. Calling a fallback safe without checking freshness and business meaning.

## Two practical questions

### Can mocks prove dependency recovery?

They can exercise client branches, but recovery claims need observable state and provider or simulation evidence.

### What if the provider contract is incomplete?

Keep the unknown state and define the smallest safe containment action.

The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
