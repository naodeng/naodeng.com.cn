A dependency timeout does not tell you whether a write happened. The caller may have stopped waiting after a provider committed the request, leaving a retry capable of creating a duplicate reservation or payment. Dependency Failure Testing keeps that uncertainty and its business side effects visible.

## What this Skill examines

Use this Skill to review dependency-failure classification, isolation, degradation, fallback, and recovery preparation across services, databases, queues, and external providers. It does not inject faults, access live dependencies, or claim that a recovery test ran.

## Start with the dependency contract

Record the caller and dependency, synchronous or asynchronous interaction, timeout and retry rules, fallback behavior, and business or data invariants. Then identify which source supports each rule and what evidence is missing or stale.

| Failure shape | Questions the review must answer |
| --- | --- |
| Unreachable or error response | Was the request rejected before any side effect? What evidence supports that? |
| Timeout or slow response | Could the dependency have accepted or committed the operation after the caller stopped waiting? |
| Partial success | Which records, messages, or downstream calls may already have changed? |
| Async delay, duplicate, or reordering | What do pending state and acknowledgment mean? How is replay made safe? |
| Recovery | How are backlog, local state, and dependency state reconciled or compensated? |

Do not infer “not committed” from a timeout or HTTP 500. Join the caller record, dependency outcome, retry, and message or database side effects by request or message ID and timeline.

## Worked example: inventory reservation

Assume a synchronous inventory request times out after it is sent, and the caller considers a retry. The design review should ask whether the dependency received the first request, whether the operation has an idempotency key, what state can be queried, and how a duplicate reservation would be detected or compensated.

The expected contract might distinguish a confirmed rejection from an unknown outcome. In the unknown case, the caller should reconcile before retrying a non-idempotent write. This is a design example only; it supplies no real provider behavior or execution evidence.

For an asynchronous queue, review delayed delivery, duplicate messages, ordering, and lost acknowledgment separately. A message still pending is not the same state as a failed operation, and a successful acknowledgment is not automatically proof that every business side effect completed.

### How to interpret example evidence

These are illustrative outcomes, not claims about a provider's actual behavior.

| Supplied observation | Bounded interpretation | Next action |
| --- | --- | --- |
| The caller timed out and the dependency lookup still says unknown | The write outcome is unresolved; a timeout is not a rejection | Reconcile by request identity and do not blindly retry a non-idempotent write |
| An authoritative dependency record says the request was rejected before side effects | This supports rejection only for that request and evidence scope | Retain the lookup result, request ID, and timestamp, then review retry behavior |
| Multiple reservation records share one business intent | This suggests a duplicate side effect, but the impact needs source-record review | Join the original request, retry, and ledger; let the owner decide compensation or further validation |

## Build a reviewable finding

Use DPF-## for each risk. Record the caller and dependency, interaction mode, failure trigger, side-effect window, invariant at risk, source and evidence state, expected result, priority, owner role, close condition, validation method, and stop condition. The scenario should distinguish synchronous rejection, asynchronous pending work, and unknown commit.

A useful validation proposal names an isolated environment, synthetic or masked data, the request identity to trace, the expected state reconciliation, and the point at which the exercise must stop. Do not run the fault injection as part of this design review.
