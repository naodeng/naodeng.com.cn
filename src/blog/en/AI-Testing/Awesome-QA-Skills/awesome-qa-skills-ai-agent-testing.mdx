AI Agent Testing evaluates an agent's task completion and the path it took to get there. The test needs a task-success oracle and a trace: a plausible answer can still hide a skipped step, unauthorized tool call, contaminated memory, or unsafe stop decision.

## Define the task and its permitted path

For each sample, record the task ID, success oracle, allowed tools and resources, prohibited side effects, and stopping conditions. Then compare the final result with the run and step trace.

| Dimension | What to observe | Failure that can be hidden by the final answer |
| --- | --- | --- |
| Planning | Step order, dependencies, and response to new information | A skipped prerequisite or unsupported plan change |
| Tool use | Selection, arguments, permissions, and result interpretation | A correct-looking answer after an unsafe or irrelevant call |
| Memory | What state persists, resets, or leaks between tasks | One user's data or an earlier task influencing the next run |
| Recovery | Retry, fallback, and human handoff after a failed step | Repeated side effects or continuation after a hard blocker |
| Termination | Success, goal failure, budget exhaustion, cancellation, safety block, or environment error | Missing terminal evidence being mistaken for completion |

## Repeat trials when behavior can vary

Use the same sample IDs and record model, prompt, tool, data, and environment versions. Follow the project's repetition plan; do not invent a sample threshold. Report outcomes per sample and keep intermittent failures visible. A single successful run shows one observed result, not reliability.

For example, a multi-step support task may pass on its final answer but fail its process check if the trace shows an unapproved data lookup. Judge outcome correctness and process compliance separately; either failure can prevent an overall pass. Preserve run and step IDs so reviewers can reconstruct the decision.

Record a multi-step task under one `sample ID`: define the success oracle, allowed tools and resources, prohibited side effects, and stopping conditions before the run. Then capture model, prompt, tool, data, and environment versions, and link each step's input, arguments, authorization decision, tool response, and state change to a `run ID`. The table below illustrates how to interpret one run:

| Observation | Interpretation |
| --- | --- |
| The final answer meets the oracle and every step meets the process assertions defined for the case | This run meets the case's outcome and process conditions |
| The final answer is correct, but the trace includes an unauthorized data lookup | Process failure; the answer does not offset it |
| The final answer looks correct, but a key step or terminal record is missing | Insufficient evidence to judge the full path |

The table describes one run. Repeat trials under the project's plan and report each result before judging whether behavior is stable.

## Produce cases with an oracle and evidence

Each proposed case needs preconditions, an action or stimulus, expected behavior, and required evidence. Separate static analysis or a designed fixture from a real run. If the project has not supplied a success rule, permission, or stop threshold, list it as an open question instead of creating one.

The output can include a capability matrix, task suite, trace assertions, recovery and safety cases, scoring rubric, observability measures, blockers, and next actions. Keep confirmed facts, assumptions, and unknowns visible. The Skill helps structure the work; it does not certify the agent or a release.

## FAQ

**Does a correct final answer make the case a pass?** Not by itself. Check whether the trace meets the case's permission, tool, step, and stopping assertions. If a key part of the trace is missing, report insufficient evidence.

**How many times should a task be repeated?** Follow the repetition plan defined by the project. If the plan or stability threshold is missing, list it as an open question instead of inventing a count or pass threshold.
