Agent tool testing focuses on the boundary between an agent and the tools it can call. The review asks whether the agent chose the right tool, formed valid arguments, had permission for the action, handled failure safely, and left traceable evidence. A correct final answer does not prove that the call itself was safe.

## Treat each call as a contract

Start from the tool schema, routing rules, authorization model, sandbox, and available traces. For every scenario, record preconditions, stimulus, expected behavior, and the evidence that would confirm it.

| Boundary | What to check | Useful evidence |
| --- | --- | --- |
| Selection | The chosen tool matches the requested action; ambiguity leads to a question or safe stop | Request, candidate tools, routing trace |
| Arguments | Required fields, types, ranges, and object identifiers match the schema | Tool schema, serialized arguments, validation result |
| Authorization | The actor may perform this action on this resource in this tenant | Role and policy snapshot, allow or deny result |
| Retry and recovery | Timeouts, partial failures, and retries do not repeat a write | Request IDs, retry trace, before-and-after state |
| Result handling | Tool errors and partial results are not presented as completed work | Response payload, agent trace, user-facing answer |

## Exercise failure paths in an isolated environment

A refund workflow is one illustrative scenario, not a claim about a particular product. In a mock or authorized sandbox, test an allowed request, a request outside the actor's permission, and a timeout that occurs after the service may have accepted the first call. Confirm that the denied request leaves no write. For the timeout case, have the mock record the request as accepted before returning a timeout, then inspect the trace under the project's retry rule and evaluate side effects against the tool contract. Assert that no duplicate refund or notification occurs only if the contract defines idempotency; if it does not, leave retry semantics open. Capture arguments, authorization decisions, request and call IDs, responses, retry count, before-and-after state, and notification records. A timeout without mock-state evidence cannot show whether the first call took effect; mark it “insufficient evidence.”

Use mocks, dry runs, or isolation by default. Never execute real writes without authorization. For each issue, rank impact and likelihood using the project's scale; label unconfirmed causes as hypotheses. Missing schemas, policies, or run records are input gaps, not proof that a call passed.

## Hand off an executable test plan

The result should let another tester act without reconstructing the conversation. Include the tool-contract matrix, normal and failure scenarios, assertions, evidence locations, blockers, and residual risk. Keep an action owner and a next check for each open item. The Skill can organize the test plan; it cannot manufacture authorization or runtime evidence.
