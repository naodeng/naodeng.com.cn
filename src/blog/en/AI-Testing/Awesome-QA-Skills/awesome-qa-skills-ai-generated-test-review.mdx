An AI-generated test suite can contain fifty polished cases and still miss the one rule that refunds an expired coupon. Volume is a poor substitute for a source.

AI-Generated Test Review checks whether generated tests are grounded in requirements, identify real risks, use valid oracles, and remain maintainable when the product changes.

The AI-Generated Test Review Skill is useful when a team needs a structured review of source traceability, invented behavior, boundary coverage, oracle quality, and maintenance cost. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

## AI-Generated Test Review Skill: what it is for


Use it when the team needs a repeatable review of source traceability, invented behavior, boundary coverage, oracle quality, and maintenance cost—especially when several evidence sources disagree or a handoff must explain what remains unverified.

A good result keeps source traceability, invented behavior, boundary coverage, oracle quality, and maintenance cost connected to a source and a verification action. It does not turn a design checklist into a passing result.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Source rules | Promotion requirements, examples, exclusions, and version | Reject tests that have no supporting rule |
| Generated suite | Cases, data, expected results, setup, and cleanup | Mark invented fields and endpoints |
| Review context | Known defects, risk priorities, test framework, and maintenance owner | Do not optimize for case count alone |

Use a request like this:

```text

Use the ai-generated-test-review Skill.

Task: review AI-generated tests for a promotion engine that combines customer tier, coupon expiry, and cart thresholds
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.

```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Traceability map | Case to rule, risk, and decision oracle | Covered, weak, or unsupported |
| Finding | Missing boundary, hallucinated behavior, duplicate case, or brittle setup | Priority and basis |
| Repair action | Keep, rewrite, remove, or request source clarification | Owner and next check |

Do not write “passed” without a run record, query result, or source artifact. A useful review asks what would make a generated case fail for the right reason. If the expected result is only “returns success,” the case probably needs a business state, invariant, or source-backed comparison.

## Run one focused pass

Start with a bounded pass—review AI-generated tests for a promotion engine that combines customer tier, coupon expiry, and cart thresholds. For an expired coupon, trace each generated case back to the expiry rule and check whether it asserts both the rejected discount and the unchanged cart total. Delete a case that invents a “coupon grace period” unless the requirements actually define one.

The useful handoff keeps the input version, time window, evidence index, owner, and next validation action together. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, the output should stay limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.


## Common traps

1. Treating natural language quality as requirement coverage.
2. Accepting an expected result that cannot distinguish correct and incorrect behavior.
3. Keeping duplicate cases because they use different wording.

## Two practical questions

### Can the reviewer use only the generated suite?

No. The source requirement is the authority; the suite is the object under review.



### Should every generated case be repaired?

No. Remove unsupported cases when repair would require inventing product behavior.



The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
