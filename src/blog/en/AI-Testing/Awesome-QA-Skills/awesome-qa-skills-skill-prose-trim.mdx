Shorter Skill documentation is not automatically safer or clearer. Process Prose Trimming removes material that readers cannot resolve from the current repository while preserving the rules, measurements, and negative guarantees that still govern behavior.

## Classify a passage before editing it

First confirm the file scope, language pair, and permission to edit. Then decide what each passage represents:

| Passage type | Treatment | Example |
| --- | --- | --- |
| Current fact | Verify it and state it in the present tense | A supported command, path, or behavior |
| Contract or negative guarantee | Preserve its meaning and conditions | A refusal boundary or statement that an action is not performed |
| Historical record | Keep it in the appropriate archive when it is still needed | A dated release decision or incident record |
| Reasoning transcript or review dialogue | Remove process residue, or restate a durable fact if one remains | “The reviewer suggested this in PR 12” |
| Measurement or formal reference | Retain the value, scope, date, and source | A benchmark result or cited standard |
| Generated file, sealed archive, or fixture | Report it; do not edit without explicit authorization | A recorded Eval fixture used to reproduce a case |

This classification prevents two opposite mistakes: leaving temporary review notes in a reader-facing Skill, and deleting history or a safeguard that users still need.

Work in this order: list the authorized files and language pairs; classify each passage; find a current source for claims about commands, paths, or product behavior; then edit only material confirmed to be process residue. Report unverifiable facts as uncertain instead of rewriting them as capabilities to make the prose smoother.

## Example: remove the process note, keep the rule

Imagine a document says: “This PR follows up on design note 4. The importer rejects rows without an account ID.” If the first sentence has no meaning outside its review history, remove it from the active guide. Keep the second sentence only after checking it against the current implementation or contract. If that fact is no longer verifiable, report the uncertainty rather than converting it into a promise.

A trim report should make the change auditable:

```markdown
# Trimming report
## Deleted or restated
| Location | Type | Action | Reason |
## Preserved contracts and facts
## Unchanged scope
## Bilingual synchronization
```

## Preserve what controls behavior

Before accepting a shorter version, compare the original and edited text for trigger conditions, required inputs, exceptions, refusal rules, failure handling, measurements, identifiers, and references. Keep an important negative guarantee even when it costs words. Do not collapse “not run” into “passed,” or change an assumption into a capability.

The source Skill does not set a target word count. It asks the maintainer to remove process residue and preserve durable content. After editing, read the complete affected page and its language pair; then verify that links, examples, and the unchanged scope still make sense. Do not edit generated files, sealed archives, fixtures, or related files outside the authorized scope.

Before delivery, compare the trigger and required inputs, limits and exceptions, failure paths, commands, versions, IDs, numbers, and references. Check that both languages still describe the same behavior. If deleting a sentence changes what a downstream user can rely on, treat it as a contract change and send it through prose review and change verification instead of treating it as a word-count edit.

## FAQ

### Should the edit aim for a fixed word count?

No. The source Skill sets no target length. Remove only material that no longer helps the reader or controls behavior, while preserving the full contract.

### Can generated files or fixtures be trimmed with the prose?

No. The source Skill treats them as protected evidence; report them and edit only the files explicitly in scope.
