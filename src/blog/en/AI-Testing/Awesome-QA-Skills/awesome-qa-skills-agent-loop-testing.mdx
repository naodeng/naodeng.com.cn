An agent that keeps asking the same search service a slightly different question is not making progress. It is spending budget while hiding the fact that its plan has stopped moving.

Agent Loop Testing evaluates whether each iteration changes the state of the task, whether the loop has useful stop conditions, and whether repeated tool calls remain safe and explainable.

The Agent Loop Testing Skill is useful when a team needs a structured review of state delta, repeated actions, termination criteria, budget limits, and loop trace. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

## Agent Loop Testing Skill: what it is for


Use it when the team needs a repeatable review of state delta, repeated actions, termination criteria, budget limits, and loop trace—especially when several evidence sources disagree or a handoff must explain what remains unverified.

A good result keeps state delta, repeated actions, termination criteria, budget limits, and loop trace connected to a source and a verification action. It does not turn a design checklist into a passing result.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Goal and stop rule | Three verified sources, source authority criteria, and maximum iterations | Separate completion from “the model says done” |
| Trace | Per-iteration plan, tool call, observation, state update, and token or time budget | Do not reconstruct a loop from the final answer |
| Failure policy | Blocked source, duplicate result, empty result, and escalation behavior | Keep unresolved loops as blocked |

Use a request like this:

```text

Use the agent-loop-testing Skill.

Task: a research agent must collect three authoritative sources but keeps revisiting a blocked publisher page
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.

```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Iteration map | What changed between two iterations | Useful delta or no-progress |
| Loop finding | Repetition, drift, premature stop, or runaway behavior | Evidence and severity |
| Termination action | Stop, retry with a new strategy, ask for input, or escalate | Condition and owner |

Do not write “passed” without a run record, query result, or source artifact. A strong loop review compares state before and after each iteration. It does not punish repetition automatically—some retries are justified—but it requires a changed hypothesis, a changed input, or a changed verification path.

## Run one focused pass

Start with a bounded pass—a research agent must collect three authoritative sources but keeps revisiting a blocked publisher page. For the blocked publisher, cap attempts at two, record the reason for failure, and switch to an official repository or registry. The output should show the exact point where the strategy changed and why the loop was allowed to continue.

The useful handoff keeps the input version, time window, evidence index, owner, and next validation action together. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, the output should stay limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.


## Common traps

1. Counting iterations without comparing state.
2. Using a global iteration cap that hides different risk levels.
3. Stopping on a plausible sentence before the source requirement is met.

## Two practical questions

### Is repeated tool use always a loop failure?

No. It is a finding only when the retry adds no new evidence or violates the defined budget or side-effect boundary.



### What should happen when the agent cannot progress?

Stop with the missing condition, the attempted strategies, and one human or system action that can unblock it.



The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
