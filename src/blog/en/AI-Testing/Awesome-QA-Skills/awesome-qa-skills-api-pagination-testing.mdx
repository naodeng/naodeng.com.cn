Pagination bugs rarely announce themselves on page one. They appear when a record is inserted between two requests and the consumer quietly skips an audit event.

API Pagination Testing checks whether a consumer can traverse a changing collection without missing, duplicating, or reordering records beyond the contract.

The API Pagination Testing Skill is useful when a team needs a structured review of page size, cursor or offset semantics, stable ordering, mutation, duplicates, gaps, and termination. It turns a vague testing request into a bounded analysis with sources, assumptions, output fields, and a next action.

## API Pagination Testing Skill: what it is for


Use it when the team needs a repeatable review of page size, cursor or offset semantics, stable ordering, mutation, duplicates, gaps, and termination—especially when several evidence sources disagree or a handoff must explain what remains unverified.

A good result keeps page size, cursor or offset semantics, stable ordering, mutation, duplicates, gaps, and termination connected to a source and a verification action. It does not turn a design checklist into a passing result.

## Begin with project facts

| Material | What to provide | What to do when it is missing |
| --- | --- | --- |
| Collection contract | Ordering key, cursor or offset rules, page size limits, and snapshot semantics | Do not assume offset means snapshot |
| Mutation schedule | Insert, update, delete, archive, and duplicate-key events between page requests | Record exact timing |
| Traversal evidence | IDs seen, cursor returned, total count, and final termination marker | Compare against an authoritative fixture |

Use a request like this:

```text

Use the api-pagination-testing Skill.

Task: traverse an audit-log API while new events arrive and older events are archived
Inputs: [requirements, versions, links, logs, reports, or data paths]
Scope: [included and excluded objects]
Unknowns: [missing environment, accounts, data, or permissions]
Expected output: [risk-ordered findings, evidence status, and next actions]

Audit the inputs first. Separate facts, assumptions, and open questions. Do not claim execution without a run record.

```

## Make the result usable by the next person

| Output field | Why it exists | Example status |
| --- | --- | --- |
| Traversal result | Complete, duplicate-free, ordered record set | Observed IDs and expected IDs |
| Pagination finding | Gap, duplicate, invalid cursor, unstable order, or wrong count | Page and mutation point |
| Consumer action | Retry, snapshot, cursor change, or contract clarification | Owner and evidence |

Do not write “passed” without a run record, query result, or source artifact. A useful pagination test treats the collection as a moving target when the API does. It records IDs rather than trusting total counts, and it makes the ordering key visible.

## Run one focused pass

Start with a bounded pass—traverse an audit-log API while new events arrive and older events are archived. Read audit events with a page size of 50, insert two newer events after page one, then continue with the returned cursor. Compare the collected IDs with a timestamp-and-ID ordered fixture. A correct cursor may exclude new events from the current traversal, but it must not repeat or skip the original snapshot.

The useful handoff keeps the input version, time window, evidence index, owner, and next validation action together. The Skill can organize uncertainty; it cannot manufacture the missing artifact.

## Improve the first result

If the first request contains only a one-line goal, the output should stay limited. Add the source version, affected objects, environment, known defects, and decision owner to move from a plausible checklist to a useful review.


## Common traps

1. Asserting only page length.
2. Using a mutable total count as completeness proof.
3. Testing a cursor without changing the collection between requests.

## Two practical questions

### Is offset pagination always wrong?

No. It can be valid with a defined snapshot or stable ordering; the test must verify the contract that exists.



### What should an empty final page mean?

It should be explicit—end of collection, invalid cursor, or a transient read—and clients need different actions.



The example above is a design and review pattern, not an execution result. Keep static analysis, runtime evidence, human approval, and release acceptance separate.
