A Skill edit can change more than wording: it may alter activation, required inputs, output fields, constraints, or failure handling. Skill Change Verification starts from the actual diff, chooses checks for the affected behavior, and reports exactly what the evidence supports. It does not turn a configuration check into a runtime claim.

## Classify the change before choosing a check

Use the changed files and their consumers to decide what to verify. A broad test run does not replace checking the paths touched by the diff.

| Changed surface | Minimum evidence to consider | Claim that evidence can support |
| --- | --- | --- |
| Entry point, metadata, links, or layout | Relevant static and structural checks, plus a standalone copy where applicable | The package shape and referenced resources are valid; behavior was not run |
| Prompt, procedure, or output contract | Representative success, missing-input, and boundary cases with actual runs and judge results | Only the selected cases, versions, host, and environment were exercised |
| Parser, generator, or installer | A regression for the original fault, a valid control, and execution with the target format or tool | Only the tested paths worked |
| Release recommendation | Change evidence, version, residual risks, and an authorized decision record | The recommendation and formal approval are separate facts |

Keep evidence levels distinct: **Static** checks files and frontmatter; **Structural** checks pairing, indexes, and Eval shape; **Configuration** checks setup such as `skill-up validate`; **Evaluation** records an actual `skill-up run`, selected cases, metadata, and judge results; **Runtime** records the Skill or Prompt behavior in its target host; **Human review** covers meaning and risk. A successful configuration command alone does not prove Evaluation or Runtime.

## Example: changing a Skill description

Suppose a description change is intended to make a Skill activate for API compatibility reviews. First record the old and new package versions and the actual diff. Then test a small fixed request set: an in-scope compatibility review, a neighboring API task, and an unrelated request. Where the host exposes Skill selection, retain that evidence alongside the produced output. Include a missing-input case if the revised instructions depend on a specification or version.

If only frontmatter and `skill-up validate` were checked, report the configuration result and mark Evaluation and Runtime `NOT_RUN`. Do not say that activation improved, that the Skill is reliable, or that the change is production-ready without the corresponding runs and human decision.

When the output contract changes, use normal, missing-input, and conflicting-source cases. Check that the new version still emits required fields, preserves unknown states, and does not turn competing sources into one certain answer. Add a neighboring but out-of-scope request to check the trigger boundary. Compare old and new versions on the same cases so a new behavior does not hide a removed constraint.

## Write a report another person can audit

Preserve the selected commands, versions, environment, selected Eval cases, raw outputs, and judge status. For every omitted check, give the reason and the risk it leaves open. A timeout, missing authentication, filtered-out case, or failed judge is not a full-suite pass.

```markdown
# Verification report
## Change classification
## Checks run
| Command | Evidence level | Result |
## Checks not run
| Item | Reason | Risk |
## Claims supported
## Claims not supported
## Residual risks
```

A `NOT_RUN` entry is a useful boundary: it tells the next reviewer what remains unknown instead of hiding the gap behind a green configuration check.
