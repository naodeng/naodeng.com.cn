For one login requirement, a tester can ask directly, use a Prompt, or invoke a Skill. A few sample responses cannot show which works better. Model versions, requirement materials, conversation history, and run settings all affect the output. When conditions differ, you cannot isolate the effect of the approach.

The examples below show what to review in each approach. Measure actual performance by running the same samples under controlled conditions.

## Getting started: a first comparison

For a first comparison, one requirement is enough. Prepare a review reference, then follow these steps:

1. **Fix the task and requirement version.** State what all three approaches must do, such as “identify key test scenarios and flag unspecified behavior.”
2. **Start clean sessions.** Do not let one approach inherit another's conversation. Record the tool, model, settings, and versions.
3. **Save every output.** Keep follow-up questions, human input, edits, and time spent for every run.
4. **Review against one checklist.** Hide the approach name where possible and check evidence, omissions, unsupported claims, and usability.
5. **Choose for the task.** Direct chat may be enough for a one-off exploration; recurring work may justify maintaining a Prompt or Skill.

## Prepare a review reference first

For the phone-number login requirement, ask someone who knows the business to prepare a reference list: confirmed rules, important risks, open questions, and acceptable output requirements. For example, the five-minute code expiry may be confirmed while the exact 300-second boundary remains unknown. Raising that question is useful; choosing an answer without evidence is not.

Prepare the reference before reading outputs from the three approaches so reviewers do not mistake a model suggestion for the “correct answer.” It only needs to list the important conditions the team can support with evidence; it does not need to cover every possibility.

Redact real phone numbers, tokens, and other sensitive material before using requirements in the comparison.

The examples below use this exercise requirement. It is only a review exercise, not a statement of a real product's rules:

| ID | Given exercise rule | Still to confirm |
| --- | --- | --- |
| R-01 | An SMS verification code is valid for five minutes | Is it still valid at exactly 300 seconds? |
| R-02 | The phone number is locked for 15 minutes after five consecutive incorrect attempts | What happens after attempt five, at unlock, and when the counter resets? |
| R-03 | An account is created after the first successful verification | Can a failed path leave account or session state behind? |

Keep the inputs identical across the three groups. Record newly raised questions as open questions, then add them to all groups in the next round.

## Control the inputs and change only the approach

Set up three groups:

- **Direct chat:** ask the same testing question in concise natural language.
- **Prompt:** use the structured template from the previous article about Prompt-based test design.
- **Skills:** invoke a reviewed requirement-analysis or test-design Skill.

Use the same requirement and context, model version, and parameters in all three groups. Keep the host tool and its settings the same where possible; vary only the direct-chat, Prompt, or Skill instructions. If the tool or settings differ, disclose that limitation: the result then compares tool configurations, not the method alone. Start each run in a clean session so one group does not inherit context from another.

Record the tool, model, Prompt or Skill version, and the time until each result is ready to deliver. Where possible, run each approach at least three times and review all outputs for consistency. Three runs provide an initial stability check, not statistical significance or evidence about other requirements. If time or budget limits the run count, report that limit.

Keep the task fixed: for example, ask all three approaches to list key test scenarios and include the requirement source, preconditions, expected result, and open questions. Change only whether the instruction arrives as a one-off natural-language request, a reusable Prompt, or a Skill with fixed steps and output rules.

## Do not score by test-case count

| Observation | What to record |
| --- | --- |
| Critical gaps found | How many pre-marked important unknowns were identified |
| Unsupported conclusions | How many unconfirmed rules were stated as facts |
| Risk coverage | Whether important states, boundaries, failure paths, and side effects were addressed |
| Executability | Whether preconditions, steps, and expected results can be used in the project |
| Format compliance | Whether the output meets agreed fields and traceability requirements |
| Consistency | Whether repeated runs find similar issues and how much scores vary |
| Human effort | Time spent on follow-up, review, and revision |

If you calculate a rate, define the denominator. For example, “critical-gap recall” can be the number of pre-marked critical gaps found divided by the total number on the reference list. It measures only that list; it does not prove that every unknown risk has been found.

If completeness also matters, agree on scoring rules before the experiment and have reviewers score independently. For example, 0 could mean “not identified,” 1 “mentioned without a source or action,” and 2 “supported by evidence with a next step.” Count unsupported conclusions separately so strong scores elsewhere cannot hide them. This scale is only an example for the experiment team to adapt; write the actual criteria down before running the comparison.

## Best practices for a reviewable comparison

- Write down requirement sources, confirmed rules, and open questions before reading model outputs.
- Keep the task, context, output fields, and model settings aligned. If the tools differ, limit the conclusion to the complete tool configurations.
- Save all runs, including failures and incomplete outputs; do not select one best run to represent an approach.
- Count unsupported claims separately so a format score or a large number of cases cannot hide them.
- Have reviewers score independently before discussing disagreements. Mark major unresolved disagreements instead of averaging them away.
- Include preparation, follow-up, review, and revision time in human cost; record versions and run counts.
- Use small samples only to make a decision about the current task, not to claim that one approach is universally better.

## Interpret results in the context of the task

If direct chat quickly finds the important issues and a Prompt or Skill mainly improves formatting, a simple task may not justify the upkeep. If a Skill reduces omissions and rework, include its reference and maintenance costs in the comparison. When the scores are close, choose the lighter method the team can keep using.

Review bias matters too. Hide which approach produced each result where possible, and have two reviewers use the same criteria before discussing disagreements. Keep “looks professional” separate from “has evidence and can be executed.” Familiarity with a tool should not automatically earn it a higher score.

For disputed items, return to the requirement and reference list. Record the evidence each reviewer cites and clarify the scoring rules where needed. If reviewers still define a critical gap differently, revise the list or mark the result unresolved. Do not calculate an average score until the reviewers agree on what counts.

## Focus: Put the comparison into a quality loop

Use each comparison to define a reviewable improvement for the next round:

![Quality loop for comparing direct chat, Prompts, and Skills: freeze requirements and samples, run all three approaches, review blind, classify gaps and cost, revise the method, then rerun the same samples](/images/blog/ai-testing-quality-loops/chat-prompt-skill-comparison-loop-en.svg)

1. **Freeze the baseline:** save requirement versions, references, samples, scoring rules, and model settings. Record known rules separately from critical unknowns.
2. **Run in parallel:** use the same task and materials for direct chat, Prompt, and Skill. Start clean sessions and keep every raw output.
3. **Review blind:** hide approach names and apply the same checks for traceability, omissions, unsupported claims, usability, and human revision time.
4. **Classify issues:** decide whether each issue came from the requirement, input context, Prompt or Skill instructions, model variation, or review criteria. Keep it open when evidence is insufficient.
5. **Change one explainable factor:** for example, add a boundary check, clarify an output field, or update a reference. Record the version and reason.
6. **Regress on the same samples:** confirm the known issue is fixed without creating new false positives. Add a new, untuned sample to check for overfitting.

For each round, retain input and method versions, model and tool, raw output, human edits, findings, and review outcome. Reassess when the method, model, or business conditions change; old results describe only the conditions under which they were collected.

## FAQ

### Is a Prompt or Skill always better than direct chat?

No. Recurring tasks may benefit more from consistent structure and traceable steps. Direct chat may be cheaper for a one-off, low-risk exploration. Use task samples to decide instead of inferring quality from the method's name.

### Are the three output snippets measured results?

No. They illustrate the review criteria, and the scores only assess those snippets. They are not model-run results; measure consistency and revision time through actual repeated runs.

### Must I run each approach three times?

Three runs can be an initial check for consistency, but they are not a universal statistical standard. Record the actual run count and limit conclusions to what the samples, model, and settings support.

### What if the scores are close?

Consider task frequency, omission risk, human review cost, and maintenance capacity. If quality differences are unclear, choose a method the team can keep using and maintain, while continuing to capture failures in the quality loop.
