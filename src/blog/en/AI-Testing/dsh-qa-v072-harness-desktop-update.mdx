# dsh-qa v0.7.2: DeepSeek Harness Desktop Support and Conversation History Fixes

dsh-qa v0.7.2 is out. It supports Host Smoke against dsh-v0.2.0-rc.2 and fixes the discovery, preservation, ordering, and rendering of historical DSH conversations.

The official DeepSeek Harness desktop preview is also available to download from the product page.

DeepSeek Harness product page:https://www.deepseek.com/harness/

![DeepSeek Harness Desktop screenshot](https://images.naodeng.com.cn/2026/dsh-desktop.png)

Desktop provides the installation entry point; dsh-qa continues to provide the QA workflow. Here is what changes on each side:

| Desktop entry | dsh-qa update |
| --- | --- |
| Download and open Harness from the official website | Use the latest QA Workbench with the current Harness host |
| Choose an official or custom model | Keep historical DSH conversations visible across sessions |
| Add dsh-qa through the Plugin entry | Validate the QA profile against a real Harness Host |

If you previously used Harness through the CLI or another local workflow, the official client makes it easier to get started. Once installed, choose a model mode and the Plugins you need.

One qualification matters:

> **DeepSeek Harness Desktop is a Preview release. It is suitable for evaluation and compatibility work, but it should not automatically replace every stable workflow.**

## DeepSeek Harness now has an official desktop client

DeepSeek Harness has evolved as an Agent runtime and development framework. For many users, the original path still involved a CLI, configuration files, a local runtime, and a browser window.

The official client turns that into a few steps: download and install the client, open Harness, sign in to a DeepSeek account or configure a custom model according to the mode you choose, then use Plugins, Skills, and Agents.

The product page is now the main public entry point:

DeepSeek Harness product page:https://www.deepseek.com/harness/

The official desktop implementation wraps the existing Harness capabilities. The architecture has four visible layers:

| Core | Local host | Web application | Desktop entry |
| --- | --- | --- | --- |
| DeepSeek Harness | Harness Host | Harness Web application | DeepSeek Harness Desktop |

The core capabilities remain Sessions, Models and Providers, Plugins, Skills, Commands, Tools, and Agents.

The desktop client adds a native entry point and supports local Host startup, native folder selection, and Plugin management. It also integrates the Windows system tray, macOS application menus, desktop shortcuts, and DevTools; the current implementation includes application updates, background-task protection, exit protection, and built-in pnpm.

For most users, the visible change is that Harness can be downloaded and opened as an official desktop application. The implementation details can wait until they are useful.

## Official models and custom models

DeepSeek Harness currently supports two usage modes:

| Mode | Requirement | Responsibility boundary |
| --- | --- | --- |
| Official model | Sign in to a DeepSeek account | Use the official model service configured by DeepSeek |
| Custom model | Configure the model provider and API details | Harness provides the local interface, supporting tools, and communication layer; the configured provider supplies the model service |

The official terms say that custom-model mode does not require a DeepSeek account or sign-in. When planning Plugin, Agent, or multi-model workflows, keep the two paths distinct: official models require a DeepSeek sign-in; custom models use the provider and API details you configure.

The desktop client supplies the Harness runtime and the Plugin entry point. dsh-qa supplies the QA and software-quality workflow.

## Install dsh-qa from the official client

Install it in six steps:

1. Open the official Harness client. Sign in to a DeepSeek account for official models, or configure the provider and API details for a custom model.
2. Open **Plugins**.
3. Choose **Add Plugin**.
4. Enter dsh-qa GitHub repository:https://github.com/naodeng/dsh-qa.
5. Confirm the installation.
6. Open **QA Workbench** after the Plugin finishes installing.

For new users, this GUI entry point is easier to follow than starting with Harness CLI commands. It also makes the boundary visible: Harness owns the runtime and Plugin loading; dsh-qa owns the QA Workbench.

## What dsh-qa provides

The desktop client does not change the role of dsh-qa. It remains a local QA Workbench for turning quality work into connected records and decisions.

Its current scope falls into three groups:

- Planning and assets: test project and iteration management, requirements, test cases, and test milestones.
- Execution and collaboration: defects, risks, QA Skills, AI-assisted testing, Native QA Execution, Action Desk, and test evidence.
- Analysis and delivery: test reports, QA Kanban, test calendar, failure analysis, regression analysis, quality gates, and release and delivery decisions.

The workflow can be summarized as:

| Requirements and planning | Execution and evidence | Analysis and decision |
| --- | --- | --- |
| Requirement or source → Quality Task → Test Plan | Controlled Execution → Evidence → Failure Analysis | Regression → Quality Gate → PASS / WARN / BLOCK |

AI can assist with requirements analysis, test design, execution analysis, and evidence organization. A generated suggestion or a passing command does not remove the need for a human quality decision.

## The important v0.7.2 fix: historical DSH conversations

The v0.7.2 fix restores historical DSH conversations. In some earlier cases, a project could lose access to older conversations after a Session rebind or the creation of a new Session.

Testing rarely ends in one conversation. A project may move through requirements analysis, test design, issue discussion, regression, and release review, and those steps can cross multiple Sessions. If an earlier conversation disappears after a rebind or a new Session, the project context gets cut off.

The release notes list fixes to historical conversation discovery, preservation, ordering, and rendering, including archived chats. Within the same Project Workspace, historical conversations should remain visible after rebinding the DSH Session or creating a new one.

## Why conversation history matters in a QA Workbench

dsh-qa increasingly connects projects, tasks, DSH conversations, executions, evidence, and decisions.

If a conversation is only temporary chat, losing an old Session is inconvenient. Once it contains requirements analysis, test discussions, Skill execution, risk assessments, Agent tool calls, and quality conclusions, the history becomes part of the project context.

That context also helps explain how evidence was produced. The conversation is not automatically proof of product quality, but it can preserve the reasoning and decisions around the evidence.

## Why start with the official client?

Before the official desktop client appeared, the community already had several useful third-party Harness desktop projects. Some provide a good user experience and helped move the ecosystem forward.

Now that an official client exists, I would start there for regular use and compatibility validation.

DeepSeek Harness can interact with more than a chat window:

| Local files | Model credentials | Sessions and extensions | Tool calls | Local execution |
| --- | --- | --- | --- | --- |
| Project files | Model and Provider credentials | Sessions; Plugins and Skills | Tool invocation | Local commands and tasks |

Third-party clients still need individual assessment. The official client has a clearer relationship to the upstream project, its installer source, its update path, and the Harness Host it is expected to run.

I would still evaluate third-party clients individually:

| Source and maintenance | Distribution and updates | Permissions and credentials | Execution and compatibility |
| --- | --- | --- | --- |
| Is the source available? Is maintenance active? | Where are installers published? How do updates work? | Which permissions are required? How are credentials stored? | Are local commands executed? Which Harness versions are supported? |

For software that can reach local projects and execution environments, those questions deserve an answer before adoption.

## One AI runtime, one QA Workbench

dsh-qa does not maintain a second AI runtime.

DeepSeek Harness continues to manage models, API keys, Providers, Sessions, Skills, Commands, and Tools.

Each test project binds to a native Harness Session and uses the corresponding QA mode.

The responsibility boundary is:

| DeepSeek Harness / AI runtime | dsh-qa / QA Workbench |
| --- | --- |
| Models; Sessions; Agents; Skills; Commands; Tools; Plugins | Requirements; Risks; Tests; Executions; Evidence; Defects; Reports; Quality Gates |

The desktop client keeps that architecture and makes the first step easier.

## Local-first remains the foundation

The desktop entry does not change the local-first direction of dsh-qa.

Test projects, testing materials, and structured quality data remain local by default.

The combined model is:

| DeepSeek Harness | dsh-qa | Combined result |
| --- | --- | --- |
| AI runtime | QA Workbench | AI-native QA workspace |

This lets teams use Harness models, Agents, Skills, and Tools without building a separate test-project system just to make AI useful.
