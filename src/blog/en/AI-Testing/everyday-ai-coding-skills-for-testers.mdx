An AI coding agent can connect to a ticket, inspect a design, write test cases, create automation, run it, and prepare a pull request. That sounds efficient—until the agent fills gaps with invented requirements or produces dozens of weak scenarios.

In the Ministry of Testing session *Everyday AI coding: skills & plugins in a tester’s workflow*, Principal Software Engineer in Testing Maneesh Maddala argues for a more disciplined approach: give the agent small, well-defined responsibilities; provide tools deliberately; and keep humans at the approval points that matter. The session took place on July 31, 2026. The following turns its examples into a workflow teams can inspect and adapt.

## A Skill is a trail map, not magic

A reusable Skill is closer to a trail map than a guarantee. It gives an agent instructions, context, and a repeatable method for a task. It can improve consistency, but it cannot guarantee that the agent will follow every rule or correctly understand missing information.

That distinction matters in testing. A Skill may ask for evidence before creating a test, but the agent still needs permission boundaries, representative evaluations, and a safe way to stop when requirements are unclear. Treat the Skill as part of an engineered workflow, not as a substitute for one.

## Commands, Skills, plugins, MCP, and agents

The talk uses a kitchen analogy to make the different pieces easier to understand. The analogy is useful, but it is not a technical specification.

| Concept | Kitchen analogy | Practical role |
| --- | --- | --- |
| Slash command | A shortcut to a named task | Starts a known action on request |
| Skill | A recipe or working method | Supplies task-specific instructions and context |
| Plugin | A kitchen extension | Packages or exposes capabilities in a host environment |
| MCP server | A connection to an outside supplier | Gives a model access to external data or actions through a defined interface |
| Agent | A cook carrying out work | Uses instructions and tools to complete a task |

Skills do not replace MCP. A Skill can describe how to use a connected system; MCP can provide the connection itself. Whether the workflow needs MCP depends on whether it must retrieve external data or perform an action.

## Why one giant prompt failed

The session describes an early end-to-end prompt spanning Asana requirements, Jira, Figma, TestRail, Playwright, and pull-request review. The agent produced roughly 50–60 scenarios, but many were weak or fabricated. It also invented locators despite having browser access.

The problem was not simply prompt length. The task combined too many decisions, systems, permissions, and output types without enough project context or checks. A large scenario count was mistaken for coverage. In practice, more generated cases can mean more noise to review.

## Split the workflow into focused responsibilities

Give each Skill a narrow job and a clear handoff. A planner can read requirements and propose scenarios, while remaining unable to write test cases or code. A scenario writer can create cases after approval. A coding Skill can implement page objects and tests. A test runner can execute and report. A reviewer can prepare a pull request, but should stop before merge unless the owner has explicitly authorized more.

Set limits based on task complexity. The talk gives examples such as roughly 3–5 scenarios for a small change and 10–12 for a larger one. These numbers are starting points from the demonstration, not universal caps. Every scenario still needs a reason to exist.

## A five-stage workflow with human approval

| Stage | Agent responsibility | Human decision or handoff |
| --- | --- | --- |
| Plan | Read requirements and propose a bounded scenario list in scenarios.md | Review scope and approve scenarios |
| Test management | Map approved scenarios to existing TestRail cases and propose additions or updates | Approve managed test-case changes |
| Implementation | Create or update page objects and automated tests | Review code and confirm repository conventions |
| Execution | Run the approved suite and summarize failures with evidence | Decide whether failures are product, test, data, or environment issues |
| Review | Prepare a pull request with changes, results, and known limitations | Engineer reviews and merges |

The table is a suggested decomposition of the session’s workflow, not a guarantee that every integration behaves this way. Make each transition explicit: which artifact is produced, who reviews it, and what must be true before the next step begins.

For example, a scenario record might include its source requirement, user intent, preconditions, expected behavior, risk, and open questions. A concise structured format is easier to validate than free-form prose. Do not let an agent write to TestRail, edit repository files, or open a pull request until the appropriate approval has been given.

Autonomous loops need their own boundaries: a retry limit, timeout, spending budget, failure classification, and success condition. “Keep trying until green” is not a safe completion rule.

## Why human review remains essential

The human boundary is not one final approval at the end. It belongs at the points where assumptions become managed test assets, code changes, external writes, or release-impacting decisions.

Reviewers should check whether the output follows the requirement, whether scenarios are distinct and risk-based, whether selectors use stable semantics, whether page objects contain actions rather than hidden assertions, and whether the evidence really comes from the claimed execution. The browser being available does not prove the agent actually used it correctly.

Approvals should be explicit and scoped. A person who approves scenario intent has not automatically approved repository edits, external system changes, or merging a pull request.

## What the SauceDemo comparison showed

The live demonstration used SauceDemo to create around eight to ten checks covering login, cart, and checkout. Without enough instruction, the agent did not clarify project assumptions and generated tests with avoidable gaps.

Adding the grill-me Skill changed the conversation: the agent asked about TypeScript, npm, linting, GitHub Actions, authentication, test types, browser coverage, and repository conventions before proposing fixtures, page objects, and tests. The useful lesson is the value of clarification before implementation. This was a demonstration, not a controlled benchmark proving that one Skill always produces better tests.

## Guardrails and Evals answer different questions

Guardrails define what an agent may do: read-only access, allowed commands, protected files, external write permissions, budget limits, and approval requirements. Evals check whether it behaves as intended across representative inputs.

Evaluate at three levels:

1. **Structure:** Does the output satisfy the required format and include required fields?
2. **Behavior:** Does the Skill follow its instructions, use only permitted tools, and stop at the approval boundary?
3. **Quality:** Are the scenarios traceable to real acceptance criteria, non-duplicative, and free of fabricated features or weak assertions?

An evaluation case might be as small as this:

```yaml
case: missing_acceptance_criteria
input: "Create tests for an unspecified checkout change"
expected:
  ask_for_clarification: true
  fabricate_requirements: false
  create_testrail_cases: false
```

“The output looks good” is not a sufficient pass condition. Keep real failure examples as a regression set; after changing a Skill, record pass rate, policy violations, human edits, and regressions.

## What does the ROI really show?

In one team example, a Jira story that took about eight hours from analysis through pull request took 2–2.5 hours with a semi-autonomous workflow. That is approximately 69%–75% less elapsed time for that example. It is not a general productivity guarantee.

The speaker also said Skills can use more tokens: about twice as many in the demo and two to three times as many in some scenarios. Measure end-to-end elapsed time, review effort, useful-scenario rate, code rework, flaky-test rate, incorrect external writes, and model cost together. Faster generation is not automatically lower total cost.

The speaker noted that production defects had declined over the preceding six months but did not attribute the decline solely to AI. Team maturity and risk-management changes may also have contributed. That distinction is important when describing impact.

## From personal prompts to organizational capability

The session describes four stages of organizational maturity:

1. Individuals use AI as a chatbot.
2. A team creates reusable Skills for its work.
3. Teams share Skills and combine them into cross-team agent workflows.
4. An organization provides a central registry and managed access.

As adoption grows, a Skill needs an owner, version, input and output contract, permission boundary, evaluation set, changelog, and deprecation path. Sharing a file is not the same as governing a capability. The same Skill may behave differently across IDEs, models, and agents, so test its host-specific triggers and tool access rather than assuming portability.

## Five questions from the session

**Will Skills replace MCP?** No. They serve different roles: one can describe the work method; the other can connect a model to external data or actions.

**Why not make the whole workflow autonomous?** Because stopping conditions, retries, budget controls, and failure recovery need to be reliable first. Connecting several Skills does not automatically create a safe autonomous system.

**Will AI replace testers?** The session’s answer was no. People still need to set objectives, review reasoning, identify risks, maintain standards, and use saved time for higher-value quality work.

**What if Claude is too expensive?** Teams can evaluate Copilot or another model after enterprise security review, then rerun the same behavioral and quality evaluations. A replaceable model is not automatically an equivalent one.

**How should teams demonstrate value?** Start with a bounded story-level time comparison, then include quality, cost, and reuse. Do not attribute a production-defect trend to AI without evidence.

## Make Skills testable assets

The strongest transferable lesson is not a specific plugin. It is the engineering discipline behind the workflow: narrow responsibilities, explicit contracts, limited tools, human approvals, and regression evaluation against real failures.

A team can maintain a small quality scorecard for each Skill: does it trigger at the right time, respect its tool boundary, avoid inventing tests, satisfy its output contract, behave consistently across supported models, and stop safely when something is missing? That turns a useful prompt into a maintainable engineering asset.

Skills save teams from repeatedly explaining how work should be done, but they do not replace engineering judgment. A useful AI coding workflow is not the one that generates the most code. It is the one that reduces repeated coordination while producing results people can verify, trace, and review.
