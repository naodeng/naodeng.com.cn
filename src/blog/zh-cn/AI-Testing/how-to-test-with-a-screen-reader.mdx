**为什么屏幕阅读器测试值得进入日常 QA 工作？**

视觉界面通过位置、颜色、图标和排版传递信息；屏幕阅读器会把页面结构、可访问名称、控件角色、状态和变化转化为辅助技术可使用的信息。一个看起来正常的登录页，仍可能有无名称的输入框、没有播报的错误，或无法抵达的按钮。

学习笔记引用全球约 22 亿人存在某种程度的视力障碍。这个数字说明无障碍需求的规模，**但不能把所有视力障碍者都等同于屏幕阅读器用户**。屏幕阅读器测试既服务于实际用户，也能暴露页面语义和交互状态的结构性问题。

核心问题应从“页面看起来对不对”转为：**用户能否理解当前页面、找到下一步并完成任务？**

原文：Ady Stokes, “How to Test with a Screen Reader”: https://wonderproxy.com/blog/how-to-test-with-a-screen-reader/

## 先认识工具，再听懂它传达的信息

| 工具 | 常见平台 | 说明 |
| --- | --- | --- |
| JAWS | Windows | 商业屏幕阅读器，在企业环境中较常见 |
| NVDA | Windows | 免费、开源，适合建立桌面 Web 测试能力 |
| VoiceOver | macOS、iOS | Apple 系统内置，桌面和移动端操作方式不同 |
| TalkBack | Android | Android 内置屏幕阅读器，常用手势和焦点导航 |

学习笔记提到 JAWS 的份额约为 40%。这类数字会随调查年份、样本、地区和人群变化；应结合真实用户、目标平台与最新调查选择测试组合，而不是只按单个比例决定。

**文字转语音不等于屏幕阅读器。**朗读工具可能会读出文本，却未必提供标题导航、控件角色、可访问名称、状态和操作方式。

**听传达的信息，不要死记播报原文。**

除了可见文字，屏幕阅读器还能读取 HTML 语义和无障碍 API 提供的信息，例如输入框名称、是否为空、是否必填、密码是否受到保护；元素是链接还是按钮、当前是否可操作；标题层级和导航区等地标；控件是否展开、选中、禁用或处于校验错误状态。

有经验的用户不一定从页面顶部一路听到末尾。他们会按标题、链接、表单控件或地标跳转。这些入口像同一座城市的不同地图，各自适合不同任务。笔记提到，部分熟练用户的聆听速度可能超过每分钟 300 个单词；初学者不需要追求这个速度。

例如，邮箱输入框可能被读作“电子邮件地址，编辑框，空白，必填”；密码框可能被读作“密码，编辑框，受保护，空白，必填”。标题也可能播报为“一级标题，欢迎回来”“二级标题，登录”。

**不同屏幕阅读器、浏览器、语言和设置下的具体措辞与顺序会变化。**测试应关注信息是否完整传达，不要硬编码某一段语音文本作为唯一标准。

## 开始测试前先练习

Stokes 提到一次有些尴尬的经历：他在没有耳机的火车车厢里打开了手机屏幕阅读器，却不知道如何关闭，慌乱了大约五分钟才恢复。作者给出的第一条建议很实用：先弄清设备的开关快捷方式；他自己的 iPhone 是轻点机背三次。

1. 先学会开启和关闭屏幕阅读器；移动设备快捷方式可能因设置不同。
2. 手边准备键盘或手势速查表，记录下一项、标题、控件和交互模式切换方式。
3. 完成内置教程。屏幕阅读器导航并不等同于按 Tab 键浏览。
4. 从熟悉的页面开始，例如登录、搜索或个人资料页。
5. 短时间练习即可，先从五分钟开始，适应后再延长。
6. 条件允许时先不使用鼠标，比较纯键盘操作和屏幕阅读器导航。
7. 尝试按标题、链接、按钮、输入框和地标等不同方式导航，留意“点击这里”这类脱离上下文后没有意义的链接。
8. 调整朗读速度；听懂和完成任务，比追求熟练用户的速度重要。

可以每周用键盘和屏幕阅读器重复走一遍熟悉的业务流程，记录用户在哪些地方难以发现、理解或操作界面。

## 检查任务能否完成，不要追求固定播报稿

**标题与页面结构。**

用户能否通过标题理解页面并跳到目标部分？标题层级是否符合内容结构？从三级标题跳到五级标题值得调查，**但不能脱离语境就自动判为失败**。Stokes 建议页面只设一个 H1，除非页面包含彼此独立的区域；应把它当作结合语义结构判断的建议，而不是机械套用的规则。

检查 header、main、nav、footer 等地标是否暴露；如果页面有多个导航区域，用户能否区分它们？

**表单名称与错误提示。**

用户能否识别邮箱和密码字段及其要求？提交无效内容后，能否发现错误、找到对应字段并理解如何修正？只有红色边框却没有可访问说明，是常见问题。“提交”有时足以说明按钮作用，有时则需要更具体的名称；要结合页面上下文判断。

**动态内容与焦点。**

对话框打开时，焦点是否移到合适位置？关闭后是否回到触发按钮或其他合理位置？实时搜索结果会不会在每次按键时都打断用户？

aria-live 和 role="alert" 有时能帮助播报，但过度使用会制造噪声。应使用真实屏幕阅读器检查时机、重复提示和上下文。

**链接、按钮与重复播报。**

把链接单独列出时，它们是否仍然说得清楚？只写“这里”或“点击这里”的链接，以及多个“查看详情”，都可能难以区分。有些屏幕阅读器还会提示链接是否访问过或已失效；要检查这些状态在当前任务里是否清晰、有用。图标和文字被读了两遍时，应检查可访问名称和替代文本。**重复播报是调查线索，不代表相关元素永远都应该隐藏。**

**任务能否等价完成。**

比较鼠标、纯键盘和屏幕阅读器路径。每类用户都应能找到关键操作、完成任务，并理解成功或失败。操作步骤可以不同，但不能因此失去核心功能。

**登录流程：一条完整的测试路径。**

| 步骤 | 操作 | 收集的证据 |
| --- | --- | --- |
| 进入页面 | 按标题和地标导航 | 页面身份、主要内容与标题结构 |
| 找到邮箱 | 按表单控件导航 | 名称、角色、必填状态 |
| 找到密码 | 输入测试数据 | 受保护状态与输入指引 |
| 空表单提交 | 触发校验 | 错误是否可感知，能否到达相关字段 |
| 正常登录 | 完成登录 | 进度、成功反馈、焦点与页面跳转 |
| 可恢复错误 | 打开并关闭提示框 | 提示框名称、焦点顺序与焦点恢复 |

记录平台、浏览器、屏幕阅读器及版本、操作步骤、预期可访问信息、实际播报摘要、焦点位置，以及必要的 DOM 或无障碍树证据。“屏幕阅读器坏了”不是可执行的缺陷报告。

## 自动化可以检查什么，真实读屏仍要由人判断

> 本节是受原文启发的工程建议，不是作者列出的实践清单。

自动化检查可以发现缺少标签、明显的语义问题和部分 ARIA 误用，**却无法代替真人用屏幕阅读器完成任务**。可采用分层方法：用静态与组件检查验证语义化 HTML、可访问名称和状态；用键盘与浏览器检查元素可达性、Tab 顺序、对话框焦点和错误反馈；再用真实辅助技术检查代表性组合中的任务完成、导航效率、播报时机和理解程度。

下面的 Playwright 示例只能检查部分相关行为，不代表 NVDA、JAWS 或 VoiceOver 会如何播报：

~~~typescript
import { test, expect } from '@playwright/test';

test('login form exposes meaningful names and errors', async ({ page }) => {
  await page.goto('/login');

  const email = page.getByRole('textbox', { name: /email/i });
  const password = page.getByLabel(/password/i);
  await expect(email).toBeVisible();
  await expect(password).toBeVisible();

  await page.getByRole('button', { name: /sign in/i }).click();
  await expect(page.getByText(/email is required/i)).toBeVisible();
});
~~~

在 AI 原生 QA 流程中，技能可以准备任务、收集环境信息、检查无障碍树并提出风险；智能体可以整理证据、追踪回归。但体验是否易懂、任务是否可完成，仍需要以用户为中心的判断。自动化无障碍检查通过率不等于符合标准，也不等于真实可用。

**在现有策略中安排辅助技术测试。**

从登录、搜索、结账或付款等高价值任务开始，记录可重复的环境和工具版本。在组件检查和键盘测试之外，每轮迭代都留出稳定时间进行真实屏幕阅读器测试；修复后在相关辅助技术组合中重新执行同一任务。按用户影响排序问题，而不是按缺陷看起来有多显眼。

WCAG 2.2 可以帮助确定相关成功准则，但**符合标准与某一种屏幕阅读器上的实际体验不是一回事**。测试设备和辅助技术应结合用户、平台与风险确定。

屏幕阅读器测试不是简单地“让页面读出声音”，而是在检查产品如何传达结构、状态和反馈。**视觉上正确的界面，不一定容易理解或操作。**从一个熟悉流程、一种工具和五分钟练习开始，就能逐步形成可持续的无障碍测试习惯。
