Skill 文档变短，不一定更安全或更清楚。过程性文案清理要删除读者无法从当前仓库理解的临时内容，同时保留仍然约束行为的规则、测量结果和负向保证。

## 修改前先给段落分类

先确认文件范围、双语配对和修改权限，再逐段判断它属于什么：

| 段落类型 | 处理方式 | 示例 |
| --- | --- | --- |
| 当前事实 | 核实后改成现在时表述 | 仍受支持的命令、路径或行为 |
| 契约或负向保证 | 保留含义和适用条件 | 拒绝边界，或明确说明某项动作不会执行 |
| 历史记录 | 如仍有保留价值，放在合适的归档中 | 带日期的发布决定或事故记录 |
| 推理过程或审查对话 | 删除过程残留；若其中有持久事实，则改写该事实 | “审查者在 PR 12 提了这个建议” |
| 测量结果或正式引用 | 保留数值、范围、日期和来源 | 基准测试结果或引用的标准 |
| 生成文件、封存档案或 fixture | 只报告；没有明确授权时不修改 | 用来复现问题的记录型 Eval fixture |

分类可以避免两类错误：把临时审查对话留在用户会读到的 Skill 里，以及误删仍然有效的历史或防护规则。

实际清理可以按这个顺序进行：先列出获准修改的文件和语言配对；再按段落分类；对可能描述当前命令、路径或产品行为的内容找现行来源；最后只改已确认属于过程残留的句子。无法核实的事实要作为不确定项报告，不能为了让文档更顺而改成确定能力。

## 示例：删掉过程说明，保留有效规则

假设文档写着：“本 PR 跟进设计记录 4。导入器会拒绝缺少 account ID 的数据行。”如果第一句脱离审查历史后无法理解，就从当前指南中移除。第二句先对照现行实现或契约核实，再决定是否保留；如果已经无法验证，就报告这个不确定项，不要把它改写成承诺。

清理报告应让处理过程可以复核：

```markdown
# 清理报告
## 已删除或改写
| 位置 | 类型 | 处理 | 理由 |
## 保留的契约与事实
## 未修改范围
## 双语同步状态
```

## 保留会改变行为的内容

接受精简稿前，对照原文检查触发条件、必需输入、例外、拒绝规则、失败处理、测量结果、标识符和引用。重要的负向保证即使占字数也要保留。不要把“未运行”压缩成“已通过”，也不要把假设改写成能力。

源 Skill 没有规定目标字数；它要求清除过程残留并保留持久内容。编辑后要通读受影响页面及其语言配对，再检查链接、示例和未修改范围是否仍然成立。没有授权时，不改生成文件、封存档案、fixture 或范围之外的关联文件。

提交前可做一遍逐项对照：触发条件和必需输入是否还在；限制、例外和失败路径是否保留；命令、版本、ID、数字和引用有没有变化；中英文是否仍指向相同的行为。若删除一句话会改变下游消费方式，就应把它当作契约修改，交给文案契约审查和变更验证，而不是当作简单删字。

~~~

## 常见问题

### 清理时要达到固定字数吗？

不需要。源 Skill 没有规定目标长度。只删掉对读者和行为契约都没有帮助的内容，不能为了缩短而删掉有效契约。

### 可以顺手精简生成文件或 fixture 吗？

不可以。源 Skill 将它们视为受保护证据；应报告这些文件，并且只编辑明确授权的范围。
