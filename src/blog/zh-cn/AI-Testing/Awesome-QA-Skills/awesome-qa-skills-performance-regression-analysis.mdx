一次发布后慢了 10%，并不意味着每个用户、每条路径都变差。性能回归判断需要可比基线、稳定环境和对变化机制的解释。

性能回归分析 Skill 用可比对象衡量差异和不确定性，并在要求优化前将变化关联到具体行为。

本文通过具体场景说明如何收集、连接和解释证据，让结论能够服务下一步的工程或业务决定。

## 性能回归分析 Skill 用来做什么

性能回归分析适合需要比较版本却经常遇到环境噪声的团队。它先固定基线、负载和重复次数，再判断差异是否足够稳定，避免一次异常就阻断发布。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [性能回归分析 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/performance-regression-analysis/prompts/performance-regression-analysis.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 环境或负载不可比时不得下回归结论
- 报告绝对值和相对变化
- 区分噪声与稳定退化

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 比较两个版本的结账性能，判断延迟回归是否真实、影响多大以及是否阻断发布 | 标出不在本轮判断内的链路 |
| 版本与环境 | 基线版与候选版、负载模型、实例规格和运行时间 | 两次运行条件不一致时先标环境噪声 |
| 证据 | p50/p95/p99、错误率、资源曲线、请求分布和 run ID | 只看平均值时结论降级为初步信号 |
| 决策边界 | 回归阈值、复跑条件、发布门禁和性能 Owner | 将真实回归与测试失效分开处理 |

可以这样调用：

```text
请使用 performance-regression-analysis Skill。

任务：比较两个版本的结账性能，判断延迟回归是否真实、影响多大以及是否阻断发布
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## 性能回归分析要先保证比较公平

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 比较条件 | 两个版本是否使用同一环境和负载 | 构建号、资源规格和脚本版本 |
| 差异指标 | 哪些变化超过噪声范围 | p50/p95/p99、吞吐和错误率 |
| 统计可信度 | 差异是否能重复出现 | 重复次数、置信区间或波动范围 |
| 发布决定 | 退回、继续观察还是接受风险 | 阈值、负责人和例外记录 |

没有可比环境和重复运行时，只能记录观测差异，不能宣布性能回归。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——比较两个版本的结账性能，判断延迟回归是否真实、影响多大以及是否阻断发布。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

比较前要锁定负载、环境、数据和统计口径，差异不一致时不能直接下结论。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

比较前要锁定负载、环境、数据和统计口径，差异不一致时不能直接下结论。

每次性能回归分析都保存基线版本、候选版本、负载脚本和资源规格。门禁阈值变化时，保留旧阈值和例外原因，避免历史结论被悄悄改写。

### 三段式 Skill 链

`performance-workload-modeling` → `performance-regression-analysis` → `release-testing-workflow`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 performance-regression-analysis | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| performance-regression-analysis 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 performance-regression-analysis | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| performance-regression-analysis 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| performance-regression-analysis 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| performance-regression-analysis 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| performance-regression-analysis 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 两个版本没有固定数据和环境，却直接比较单次结果。
2. 只看平均值，忽略尾延迟和错误率退化。
3. 把缓存预热、依赖波动或流量差异当成代码回归。
4. 发现退化后只调阈值，没有保留接受风险的理由。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 性能回归分析，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
