一个 Skill 改完后，单看一两个成功示例，很难判断它是否真的更可靠。触发条件可能变得过宽，关键步骤可能被跳过，输出也可能更长却更难用。Skill 评测要把这些变化放回可重复的案例里比较。

skill-evaluation 帮助团队设计评测、选择判断方法并解释结果。它评估的是 Skill 在一组明确任务上的表现，不会因为一次通过就证明它在所有工具、模型和项目里都有效。

## 先说清要评什么

评测开始前，固定目标 Skill、版本、运行环境和想回答的问题。例如，是要检查它能否在适当场景触发，还是验证它能否遵守写入前确认规则。目标不同，案例和判断规则也不同。

可从四个角度整理观察点：

| 角度 | 需要检查什么 |
| --- | --- |
| 结果 | 输出是否解决了任务，是否保留来源和必要信息 |
| 过程 | 是否遵循要求的步骤、授权和边界 |
| 风格与质量 | 结构是否清楚，格式是否符合交付契约 |
| 效率 | 完成任务所需的调用、步骤或资源是否合理 |

不要把这些角度压成一个看不出原因的总分。每个检查点都应说明什么证据算通过，什么情况算失败或证据不足。

## 案例要覆盖真实边界

评测集可以从代表性正常请求开始，再加入容易暴露问题的输入：缺少关键信息、超出范围、相似能力竞争、边界条件、负面请求和已知回归。每个案例都应有输入、预期行为、检查依据和可重复的运行设置。

案例不必追求数量多。重点是每项规则都能被某个案例验证，也要避免多个案例只测同一种简单路径。若评测对象包含对话路由，至少要区分应该触发、不应该触发和信息不足时应先澄清的情况。

## 选择合适的判断器

先用确定性规则判断可机械核对的内容，例如必需字段、标准状态值、链接、文件范围和是否出现未经授权的写入声明。只有当判断涉及语义、质量或上下文时，再考虑使用模型评审，并为评审者给出明确量表和参考答案。

脚本适合检查格式和可执行的契约；人工或模型判断适合解释复杂语义。模型评审也可能不稳定，因此需要记录评审提示、模型与版本、评分依据，并对关键案例做人工抽查。不能因为 judge 给出高分就把结果当作客观事实。

如果项目使用 skill-up，可以先用其校验命令检查 Eval 配置。配置校验只说明工件符合工具要求，不能替代实际运行或证明模型行为符合预期。

## 比较结果时保留运行身份

每轮记录目标 Skill 的版本或提交、案例集版本、运行环境、judge、时间和未获得的证据。这样才知道比较的是 Skill 的变化，还是模型、工具或案例同时变了。

评测失败时先分类再修改：

- **Skill 缺陷**：案例清楚、运行条件满足，但输出违反 Skill 契约。
- **评测缺陷**：预期答案或断言与任务目标不一致，或者案例没有稳定判定方式。
- **基础设施问题**：模型、工具、网络或数据不可用，无法得到有效结果。
- **未知**：当前证据不足，暂时不能归因。

不要把基础设施故障统计为 Skill 失败，也不要为了让趋势变好而删掉真实回归案例。只有确认失败根因后，才将其整理成长期回归用例并保留原始运行记录。

## 用 AI 设计评测，再用证据审查

AI 可以根据 Skill 的目标生成候选案例、找出正反边界、草拟断言，并对比两版输出。评测负责人需要确认案例是否代表真实任务、判断器能否稳定区分结果，以及比较是否基于同一环境。

~~~text
请使用 skill-evaluation 为目标 Skill 设计一组评测。

Skill 与版本：[路径、版本或提交]
评测目标：[要验证的触发或行为]
运行条件：[模型、工具、环境与数据]
现有案例和结果：[提供文件或记录]

先列出评测目标与覆盖缺口，再设计正常、负向、边界和回归案例。
每个案例写明输入、预期行为、判断依据和证据要求。
优先使用确定性断言；需要语义判断时说明 judge 的限制。
不要把未运行的案例写成通过，也不要把环境故障归因成 Skill 缺陷。
~~~

AI 产出的案例只是候选。团队应检查预期是否能从 Skill 契约和真实需求推出，并在运行后保存原始结果与人工修订记录。

### 评测通过就能发布吗？

不能单独据此决定。评测结果是特定版本、案例和运行环境下的证据，还需结合风险、其他检查和负责人的发布标准。

### Skill 变了，必须重跑全部案例吗？

根据变更影响和评测目标选择。若共享规则或边界发生变化，应检查关联案例；保留完整基准集有助于观察意外回归。

### 可以只用模型 judge 吗？

不建议。机械规则优先用脚本；语义判断可用模型或人工。关键结论应能回到案例、标准和输出证据。
