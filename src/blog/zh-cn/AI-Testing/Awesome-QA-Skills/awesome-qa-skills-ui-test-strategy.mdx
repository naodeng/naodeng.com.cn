从页面数量开始做 UI 自动化，很快就会变贵。有效策略应在选择浏览器测试前连接用户流程、状态、平台、角色、可访问性和已知故障。

## 为什么需要这个 Skill

UI Test Strategy Skill 根据用户流程、页面和组件清单、状态流、设计、平台矩阵、可访问性要求和缺陷证据形成 UTS-## 候选，不能执行测试或声称覆盖。

## Skill 用来做什么

本文关注的策略从用户结果和风险出发，再选择最小而有依据的 UI 证据。

当你要为流程或发布定义可追踪的 UI 质量候选和边界时，使用这个 Skill。它让平台和状态取舍可见，不会直接变成完整测试策略或可执行集合。

UTS 发现要写清流程或状态、前置条件、风险、来源证据、平台适用性、优先级、负责人、关闭条件和验证动作。

当团队需要决定哪些流程、状态、设备、浏览器、语言或可访问性路径优先关注时，使用这个 Skill。

## 它不做什么

UI 测试策略 Skill 可以组织流程候选的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 流程候选 | 用户结果、状态和风险 | UTS 编号与来源 |
| 平台边界 | 浏览器、设备、语言、输入和无障碍范围 | 适用性 |
| 优先级理由 | 为什么需要深测或抽样 | 证据与不确定性 |
| 验证动作 | 扩展前的最小 UI 检查 | 负责人与 NOT_RUN 状态 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“流程候选”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕流程候选，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 流程与状态 | 核心流程、空/加载/错误/成功状态、角色和转换 | 缺失状态要可见 |
| 平台矩阵 | 浏览器、设备、视口、语言、输入方式和无障碍需求 | 不要假设一个浏览器代表全部 |
| 风险证据 | 缺陷、分析数据、业务重要性和变更面 | 事实与推断分开 |
| 已有资产 | 设计、组件、测试、夹具和环境 | 存在不等于执行 |

可以这样调用：

~~~text
请使用 ui-test-strategy Skill。

任务：为旅行预订结账定义 UI 测试候选，覆盖桌面、移动 Web、键盘导航和支付错误状态。
输入材料：[用户流程、状态图、平台矩阵、可访问性要求、设计和缺陷历史]
范围：[搜索、乘客信息、支付和确认]
限制：[一个 staging 环境、设备容量有限]

输出 UTS-## 发现，包含对象、前置条件、问题、来源、平台适用性、证据状态、负责人、关闭条件和验证方式。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：覆盖键盘和移动端的支付错误状态

桌面快乐路径已经存在，但缺陷历史显示支付错误会卡住键盘用户，移动端还会丢失已填乘客信息。这个 Skill 应提升错误状态和恢复路径候选，连接平台证据，并把未执行工作保留为 NOT_RUN。

结果是策略候选清单，不能证明 UI 行为、无障碍合规、覆盖或发布就绪。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“流程候选”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和流程候选的具体对象 |
| 发现 | 流程候选的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 流程候选 | 用户结果、状态和风险 | UTS 编号与来源 |
| 平台边界 | 浏览器、设备、语言、输入和无障碍范围 | 适用性 |
| 优先级理由 | 为什么需要深测或抽样 | 证据与不确定性 |
| 验证动作 | 扩展前的最小 UI 检查 | 负责人与 NOT_RUN 状态 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供流程、状态转换、平台和语言矩阵、无障碍预期、变更与缺陷证据、设计、已有测试、数据和环境容量。未知平台行为保持未评估。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 从页面数量开始，而不是从用户流程和风险开始。
2. 只在一个桌面浏览器测试快乐路径。
3. 把候选测试清单叫完整策略或已执行覆盖。

## FAQ

### 这个 Skill 会决定完整浏览器矩阵吗？

它提出有证据的候选和取舍，平台覆盖仍取决于风险、容量和人工决定。

### 页面清单能证明 UI 覆盖吗？

不能。它只是输入材料，覆盖还需要可追踪意图和执行证据。
