压测结束后的图表很多，真正困难的是判断瓶颈何时出现、影响了谁，以及结果是否足以改变发布或扩容决定。分析必须把指标还原成系统行为。

性能结果分析 Skill 关联延迟、错误、饱和度和负载变化，产出带适用边界的结论，而非逐图评论。

本文通过具体场景说明如何收集、连接和解释证据，让结论能够服务下一步的工程或业务决定。

## 性能结果分析 Skill 用来做什么

性能结果分析适合需要把吞吐、尾延迟、错误率和资源成本交给产品或发布负责人解释的团队。它把数字放回业务比例和时间窗口，帮助读者从报告走到决定。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [性能结果分析 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/performance-result-analysis/prompts/performance-result-analysis.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 不能只看平均延迟
- 先检查压测是否有效
- 结论要说明适用负载和环境边界

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 解读一次结账压测结果，区分吞吐、尾延迟、错误率、资源使用和测试有效性 | 标出不在本轮判断内的链路 |
| 版本与环境 | 压测 run ID、负载阶段、实例规格、版本和时间窗口 | 运行元数据缺失时只做描述性解读 |
| 证据 | summary、分位数分布、错误样本、资源曲线和服务指标 | 只有吞吐量时不推断容量结论 |
| 决策边界 | 结果解释、复跑条件、容量建议和性能 Owner | 将测试有效性与产品风险分别列出 |

可以这样调用：

```text
请使用 performance-result-analysis Skill。

任务：解读一次结账压测结果，区分吞吐、尾延迟、错误率、资源使用和测试有效性
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## 性能结果分析要把数字翻译成决定

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 吞吐 | 系统完成了多少业务工作 | 请求率、事务比例和成功率 |
| 尾延迟 | 最慢的一批用户体验如何 | p95/p99、分位数窗口和样本量 |
| 错误行为 | 失败发生在哪条业务链路 | 错误类型、请求 ID 和日志 |
| 资源代价 | 结果是否靠过度消耗资源换来 | CPU、内存、连接池和成本 |

没有负载条件、时间窗口和资源曲线时，数字只能作为孤立观察，不能直接支撑发布决定。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——解读一次结账压测结果，区分吞吐、尾延迟、错误率、资源使用和测试有效性。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

报告要先判断负载是否有效，再解释性能结果，不能只摘平均响应时间。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

报告要先判断负载是否有效，再解释性能结果，不能只摘平均响应时间。

每次性能结果分析都保存脚本、构建号、数据集、时间窗口和监控链接。报告更新时保留原始 summary，保证别人能重新计算关键数字。

### 三段式 Skill 链

`performance-workload-modeling` → `performance-result-analysis` → `performance-bottleneck-analysis`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 performance-result-analysis | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| performance-result-analysis 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 performance-result-analysis | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| performance-result-analysis 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| performance-result-analysis 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| performance-result-analysis 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| performance-result-analysis 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只报吞吐量，不说明业务比例和成功率。
2. 用平均延迟掩盖尾部用户的超时。
3. 看到错误率上升，却没有按事务、版本和时间窗口拆分。
4. 只保存图表，不保存脚本、原始结果和资源指标。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 性能结果分析，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
