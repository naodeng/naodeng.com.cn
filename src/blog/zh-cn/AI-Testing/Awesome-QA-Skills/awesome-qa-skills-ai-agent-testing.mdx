AI Agent 的质量取决于多步决策，而不是单轮回答。计划、记忆、工具反馈和终止条件只要有一处偏差，就可能把任务带到错误的结果。

AI Agent 测试 Skill 同时评估执行轨迹和最终结果，并用受控环境暴露不安全或无效的循环。

本文给出可落地的检查框架和案例，帮助你在不确定性存在时仍能做出有证据的判断。

## AI Agent 测试 Skill 用来做什么

AI Agent 测试适合验证客服、研发或运营 Agent 的规划、记忆和工具协作。它会把一次会话拆成目标完成、过程选择和失败恢复，帮助团队定位“答案错了”之外的行为问题。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [AI Agent 测试 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/ai-agent-testing/prompts/ai-agent-testing.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 同时评价最终结果和过程轨迹
- 将随机性纳入重复试验
- 不要把单次成功当作可靠性证明

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 评估客服 Agent 的目标完成、规划、记忆、工具调用、失败恢复和安全边界 | 标出不在本轮判断内的链路 |
| 版本与环境 | 模型、系统 Prompt、记忆存储、工具版本、会话 ID 和运行窗口 | 环境未锁定时只评估轨迹样本 |
| 证据 | 任务轨迹、计划修订、记忆读取、工具结果和终止原因 | 缺少中间步骤时不判定规划可靠 |
| 决策边界 | 自动执行范围、重试上限、人工接管和数据保留 | 每个副作用动作绑定停止条件 |

可以这样调用：

```text
请使用 ai-agent-testing Skill。

任务：评估客服 Agent 的目标完成、规划、记忆、工具调用、失败恢复和安全边界
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## AI Agent 测试要把行为拆成可复核的产物

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 目标完成 | Agent 是否真正完成用户任务 | 目标状态、业务结果和工具记录 |
| 规划过程 | 计划是否覆盖约束和必要步骤 | 计划版本、分支选择和理由 |
| 记忆使用 | 记忆是否过期或污染当前任务 | 记忆来源、时间和读取范围 |
| 失败恢复 | 失败后是否重试、降级或交给人工 | 重试次数、最终状态和接管记录 |

没有完整会话、工具结果和最终状态时，只能说明设计覆盖，不能说明 Agent 行为稳定。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——评估客服 Agent 的目标完成、规划、记忆、工具调用、失败恢复和安全边界。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

单次成功不足以证明可靠，重复试验需要保留任务轨迹和失败分类。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

单次成功不足以证明可靠，重复试验需要保留任务轨迹和失败分类。

每次 AI Agent 测试都保存模型版本、系统 Prompt、工具清单和会话 ID。模型、记忆或工具变化时，按变化类型重跑规划、工具调用或恢复用例，并标记复核状态。

### 三段式 Skill 链

`llm-testing` → `ai-agent-testing` → `agent-tool-testing`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 ai-agent-testing | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| ai-agent-testing 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 ai-agent-testing | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| ai-agent-testing 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| ai-agent-testing 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| ai-agent-testing 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| ai-agent-testing 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只看最终答案，漏掉错误规划和不必要的工具调用。
2. 用一条成功会话代表 Agent 在多轮任务中的稳定性。
3. 记忆没有版本和来源，导致旧事实继续影响新任务。
4. 失败后无限重试，却没有停止条件和人工接管路径。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 AI Agent 测试，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
