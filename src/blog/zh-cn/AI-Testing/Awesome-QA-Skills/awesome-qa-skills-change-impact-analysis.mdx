一次看似很小的改动，可能同时改变数据流、权限、缓存和依赖方。变更影响分析要找出哪些地方必须重新获得证据，并把理由写回版本和依赖链。

变更影响分析 Skill 从改动表面追踪到受影响的用户、集成和测试，形成有依据的验证范围。

本文将用明确的输入、边界和输出组织实践过程，帮助你把结论交给下一个需要据此行动的人。

## 变更影响分析 Skill 用来做什么

变更影响分析适合改动跨越服务、数据和发布流程的项目。它把 diff、依赖链和历史缺陷连接起来，产出测试范围与发布动作，而不是只列一串受影响文件。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [变更影响分析 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/change-impact-analysis/prompts/change-impact-analysis.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 区分已证实影响与推测影响
- 不要只按改动文件选测试
- 无法追踪的依赖要显式标为风险

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 分析退款状态机修改会影响哪些服务、接口、数据、测试和发布门禁 | 标出不在本轮判断内的链路 |
| 版本与环境 | base/head 提交、部署环境、配置版本和依赖锁定状态 | 无法确认版本时停止传播判断 |
| 证据 | diff、调用关系、schema、配置引用和受影响测试 | 证据互相冲突时保留冲突项，不强行合并 |
| 决策边界 | 影响路径、未知区域、验证顺序和发布 Owner | 给每条路径标验证人和截止时间 |

可以这样调用：

```text
请使用 change-impact-analysis Skill。

任务：分析退款状态机修改会影响哪些服务、接口、数据、测试和发布门禁
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## 变更影响分析要把链路画到可以行动

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 变更对象 | 哪些文件、接口、配置或数据结构变了 | diff、提交和配置版本 |
| 依赖链 | 哪些服务、消费者和数据流会受影响 | 调用关系、schema 和依赖清单 |
| 测试范围 | 哪些测试必须重跑，为什么 | 映射规则、历史缺陷和风险 |
| 发布动作 | 灰度、迁移、回滚和通知需要什么 | 发布计划、Owner 和关闭条件 |

没有明确变更版本和依赖来源时，只能输出候选影响，不能把“未发现影响”当成结论。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——分析退款状态机修改会影响哪些服务、接口、数据、测试和发布门禁。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

影响范围来自依赖和行为证据，不能只凭文件名或模块名猜测。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

影响范围来自依赖和行为证据，不能只凭文件名或模块名猜测。

每次变更影响分析都保存基准分支、提交、依赖版本和判断来源。后续提交只重算被触及的链路，并标记新增、保持或需要人工复核的影响。

### 三段式 Skill 链

`change-impact-analysis` → `regression-scope-analysis` → `regression-test-selection`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 change-impact-analysis | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| change-impact-analysis 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 change-impact-analysis | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| change-impact-analysis 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| change-impact-analysis 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| change-impact-analysis 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| change-impact-analysis 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只看改动文件名，漏掉 schema、配置和运行时依赖。
2. 把“没有直接调用”当作没有影响，忽略事件、缓存和数据共享。
3. 只列受影响测试，不说明选择依据和被排除的范围。
4. 变更继续合并后仍沿用旧影响图，没有重新计算。

## 相关 Skill

变更影响分析完成后，回归边界和执行顺序还需要单独判断：

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 变更影响分析，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
