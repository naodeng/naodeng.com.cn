Node 服务的接口测试如果只断言状态码，很容易遗漏中间件、错误体和异步状态带来的真实行为变化。Supertest 应围绕 HTTP 边界而不是内部实现组织。

Supertest API 测试 Skill 从客户端视角覆盖路由、鉴权、载荷校验和错误结构，而不耦合框架内部。

本文将用明确的输入、边界和输出组织实践过程，帮助你把结论交给下一个需要据此行动的人。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。项目结构与通用安装方式已经在[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/)说明，这里只讲 Supertest 接口自动化。

## 先看源 Skill

主 Prompt 把工作拆到 输入解析顺序、默认约定（无用户指定时直接采用）、Gotchas、交付前自检、质量要求。这些标题只是导航，真正使用时还要回到项目材料。

源目录现有示例、参考和脚本入口。先看 [框架使用说明](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/api-test-supertest/references/framework-spec.md)。

如果团队已经维护 Bruno Collection，也可以把它作为接口材料交给 Skill 解析；Bruno 不是 Supertest 的依赖，更不是开始回归测试的前提。

## 相关 Skill

Supertest 负责把接口场景落成 Node 应用实例上的 HTTP 测试。遇到下面这些相邻问题时，再把结果交给对应 Skill：

| Skill | 什么时候接上 | 它补什么 |
| --- | --- | --- |
| [API 契约测试](https://inaodeng.com/zh-cn/qaskills/api-contract-testing/) | OpenAPI、错误体或字段兼容性发生变化时 | 检查提供方与消费者之间的契约、语义和迁移风险 |
| [回归测试选择](https://inaodeng.com/zh-cn/qaskills/regression-test-selection/) | 接口改动已经定位到影响范围时 | 根据变更、依赖和历史失败选择本次回归集合 |
| [测试报告](https://inaodeng.com/zh-cn/qaskills/test-reporting/) | 测试已经执行，需要给出可复核结论时 | 整理命令、报告、失败请求和证据边界 |

## 从材料到可运行入口

这次任务是：为 Node.js API 生成 Supertest 测试套件，隔离应用实例、数据和认证状态。

给 Skill 的输入可以很短，但不能含糊。

```text
业务链路：登录 → 创建订单 → 支付 → 查询结果
环境：staging
已有材料：接口定义、测试账号、CI 运行方式
交付：tests/api/orders.api.test.ts，附本地命令和失败证据
```

Skill 应先确认版本、认证方式和数据清理策略，再生成文件。示例输出片段如下，它展示结构，不代表代码已经运行。

```yaml
tool: Supertest
entry: tests/api/orders.api.test.ts
checks: 401/403 权限边界、错误 schema、重复请求幂等性
run_evidence: pending
```

最后一行很重要。没有命令输出、报告或 Trace，就只能写 pending。源 Prompt 还要求关注 输入解析顺序、默认约定（无用户指定时直接采用）、Gotchas。

## 把示例补成项目骨架

代码片段只有放回目录和命令里才有用。下面这份骨架够小，适合先接通一条链路。

```text
tests/api/orders.api.test.ts
├── 场景与断言
├── 数据或 feeder
├── 环境配置
└── 失败证据输出到 artifacts/
```

本地或 CI 的第一条命令可以写成：

```bash
npm test -- orders.api.test.ts
```

每组测试创建隔离的应用实例，数据库状态在用例之间重置，别让执行顺序决定结果。

### 怎么算接入完成

| 检查项 | 最低要求 | 不满足时怎么处理 |
| --- | --- | --- |
| 可重复执行 | 连续运行不依赖上一次残留数据 | 重做数据创建与清理 |
| 失败可定位 | 测试报告、失败请求与响应、接口版本、构建号 能回到同一次运行 | 给产物加 run ID 和构建号 |
| CI 可判定 | 进程退出码与质量门禁一致 | 修正 reporter 或 threshold 配置 |
| 维护成本 | 定位、认证或公共请求只有一个修改点 | 提取应用创建器、中间件装配或公共请求封装 |

先只接一条关键链路。它在本地和 CI 都稳定以后，再扩到异常、边界和并发场景。

## 一段可以直接改的调用词

把下面的方括号换成项目内容。材料越具体，Skill 越少猜。

```text
请使用 api-test-supertest Skill。

任务：为 Node.js API 生成 Supertest 测试套件，隔离应用实例、数据和认证状态
版本与环境：[需求版本 / 构建号 / 环境]
输入材料：[文件路径或链接]
范围：[本次包含与排除的业务链路]
限制：[账号、数据、时间、合规要求]

先确认 Node、应用创建器和中间件装配方式，再生成 Supertest 入口、测试数据清理和执行命令。断言要覆盖响应与关键副作用；代码未运行时，把结果标成待验证。
最后列出待确认问题，不要补写材料里没有的事实。
```

第一次调用先看结构和缺口。补齐材料后再生成正式产物，能省掉不少来回修改。

## Supertest 的边界在应用实例，不在 HTTP 客户端

Supertest 可以直接接入 Express 或 Nest 的应用实例。测试先决定哪些中间件、异常过滤器和依赖替身必须保留；把真实数据库、第三方支付和后台队列换成可控替身。否则测试看起来在验路由，实际把部署环境也拖进了断言。

一条高价值用例要验证状态码、响应体和副作用。创建订单后，既检查 `201` 与订单字段，也检查消息是否入队或库存是否变化。清理数据写进 `afterEach`，不要依赖测试执行顺序。

## 这类工具最容易踩的坑

1. 只生成代码，不给运行命令。拿到文件的人仍然不知道怎么验证。
2. 忽略版本和依赖。Supertest 的配置、API 和报告插件都会变化。
3. 共用脏数据。接口、UI 和性能测试都会被残留数据拖垮。
4. 把一次绿色结果写成长期稳定。至少保留报告、日志和失败重试信息。

## 常见问题

### Supertest 接口自动化 会直接给我一个能跑的项目吗？

有完整定义、版本、目录和依赖时，它可以生成很接近可运行的入口。最终仍要在你的仓库里安装依赖、执行命令并修正环境差异。

### 什么时候应该停下来补信息？

认证方式、测试数据或目标版本缺失时先停。继续生成只会得到一份看起来完整的猜测。

### 代码生成后先检查哪一处？

先看入口命令能否发现并运行目标文件，再看失败产物是否写到约定目录。连入口都没接通时，先别扩用例。

### 可以直接放进发布门禁吗？

等本地和 CI 使用同一命令、数据可重置、失败证据可追踪以后再放。

先拿一份真实材料跑 Supertest 接口自动化，保留输入、输出和复核意见。文章里的片段只能帮你搭起结构，项目证据还得在项目里产生。
