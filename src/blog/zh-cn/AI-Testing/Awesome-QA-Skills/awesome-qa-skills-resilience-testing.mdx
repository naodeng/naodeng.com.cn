依赖变慢、不可用或部分失败时，系统仍能保留多少有用能力，才是韧性。正常路径冒烟测试或泛化事故描述不能代替它。

## 为什么需要这个 Skill

Resilience Testing Skill 分析降级行为、隔离边界、恢复能力和残余风险，并把计划中的实验与已经执行的故障测试分开。

## Skill 用来做什么

本文关注的产物，是一个小范围、可回退，并能改变当前韧性判断的验证动作。

当你要复核依赖失败时服务如何降级，以及恢复或隔离证据是否就绪时，使用这个 Skill。它不会注入故障，也不会调用生产依赖。

结果要写清故障触发、预期降级、隔离边界、恢复能力、残余风险、负责人、停止条件和验证方式。

当准备受控韧性演练、复核依赖设计，或者调查 fallback 路径不清楚时，使用这个 Skill。

## 它不做什么

韧性测试 Skill 可以组织降级行为的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 降级行为 | 用户和操作人员应该观察到什么 | 预期结果与来源 |
| 隔离边界 | 故障不能传播到哪里 | 边界与证据 |
| 恢复能力 | 正常行为如何回来 | runbook 与验证 |
| 残余风险 | 仍未知或已接受的内容 | 负责人和下一步 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“降级行为”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕降级行为，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 韧性目标 | 用户可见行为、服务边界和可接受降级 | 未批准目标保持 pending |
| 故障场景 | 依赖超时、部分中断、队列压力或资源耗尽 | 不要只写系统故障 |
| 隔离设计 | 舱壁、熔断、队列、fallback 和数据一致性边界 | 未文档化边界标为未知 |
| 恢复证据 | runbook、指标、告警、恢复步骤和安全环境 | 设计与执行分开 |

可以这样调用：

~~~text
请使用 resilience-testing Skill。

任务：准备结账服务在税费供应商超时、支付队列延迟时的受控复核。
输入材料：[依赖图、fallback 设计、队列策略、告警、runbook 和验证环境]
范围：[仅 staging、不注入生产故障]
限制：[数据脱敏和明确停止条件]

覆盖降级、隔离、恢复能力和残余风险。没有依据的阈值和执行结论保持 pending。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：复核税费超时，不要把 fallback 当成证明

设计说税费供应商超时时结账使用缓存估算，但没有说明支付捕获前如何对账过期估算。这个 Skill 应指出一致性边界，要求带停止条件的 staging 验证，在证据出现前保持恢复行为未评估。

分析可以准备隔离验证并分类设计证据，不能在授权运行产生证据前证明故障隔离、可用性或恢复能力。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“降级行为”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和降级行为的具体对象 |
| 发现 | 降级行为的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 降级行为 | 用户和操作人员应该观察到什么 | 预期结果与来源 |
| 隔离边界 | 故障不能传播到哪里 | 边界与证据 |
| 恢复能力 | 正常行为如何回来 | runbook 与验证 |
| 残余风险 | 仍未知或已接受的内容 | 负责人和下一步 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供故障模式、依赖和数据流图、fallback 规则、负责人、监控、runbook 版本、安全环境和停止条件。边界缺失时先请求边界，不要套用通用模式。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 和其他 Skill 怎么配合

- [可靠性测试](https://inaodeng.com/zh-cn/qaskills/reliability-testing/)：把故障模式连接到可用性证据。
- [熔断器测试](https://inaodeng.com/zh-cn/qaskills/circuit-breaker-testing/)：聚焦打开、半开和关闭行为。
- [恢复测试](https://inaodeng.com/zh-cn/qaskills/recovery-testing/)：检查重大故障后的恢复路径。

## 容易踩的坑

1. 只看到 fallback 返回成功，却不检查旧数据和下游一致性。
2. 列出故障模式，却不说明要隔离什么、如何判断恢复。
3. 没有定义可回退场景和升级路径，就先注入大范围故障。

## FAQ

### 这个 Skill 会直接运行混沌实验吗？

不会。它准备场景和证据计划，实际执行需要授权的操作者或测试流程。

### 写好 fallback 就够了吗？

不够。它只是设计证据，还需要隔离验证和可观察的恢复结果。
