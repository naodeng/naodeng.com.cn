韧性测试检查系统在扰动前、扰动中和扰动后必须保留什么能力。若关键业务不变量丢失，或系统无法安全退出降级状态，仅有回退响应并不足以证明韧性。

## 定义状态与受保护功能

依据已有业务合同描述正常、降级和不可用状态。逐个状态记录必须保留的功能与数据不变量，以及可以变化或暂停的用户体验。

| 阶段 | 根据现有合同回答的问题 |
| --- | --- |
| 扰动前 | 哪些数据和业务不变量构成基线？ |
| 降级期间 | 哪些功能可用、哪些暂停，故障不能扩散到哪里？ |
| 恢复与退出 | 恢复正常行为前，哪些不变量必须重新成立？ |

不要自设可用性目标或阈值。受保护的核心功能、允许的降级方式或退出条件未定义时，应保留为缺口。

## 沿依赖故障追踪系统行为

把部分或缓慢的依赖故障、回退、隔离边界和恢复路径连成一条时间线。追踪受影响请求与账本，检查重复副作用、过期回退数据、资源耗尽和补偿需求；既检查扰动期间的行为，也检查恢复后的不变量是否足以安全退出降级。

例如，结账设计可能在税费服务超时时使用缓存估算。复核可以追问支付捕获前如何对账，以及需要什么证据确认这一边界。该例是复核候选，不代表执行过故障测试。

### 示例结果如何解读

以下仍是说明性场景。若隔离运行的请求记录显示系统在依赖超时时返回了缓存估算，这只支持“回退响应在该请求中出现”这一有限判断。若恢复后的账本对账缺失，数据不变量仍未验证；若发现重复或缺失记录，应将其作为该范围内的差异交给负责人评估。没有请求身份、运行环境和原始记录时，不把设计预期写成运行结果。

## 区分韧性与相邻证据

韧性场景要一起评估降级行为和恢复能力。系统在中断时仍有响应，但无法恢复数据不变量，就不能说已经证明完整韧性。长期可靠性指标和混沌注入实验回答的是不同问题，都不能替代有证据的场景分析。

## 记录 RES-## 发现

记录对象或规则、来源、触发条件或适用范围、预期关注点、证据状态、影响与优先级、责任角色、关闭条件和验证方法。事实、证据支持的推断、候选建议和人工决策应分开。

## 将验证限制在授权范围内

把已有合同、依赖图、回退规则、账本及过往运行记录作为静态证据复核。只建议最小、隔离且可回滚的验证，并标明负责人和停止条件。不要注入故障、访问线上依赖，也不要把计划实验写成韧性结论。

## 安装与调用

安装这个 Skill：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh --skill resilience-testing
```

调用 resilience-testing 时，提供业务不变量、允许的降级方式、依赖图、回退与隔离规则、恢复证据及剩余风险问题。

也可以直接使用下面的请求模板：

~~~text
请使用 resilience-testing Skill。
复核这份服务设计：[带版本的设计文档和依赖图]。
业务不变量：[来源，以及必须保护的数据或功能]。
允许的降级：[已批准的行为与边界]。
恢复证据：[已有运行记录；如果没有，请明确说明]。
不要访问线上系统或注入故障。区分材料支持的事实、缺口和假设；按 RES-## 输出发现，并给出负责人、关闭条件和最小隔离验证方式。
~~~

## 常见问题

### 有回退响应就能证明系统有韧性吗？

不能。还要沿恢复过程检查受保护的数据和业务不变量，以及系统何时可以安全恢复正常。一次运行中观察到回退，只支持这次运行范围内的判断。

### 什么时候可以说设计中的恢复机制有效？

只能根据已有的执行证据，在其实际范围内作出判断。保留运行身份、版本、环境、时间和原始结果；没有这些记录时，应报告设计缺口或验证计划。
