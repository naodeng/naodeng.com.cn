接手陌生项目或收到范围模糊的测试请求时，先确认任务目标、项目入口、依赖、环境、风险和已有测试，再选择匹配的 Skill。

discover-testing 用于这类探索和路由。它会盘点 QA Skills、相关项目材料和信息缺口；如果目标不清楚，应先提出澄清问题。仓库里存在某个 Skill，不代表它已安装或当前 Host 可用；这类结论需要环境或清单证据。

## 从目标和项目现状开始

先说明要交付什么、当前阶段、希望覆盖的范围，以及不允许触碰的内容。随后检查仓库入口、依赖、测试结构、环境和相关文档。把观察到的事实、推断和待确认问题分开，不用内部记忆代替项目材料。

可用下面这段请求启动：

~~~text
请使用 discover-testing 帮我探索这个测试任务。

目标：[要解决的问题或需要交付的结果]
项目材料：[仓库、需求、测试、运行记录和版本]
范围：[包含与排除的业务路径]
约束：[环境、数据、权限、时间和合规要求]

先检查目标是否清楚、材料是否可访问。
列出已知事实、风险、缺口和可用 Skill，再选择一个主要 Skill。
只有确实需要时再建议一个辅助 Skill，并说明交接输入。
不要把 Skill 存在于仓库里说成当前 Host 已安装。
~~~

目标不清时，先确认会影响路由的信息：任务是设计测试、导入旧用例、检索现有用例，还是检查一次提交。

## 选择一个主 Skill，再决定是否需要辅助能力

路由依据应包括用户目标和可用材料，关键词只作为线索。一次工作默认选择一个主要 Skill；只有主 Skill 范围之外还有独立步骤时，才增加至多一个辅助 Skill。

例如，已有测试资产需要搜索时，可以先用 test-case-retrieval 找候选，再由人确认目标记录；需要迁移已选中的旧用例时，才交给 test-case-importer。检索候选不会自动成为导入授权或导入清单。若用户要按 Red、Green、Refactor 推进开发或审查 TDD 阶段，则优先考虑 tdd-quality-workflow，而不是把它误路由成普通测试设计。

路由结果应说明为什么选择当前 Skill、还缺什么输入、下一步需要什么证据，以及哪些工作仍未执行。若没有安装或 Host 能力的明确证据，应将可用性标记为未知。

## 用 AI 做探索，也核对它的依据

AI 能快速整理文件入口、测试目录和候选流程，也能把大问题拆成待确认项。它给出的每条事实都应回到可访问的仓库文件、用户提供的记录或明确来源。不要把 AI 的内部记忆、对话日志或无法复查的判断当作面向用户的证据。

适合复核的输出至少包括：

| 内容 | 需要确认什么 |
| --- | --- |
| 任务目标 | 是否足够清楚，是否需要先澄清 |
| 项目事实 | 是否有对应文件、版本或运行记录 |
| 风险与缺口 | 哪些来自材料，哪些仍是推断 |
| Skill 路由 | 主 Skill 是否匹配，辅助 Skill 是否必要 |
| 下一步 | 输入、交接和执行权限是否明确 |

探索只产出路由判断和证据缺口，不代表测试已经执行，也不授权项目操作。

### 可以一次推荐多个 Skill 吗？

可以列出候选供比较，但最终路由应先确定一个主要 Skill。只有存在独立、明确的交接任务时，再增加至多一个辅助 Skill。

### 如果没有看到 Skill 的安装记录呢？

将 Host 可用性保留为 UNKNOWN，并先核对当前工具或安装清单。仓库源码、网站详情页和本机安装状态是不同证据。

### 检索到的旧用例可以直接导入吗？

不应自动导入。先由人确认候选记录、来源和目标，再进入导入预览与确认流程。
