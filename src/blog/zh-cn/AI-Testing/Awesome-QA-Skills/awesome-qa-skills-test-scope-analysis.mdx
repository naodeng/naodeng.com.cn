测试范围是在回答团队现在要学习什么、暂时留下什么未知。如果排除项和扩展触发被隐藏，有限检查很容易被误认为全覆盖。

## 为什么需要这个 Skill

Test Scope Analysis Skill 在测试前分析目标、产品面、变更、风险、限制、资产、平台、角色、数据和环境，产出 TS-## 边界，不产出执行结果。

## Skill 用来做什么

本文关注的范围应该让不确定性可见，而不是藏在一份短测试清单后面。

当你要为迭代、发布、变更或风险复核定义可解释范围，包括核心流程、直接和传递影响、非功能范围、兼容性、依赖和未评估区域时，使用这个 Skill。

TS-## 条目写清纳入和排除对象、理由、深度、依赖、停止条件、扩展触发、残余风险、来源和负责人。

当发布或测试活动需要先限定范围，在选择可执行集合或汇报覆盖前，使用这个 Skill。

## 它不做什么

测试范围分析 Skill 可以组织纳入范围的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 纳入范围 | 对象、流程、平台、角色、数据和深度 | 理由与来源 |
| 排除范围 | 本次有意不评估的内容 | 原因与风险 |
| 扩展触发 | 什么证据会让范围扩大 | 可观察条件 |
| 残余风险 | 仍未评估或未执行的内容 | 负责人和决策边界 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“纳入范围”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕纳入范围，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与产品面 | 发布目标、流程、组件、平台、角色和数据 | 产品面缺失要明确 |
| 变更与风险 | 直接和传递影响、故障模式、缺陷和非功能关注 | 不要只看变更文件名 |
| 限制与资产 | 时间、环境、测试数据、已有测试和依赖 | 阻塞要记录 |
| 决策边界 | 负责人、残余风险接受人、停止与扩展规则 | 不要声称全覆盖 |

可以这样调用：

~~~text
请使用 test-scope-analysis Skill。

任务：为修改账号删除和通知偏好的发布定义测试范围。
输入材料：[发布说明、依赖图、用户流程、平台矩阵、风险、缺陷、环境和数据限制]
范围：[Web 与移动端、自助删除、通知事件]
限制：[一个 staging 环境和固定验证窗口]

输出 TS-## 的纳入、排除、深度、依赖、停止条件、扩展触发、证据、负责人和残余风险。不要执行测试或声称全覆盖。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：限定账号删除，不要隐藏移动端风险

发布说明只改了 Web 删除，但同一个 API 也被移动端使用。这个 Skill 应纳入共享 API 和移动端确认行为，或者记录排除项并绑定 API 变化或删除缺陷的扩展触发。不能把仅 Web 的检查叫全覆盖。

范围分析可以说明边界和取舍，不能证明测试已运行、覆盖完整、风险为零或发布批准。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“纳入范围”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和纳入范围的具体对象 |
| 发现 | 纳入范围的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 纳入范围 | 对象、流程、平台、角色、数据和深度 | 理由与来源 |
| 排除范围 | 本次有意不评估的内容 | 原因与风险 |
| 扩展触发 | 什么证据会让范围扩大 | 可观察条件 |
| 残余风险 | 仍未评估或未执行的内容 | 负责人和决策边界 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供目标、版本、产品面、直接和传递变更、风险、限制、平台、角色、数据、环境、已有资产和残余风险负责人。上下文缺失时保持未评估。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把变更文件名或范围表当成覆盖证明。
2. 排除传递依赖却不给理由或扩展触发。
3. 只要求范围分析，却顺手写成完整策略或可执行集合。

## FAQ

### 排除等于不重要吗？

不等于。它表示本次活动没有评估，必须保留理由、残余风险和扩展触发。

### 这个 Skill 会选择具体测试 ID 吗？

不会。它定义范围和深度依据，可执行选择属于独立活动。
