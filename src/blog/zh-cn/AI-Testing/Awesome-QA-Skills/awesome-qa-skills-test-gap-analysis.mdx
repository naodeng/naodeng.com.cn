“覆盖不够”不是可交接结果。有效缺口应该说明哪个义务没有保护、缺什么证据、谁负责下一步，以及怎样关闭。

## 为什么需要这个 Skill

Test Gap Analysis Skill 双向比较测试义务和测试资产，产出 TG-## 缺口，覆盖缺失映射、孤儿测试、未验证执行、过期证据、未覆盖风险和低价值重复。

## Skill 用来做什么

本文关注的是把模糊的覆盖担忧变成可关闭的工作项。

当发布或变更需要一份有边界的测试缺口清单时，使用这个 Skill。它不是完整可追溯矩阵、用例编写、可执行集选择或测试执行。

好的缺口包含义务、来源、缺口类型、证据状态、影响、优先级、建议的测试意图、负责人、关闭条件和验证方式。

当发布或变更复核需要在声称全覆盖前确认哪些风险没有得到充分保护时，使用这个 Skill。

## 它不做什么

测试缺口分析 Skill 可以组织测试义务的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 测试义务 | 什么行为或风险需要保护 | 来源与范围 |
| 缺口类型 | 缺失、孤儿、过期、未验证、未覆盖或重复 | 证据状态 |
| 关闭动作 | 测试意图、映射、重跑或补证请求 | 负责人和条件 |
| 残余边界 | 仍未知或延期的内容 | 不是覆盖结论 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“测试义务”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕测试义务，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 测试义务 | 需求、风险、变更行为、缺陷和故障模式 | 固定范围和版本 |
| 测试资产 | 测试意图、代码、用例、执行记录和报告 | 不要从文件名推断 |
| 证据状态 | 运行 ID、时间、环境、结果和新鲜度 | 标为未验证或过期 |
| 决策边界 | 负责人、优先级、发布上下文和风险接受人 | 不要替人接受残余风险 |

可以这样调用：

~~~text
请使用 test-gap-analysis Skill。

任务：为修改发票导出权限并新增重试路径的发布寻找测试缺口。
输入材料：[需求、风险清单、diff、缺陷、测试清单和运行记录]
范围：[导出授权和重试副作用]
限制：[不执行测试、不构建完整追踪矩阵]

输出 TG-## 发现，包含义务、缺口类型、来源、证据、影响、优先级、负责人、关闭动作和验证方式。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：找出缺失的授权负向路径

导出需求覆盖管理员下载，却没有覆盖支持人员尝试下载。这个 Skill 应记录未覆盖的授权义务，要求补测试意图和角色矩阵，在真实运行前保持执行状态未评估。

缺口清单可以识别缺失保护和证据，不能声称全覆盖、通过、发布就绪或风险已接受。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“测试义务”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和测试义务的具体对象 |
| 发现 | 测试义务的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 测试义务 | 什么行为或风险需要保护 | 来源与范围 |
| 缺口类型 | 缺失、孤儿、过期、未验证、未覆盖或重复 | 证据状态 |
| 关闭动作 | 测试意图、映射、重跑或补证请求 | 负责人和条件 |
| 残余边界 | 仍未知或延期的内容 | 不是覆盖结论 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供稳定义务 ID、范围、版本、测试资产、缺陷历史、执行记录和目标决策。只有名称时，把映射候选标为未验证。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试文件当成需求已覆盖的证明。
2. 只说覆盖不足，不指出缺少哪个义务。
3. 所有缺口都标 P0，或把建议测试写成执行结果。

## FAQ

### 这是测试用例生成器吗？

不是。它识别义务和缺口，详细用例属于下一步设计。

### 未执行的测试可以关闭缺口吗？

可以关闭意图或映射缺口，但不能关闭执行证据缺口。
