固定 sleep 隐藏了 UI 测试真正要回答的问题：哪个可观察状态说明页面已准备好，如果它一直不出现怎么办？

## 为什么需要这个 Skill

UI Test Wait Strategy Review Skill 根据异步状态、网络和渲染事件、可观察条件、轮询、超时配置、失败 Trace、重试和固定 sleep 复核等待，产出 UWR-## 发现。

## Skill 用来做什么

本文关注的等待策略应该观察重要的产品状态，而不是单纯消耗时间。

当你要识别 UI 自动化中脆弱或误导性的等待时，使用这个 Skill。它不执行测试，也不把等待模式当成覆盖或通过证据。

UWR 发现需要写清异步对象、预期条件、超时、轮询或事件来源、失败行为、来源证据、负责人、关闭条件和验证方式。

当 UI 测试使用固定 sleep、超时经常被修改，或者失败时看不出页面是否真的准备好时，使用这个 Skill。

## 它不做什么

UI 测试等待策略评审 Skill 可以组织等待发现的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 等待发现 | 固定 sleep、弱条件、轮询、重试或超时问题 | UWR 编号与来源 |
| 可观察条件 | 真正证明就绪的状态 | DOM、事件或 API 证据 |
| 失败边界 | 条件一直不出现时如何处理 | 超时与诊断 |
| 验证动作 | 最小重放或埋点检查 | 执行前为 NOT_RUN |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“等待发现”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕等待发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 异步行为 | 网络、渲染、动画、轮询、WebSocket 或后台任务状态 | 就绪状态未知时保留未评估 |
| 测试等待代码 | sleep、定位等待、事件、轮询、超时、重试和断言 | 检查完整顺序 |
| 失败证据 | Trace、截图、网络日志、时间和环境 | 不要只从代码推断运行 |
| 边界 | 用户可见预期状态、停止条件和负责人 | 人工时间取舍要可见 |

可以这样调用：

~~~text
请使用 ui-test-wait-strategy-review Skill。

任务：复核一个搜索结果 UI 测试：断言结果列表前固定等待五秒。
输入材料：[测试代码、网络 Trace、DOM 状态、超时配置、失败截图和浏览器环境]
范围：[搜索加载、空结果、错误和结果状态]
限制：[不执行、不修改测试]

输出 UWR-## 发现，包含对象、预期条件、证据、问题、影响、负责人、关闭条件和验证方式。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：用状态检查替换搜索的五秒等待

测试固定等待五秒，但搜索列表可能是空结果、错误或旧数据。这个 Skill 应要求明确从 loading 到结果或错误的稳定条件，保留超时和诊断要求，不要简单把五秒改成另一个数字。

复核可以识别等待质量候选，不能在没有执行证据前证明时序稳定、没有 flaky 或 UI 覆盖。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“等待发现”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和等待发现的具体对象 |
| 发现 | 等待发现的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 等待发现 | 固定 sleep、弱条件、轮询、重试或超时问题 | UWR 编号与来源 |
| 可观察条件 | 真正证明就绪的状态 | DOM、事件或 API 证据 |
| 失败边界 | 条件一直不出现时如何处理 | 超时与诊断 |
| 验证动作 | 最小重放或埋点检查 | 执行前为 NOT_RUN |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供等待代码、组件状态、网络/渲染事件、超时与重试配置、失败 Trace、浏览器范围和用户可见预期。事件证据缺失时保持 pending。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把一个固定 sleep 换成另一个数字。
2. 只等待元素存在，却不确认它没有隐藏、过期或仍在加载。
3. 超时自动重试，却丢掉第一次失败的诊断证据。

## FAQ

### 显式等待一定比 sleep 好吗？

只有条件有意义且可观察时才是。弱条件和 sleep 一样会误导。

### UI 等待应该自动重试吗？

不要默认重试。先判断是否掩盖产品缺陷、选择器问题或真实瞬态状态。
