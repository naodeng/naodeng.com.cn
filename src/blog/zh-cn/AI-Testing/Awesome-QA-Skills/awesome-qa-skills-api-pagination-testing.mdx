分页 Bug 很少在第一页就暴露。它通常发生在两次请求之间插入了一条记录，然后消费者悄悄漏掉一条审计事件。

API 分页测试用于检查消费者遍历变化中的集合时，是否会漏项、重复或产生超出契约的不稳定排序。

当团队需要围绕“页大小、游标或 offset 语义、稳定排序、数据变化、重复、漏项和终止”工作时，使用 API 分页测试 Skill。它把模糊的测试请求变成有来源、有假设、有输出字段和下一步动作的受限分析。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦 API 分页测试。

## API 分页测试 Skill 用来做什么


它适合这些场景：团队需要重复检查页大小、游标或 offset 语义、稳定排序、数据变化、重复、漏项和终止；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

好的结果会把页大小、游标或 offset 语义、稳定排序、数据变化、重复、漏项和终止接回来源和验证动作。设计清单不能直接写成通过结论。

## 用一份项目材料开始

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 集合契约 | 排序键、游标或 offset 规则、页大小限制和快照语义 | 不要假设 offset 自动代表快照 |
| 变化计划 | 分页请求之间的插入、更新、删除、归档和重复键事件 | 记录准确时间 |
| 遍历证据 | 已看到的 ID、返回游标、总数和结束标志 | 与权威 fixture 比较 |

可以这样调用：

```text

请使用 api-pagination-testing Skill。

任务：在新事件持续写入、旧事件不断归档时遍历审计日志 API
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。

```

## API 分页测试 要交付什么

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 遍历结果 | 完整、无重复且有序的记录集合 | 观察到的 ID 与预期 ID |
| 分页发现 | 漏项、重复、游标无效、排序不稳或总数错误 | 页码与变化时点 |
| 消费者动作 | 重试、使用快照、更换游标或澄清契约 | 负责人和证据 |

没有运行记录、查询结果或原始产物时，不要写“已通过”。好的分页测试会在 API 允许数据变化时把集合当成移动目标。它记录 ID 而不是盲信总数，并明确排序键。

## 在项目里跑一轮

先从一个边界清楚的小回合开始：在新事件持续写入、旧事件不断归档时遍历审计日志 API。以每页 50 条读取审计事件，在第一页之后插入两条新事件，再使用返回游标继续读取。把收集到的 ID 与按时间戳和 ID 排序的 fixture 比较。正确的游标可以让新事件不进入本轮遍历，但不能重复或漏掉原集合。

交接产物要同时保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

## 如何把初版做得更好

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从“看起来完整的清单”推进到可用评审。


## 容易踩的坑

1. 只断言每页数量。
2. 把变化中的总数当成完整性证明。
3. 不在分页请求之间改变集合就测试游标。

## 常见问题

### offset 分页一定是错误的吗？

不一定。如果有明确快照或稳定排序，它可以成立；测试要验证真实契约。



### 最后返回空页代表什么？

必须明确是集合结束、游标无效还是临时读取问题，因为客户端动作不同。
