智能体工具调用测试关注 Agent 与工具之间的边界：是否选对工具、参数是否符合契约、调用者是否有权限、失败后能否安全恢复，以及证据能否追溯。最终回答看起来正确，并不能证明工具调用过程安全。

## 把每次调用当作契约检查

先看工具 schema、路由规则、权限模型、沙箱和可用轨迹。每个场景都写明前置条件、刺激动作、预期行为和所需证据。

| 边界 | 检查重点 | 可用证据 |
| --- | --- | --- |
| 工具选择 | 工具是否符合请求；请求有歧义时是否先澄清或安全停止 | 请求、候选工具、路由轨迹 |
| 参数 | 必填字段、类型、范围和对象标识是否符合 schema | 工具 schema、序列化参数、校验结果 |
| 授权 | 当前角色是否能对这个资源或租户执行此动作 | 角色与策略快照、允许或拒绝结果 |
| 重试与恢复 | 超时、部分失败和重试是否会重复写入 | 请求 ID、重试轨迹、前后状态 |
| 结果处理 | 工具错误或部分结果是否被误报为完成 | 响应内容、Agent 轨迹、用户可见回答 |

## 在隔离环境覆盖失败路径

退款流程只是一个说明性场景，不代表某个具体产品。在 mock 或获准的沙箱中，分别验证允许的请求、超出当前角色权限的请求，以及服务端可能已接收首次调用后发生的超时。确认拒绝请求没有写入；重试状态不确定的请求时，不会重复退款或通知。每轮都保存参数、授权上下文、响应和状态变化。

默认使用 mock、dry-run 或隔离环境；未经授权不执行真实写操作。按项目分级标准排列影响和可能性，未确认根因标为假设。缺少 schema、策略或运行记录属于输入缺口，不是调用通过的证据。

## 交付可执行的测试计划

结果应让下一位测试人员无需还原整段对话就能继续。写清工具契约矩阵、正常和失败场景、断言、证据位置、阻塞项与残余风险；未完成事项要有负责人和下一步。这个 Skill 可以整理测试计划，但不能替团队创建授权或运行证据。
