Agent 调用工具时，危险不在于它能否发出请求，而在于它是否选择了正确工具、传递了正确参数，并在失败后安全地停下。

Agent 工具测试 Skill 将工具契约、权限、状态变化和恢复路径视为一次受控交互来验证。

本文围绕订单查询、退款和通知工具，说明如何把权限、参数和副作用接回证据。

## Agent 工具调用测试 Skill 用来做什么

Agent 工具调用测试适合维护 Agent 工具目录、权限策略和写操作的 QA 与平台团队。它把一次调用拆成契约、授权、副作用和恢复四类证据，方便在真正接入生产工具前发现危险路径。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [Agent 工具调用测试 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/agent-tool-testing/prompts/agent-tool-testing.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 默认只使用 mock、dry-run 或隔离环境
- 未经授权不得执行真实写操作
- 重试测试必须验证重复副作用

## 用一份项目材料开始

先把现有材料列出来。缺口可以保留，但状态要说清楚。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 验证 Agent 调用订单查询、退款和通知工具时的参数边界、权限、幂等性与副作用 | 标出不在本轮判断内的链路 |
| 版本与环境 | Agent、工具 schema、模型版本、沙箱账号和数据快照 | 工具权限未隔离时不执行副作用动作 |
| 证据 | 工具调用参数、授权结果、幂等键、写入记录和错误响应 | 没有调用链时只评估设计边界 |
| 决策边界 | 可调用工具、敏感参数、回滚方式和安全 Owner | 每个副作用动作写人工接管条件 |

可以这样调用：

```text
请使用 agent-tool-testing Skill。

任务：验证 Agent 调用订单查询、退款和通知工具时的参数边界、权限、幂等性与副作用
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## Agent 工具调用测试要交付什么

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 工具契约 | 参数、返回值和错误码是否符合约定 | schema、请求样例和版本 |
| 授权判断 | 当前 Agent 是否有权调用这个工具 | 角色、策略和拒绝记录 |
| 副作用记录 | 重试、写入和外部通知发生了什么 | 请求 ID、数据差异和审计日志 |
| 恢复动作 | 失败后如何停止、补偿或人工接管 | dry-run、回滚或人工确认记录 |

没有授权上下文或副作用记录时，只能交付设计检查，不能写成工具调用已通过。

## 在项目里跑一轮

先从一个边界清楚的小回合开始：验证 Agent 调用订单查询、退款和通知工具时的参数边界、权限、幂等性与副作用。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

每次工具调用都应留下参数、授权上下文、响应和副作用记录。这一轮至少要留下可复查的证据索引、仍然成立的假设，以及下一位同事可以直接执行的动作。


## 进阶使用：把一次分析变成持续机制

每次 Agent 工具调用测试都保存工具版本、授权上下文和请求 ID。工具契约或权限策略变化时，只重跑受影响的调用，并标记 `changed`、`unchanged` 或 `needs-review`。

### 三段式 Skill 链

`ai-agent-testing` → `agent-tool-testing` → `production-verification`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 agent-tool-testing | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| agent-tool-testing 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 agent-tool-testing | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时同时传摘要、证据索引和原始材料的位置。这样即使结论出了问题，也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| agent-tool-testing 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| agent-tool-testing 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| agent-tool-testing 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| agent-tool-testing 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只验证参数格式，漏掉授权上下文和资源归属。
2. 用 mock 的成功响应替代真实失败、超时和拒绝路径。
3. 重试写操作却没有检查重复订单、重复通知或重复扣款。
4. 记录了响应，却没有记录工具调用造成的数据变化。

## 相关 Skill

工具调用测试需要和 Agent 行为、安全边界及上线后的验证接起来：

## 交付前复核：把判断落到证据

拿到 Skill 输出后，先核对四件事：输入版本是否明确、范围是否完整、每条结论能否回到证据、下一步由谁执行。缺一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，否则下一次复核时无法解释结论为何变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 Agent 工具调用测试，并把输入、产物、人工修改和验证证据留在同一条工作链上。这样下一次发生变化时，才有东西可以复用。
