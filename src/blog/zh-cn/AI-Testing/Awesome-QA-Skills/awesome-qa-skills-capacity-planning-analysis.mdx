扩容请求若只基于“感觉快不够了”，很容易买错资源或忽略真正的限制。容量规划要把业务增长、系统余量和失效阈值放在同一张图里。

容量规划分析 Skill 将需求预测和已测得的饱和信号转为假设、余量和面向决策的增长计划。

本文通过具体场景说明如何收集、连接和解释证据，让结论能够服务下一步的工程或业务决定。

## 容量规划分析 Skill 用来做什么

容量规划分析适合需要把业务增长、资源成本和扩容时间放到同一个决定里的团队。它交付增长假设、饱和点和扩容条件，帮助负责人回答“什么时候必须扩、扩多少”。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [容量规划分析 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/capacity-planning-analysis/prompts/capacity-planning-analysis.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 没有数据时给区间而非伪精确数字
- 明确平均值与峰值
- 容量结论必须关联 SLO 和验证方式

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 根据业务增长预期、峰值交易和资源曲线，评估下季度订单服务容量与扩容条件 | 标出不在本轮判断内的链路 |
| 版本与环境 | 当前容量、增长预测、峰值活动、区域和预算周期 | 预测没有时间范围时只列假设 |
| 证据 | 历史流量、资源曲线、队列深度、数据库上限和压测结果 | 没有峰值样本时标注外推风险 |
| 决策边界 | 扩容阈值、降级策略、预算 Owner 和复评日期 | 方案要同时写容量余量与成本影响 |

可以这样调用：

```text
请使用 capacity-planning-analysis Skill。

任务：根据业务增长预期、峰值交易和资源曲线，评估下季度订单服务容量与扩容条件
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## 容量规划分析要交付一条可解释的资源曲线

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 增长假设 | 业务量怎样随时间和活动变化 | 订单、用户或请求历史 |
| 资源曲线 | 流量增加时 CPU、连接池和队列如何变化 | 指标时间窗和压测结果 |
| 饱和点 | 哪个资源先接近上限 | 资源阈值、错误率和尾延迟 |
| 扩容决定 | 何时扩容、扩多少、谁批准 | 成本估算、容量余量和截止日 |

没有增长基线或资源时间序列时，只能给出容量假设，不能把估算写成系统承载上限。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——根据业务增长预期、峰值交易和资源曲线，评估下季度订单服务容量与扩容条件。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

容量结论要说明负载假设、瓶颈资源、余量和触发扩容的条件。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

容量结论要说明负载假设、瓶颈资源、余量和触发扩容的条件。

每次容量规划分析都保存业务基线、资源规格、负载模型和时间窗口。业务增长或部署规格变化时，重算受影响的曲线，并保留旧结论用于对比。

### 三段式 Skill 链

`performance-workload-modeling` → `capacity-planning-analysis` → `production-verification`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 capacity-planning-analysis | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| capacity-planning-analysis 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 capacity-planning-analysis | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| capacity-planning-analysis 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| capacity-planning-analysis 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| capacity-planning-analysis 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| capacity-planning-analysis 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只按平均流量估算，漏掉峰值、突发和业务比例。
2. 看到 CPU 余量就宣布容量充足，忽略数据库、连接池或队列先到上限。
3. 用一次压测曲线外推全年增长，没有说明假设和置信度。
4. 给出扩容数字，却没有成本、交付周期和回滚条件。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 容量规划分析，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
