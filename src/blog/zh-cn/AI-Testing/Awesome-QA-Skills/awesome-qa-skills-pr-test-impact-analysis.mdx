PR 改了哪些文件，并不能直接回答哪些行为会受影响。一个共享函数的变更可能触及多个业务入口；按目录选测试容易漏掉调用链上的消费者。

pr-test-impact-analysis 根据实际差异梳理受影响行为、依赖和测试范围。每项判断都要有证据，不能只凭文件名推测；风险较高但映射证据不足时，应扩大检查范围或保留不确定性。

## 从 Diff 建立可追踪的影响链

提供明确的 base/head、完整 Diff、需求或接口契约、相关消费者和已有测试映射。分析时按下面的链条记录：

**变更符号 → 消费者 → 行为义务 → 测试 ID、级别与版本**

例如，订单校验规则发生变化时，要找到调用该规则的 API、后台任务或 UI 流程，确认每条业务路径的预期行为，再对应到单元、接口、端到端或回归测试。不能因为某个文件名含有“订单”就断言所有相关测试都已覆盖。

若仓库缺少调用图或测试映射，可以先给候选影响路径，同时标出未知项和最小验证动作。高风险、共享接口、历史缺陷或证据薄弱的区域应扩大检查范围，并说明测试选集和排除项的理由。

## 预测状态不等于运行结果

分析输出中的预测用于表达测试与预期行为的关系；实际运行状态则描述是否执行以及执行结果，两者不能混为一组状态。

| 预测状态 | 含义 | 运行状态示例 |
| --- | --- | --- |
| PREDICTED_PASS | 依据当前分析，预期测试通过 | RUN_PASS：有对应运行记录且通过 |
| PREDICTED_FAIL | 依据当前分析，预期测试失败或暴露问题 | RUN_FAIL：实际运行记录显示失败 |
| UNCERTAIN | 现有证据不足以预测结果 | NOT_RUN 或 UNKNOWN：尚未执行或执行状态未知 |

预测不是测试结果。只有命令或 CI 记录、对应版本和真实退出结果才能支持运行状态；旧版本的绿灯也不是新 Diff 的证据。

## 让 AI 追踪影响，但保留证据链

AI 可以帮助读 Diff、搜索调用关系和整理测试候选。复核者需要确认每条路径能回到具体符号、依赖或契约，并检查测试 ID、级别和版本是否匹配。

~~~text
请使用 pr-test-impact-analysis 分析这个 PR 的测试影响。

版本和范围：[base/head、文件范围、包含与排除路径]
代码证据：[完整 Diff 与相关符号]
项目依据：[需求、契约、消费者、测试映射和历史缺陷]
限制：[环境、时间和权限]

按“变更符号 → 消费者 → 行为义务 → 测试 ID/级别/版本”追踪。
每项结论引用来源，不要只按文件名推断。
分别给出 PREDICTED_PASS、PREDICTED_FAIL 或 UNCERTAIN，
并将预测与实际运行状态分开记录。
~~~

PR 更新后，应基于新 Diff 重算相关路径，保留变化过的测试、未变的判断和需要复核的内容。旧结论不能自动成为新证据。

### 没有测试映射时还能给范围吗？

可以提供候选路径，但要说明依据缺口和验证方法。高风险且证据不足时，应扩大检查范围。

### PREDICTED_PASS 能当作测试通过吗？

不能。它只是对预期结果的分析。RUN_PASS 需要对应版本的实际运行记录。

### 哪些风险应由人确认？

测试取舍、排除范围、剩余风险和发布决策应由有责任的负责人确认。Skill 提供可追溯的证据与选项，不替团队批准风险。
