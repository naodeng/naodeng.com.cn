负向测试不是往接口里随便塞一串乱码。它应该明确说明 API 必须拒绝、保持不变或解释什么。

## 为什么需要这个 Skill

API 负向测试根据契约规则、边界、授权、状态转移和依赖行为设计失败场景。

## Skill 用来做什么

当团队需要围绕“无效结构、边界值、禁止状态、授权、依赖失败和安全响应”工作时，使用 API 负向测试 Skill。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦 API 负向测试。

它适合这些场景：团队需要重复检查无效结构、边界值、禁止状态、授权、依赖失败和安全响应；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

结果至少要把无效结构、边界值、禁止状态、授权、依赖失败和安全响应接回来源和验证动作。设计清单不能直接写成通过结论。

## 它不做什么

API 负向测试 Skill 可以组织负向用例的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 负向用例 | 无效条件和预期拒绝 | 对应规则来源 |
| 响应判断 | 状态码、错误码、安全消息和可重试性 | 客户端动作 |
| 变更检查 | 不应变化的记录或事件 | 状态证据 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“负向用例”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕负向用例，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 契约规则 | 必填字段、格式、限制、枚举值和状态转移 | 生成用例前先列规则 |
| 无效分区 | 单个无效因素、组合无效因素和格式错误载荷 | 保留拒绝原因 |
| 安全证据 | 状态码、错误体、持久化记录和下游事件 | 必须证明拒绝没有产生错误写入 |

可以这样调用：

```text

请使用 api-negative-testing Skill。

任务：用格式错误行、超大批次、重复记录和非法状态转移挑战批量导入 API
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。

```

### 分析（Analysis）

先从一个边界清楚的小回合开始：用格式错误行、超大批次、重复记录和非法状态转移挑战批量导入 API。对导入行分别测试未知币种、负金额、重复外部 ID，以及更新已关闭账户的请求。除了断言错误契约，还要确认除非 API 明确承诺部分成功，否则有效行不会被部分提交。

交接产物要同时保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

### Finding

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“负向用例”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和负向用例的具体对象 |
| 发现 | 负向用例的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 负向用例 | 无效条件和预期拒绝 | 对应规则来源 |
| 响应判断 | 状态码、错误码、安全消息和可重试性 | 客户端动作 |
| 变更检查 | 不应变化的记录或事件 | 状态证据 |

没有运行记录、查询结果或原始产物时，不要写“已通过”。好的负向套件是分区设计的，不是表演式的。先找出违反一条规则的最小输入，再只在交互本身有风险时增加组合。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从“看起来完整的清单”推进到可用评审。

## 容易踩的坑

1. 生成无效数据，却没有对应规则。
2. 断言被拒绝，却忽略部分写入。
3. 所有失败类别都使用同一个格式错误载荷。

## FAQ

### 负向测试应该直接打生产吗？

应使用隔离环境或获批准的安全数据；设计用例不等于授权破坏性请求。



### 无效组合要测多少？

覆盖独立规则和高风险交互即可，按影响排序，不按组合数量堆积。
