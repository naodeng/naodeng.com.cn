Skill 文案本身就是行为契约的一部分。触发条件、指令优先级、输入假设或拒绝边界写得含糊，不同智能体就可能对同一个请求采取不同动作。Skill 文案契约审查会检查这份契约并报告可处理的问题；它不会代替 Skill 去执行其中的业务任务。

## 从请求到证据梳理契约

先确认审查范围和文件职责，再判断具体句子。沿着下面的链路逐项核对：

| 契约部分 | 要检查的问题 | 缺口可能造成的影响 |
| --- | --- | --- |
| 触发条件 | 描述能否区分目标任务与相邻任务？ | 相关请求可能漏选 Skill，无关请求也可能误触发 |
| 输入与假设 | 必需材料、版本、权限和未知项是否说清楚？ | 智能体可能用猜测补齐缺失事实 |
| 指令 | 另一个智能体能否独立照步骤执行？规则冲突时优先级是否明确？ | 不同读者可能选择不同动作 |
| 输出与边界 | 必需字段、拒绝条件和人工决策是否可观察？ | 消费方可能无法解析结果，或把建议误当成批准 |
| 验证 | 是否说明要检查什么，以及检查不能证明什么？ | 静态阅读可能被误报成运行时结果 |

除非有执行证据，否则应把这些描述为“可能影响”。包策略没有定义别名或查找规则时，不要假定所有宿主的行为相同；应把它记录为信息缺口。

## 把宽泛意见写成可执行发现

看这条示例指令：“检查输出质量，确保结果准确完整。”它没有说明事实来源、字段级标准，也没有定义材料缺失时怎么办。可处理的发现应写清位置、对使用者的可能影响和依据：

| 位置 | 发现 | 影响 | 证据 |
| --- | --- | --- | --- |
| `SKILL.md` 输出规则 | “准确完整”没有评判标准或来源优先级 | 智能体可能把缺少依据的字段写成已验证事实 | 指令未规定所需证据和缺材料状态 |

审查者可以建议补上判断标准或 `pending` 状态，但不能悄悄改写文件，也不能声称修改已经过测试。

严重度要跟行为影响对应。若仓库已有分级规则，沿用项目定义；没有时，可用下面的判断问题校准结论：

| 级别 | 判断依据 | 例子 |
| --- | --- | --- |
| 阻塞 | 当前指令可能让智能体越过权限、误报完成，或丢失关键拒绝条件 | 对冲突规则没有优先级，且可能触发未授权动作 |
| 重要建议 | 缺少的条件会让常见任务结果不稳定，但不会直接越权 | 没说明缺少输入时应暂停还是请求补充 |
| 信息缺口 | 现有材料不足以判断实际行为，需指定补充来源 | 没有目标宿主的选择记录，无法验证触发是否准确 |
| 风格建议 | 文案不够清楚，但没有证据显示会改变执行或消费结果 | 可精简重复说明或改进术语一致性 |

给出级别时同时写出受影响的请求、输出字段或权限边界。单纯“不喜欢这种写法”不足以构成阻塞问题。

## 把审查和执行分开

源 Skill 要求限定审查范围，并按结论、阻塞问题、重要建议、信息缺口和证据边界报告。它明确不执行 Skill 描述的业务任务；除非用户授权，也不直接编辑文件。静态阅读可以说明给定文本写了什么，却不能证明目标宿主如何选择或运行这个 Skill。

仓库还有 `evals/cases/` 评测输入。这些文件可以帮助选择值得关注的案例，但文件存在不代表已经运行评测。若需要运行时行为证据，就应指出缺少的宿主、源码或授权，不要自行猜测。

## 按源格式交付审查结论

```markdown
# 审查结论
结论：通过 / 有条件通过 / 不通过

## 阻塞问题
| 位置 | 问题 | 影响 | 证据 |

## 重要建议
| 位置 | 建议 | 原因 |

## 信息缺口
- …

## 证据边界
- 已验证：…
- 未验证：…
```

纯风格偏好最多作为改善清晰度的建议；只有当契约或使用者可能受到影响时，才有理由升为阻塞问题。严重度要对应明确后果和证据。

## 只在授权范围内继续处理

如果审查发现过程性残留，在获准的范围内可交给[过程性文案清理](/zh-cn/qaskills/skill-prose-trim/)；编辑完成后，[Skill 变更验证](/zh-cn/qaskills/skill-change-verification/)会根据实际 diff 选择检查，确认改动后的契约是否仍然成立。

安装命令：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/skill-engineering/skill-prose-review -g
```
