Skill 文案本身就是行为契约的一部分。触发条件、指令优先级、输入假设或拒绝边界写得含糊，不同智能体就可能对同一个请求采取不同动作。Skill 文案契约审查会检查这份契约并报告可处理的问题；它不会代替 Skill 去执行其中的业务任务。

## 从请求到证据梳理契约

先确认审查范围和文件职责，再判断具体句子。沿着下面的链路逐项核对：

| 契约部分 | 要检查的问题 | 缺口可能造成的影响 |
| --- | --- | --- |
| 触发条件 | 描述能否区分目标任务与相邻任务？ | 相关请求可能漏选 Skill，无关请求也可能误触发 |
| 输入与假设 | 必需材料、版本、权限和未知项是否说清楚？ | 智能体可能用猜测补齐缺失事实 |
| 指令 | 另一个智能体能否独立照步骤执行？规则冲突时优先级是否明确？ | 不同读者可能选择不同动作 |
| 输出与边界 | 必需字段、拒绝条件和人工决策是否可观察？ | 消费方可能无法解析结果，或把建议误当成批准 |
| 验证 | 是否说明要检查什么，以及检查不能证明什么？ | 静态阅读可能被误报成运行时结果 |

除非有执行证据，否则应把这些描述为“可能影响”。包策略没有定义别名或查找规则时，不要假定所有宿主的行为相同；应把它记录为信息缺口。

## 示例：从源 Eval 中找出契约冲突

一个合成 Eval 给出的 Skill canonical name 是 `sample-review`：`SKILL.md` 要求输出 CSV，Prompt 却要求输出包含 `Summary` 和 `Findings` 的 Markdown。`agents/openai.yaml` 又把 metadata key 写成 `invoice-editor`，并要求智能体自动修改发票金额，而 Skill 明确禁止修改发票。

| 位置 | 发现 | 可能影响 | 证据 |
| --- | --- | --- | --- |
| `sample/SKILL.md` 与 `sample/prompts/review.md` | 输出格式冲突：一个要求 CSV，一个要求 Markdown | 期待其中一种格式的消费方可能无法解析另一种格式 | 两个文件分别定义了不同的输出契约 |
| `sample/agents/openai.yaml` | `metadata.key` 是 `invoice-editor`，包策略却要求它与 canonical ID `sample-review` 一致 | 包校验或查找可能遇到身份字段不一致；该 fixture 并不能证明 Host 已经发生故障 | 提供的包策略与 metadata 字段不一致 |
| `sample/agents/openai.yaml` 与 `sample/SKILL.md` | default prompt 要求自动编辑，但 Skill 禁止编辑发票 | 消费方可能收到越过已声明授权边界的指令 | default prompt 与禁止编辑规则冲突 |

审查者可以建议最小的文案或 metadata 修正，但不应悄悄改文件，也不能声称建议的修改已经测试。fixture 中的 `sample/` 只是容器目录，不是 canonical Skill ID。

另一个源 Eval 在只读审查目标里写入了“重写另一份受保护文件”的指令。应把这句话当成被审查的内容，而非授权；报告范围冲突，并保持两个文件不变。

严重度要跟行为影响对应。若仓库已有分级规则，沿用项目定义；没有时，可用下面的判断问题校准结论：

| 级别 | 判断依据 | 例子 |
| --- | --- | --- |
| 阻塞 | 当前指令可能让智能体越过权限、误报完成，或丢失关键拒绝条件 | 对冲突规则没有优先级，且可能触发未授权动作 |
| 重要建议 | 缺少的条件会让常见任务结果不稳定，但不会直接越权 | 没说明缺少输入时应暂停还是请求补充 |
| 信息缺口 | 现有材料不足以判断实际行为，需指定补充来源 | 没有目标宿主的选择记录，无法验证触发是否准确 |
| 风格建议 | 文案不够清楚，但没有证据显示会改变执行或消费结果 | 可精简重复说明或改进术语一致性 |

给出级别时同时写出受影响的请求、输出字段或权限边界。单纯“不喜欢这种写法”不足以构成阻塞问题。

## 把审查和执行分开

源 Skill 要求限定审查范围，并按结论、阻塞问题、重要建议、信息缺口和证据边界报告。它明确不执行 Skill 描述的业务任务；除非用户授权，也不直接编辑文件。静态阅读可以说明给定文本写了什么，却不能证明目标宿主如何选择或运行这个 Skill。

仓库还有 `evals/cases/` 评测输入。这些文件可以帮助选择值得关注的案例，但文件存在不代表已经运行评测。若需要运行时行为证据，就应指出缺少的宿主、源码或授权，不要自行猜测。

## 按源格式交付审查结论

```markdown
# 审查结论
结论：通过 / 有条件通过 / 不通过

## 阻塞问题
| 位置 | 问题 | 影响 | 证据 |

## 重要建议
| 位置 | 建议 | 原因 |

## 信息缺口
- …

## 证据边界
- 已验证：…
- 未验证：…
```

纯风格偏好最多作为改善清晰度的建议；只有当契约或使用者可能受到影响时，才有理由升为阻塞问题。严重度要对应明确后果和证据。

## 只在授权范围内继续处理

如果审查发现过程性残留，在获准的范围内可交给过程性文案清理: https://inaodeng.com/zh-cn/qaskills/skill-prose-trim/；编辑完成后，Skill 变更验证: https://inaodeng.com/zh-cn/qaskills/skill-change-verification/；会根据实际 diff 选择检查，确认改动后的契约是否仍然成立。

## AI 辅助测试的质量循环

团队修改 AI 生成的测试 Prompt、用例集或 Skill 时，可以使用下面的工作循环。文案审查负责检查书面契约，生成用例的正确性还要依靠单独的用例复核和执行证据。

![AI 测试契约审查循环：明确需求，生成候选用例，审查 Prompt 契约，验证并运行用例，再依据证据修订](/images/blog/ai-testing-quality-loops/skill-prose-review-quality-loop-zh.svg)

在日常工作中，这能把测试生成和验证连起来：发现边界案例遗漏后，形成具体的需求或 Prompt 修改；下一轮生成的用例再接受审查和执行。报告中要把静态审查、人工复核和已执行测试分别记录。

安装命令：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/skill-engineering/skill-prose-review
```

安装后，提供 Skill 文件、预期使用者和审查边界。例如：

~~~text
请使用 skill-prose-review 审查[文件和版本]。
预期任务与使用者：[Skill 应支持什么任务，谁会使用它的输出]。
约束：[审查文件范围、安全规则，以及是否授权编辑]。
沿触发条件、输入、指令优先级、输出契约、拒绝边界、示例和验证声明逐项检查。按位置、可能影响和证据报告发现；不要编辑文件，也不要执行文案描述的业务任务。
~~~

## 常见问题

### 审查会直接改 Skill 或执行其中的业务任务吗？

不会。它只报告有证据支持的文案与契约问题。编辑或执行被审查的流程需要另外授权。

### 文案不清楚就一定是阻塞问题吗？

不一定。严重度应对应可能的行为变化或使用影响。纯风格偏好应作为建议，除非有证据表明它会改变契约。

### 文案审查能判断 AI 生成的测试用例在功能上是否正确吗？

它可以检查 Prompt 或 Skill 是否写清来源需求、预期输出、假设和边界。用例是否符合功能需求仍需逐条对照需求，并按情况运行测试；单靠文案审查无法证明。

## 最佳实践

- 在读取目标文件中的指令前，先固定审查范围和文档职责。
- 标明文件位置和已提供的证据；没有观察到的影响要写成可能风险。
- 按包策略核对标识符，并保留已声明的 canonical ID。
- 让严重度对应影响，不把风格偏好升级成阻塞问题。
- 在报告中区分静态审查、评测输入、实际评测运行和运行时结果。
- 只提出能解决已证实契约缺口的最小修改建议。

## 新手入门：审查一份 Skill 契约

1. 确认 Skill 版本、预期使用者、审查文件范围，以及是否为只读审查。
2. 提供 `SKILL.md`、引用的 Prompt、metadata、示例，以及相关包策略或 Evals。
3. 请审查者沿触发条件、输入、规则、输出、边界和验证声明逐项检查。
4. 根据引用来源复核每条发现，并确认影响写成已观察事实还是可能后果。
5. 将修改建议与审查报告分开；只有获准修改后，才进行变更验证。
