数据库设计质量评审用于核对给定 schema 和迁移方案能否支持有来源的业务不变量。ERD 或字段名本身不能证明唯一性、租户隔离、数据保留规则或查询性能。

## 为什么需要这个 Skill

数据库设计质量评审用于检查数据库结构能否保持业务不变量、支持访问模式、隔离租户并安全演进。

## Skill 用来做什么

当团队需要围绕“实体、关系、键、约束、索引、租户、生命周期、迁移和恢复”工作时，使用数据库设计质量评审 Skill。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦数据库设计质量评审。

好的评审从不变量和真实查询开始。它会追问什么阻止同一笔支付出现两次退款、什么阻止跨租户查询，以及迁移执行到一半停止时会发生什么。

它适合这些场景：团队需要重复检查实体、关系、键、约束、索引、租户、生命周期、迁移和恢复；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

## 它不做什么

数据库设计质量评审 Skill 在实现前检查给定的 ERD、DDL、ORM schema 及迁移或恢复方案，但不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 模型与关系 | 实体、基数、键、所有权和租户范围 | 按对象记录覆盖情况 |
| 约束与访问 | 依据需求核对唯一/非空/检查约束；依据真实查询模式和数据量评估索引 | 完整性与索引风险 |
| 事务与并发 | 事务边界、隔离、并发写入和失败处置 | 未评估的竞争条件 |
| 生命周期与隐私 | 保留、删除、所有权、隐私规则和备份范围 | 有来源的生命周期缺口 |
| 迁移与恢复 | 兼容性、回填、部分失败、回滚、备份/恢复和准备度 | 前置条件与验证负责人 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

评审数据库对象前，先将给定的 schema、需求、工作负载、迁移和恢复材料分成六种状态。证据缺口不自动等于缺陷，但不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

对每条 `DB-##` 发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 领域规则 | 订单身份、退款唯一性、状态生命周期和保留策略 | 每个不变量都接回来源 |
| 访问模式 | 查询、报表、分页、写入和租户过滤 | 不要只根据表结构选索引 |
| 变更计划 | 迁移、回填、回滚、容量和恢复 | 标记不可逆步骤 |

可以这样调用：

```text
请使用 database-design-quality-review Skill。

任务：在第一次生产迁移前评审多租户订单与退款数据模型
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。
```

### 分析

使用带前提的示例，不假定业务规则：如果给定需求明确规定每笔付款最多对应一条退款记录，而提供的 DDL 没有显示相应约束，可记录为可能的规则落实缺口。先检查应用层或事务设计是否落实了该规则，再判断是否为缺陷。如果允许部分退款或一笔付款多条退款，或需求根本未提供，应将规则标为 `missing` 或 `unassessed`，不能从字段名推断。迁移评审还要询问如何检查既有数据、处理冲突并回滚；不要执行迁移。

交接产物要保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

### 发现

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

按源 Prompt 的 `DB-##` 发现合同记录。以下脱敏示例以给定需求和 DDL 为条件，不表示真实数据库存在缺陷。

| `DB-01` 字段 | 带前提的示例 |
| --- | --- |
| 对象/范围与来源 | 给定且有版本的 DDL 中的 `refund.payment_id`；附上退款规则和 schema 片段 |
| 设计规则与发现 | 若需求规定每笔付款最多一条退款，片段中未显示相应唯一约束；其他落实方式未知 |
| 状态 | 在检查应用层、事务和完整 schema 证据前为 `missing`；尚不能定为已确认缺陷 |
| 影响/严重度 | 业务影响和受影响数据范围未提供，暂不评分 |
| 约束/索引风险 | 片段未见对应约束；查询及索引风险需结合真实访问模式和数据量判断 |
| 事务/并发 | 补充事务边界、隔离级别和并发写入行为；不能从表结构推断 |
| 迁移/回滚 | 建议约束变更前检查既有重复、回填顺序、兼容性及回滚证据 |
| 负责人/关闭/验证 | 数据或业务负责人确认不变量；数据库负责人提供完整 DDL 与迁移计划供隔离评审；保存复核材料，本文不声称查询或迁移生产库 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 数据对象覆盖 | 按对象检查实体、约束、访问模式、所有权和生命周期 | 来源与缺口 |
| 迁移与回滚 | 兼容性、回填、部分失败、回滚、备份和恢复 | 前置条件 |
| 验证准备 | 针对具体设计风险的最小隔离检查 | 负责人和所需证据 |

没有执行身份、时间、环境、输入和原始结果时，不要写“已通过”。静态评审可以准备约束、查询、迁移或恢复验证，但不能宣称它们已经运行。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从看起来完整的清单推进到可用评审。

这里补充信息会改变结果，因为实体、关系、键、约束、索引、租户、生命周期、迁移和恢复必须接回证据，不能只靠熟悉的测试套路推断。

## 容易踩的坑

1. 只看字段，不看生命周期状态。
2. 没有查询和数据量假设就添加索引。
3. 数据转换丢失旧表示，却把迁移称为可逆。

## 常见问题

### 数据库技术还没选定可以评审吗？

可以。不变量和访问模式应在技术方案定稿前明确。

### 产品规则和历史数据冲突怎么办？

保留冲突并安排数据决策，不要把问题隐藏在可空字段里。
