代码还没写，产品就可能已经失败：一份文档把状态叫“已支付”，另一份叫“已授权”，第三份却把两者都当作终态。

## 为什么需要这个 Skill

Requirement Consistency Analysis Skill 使用稳定比较键对多个材料进行对照，同时保留来源和版本边界。它区分 aligned、inconsistent、conflict 三种关系，也区分 assessed、missing、stale 和未评估四种证据状态。

## Skill 用来做什么

本文提醒：相似词不自动等义；比较前必须确认材料指的是同一对象和范围。

当 PRD、故事、API 契约、原型、技术说明或验收条件对同一个流程使用不同术语、标识符、格式、状态、规则或行为时，使用这个 Skill。

结果需要为每条 RC 发现写清来源对、比较键、关系、证据状态、范围或版本、影响、负责人、动作和验证方式。

如果多个材料应该描述同一个角色、字段、状态流转或结果，却看起来不一致，应在实现或集成测试前使用这个 Skill。

## 它不做什么

需求一致性分析 Skill 可以组织比较键的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 比较键 | 正在比较的字段、状态、规则或行为 | 稳定标识 |
| 关系 | aligned、inconsistent 或 conflict | 与证据状态分开 |
| 证据状态 | assessed、missing、stale 或未评估 | 来源与版本 |
| 动作 | 负责人问题、关闭条件和验证方式 | 不要静默合并 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“比较键”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕比较键，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 材料集合 | PRD、API 契约、原型、验收条件和技术说明 | 明确指出缺失材料 |
| 比较范围 | 流程、角色、字段、状态、平台、租户、版本和生效时间 | 边界不清时不要直接比较 |
| 稳定键 | 字段名、流转、业务规则、标识符或可观察结果 | 先定义比较键 |
| 证据 | 来源位置、历史决策、实现说明和样例 | 证据缺失与不一致分开 |

可以这样调用：

~~~text
请使用 requirement-consistency-analysis Skill。

任务：比较结账 PRD、支付 API 契约和验收条件中关于地址字段、支付状态和退款行为的描述。
输入材料：[材料版本、来源位置、平台范围、样例和实现说明]
范围：[Web 结账、银行卡支付、R25.1 发布]
限制：[不要自行发明状态含义或合并冲突]

输出 RC-## 发现，包含来源对、稳定键、关系、证据状态、影响、负责人、待决问题、关闭条件和验证方法。明确互斥规则只按 Skill 名称路由到冲突检测。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：比较支付状态，不要把名称相似当成同义

PRD 说授权后订单就是 paid，API 契约返回 authorized，验收条件却要求确认前必须 captured。这个 Skill 应保留三个来源，比较状态流转和时间点，确认范围及实现含义后再判断关系。不能因为 paid 更常见，就直接选它做标准术语。

结果可以说明给定材料之间的关系，不能证明运行时状态行为；静态一致也不能替代 API 或集成测试。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“比较键”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和比较键的具体对象 |
| 发现 | 比较键的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 比较键 | 正在比较的字段、状态、规则或行为 | 稳定标识 |
| 关系 | aligned、inconsistent 或 conflict | 与证据状态分开 |
| 证据状态 | assessed、missing、stale 或未评估 | 来源与版本 |
| 动作 | 负责人问题、关闭条件和验证方式 | 不要静默合并 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供所有材料的版本和位置、比较范围、稳定键、样例和已知决策。只有一份来源时，标记缺少比较证据，不要因为没发现差异就叫一致。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 没有检查状态、时间和角色，就把相似标签当成同一个对象。
2. 缺少第二份材料时，因为没看到差异就称为一致。
3. 为了让报告整洁，把真实冲突降级为普通不一致。

## FAQ

### 关系和证据状态有什么区别？

关系说明两份陈述之间是什么关系，证据状态说明这次比较是否有足够、最新或完整的依据。

### 这个 Skill 应该创建统一术语表吗？

它可以提出问题或候选映射，但最终术语和状态含义仍然属于人工或产品决策。
