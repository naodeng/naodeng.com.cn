生产事故最危险的时刻，是团队急于给出原因而证据还不足。先稳定影响、建立时间线，再验证假设，才能避免把猜测写进复盘。

生产事故分析 Skill 将即时止损与因果调查分开，在系统承压时仍保留决策和证据。

本文用贴近协作现场的案例拆解判断过程，帮助你把不同信号转化为可沟通、可追踪的行动。

## 生产事故分析 Skill 用来做什么

生产事故分析适合需要把止损、根因和复盘行动连成一条时间线的事故响应团队。它保留不确定性和被推翻的假设，让复盘能产生后续验证，而不是只留下归责结论。

## 先回到源 Skill

这个 Skill 的完整执行规则在 [生产事故分析 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/production-incident-analysis/prompts/production-incident-analysis.md)。源目录还包含 3 个评测用例，用于验证输出是否遵守契约。

它要求特别注意：

- 恢复优先于完整根因
- 不要在证据不足时归责
- 每个高风险操作写明回滚与验证

## 用一份项目材料开始

先把当前拿得到的材料摆上来。缺口可以保留，状态必须说实话。

| 材料 | 这次填什么 | 缺失时的处理 |
| --- | --- | --- |
| 目标与范围 | 处理订单支付失败事故，建立时间线、控制影响、验证缓解措施并形成复盘行动 | 标出不在本轮判断内的链路 |
| 版本与环境 | 事故发生时间、发布批次、受影响环境和时区 | 先固定时间线，根因结论标为待确认 |
| 证据 | 告警、日志、指标、变更记录和用户报障 | 影响窗口不完整时暂停根因判断 |
| 决策边界 | 止损、回滚、外部沟通和复盘行动的负责人 | 标出授权人、截止时间和验证信号 |

可以这样调用：

```text
请使用 production-incident-analysis Skill。

任务：处理订单支付失败事故，建立时间线、控制影响、验证缓解措施并形成复盘行动
输入材料：[版本、链接、日志或报告路径]
范围：[本次包含和排除的对象]
限制：[时间、数据、权限、合规要求]

先审计输入，再按风险和证据强度排序。材料没有证明的内容标为假设，并列出验证方法。
```

## 生产事故分析要让时间线推动行动

| 产物 | 要回答的问题 | 最低证据 |
| --- | --- | --- |
| 事件时间线 | 什么时候发生、发现和扩大 | 日志、告警、发布记录和时区 |
| 检测与止损 | 哪个信号触发了什么动作 | 告警、变更和影响曲线 |
| 根因假设 | 哪些事实支持或反驳假设 | 实验、配置、Trace 和样本 |
| 复盘行动 | 如何防止相同影响再次出现 | Owner、截止时间和验证信号 |

没有统一时间线和原始证据时，只能记录事件叙述，不能提前写根因或责任结论。

## 在项目里跑一轮

先用一个边界清楚的小回合启动——处理订单支付失败事故，建立时间线、控制影响、验证缓解措施并形成复盘行动。别急着把结果写成报告。先把输入版本、时间窗口和负责人贴到同一处；然后把每个判断连回具体材料；最后只安排一项能改变结论的验证动作。

恢复优先于完整根因，任何高风险操作都要写回滚与验证方式。这一轮交付应当包含：可复查的证据索引、仍然成立的假设、以及下一位同事可以直接执行的动作。这样做很朴素，也很有效。


## 进阶使用：把一次分析变成持续机制

恢复优先于完整根因，任何高风险操作都要写回滚与验证方式。

每次生产事故分析都保存事件 ID、时间线版本、影响窗口和证据链接。新增日志或实验后更新假设状态，不删除先前被推翻的判断。

### 三段式 Skill 链

`production-incident-analysis` → `root-cause-analysis` → `production-verification`

| 交接 | 传递内容 | 接收方要检查什么 |
| --- | --- | --- |
| 上游到 production-incident-analysis | 来源版本、范围、风险、未决项 | 输入是否过期，冲突是否标记 |
| production-incident-analysis 到下游 | 判断、证据索引、残余风险、待办 | 产物是否可执行，Owner 是否明确 |
| 下游回写 production-incident-analysis | 执行结果、缺陷、事实变化 | 是否更新基线与回归范围 |

交接时传摘要、证据索引和原始材料的位置。信息量足够，结论出了问题也能回到来源。

### 团队门禁

| 门禁 | 检查内容 | 未满足时 |
| --- | --- | --- |
| production-incident-analysis 输入门禁 | 版本、环境、证据来源和 Owner | 停止生成，列出缺口 |
| production-incident-analysis 产物门禁 | 关键结论带依据、状态和影响 | 退回补证据 |
| production-incident-analysis 执行门禁 | 命令、查询或验证路径可复现 | 标记基础设施或测试问题 |
| production-incident-analysis 决策门禁 | 残余风险有接受人与日期 | 不进入下一阶段 |

## 容易踩的坑

1. 只写“恢复了”，没有说明影响窗口和用户范围。
2. 把时间线上的相关事件直接当成根因。
3. 复盘行动没有 Owner、截止时间或验证信号。
4. 为了追责删掉不确定性，导致后续假设无法复核。

## 相关 Skill

生产事故分析要把时间线、链路证据和修复后的验证接起来：

- [根因分析](https://inaodeng.com/zh-cn/qaskills/root-cause-analysis/)：区分触发因素、放大因素和真正根因。
- [分布式链路分析](https://inaodeng.com/zh-cn/qaskills/distributed-trace-analysis/)：还原跨服务的错误传播。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 输入还不完整，能开始吗？

能。先交付受限初版：列出已知事实、假设、缺口和最小验证动作。环境、数据或权限缺失时，不写执行结论。

### 什么时候需要人工确认？

范围取舍、风险接受、生产操作、数据权限和发布决定必须由对应负责人确认。Skill 负责整理证据与选项，不替团队做授权决定。

先用一份真实材料跑通 生产事故分析，把输入、产物、人工修改和验证证据留在同一个工作链里。下一次变化发生时，才有东西可以复用。
