很多测试任务卡住，并不是因为团队不知道某个测试术语，而是输入太散、范围不清，最后也没人能判断输出是否足够可信。Pytest 接口自动化 Skill 解决的是这类具体问题。

本文不把 Skill 当成一段“万能提示词”。我会拆开它的输入、执行过程、输出边界和验证方式——这些细节决定它能不能进入真实项目。

## 先认识 Awesome QA Skills

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 是一个中英文分区的 AI 测试辅助技能库。每个 Skill 都是可以独立安装的目录，至少包含带 YAML frontmatter 的 `SKILL.md`，并可按需携带 Prompt、参考资料、示例、脚本和评测用例。这个结构遵循 Agent Skills 的渐进加载思路：入口保持短而可执行，深资料在真正需要时再读。

项目覆盖三层能力：测试类型负责完成具体分析与设计，测试工作流负责编排阶段活动，Skill Engineering 负责检查 Skill 自身的契约和证据。Pytest 接口自动化 位于 `testing-types/api-test-pytest`，处理的是其中一个明确环节。

Agent Skills 规范要求目录至少包含 `SKILL.md`，并用 `name` 与 `description` 描述发现和触发条件。参考：[Agent Skills Specification](https://agentskills.io/specification)。

## Pytest 接口自动化 是做什么的

一个典型任务是：根据 OpenAPI 或接口说明生成可维护的 Pytest 集合或自动化代码，并接入本地与 CI 回归。

这个 Skill 的执行说明重点覆盖 “角色定位”、“输入解析顺序”、“默认约定（无用户指定时直接采用）”、“Gotchas”、“最低覆盖清单”、“输出”。目录中还提供 `examples`、`references`、`scripts`、`evals`——需要更深资料或输出格式时再按需读取。

它应该产出一份可以继续执行或审查的结果，而不是看起来正确的一段泛泛建议。输入不完整时，Skill 应明确缺少什么、采用了哪些假设，以及这些假设会影响哪一部分结论。

## 适用场景

- 你已经有真实需求、代码、接口、测试材料或阶段产物，希望把它们整理成结构化结果。
- 团队需要统一分析步骤和输出格式，减少每个人各写一套 Prompt 的漂移。
- 输出需要交给开发、产品、QA 或发布负责人继续执行，而不是停留在聊天窗口。
- 你需要让 AI 暴露未知项、证据缺口和风险边界。

不适合的情况也很明确：没有提供任何项目上下文，却要求直接给出“完整测试结论”；需要真实运行环境或生产数据验证，却只让模型静态推测；把 Skill 输出当成人工批准或实际执行证据。

## 如何安装

只安装中文版本到 Codex：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/api-test-pytest -g -a codex -y
```

如果你使用仓库自带安装器，可以先克隆项目，再按工具和语言安装：

```bash
git clone https://github.com/naodeng/awesome-qa-skills.git
cd awesome-qa-skills
bash scripts/install-skills-mac.sh --tool codex --lang zh
```

中英文目录包含同名 Skill。全局安装时请选择一个语言目录，或者像上面一样只安装单个 Skill，避免同名发现冲突。

## 如何使用

安装后直接描述任务，并明确调用 Skill：

```text
请使用 api-test-pytest Skill。

任务：根据 OpenAPI 或接口说明生成可维护的 Pytest 集合或自动化代码，并接入本地与 CI 回归。
输入：需求说明、相关接口或页面、当前测试材料
约束：不要补造缺失事实；把假设、未知项和阻塞单独列出
输出：给出可执行结果、风险优先级、覆盖依据和下一步验证建议
```

第一次使用时不用追求“提示词写得很聪明”。把真实材料、目标、范围和限制交代清楚更重要。文件很多时，先说明哪些是事实源、哪些只是参考，避免模型把旧报告当成当前状态。

## 一个由浅入深的实践过程

### 第一步：确认任务边界

先回答四个问题：测试对象是什么，当前阶段是什么，已有材料有哪些，谁会使用输出。边界不清时，Skill 应先提澄清问题或标记假设。

### 第二步：建立证据与风险清单

把需求、代码、接口、运行记录和历史缺陷分开。事实要能追溯到来源；推断要明确写成推断；没有验证的内容不能进入“已通过”或“可发布”结论。

### 第三步：执行 Skill 的核心流程

围绕 角色定位、输入解析顺序、默认约定（无用户指定时直接采用）、Gotchas、最低覆盖清单 逐步展开。高风险路径先处理，普通路径随后补齐。如果需要生成代码或配置，先确认版本、目录、运行命令和依赖，不要把伪代码包装成已执行结果。

### 第四步：审查输出

检查每个重要结论是否有来源，风险是否带影响范围，建议是否能执行，未知项是否被隐藏。然后再决定要不要进入真实运行、人工评审或下一个 Skill。

## 最佳实践

1. **先给事实，再给期待。** 原始需求、接口定义和真实错误比“请专业一点”更有用。
2. **一次限定一个主要目标。** 分析、生成、执行和审批可以串联，但不要假装它们在一次静态回答里都已完成。
3. **保留来源追踪。** 需求 ID、文件名、接口路径、截图和日志时间能让结果被复核。
4. **让模型写出不知道的部分。** 未知项清单通常比十条通用建议更值钱。
5. **输出后做人工审查。** 尤其是安全、发布、合规和高风险业务，Skill 提供辅助判断，不替代责任人。
6. **用评测约束长期质量。** 修改 Skill 后检查成功路径、信息不足和风险边界，防止文案变长了，行为反而漂移。

## 如何与其他 Skill 组合

Pytest 接口自动化 负责一个具体测试环节。前面可以接 requirements-analysis 或 test-strategy，后面可以接 test-case-reviewer、test-reporting 和对应的日常、迭代或发布工作流。

组合的关键不是调用越多越好，而是每一步都有明确输入、输出和批准边界。

## Q&A

### Skill 会自动执行所有测试吗？

不会。它首先提供结构化分析和执行指导。只有环境、工具和权限都存在，并且任务明确授权时，才能把建议继续落到真实命令或浏览器操作。

### 输入不完整还能用吗？

可以。可靠的做法是输出澄清问题、假设和降级结果。悄悄补全业务规则会让结果显得完整，却很难用于真实决策。

### 为什么不直接复制一段 Prompt？

Prompt 只有指令。Skill 目录还能携带参考资料、示例、脚本、输出契约、工具元数据和评测用例，并通过渐进加载控制上下文。

### 如何判断输出可信？

看证据，不看语气。检查来源、执行记录、覆盖关系、失败信息和未决项。静态分析只能证明静态分析完成，不能证明系统已经运行通过。

### 应该安装中文还是英文版本？

按主要工作语言选择即可。两边目录名相同，通常不要在同一个全局 Skill 目录同时安装两套。跨语言交付时，可以切换语言安装或在项目内保留明确的作用域。

## 最后

Pytest 接口自动化 的价值来自一套可重复的工作方法：输入有来源，过程有边界，输出能执行，结论可复核。先拿一个真实任务试用，再根据团队反馈调整材料和输出格式——这比收藏一堆从未运行的 Prompt 实在得多。
