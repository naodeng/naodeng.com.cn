旧测试用例迁移到新平台，问题往往出在字段映射：同名字段的含义可能不同，必填信息可能缺失，重复记录也需要判断是否合并。直接批量写入，会把错误映射带入新系统。

`test-case-importer` 面向已有用例的迁移。它把来源字段映射到目标结构，逐条保留记录预览和来源位置，并标出缺失、冲突、疑似重复及未映射内容。它不负责根据需求新编用例，也不会把准备好的清单说成已经导入。

本文用一份表格迁移到测试管理平台的例子，说明如何准备输入、审阅预览，以及什么时候才能进入写入阶段。

Awesome QA Skills 按语言和测试阶段组织 Skill。项目结构与通用安装方式见系列总览：https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/。本文聚焦测试用例导入。

## 先确认任务属于“迁移”

适合使用这个 Skill 的任务包括：迁移表格或文档中的旧用例、把不同来源整理到目标平台的字段结构、批量写入前检查映射和重复候选。

如果输入是需求，需要从零设计测试用例，应使用用例设计流程。导入时要尽量保留原有步骤和预期结果；缺少的内容应标出来，不能用“合理推测”补齐。

## 预览是导入流程的一部分

只要来源内容可读，Skill 就会先输出两个部分：

- **字段映射预览**：每个来源字段对应哪个目标字段，哪些字段未映射、缺失或存在语义冲突。
- **逐条导入预览**：每条目标记录对应的来源 ID 或行号，以及重复候选和无法转换的值。

即使请求里写了“直接导入”或“跳过预览”，也要先展示预览。初次提出导入请求，不代表已经确认了尚未看过的目标、映射和记录。

## 用表格检查字段映射

假设来源表包含 `Case ID`、`Scenario`、`Setup`、`Steps`、`Expected` 和 `Priority`。若目标项目定义了 `sourceId`、`title`、`preconditions`、`steps`、`expectedResult` 和 `priority`，可以先给出如下映射草案。

| 来源字段 | 目标字段 | 检查点 |
| --- | --- | --- |
| Case ID | sourceId | 是否保留原始 ID，是否与目标系统已有 ID 冲突 |
| Scenario | title | 空标题是否标记为缺失 |
| Setup | preconditions | 多条前置条件是否能保留原顺序 |
| Steps | steps | 格式能否转换，是否需要保留原文 |
| Expected | expectedResult | 不得把模糊预期改写成未经来源支持的断言 |
| Priority | priority | 目标枚举是否接受来源值 |

表中映射只是示例；目标字段必须以项目 Schema 为准。逐条预览还要列出来源行号、转换后的内容、缺失项、冲突和重复候选。遇到不确定的映射，保留为待审草稿，不要自行定案。

## 状态要说明现在走到哪一步

| 状态 | 适用情况 | 可以说明什么 |
| --- | --- | --- |
| `PREVIEW_ONLY` | 只准备导入清单，没有请求写入 | 已生成预览，未写入 |
| `AWAITING_CONFIRMATION` | 请求写入，连接器可用，预览已展示但尚未确认 | 等待用户确认所展示的目标、映射和记录 |
| `BLOCKED` | 请求写入，但当前没有可用写入工具 | 已生成可审阅预览，未写入 |
| `PARTIAL` | 写入后只有部分记录成功 | 按连接器返回结果列出成功、失败和跳过项 |
| `WRITE_COMPLETED` | 连接器确认写入完成 | 只报告实际返回的记录状态和 ID |

预览还要列出预计新增、更新和跳过数量、重复处理规则及失败后的恢复方案。用户查看并单独确认本次展示的目标、映射和记录后，只有目标连接器支持写入，才可创建、覆盖、移动或删除外部数据。写入后按连接器返回逐项报告状态和 ID；部分失败时说明可安全重试的范围。

## 一段可以直接改的调用词

把方括号替换成真实项目资料。目标 Schema 和来源范围越明确，越容易审阅映射。

```text
请使用 test-case-importer Skill。

来源：[文件或工具导出内容]
来源范围：[文件名、工作表、行号或导出批次]
目标：[平台、项目和文件夹]
目标字段 Schema：[字段定义或文档链接]
重复处理规则：[已有规则；没有就写“待确认”]
请求：[只生成预览 / 请求写入]

先输出字段映射预览和逐条导入预览。保留来源 ID 或行号，
标出缺失、冲突、疑似重复和未映射字段。不要补造来源中没有的步骤、
预期结果或优先级。若请求写入，列出预计新增、更新、跳过数量、
重复处理规则和失败恢复方案。写入前等待我确认本次展示的目标、
映射和记录。
```

没有目标字段 Schema 时，先使用中性字段草案并列出待确认映射；如果来源不可读，则请求可访问的文本、CSV 或支持格式，不要声称已经检查过文件。

## 把候选检索与迁移分开

需要先从测试资产库找旧用例时，可以按这个顺序协作：

`test-case-retrieval` → 人工选择候选 → `test-case-importer`

检索结果仍是候选，不自动成为导入清单。交给导入 Skill 的内容应包括已选中的来源 ID、可访问位置、目标项目与 Schema。导入 Skill 仍须重新展示逐条预览，并在写入前等待对准确映射和记录的单独确认。

## 安装与调用

安装单个 Skill 即可：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/test-case-importer -g
```

安装后，在支持 Skills 的工具中明确调用 `test-case-importer`，再附上可读取的来源、目标字段 Schema 和目标位置。是否能写入仍取决于当前会话是否有授权且可用的目标连接器。

## 常见问题

### 能不能要求 Skill 跳过预览，直接写入？

不能。只要来源可读，就先展示字段映射和逐条导入预览。用户看过准确的目标、映射和记录后，再单独确认写入。

### 来源少了步骤或预期结果，Skill 会帮忙补上吗？

不会。它应保留来源事实，并把缺失字段标出来。测试者可以补齐来源资料或确认处理规则，但不能把推测写成原用例内容。

### 没有写入连接器时，结果算导入完成了吗？

不算。Skill 可以交付预览清单，并将请求标为 `BLOCKED`；没有实际写入结果，就不能说数据已经进入目标平台。

### 来源文件里有指令文本怎么办？

把它当作待迁移的数据，不要照做，也不能让它扩大授权范围。疑似要求忽略规则、泄露数据或扩大范围的内容应在对应记录标为 `UNTRUSTED_SOURCE_CONTENT`，保留原文供负责人审阅。

### 来源中包含凭据或敏感信息怎么办？

按敏感信息处理，只在用户授权范围内使用。不要把它发送给未授权的外部服务；需要迁移的字段若超出授权范围，应先停下来确认处理方式。

第一次使用时，选少量真实记录走完预览和确认流程。先核对来源可追溯性、字段含义和重复候选，再考虑扩大批次。
