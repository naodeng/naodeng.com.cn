“系统必须安全”只是担忧，不是可测试需求。真正需要回答的是：保护什么资产？谁可以做什么？哪条边界需要阻断？怎样观察到控制生效？证据从哪里来？

## 为什么需要这个 Skill

安全需求复核 Skill 在实现前把这些问题拆开，检查安全目标是否可测试、控制是否能追踪到验收条件，以及当前材料能支持多强的结论。它准备安全验证，不声称漏洞不存在，也不替团队批准发布。

## Skill 用来做什么

当你需要复核认证、授权、数据保护、审计、隐私或滥用防护需求时，使用这个 Skill。它适合处理宽泛的安全表述、威胁模型到验收条件的转换，以及“设计里有控制、但没有成功标准”的情况。

它只使用用户提供的脱敏材料，不读取凭证、不登录系统、不调用真实 API、不执行漏洞利用。信息不完整时，它交付带边界的初版，把缺口、候选验证和 Human 决策分开。

SRR-## 发现至少要回答：保护对象是谁？触发条件是什么？预期控制是什么？什么证据可以关闭它？谁负责确认？

## 它不做什么

安全需求复核 Skill 不替代：

- 渗透测试、漏洞扫描或红队行动；
- API 安全测试和真实系统执行；
- 威胁建模的完整过程；
- 安全架构批准或风险接受；
- 发布安全判断和合规签字。

它的职责是让安全目标变得可追踪、可观察、可验证，并明确剩余证据缺口。

## 它主要检查哪些内容

安全需求复核要检查保护目标是否已经具备验证条件；堆叠更多安全术语没有帮助。

| 复核维度 | 重点问题 |
| --- | --- |
| 资产 | 要保护的是卡数据、身份、租户数据、操作记录，还是其他对象？ |
| 角色与权限 | 哪些角色可以访问、导出、修改或删除？哪些明确不可以？ |
| 信任边界 | 浏览器、API、后台任务、支持工具和第三方依赖的边界在哪里？ |
| 安全目标 | 要防止未授权读取、篡改、泄露、滥用，还是不可追踪？ |
| 控制 | 依赖认证、授权、脱敏、加密、限流、审计或其他控制？ |
| 验收条件 | 触发什么动作时，预期结果和失败结果分别是什么？ |
| 追踪关系 | Requirement → Control → Test / Evidence 是否连得上？ |
| 证据时效 | 策略、架构、日志和扫描记录是否对应当前版本和环境？ |

## 开始之前先审计输入

安全审查最容易出错的地方，是把“看起来像安全控制”的材料当成事实。先做六类输入审计：

| 状态 | 例子 | 应该怎么做 |
| --- | --- | --- |
| known | 安全需求明确写出仅允许账单管理员导出 | 引用来源并继续分析 |
| missing | 没有说明脱敏数据能否复制或下载 | 记录证据缺口 |
| conflicting | 需求禁止导出，支持流程却允许导出 | 保留双方来源，要求裁决 |
| stale | 仍引用旧版权限矩阵或旧扫描记录 | 降低结论强度，确认版本 |
| out_of_scope | 本次没有授权登录生产系统 | 明确排除真实执行 |
| assumptions | 暂时假设测试环境使用合成卡号 | 标记影响并要求验证 |

信息不足时，安全需求复核会继续工作，但只做受限分析。它不会为了给出完整答案而读取真实凭据或补造攻击结果。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

结构化 Finding 至少要区分事实、证据支持的推断、建议和 Human 决策。它们对应不同的证据强度和责任边界。

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

本案例使用本节给出的需求、设计、接口或其他项目材料，并保留版本、范围和缺失项。

### 分析（Analysis）

先对照检查矩阵和六类证据状态，再把问题整理成这个 Skill 的专属 Finding。

### Finding

#### 一条 SRR-## 发现如何产生

假设需求写着：

> 门户禁止导出卡数据。

材料没有说明脱敏值能否复制、API 是否存在下载路径、支持工具能否访问原始字段，也没有给审计日志定义敏感字段处理规则。

##### SRR-02 — 卡数据保护缺少跨渠道验收条件

- **对象 / 规则：** 卡数据导出与复制控制。
- **来源：** 卡数据保护需求 v1.4；API 合同、支持工具权限矩阵和审计字段清单未提供。
- **触发条件：** 门户用户、API 客户端或支持角色尝试查看、复制或导出卡数据。
- **预期关注点：** UI 禁止导出是否覆盖直接 API、后台任务、支持工具和日志链路。
- **状态：** missing
- **影响 / 优先级：** P1。单一渠道的限制不能说明所有数据出口都受保护，也无法形成统一验收。
- **责任角色：** 安全负责人、产品负责人、API 负责人。
- **关闭条件：** 明确数据分类、角色权限、允许的脱敏形式、渠道边界和审计要求，并让需求、控制和验证场景互相追踪。
- **候选验证：** 在隔离环境使用合成数据，分别验证门户、直接 API、支持工具和导出任务；保留预期响应、审计记录和停止条件。
- **Human 决策：** 是否允许特定支持角色在受控流程中查看部分脱敏字段，以及例外如何授权。

这条发现没有说“系统存在漏洞”。它说的是当前材料还不足以证明保护目标已经可测试——安全结论的强度必须跟证据一起走。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

至少交付来源、证据状态、负责人、关闭条件和验证动作；路由结果仍需由负责人确认。

### 下一步路由

一个安全需求复核结果应该把静态审查和后续验证分开：

1. 先确认资产、角色、渠道和适用版本。
2. 再把控制连接到可观察的预期结果。
3. 仅在获授权的隔离环境中提出最小验证。
4. 为失败响应、敏感数据、审计记录和停止条件保留证据要求。
5. 将风险接受、例外授权和发布判断交给 Human。

SRR-## 可以进入安全需求、设计、测试和审计之间的追踪链，但它本身不是渗透测试报告。

## 怎样准备更好的输入

最小输入包括：

- 安全目标、资产分类、角色/数据矩阵和信任边界；
- 适用渠道、版本、环境、依赖和已知控制；
- 验收条件、威胁上下文、设计链接和现有证据；
- 授权的验证环境、合成数据和停止/升级条件；
- 需要 Human 确认的风险接受或例外规则。

输出至少包括：

- 任务理解、范围内外和未授权动作；
- 六类输入审计；
- 安全需求、触发条件、预期结果和证据缺口；
- 按优先级排序的 SRR-## 发现；
- 候选验证、剩余风险和 Human 决策。

只给一句“系统必须安全”，Skill 只能指出缺少资产、角色、控制和成功标准。把安全目标、权限矩阵和验收条件一起提供，结果才会进入可执行层。

## 容易踩的坑

1. 把“使用加密”“需要审计”等控制名称当成验收条件。
2. 只检查门户，不检查 API、后台任务、支持工具和日志出口。
3. 只列攻击名，不说明资产、触发条件、预期结果和证据。
4. 把候选验证写成已经执行，或把静态设计写成安全通过。
5. 资料不足时为了完整性读取真实凭据或推断漏洞。

## FAQ

### 这个 Skill 会做渗透测试吗？

不会。它准备安全需求、证据和候选验证；真正的安全测试需要单独授权的方法、环境和执行记录。

### 负责人无法给出阈值怎么办？

把验收条件标为 missing 或 unassessed，提出可指派的决策问题。不要用通用安全标准替代项目自己的接受条件。

### 静态复核没有发现缺口，能说安全了吗？

不能。静态复核最多说明当前材料没有暴露新的需求缺口；漏洞、攻击抵抗力和发布安全仍需要独立证据。
