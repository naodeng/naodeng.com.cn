发布门禁只有说明控制哪项决策、需要什么证据，以及证据缺失或无效时怎么办，才真正有用。质量门禁设计 Skill 把这些规则整理成可复核的契约。

## 什么时候使用

当团队要定义或评估交付与发布门禁的准入条件、证据要求、负责人、例外路径和回滚条件时，可以使用这个 Skill。它复核提供的策略与证据设计；不会执行流水线、批准例外或判断发布是否安全。

## 建立门禁契约

先明确每个门禁只控制一项决策：合并、部署、扩大流量还是停止。逐项列出需要满足的义务，以及对应证据的版本和时效要求。指定执行责任人，并区分以下状态：

| 状态 | 对决策的含义 |
| --- | --- |
| PASS | 新鲜、有效的证据满足已声明的义务。 |
| FAIL | 证据表明义务没有满足。 |
| BLOCKED | 因某个原因无法执行；记录原因和下一次尝试。 |
| UNKNOWN | 证据缺失、过期、冲突或无法得出结论。 |

证据不存在不代表 PASS。依照项目的汇总和失败关闭规则处理；不能让平均值掩盖必需项中的失败或未知。若策略本身缺失，应记录需要人工决定的事项，而不是自创阈值。

## 例外与失败路径

每个例外都要记录适用范围、理由、授权人、批准、过期时间、补偿控制和撤销条件。无效或过期的例外不能改写失败结果。每项阻塞或失败义务还应说明由谁调查、是否允许重跑，以及什么条件会停止或回滚发布。

门禁设计、与现有证据比较、流水线实现是不同的工作。设计好的规则或一次试运行都不能证明真实门禁已经执行。

## 示例：结算改动的分阶段发布

设想结算功能分阶段发布，需要检查单元、契约、浏览器和生产观察证据。部署前，门禁可以要求有效的单元和契约证据；扩大流量前，可以要求浏览器证据；全面发布前，则可以依赖双方约定的生产观察窗口。这些只是候选阶段，实际义务与阈值必须由项目负责人确定。

如果浏览器基础设施不可用，浏览器执行状态应为 BLOCKED，不能悄悄改成 PASS。负责人可以继续停止发布，或批准范围明确、即将过期并带有补偿控制的例外。记录由谁做了什么决定，以及哪些证据可以关闭例外。

## 交付哪些内容

发现门禁规则缺失或含糊时，用 QGD-## 记录对象或义务、来源、触发条件、预期问题、证据状态、影响与优先级、负责人角色、关闭条件和验证方法。另需写明停止、升级和回滚条件。说明剩余风险，并把人工批准与技术证据分开。

## 结论边界

门禁只能在声明的范围内控制决策。它不能替团队选择业务风险容忍度，也不能把过期证据变成当前证明。没有对应运行记录和授权决策时，不要声称所有检查通过、已经批准发布或流水线已经执行。
