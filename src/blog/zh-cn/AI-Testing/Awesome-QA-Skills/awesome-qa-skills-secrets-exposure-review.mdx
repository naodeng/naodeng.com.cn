密钥不出现在源码里，也可能泄露。配置快照、调试日志、崩溃报告、构建产物和复制的环境文件都会形成不同暴露路径。

## 为什么需要这个 Skill

Secrets-Exposure Review Skill 用有证据边界的方式检查密钥在哪里、如何流转、日志暴露了什么、哪些配置边界重要，以及是否有轮换证据。

## Skill 用来做什么

本文关注的复核应让下一步安全检查变得明确，同时不能增加暴露。

当你要用脱敏材料复核服务或流水线时，使用这个 Skill。它识别暴露风险和验证动作，不会登录、调用真实 API、读取凭证，也不会宣布系统安全。

好的发现需要写清密钥类别、位置或流转、暴露触发、证据状态、影响、优先级、负责人、关闭条件和隔离验证方式。

当凭证要从本地开发进入 CI、准备修改日志、需要限定一次安全事故复核，或轮换是否就绪不清楚时，使用这个 Skill。

## 它不做什么

敏感信息暴露审查 Skill 可以组织暴露位置的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 暴露位置 | 密钥可能存储或输出在哪里 | 脱敏来源与证据状态 |
| 流转发现 | 密钥如何经过配置或运行时 | 触发与边界 |
| 轮换就绪度 | 什么可以证明替换和回滚安全 | runbook、负责人或缺口 |
| 验证动作 | 降低不确定性的安全隔离检查 | 不访问真实凭证 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“暴露位置”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕暴露位置，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 范围与版本 | 服务、仓库、流水线、环境和变更修订 | 未知边界要标出 |
| 脱敏材料 | 配置模板、日志样例、部署清单和密钥引用 | 不要附真实值 |
| 密钥流转 | 创建、注入、使用、记录、异常处理和撤销路径 | 事实与假设分开 |
| 轮换证据 | 负责人、周期、依赖影响、dry-run 和回滚材料 | 没有证明时保持未评估 |

可以这样调用：

~~~text
请使用 secrets-exposure-review Skill。

任务：复核日志改造期间，支付服务是否可能通过 CI 日志、异常 Trace 或部署配置暴露 API 凭证。
输入材料：[脱敏清单、日志样例、流水线步骤、密钥引用和轮换 runbook]
范围：[staging 与 CI，不使用真实凭证]
限制：[不调用 API、不读取密钥值]

分开已知暴露证据、假设、候选验证、影响、负责人、关闭条件和安全决策边界。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：复核日志改造，不要复制凭证

新的异常日志器把请求头写入 CI 失败输出。这个 Skill 应指出 authorization header 可能暴露，追问写入前是否脱敏，并建议在隔离流水线用合成 token 验证。不能索要生产 token，也不能调用支付供应商。

复核可以分类脱敏证据并提出安全验证，不能证明没有密钥、漏洞利用成功、修复完成或安全通过。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“暴露位置”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和暴露位置的具体对象 |
| 发现 | 暴露位置的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 暴露位置 | 密钥可能存储或输出在哪里 | 脱敏来源与证据状态 |
| 流转发现 | 密钥如何经过配置或运行时 | 触发与边界 |
| 轮换就绪度 | 什么可以证明替换和回滚安全 | runbook、负责人或缺口 |
| 验证动作 | 降低不确定性的安全隔离检查 | 不访问真实凭证 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供脱敏配置、日志样例、流水线步骤、密钥引用名、环境边界、轮换负责人和验证环境。真实值应留在提示词和仓库之外。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 只搜索字面值，就认为系统安全，忽略派生形式或日志输出。
2. 把轮换文档当成所有消费者都能加载新凭证的证明。
3. 为了复核完整而请求真实凭证。

## FAQ

### 可以贴真实 token 让复核更准确吗？

不可以。使用脱敏值或合成 token；真实凭证会增加暴露，而且超出这个 Skill 的边界。

### 静态扫描干净就代表轮换就绪吗？

不代表。轮换还需要消费者重新加载、撤销、回滚和安全验证路径的证据。
