同一发布在产品、QA、研发和运维眼里可能是四种不同的风险图景。多角色质量汇总要保留这些差异，再把事实、影响和决策条件放到同一份材料里。

多角色质量综合 Skill 对齐不同视角、假设和未解决风险，让跨职能团队能在分歧存在时共同决策。

本文用贴近协作现场的案例拆解判断过程，帮助你把不同信号转化为可沟通、可追踪的行动。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。项目结构与通用安装方式已经在[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/)说明，这里只讲 多角色质量汇总。

## 先看源 Skill

主 Prompt 把工作拆到 输入合同、输入校验、分类规则、确定性合并规则、严重级别规则。这些标题只是导航，真正使用时还要回到项目材料。

这个 Skill 没有单独示例目录，文章里的片段依据入口、主 Prompt 和评测约束整理。

## 相关 Skill

多角色质量汇总不替任何角色做专业判断，它负责把输入校验、冲突和责任边界写清楚。四个常用输入 Skill 是：

| Skill | 主要输入 | 汇总时要保留什么 |
| --- | --- | --- |
| [产品质量视角](https://inaodeng.com/zh-cn/qaskills/product-quality-perspective/) | 用户任务、业务规则、转化和反馈 | 用户价值、业务取舍和未验证假设 |
| [QA 质量视角](https://inaodeng.com/zh-cn/qaskills/qa-quality-perspective/) | 覆盖、用例、缺口和运行结果 | 证据范围、残余风险和发布门槛 |
| [技术质量视角](https://inaodeng.com/zh-cn/qaskills/technical-quality-perspective/) | 架构、日志、指标、Trace 和回滚记录 | 运行后果、恢复能力和技术约束 |
| [UX 质量视角](https://inaodeng.com/zh-cn/qaskills/ux-quality-perspective/) | 任务观察、可访问性和失败恢复记录 | 用户影响、复现路径和体验改进动作 |

## 四个角色怎样提供可合并的材料

合并产品、QA、技术和体验视角，形成保留分歧的质量结论。

| 角色 | 关注点 | 必须带上的证据 | 不能替对方做的决定 |
| --- | --- | --- | --- |
| 产品 | 用户任务、转化和业务规则 | 漏斗、验收记录、用户反馈 | 是否调整范围和目标 |
| QA | 覆盖、缺口和残余风险 | 用例、运行记录、缺陷 | 是否接受测试证据不足 |
| 技术 | 稳定性、依赖和恢复 | 日志、指标、Trace、回滚记录 | 是否采用技术取舍 |
| 运维 | 变更窗口、告警和止损 | 发布记录、告警、容量曲线 | 是否执行生产操作 |

汇总的第一步是检查每份材料有没有来源、时间窗口和明确的观察对象。

## 共同事实和冲突意见要分开写

同一事实可以承载不同判断：支付回调在 staging 通过，产品会关注转化，QA 会关注异常覆盖，技术会关注生产配置差异。

| 输出部分 | 写法 | 示例 |
| --- | --- | --- |
| 共同事实 | 所有角色都能指向的证据 | staging 支付回调通过，构建号为 build-42 |
| 冲突判断 | 各角色的观察与影响分别保留 | QA 缺少超时用例；技术发现回滚窗口不足 |
| 待决策项 | 选项、风险、批准人和截止时间 | 缩小范围后发布，由产品负责人确认 |

不要把分歧压成“整体风险可控”。决策人需要看到每个选项会承担什么风险，以及还要补哪份证据。

最后的质量结论可以只有三行：已证实什么、仍不知道什么、谁会处理。短一点没关系，证据要能点开。

## 一段可以直接改的调用词

把下面的方括号换成项目内容。材料越具体，Skill 越少猜。

```text
请使用 multi-role-quality-synthesis Skill。

任务：合并产品、QA、技术和体验视角，形成保留分歧的质量结论
版本与环境：[需求版本 / 构建号 / 环境]
输入材料：[文件路径或链接]
范围：[本次包含与排除的业务链路]
限制：[账号、数据、时间、合规要求]

分别保留各角色观察、依据和影响。共同事实与分歧分开写，待决策项注明批准人。
最后列出待确认问题，不要补写材料里没有的事实。
```

第一次调用先看结构和缺口。补齐材料后再生成正式产物，能省掉不少来回修改。

## 多角色汇总的工作是保留冲突，再让正确的人做决定

产品、QA 和技术的结论发生冲突时，汇总不负责投票。它先把各方的事实、推断、影响和不可接受条件并排展示：产品担心转化，QA 缺少回归证据，技术发现回滚窗口不足。三者都可能成立。

最终输出需要一项可执行决定：继续发布并接受哪项风险，缩小范围后补什么证据，还是暂停等待哪个前置条件。每个选项标出决策人和截止时间，避免“综合来看可控”变成没人承担的结论。

## 这篇 Skill 适合谁

发布负责人可以用它主持跨职能评审；产品、QA、技术和运维可以用同一格式交付自己的材料。它适合意见相反、证据分散、需要明确批准人的质量决定。

## 交付前复核：把判断落到证据

Skill 输出拿到手后，先核对四件事：输入版本是否明确，范围是否完整，每条结论能否回到证据，下一步由谁执行。少一项，报告就容易变成漂亮的猜测。

| 项目 | 需要留下 | 缺失时 |
| --- | --- | --- |
| 输入边界 | 版本、环境、时间窗口和本次范围 | 标记假设，不写成事实 |
| 证据索引 | 日志、报告、Trace、截图或命令输出 | 标记 `evidence_pending` |
| 结论状态 | `verified`、`assumption`、`blocked` 或 `pending` | 停止扩大结论 |
| 后续动作 | 最小验证命令、负责人和截止时间 | 交付为待办，不进入门禁 |

```text
source_version: [版本或提交]
scope: [本次包含和排除的对象]
evidence: [日志、报告、Trace 或命令输出]
status: pending
owner: [负责人]
next_action: [最小验证动作]
```

分析类 Skill 要保留查询条件和时间窗口；执行类 Skill 要保留命令、退出码和失败产物。人工修改也要记录，下一次复核才知道结论从哪里变化。

## 常见问题

### 汇总结果必须只有一个结论吗？

不必须。共同事实、冲突意见和待决策项分开保留，反而更容易让负责人做出可追踪的决定。

### 某个角色没有材料怎么办？

标成缺席或代理分析，列出需要该角色确认的问题，不能替它补写观察。

### 谁负责最后的决定？

由有权限的产品、发布或技术负责人批准选项。Skill 只负责让依据和风险可见。

### 没有共同结论还能发布吗？

可以讨论，但必须列出未决风险、接受人和截止时间；没有这些信息就无法形成可审计的发布决定。

先拿一份真实材料跑 多角色质量汇总，保留输入、输出和复核意见。文章里的片段只能帮你搭起结构，项目证据还得在项目里产生。
