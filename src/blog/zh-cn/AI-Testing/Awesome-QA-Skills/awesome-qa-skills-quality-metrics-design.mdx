一个指标最危险的时候，是分子写清楚了，分母却没有写清楚。看起来精确的仪表盘，可能在每次发布时悄悄改变统计口径。

## 为什么需要这个 Skill

质量指标设计 Skill 帮助团队在把指标设为目标或门禁前，明确计算规则、数据源、新鲜度和解释边界，形成可复核的指标契约。

## Skill 用来做什么

最终产物应让另一位工程师能够按指定来源重新计算指标。

当你要设计线上逃逸缺陷率、测试反馈时长、不稳定测试率或需求返工率时，使用这个 Skill。它帮助团队把指标定义得可复算、可复核，并降低意外或有意刷数的空间；单一数字无法代表全部质量。

好的指标定义要写清事件、分子、分母、时间窗口、事实来源、新鲜度、分组、排除规则、解释边界，以及它能支持和不能支持的决策。

当团队要新增质量 KPI、合并多个系统数据，或者发现两个仪表盘同名却算出不同结果时，使用这个 Skill。

## 它不做什么

质量指标设计 Skill 可以组织指标契约的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

复核时要逐项追问：事件怎样识别，分子和分母如何关联，数据何时算完整，结果支持什么决策。可以先按源 Skill 的输出字段整理一张检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |
| 输出格式 | 是否需要表格、CSV、JSON 或工单字段 | 保留发现字段；机器读取前确认 schema、枚举值、必填字段和证据来源 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始分析前，先把材料按六种证据状态整理，并检查材料是否完整、来源是否可信、时间是否有效、数据是否可比。事件定义或数据来源缺失会限制当前能下的结论。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

写指标结论时，把事实、推断、建议和人工决策分开：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

源 Skill 附有一组合成样例，用来检查事件去重和首轮计算。它只用于演示，不代表生产运行记录。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 决策问题 | 根据指标字典和事件样例，复算新增缺陷数与首轮通过率 | 不要自行推导目标或发布门禁 |
| 指标字典 v1 | 新增缺陷按不同的 `defect_id` 计数；首轮通过率取每个不同 `test_id` 的首次尝试 | 统计单位或规则未定义时保留为缺口 |
| 事件样例 | D1 有创建、关闭、重开事件，并被重复导入两次；D2 被创建。T1 首次失败、重跑后通过；T2 首次通过；T3 计划执行但没有运行 | 区分缺陷实体、状态事件、首次尝试、重跑和未执行测试 |
| 尚未提供的信息 | 样例写明“本月”，但没有时区和准确的窗口边界 | 只用于演示计算，不能据此比较不同窗口 |

可以这样调用：

~~~text
请使用 quality-metrics-design Skill。

任务：根据提供的指标字典和事件样例，复算新增缺陷数与首轮通过率。
输入材料：[有版本的事件定义、缺陷 ID、测试 ID、首次尝试、重跑和执行状态]
范围：[服务、发布或时间窗口、环境]
限制：[缺少时区、迟到数据、重复导入、隐私要求]
成功标准：[另一位工程师能够复算结果]
排除事项：[未经批准的目标或发布门禁]

写出分子、分母、计算结果、排除规则、证据状态和解释边界。分开事实、假设、建议与人工决策；不要把重跑当成首次尝试，也不要把计划中的测试写成已执行。
~~~

### 分析

先确认统计单位和计算方式，再解释结果。样例只写了“本月”，没有时区和准确的窗口边界，只能用于演示计算，不能支持跨窗口比较。

### 发现

#### 计算示例：缺陷按实体去重，重跑不改变首轮结果

按样例中的规则，新增缺陷数按不同 ID 计算，D1 和 D2 共 **2 个新增缺陷**。D1 的关闭和重开属于状态事件，重复导入也没有产生新的缺陷实体。

首轮通过率只看有首次执行记录的 T1 和 T2。T2 首次通过，T1 首次失败但重跑通过，因此结果是 **1 / 2 = 50%**。重跑不能覆盖 T1 的首轮失败。T3 只有计划，没有执行记录，所以结果是 **未知**，不能记作通过。

| 样例中的判断 | 复核结果 |
| --- | --- |
| K-1 报告 4 个新增缺陷 | `WRONG`；样例中只有两个不同的缺陷 ID |
| K-2 用 T1 的重跑通过替换首次失败，得出 100% 首轮通过率 | `WRONG`；首轮结果为 1/2 |
| K-3 按不同 ID 和首次尝试复算两个指标 | `CALCULABLE`；结果是 2 个缺陷和 1/2 首轮通过 |
| K-4 把未运行的 T3 记为通过 | `UNKNOWN`；没有执行证据 |

这些计算说明指标字典会怎样约束计数方式。它们不能证明生产事件链路完整，也不能证明指标可以预测质量或团队目标公平。

设计线上逃逸缺陷指标时，“线上缺陷数 ÷ 测试用例数”不能直接表示用户暴露量，除非两组数据之间的关系已经定义。发布数或受影响交易量可以作为候选分母，但指标负责人要先确认统计对象，以及缺陷与发布之间的关联规则。

#### 示例发现：让其他工程师能够复算

| 字段 | 示例写法 |
| --- | --- |
| 发现 | `QMD-01`：字典 v1 按不同缺陷 ID 和每个测试的首次尝试计数；样例支持 2 个缺陷和 1/2 的首轮通过率 |
| 来源与触发条件 | 脱敏样例中的 D1、D2、T1、T2、T3；当报告把状态事件当缺陷、把重跑当首次尝试，或把计划测试当作已通过时触发复核 |
| 预期问题 | 重复导入会抬高缺陷数；用重跑替换首次失败会抬高首轮结果 |
| 证据状态 | 样例计算为 `known`；准确的生产窗口、时区和链路完整性未提供 |
| 影响与优先级 | 错误计数可能误导比较；样例没有业务影响分级规则，优先级保持 `NOT_SCORED` |
| 负责人和待决策项 | 指标负责人确认生产窗口、时区、数据来源链路和预期用途 |
| 动作与关闭条件 | 写清统计单位、过滤、去重、缺失数据处理和纳入示例；其他工程师能够复算样例结果 |
| 验证 | 用带版本的脱敏记录重算，并保存查询与结果；确认统计范围和链路前，生产使用保持待定 |
| 停止条件 | 生产统计窗口、时区或数据链路尚未确认时，不把指标用于目标或门禁；将决策交给相应负责人 |

这条发现按源 Skill 的 QMD 字段组织，包含来源、触发条件、预期问题、证据、影响、负责人、关闭条件和验证方式。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

生产发现关闭前，按写明的方式执行验证并保留原始产物。样例计算不代表生产数据链路已经验证。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |

每条结论都要能回到来源、证据状态和下一步动作。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补证据空白。

### 下一步路由

根据缺口把工作交给相应负责人：

| 缺口 | 下一步负责人 | 要解决的问题 |
| --- | --- | --- |
| 事件、分子或分母未定义 | 指标负责人和业务负责人 | 确认统计对象、窗口与纳入/排除规则 |
| 数据源、迟到数据或关联键不清楚 | 数据平台或系统负责人 | 说明来源链路、新鲜度和对账方式 |
| 指标拟用于门禁或团队目标 | 质量治理与业务负责人 | 审核解释边界、反向指标和授权决策 |

交接时附上证据状态和最小验证动作，后续结论不能超过现有证据。

## 怎样准备更好的输入

提供决策问题、事件字典、数据系统、发布和时间窗口规则、样例记录，以及一条纳入和一条排除样例。缺少这些内容时，分母仍然不完整。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、工单数或故事点当作用户暴露量，却不说明关系。
2. 混用事件时间、写入时间和发布时间，让迟到数据悄悄改写历史。
3. 还没有检查改标签或少报问题的可能性，就先发布指标目标。

## 最佳实践

- 从指标要支持的决策开始，写清统计单位、分子、分母、时间窗口与时区、过滤条件、去重方式、缺失数据规则、版本、来源和数据链路。
- 用样例记录复算，至少包括一条纳入和一条排除的记录。检查分母覆盖、数据延迟和排除规则；缺失记录仍然是未知，不能按零处理。记录格式有问题时先按测量问题处理，除非另有产品质量证据支持缺陷结论。
- 只比较窗口和定义匹配的数据。行动阈值应来自已批准的依据；同时保留解释边界和反刷数检查，不把相关性写成因果关系。
- 数据链路或分母覆盖尚未解决时，暂停把指标用于目标或门禁，并将生产或风险决策交给相应负责人。

## 新手入门：先从一个指标开始

1. 选一个服务、一个决策和一个指标。
2. 附上事件字典、来源、版本、样例记录，以及适用的统计窗口和时区。
3. 请 Skill 审计定义并复算样例。设定目标或门禁前，先把事实、推断、建议和人工决策分开复核。

## 常见问题

### 每个质量指标都需要目标吗？

不需要。先确认定义、数据链路、新鲜度和解释边界。目标是另外一个人工决策，基线不稳定时设置目标可能不安全。

### 如果数据源不一致怎么办？

保留两种计算，找出事件或范围差异，让负责人确认权威来源或对账规则，在此之前标为 pending。

### AI 生成的测试用例怎样纳入质量指标？

先按指标定义把它们作为候选项。通过复核、验收和执行规则后再计入相应指标；生成数量本身不能说明覆盖充分、运行可靠或产品质量。
