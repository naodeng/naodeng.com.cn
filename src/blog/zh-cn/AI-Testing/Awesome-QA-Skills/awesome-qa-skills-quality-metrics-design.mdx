一个指标最危险的时候，是分子写清楚了，分母却没有写清楚。看起来精确的仪表盘，可能在每次发布时悄悄改变统计口径。

## 为什么需要这个 Skill

Quality Metrics Design Skill 用于在团队把指标变成目标或门禁之前，先把定义做成有证据边界的指标契约，把质量问题接到计算规则、数据源、新鲜度和解释限制上。

## Skill 用来做什么

本文关注的产物，是另一位工程师可以根据指定来源重新计算的指标契约。

当你要设计线上逃逸缺陷率、测试反馈时长、flaky 测试率或需求返工率时，使用这个 Skill。重点是让指标可复算、可复核并抵抗刷数，而不是选一个数字代表全部质量。

好的指标定义要写清事件、分子、分母、时间窗口、事实来源、新鲜度、分组、排除规则、解释边界，以及它能支持和不能支持的决策。

当团队要新增质量 KPI、合并多个系统数据，或者发现两个仪表盘同名却算出不同结果时，使用这个 Skill。

## 它不做什么

质量指标设计 Skill 可以组织指标契约的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“指标契约”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕指标契约，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

在请求判断前先列出已有材料。缺口可以保留，但状态必须可见。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 决策问题 | 判断结账回归是否在发布前被发现 | 不要从流行 KPI 开始 |
| 事件定义 | 什么算发布、线上缺陷、失败运行或问题关闭 | 未定义之处保留为缺口 |
| 数据源 | 缺陷系统、CI 事件、部署记录和线上事故 | 数据链路缺失时标为未评估 |
| 使用边界 | 使用人、复核周期、隐私限制和刷数风险 | 目标与发布决定分开 |

可以这样调用：

~~~text
请使用 quality-metrics-design Skill。

任务：为结账服务定义线上逃逸缺陷率和合并前测试反馈指标。
输入材料：[事件 schema、发布标识、缺陷字段、CI 时间戳和事故来源]
范围：[服务、团队、时间窗口和环境]
限制：[迟到数据、隐私要求、缺少部署关联]

写清分子、分母、来源、新鲜度、排除规则、分组、解释边界和验证方式，分开事实、假设、建议与人工决策。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：定义线上逃逸缺陷率，不要藏住暴露量

团队提出“线上缺陷数除以测试用例数”。这个 Skill 应指出分母与用户暴露量没有直接关系，并要求改用发布或生产交易作为基础。更好的初稿可以统计同一窗口内关联到发布的线上缺陷数除以受影响交易数，迟到关联在字段核对前保持 pending。

指标设计可以证明定义明确、可复核；不能证明数据管道完整、指标一定能预测质量，也不能证明团队目标公平。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“指标契约”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和指标契约的具体对象 |
| 发现 | 指标契约的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供决策问题、事件字典、数据系统、发布和时间窗口规则、样例记录，以及一条纳入和一条排除样例。缺少这些内容时，分母仍然不完整。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、工单数或故事点当作用户暴露量，却不说明关系。
2. 混用事件时间、写入时间和发布时间，让迟到数据悄悄改写历史。
3. 还没有检查改标签或少报问题的可能性，就先发布指标目标。

## FAQ

### 每个质量指标都需要目标吗？

不需要。先确认定义、数据链路、新鲜度和解释边界。目标是另外一个人工决策，基线不稳定时设置目标可能不安全。

### 如果数据源不一致怎么办？

保留两种计算，找出事件或范围差异，让负责人确认权威来源或对账规则，在此之前标为 pending。
