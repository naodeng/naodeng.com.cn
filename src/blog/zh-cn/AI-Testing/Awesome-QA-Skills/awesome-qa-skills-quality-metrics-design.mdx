一个指标最危险的时候，是分子写清楚了，分母却没有写清楚。看起来精确的仪表盘，可能在每次发布时悄悄改变统计口径。

## 为什么需要这个 Skill

质量指标设计 Skill 帮助团队在把指标设为目标或门禁前，明确计算规则、数据源、新鲜度和解释边界，形成可复核的指标契约。

## Skill 用来做什么

最终产物应让另一位工程师能够按指定来源重新计算指标。

当你要设计线上逃逸缺陷率、测试反馈时长、不稳定测试率或需求返工率时，使用这个 Skill。重点是让指标可复算、可复核并抵抗刷数，而不是选一个数字代表全部质量。

好的指标定义要写清事件、分子、分母、时间窗口、事实来源、新鲜度、分组、排除规则、解释边界，以及它能支持和不能支持的决策。

当团队要新增质量 KPI、合并多个系统数据，或者发现两个仪表盘同名却算出不同结果时，使用这个 Skill。

## 它不做什么

质量指标设计 Skill 可以组织指标契约的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

复核时要逐项追问：事件怎样识别，分子和分母如何关联，数据何时算完整，结果支持什么决策。可以先按源 Skill 的输出字段整理一张检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始分析前，先把材料按六种证据状态整理。缺少事件定义或数据来源不等于指标计算失败，但会限制当前能下的结论。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

写指标结论时，把事实、推断、建议和人工决策分开：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

在请求判断前先列出已有材料。缺口可以保留，但状态必须可见。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 决策问题 | 判断结账回归是否在发布前被发现 | 不要从流行 KPI 开始 |
| 事件定义 | 什么算发布、线上缺陷、失败运行或问题关闭 | 未定义之处保留为缺口 |
| 数据源 | 缺陷系统、CI 事件、部署记录和线上事故 | 数据链路缺失时标为未评估 |
| 使用边界 | 使用人、复核周期、隐私限制和刷数风险 | 目标与发布决定分开 |

可以这样调用：

~~~text
请使用 quality-metrics-design Skill。

任务：为结账服务定义线上逃逸缺陷率和合并前测试反馈指标。
输入材料：[事件 schema、发布标识、缺陷字段、CI 时间戳和事故来源]
范围：[服务、团队、时间窗口和环境]
限制：[迟到数据、隐私要求、缺少部署关联]

写清分子、分母、来源、新鲜度、排除规则、分组、解释边界和验证方式，分开事实、假设、建议与人工决策。
~~~

### 分析

先根据输入、检查矩阵和证据状态整理判断，再进入发现；缺失材料保留为缺口。

### 发现

#### 聚焦例子：定义线上逃逸缺陷率，不要藏住暴露量

团队提出“线上缺陷数除以测试用例数”。这个 Skill 应指出两者没有说明如何对应，不能据此表示用户暴露量。受影响交易量可以作为候选分母之一，但要先确认纳入范围、缺陷与发布的关联规则，以及迟到关联怎样处理；是否适合当前决策仍由指标负责人确认。

指标设计可以证明定义明确、可复核；不能证明数据管道完整、指标一定能预测质量，也不能证明团队目标公平。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

沿用上面的结账示例，如果需求只说“统计线上逃逸缺陷率”，却没有定义事件、分母和发布关联，发现可以这样记录。它指出当前定义无法复算，不推断缺失链路已经造成错误数据。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 结账服务的指标请求、事件定义和拟纳入的发布窗口；具体版本以实际输入为准 |
| 发现 | “线上缺陷数 ÷ 测试用例数”没有说明两者如何对应，不能作为暴露量口径复算 |
| 证据状态 | 若缺少事件字典、发布关联和样例记录，标为 `missing`；不得假设数据管道完整 |
| 影响 | 该口径目前无法支持跨发布比较或发布门禁；优先级由受影响决策和暴露范围决定 |
| 负责人和待决策项 | 指标负责人确认事件范围、时间窗口、迟到关联处理和适用人群 |
| 动作与关闭条件 | 补上分子、分母、纳入/排除规则和至少一组边界样例；其他工程师能据此复算 |
| 验证 | 用脱敏样例核对纳入与排除记录，并保留查询、样例版本和复算结果；未运行前保持未验证 |

交接时要让接手人能从发现回到来源，找到负责人，并执行一项可能改变结论的检查。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 指标契约 | 计算方式和纳入规则 | 带版本的定义与例子 |
| 数据链路与新鲜度 | 事件来自哪里、什么时候可信 | 来源、延迟和缺口 |
| 解释边界 | 指标能解释什么、不能解释什么 | 不做未经支持的因果判断 |
| 反刷数复核 | 如何改变行为或标签就能优化数字 | 风险与反向检查 |

每条结论都要能回到来源、证据状态和下一步动作。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补证据空白。

### 下一步路由

根据缺口把工作交给相应负责人：

| 缺口 | 下一步负责人 | 要解决的问题 |
| --- | --- | --- |
| 事件、分子或分母未定义 | 指标负责人和业务负责人 | 确认统计对象、窗口与纳入/排除规则 |
| 数据源、迟到数据或关联键不清楚 | 数据平台或系统负责人 | 说明来源链路、新鲜度和对账方式 |
| 指标拟用于门禁或团队目标 | 质量治理与业务负责人 | 审核解释边界、反向指标和授权决策 |

交接时附上证据状态和最小验证动作，后续结论不能超过现有证据。

## 怎样准备更好的输入

提供决策问题、事件字典、数据系统、发布和时间窗口规则、样例记录，以及一条纳入和一条排除样例。缺少这些内容时，分母仍然不完整。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、工单数或故事点当作用户暴露量，却不说明关系。
2. 混用事件时间、写入时间和发布时间，让迟到数据悄悄改写历史。
3. 还没有检查改标签或少报问题的可能性，就先发布指标目标。

## 常见问题

### 每个质量指标都需要目标吗？

不需要。先确认定义、数据链路、新鲜度和解释边界。目标是另外一个人工决策，基线不稳定时设置目标可能不安全。

### 如果数据源不一致怎么办？

保留两种计算，找出事件或范围差异，让负责人确认权威来源或对账规则，在此之前标为 pending。
