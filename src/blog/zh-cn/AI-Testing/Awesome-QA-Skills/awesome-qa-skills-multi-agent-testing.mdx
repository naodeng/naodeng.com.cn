多智能体系统即使保留了所有消息，也可能丢失任务所有权、重放已完成的写入，或在停止一个工作者后让另一个继续操作。多智能体协作测试会沿着委派、共享状态、冲突、所有权、终止和追踪检查协调协议。

## 多智能体协作测试：追踪一次交接

对每项任务或消息记录 task ID、message 或 correlation ID、发送方、接收方、父级委派、范围、负责人、共享状态版本和确认信息。使用项目实际定义的接收、拒绝和终止规则，不假设消息只会投递一次。

| 交接内容 | 需要查找的证据 |
| --- | --- |
| 委派 | 子任务范围明确，工具权限受限，责任人清楚。 |
| 共享状态 | 消息引用接收方实际可以读取的版本或产物。 |
| 所有权 | 任务认领和提交遵循已提供的原子所有权或 fencing 协议。 |
| 确认 | 发送方能区分已接收、已拒绝、已完成和结果不确定。 |
| 终止 | 停止请求传达到所有活跃子任务，并留下可审计的终态。 |

如果协议能安全去重，重复投递本身不一定是缺陷。要检查陈旧消息能否重新取得所有权、租约过期的工作者是否仍可提交，以及重试任务是否会重复产生副作用。

## 示例：研究流水线

假设一个流水线由规划、来源核验、写作和评审 Agent 组成。来源核验 Agent 读取旧版政策，而规划 Agent 收到新需求。复核交接载荷与共享状态版本：写作者应保留这个冲突，评审者应能找出每项结论使用的来源，然后才分配最终决策责任。

如果子 Agent 在产生副作用后超时，重新分配前要区分已完成、未完成和结果不确定的工作，并保留每项工作的负责人和证据。停止请求也需要确认和终态；父任务超时不能证明所有子任务都已停止。

## 记录 MAT-## 发现

每个协调缺口都应指出任务或协议规则、来源、触发条件、消息和状态版本、预期关注点、证据状态、影响与优先级、负责人角色、关闭条件和验证方法。只有当提供的协议涉及相应情况时，才加入重复消息、陈旧状态、部分失败、重新分配和停止传播场景。

静态设计、候选验证和实际执行必须分开。任务图或消息 schema 的存在不能证明 Agent 实际运行时遵循了它。
