选择器今天通过，明天可能因为布局 class 改了就失败。稳定的 UI 自动化应该来自用户意图和组件语义，而不是最容易复制的 CSS 路径。

## 为什么需要这个 Skill

UI Test Selector Review Skill 根据 DOM 和组件代码、可访问名称、data-testid 约定、定位历史和失败证据复核选择器，产出 USR-## 发现，不执行测试也不声称覆盖。

## Skill 用来做什么

本文关注的选择器应该描述用户或可访问界面暴露的控件意图，并能抵抗无关结构变化。

当你要识别 UI 自动化中脆弱、歧义、不可访问或维护成本高的选择器时，使用这个 Skill。它保留来源证据、适用范围和最小验证动作。

USR 发现要写清 UI 对象、前置条件、选择器问题、来源证据、影响、优先级、负责人、关闭条件和验证方式。

当 UI 测试在无害的标记变化后失败、选择器依赖样式类或位置，或者团队需要统一定位约定时，使用这个 Skill。

## 它不做什么

UI 测试选择器评审 Skill 可以组织选择器发现的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 选择器发现 | 定位器为何稳定、歧义或脆弱 | USR 编号与来源 |
| 语义依据 | 角色、可访问名称、测试 ID 或无依据结构 | 适用性 |
| 维护影响 | 标记变化或本地化如何影响它 | 优先级与证据 |
| 验证动作 | 替换定位器前的最小检查 | 负责人与 NOT_RUN 边界 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“选择器发现”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕选择器发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| UI 来源 | DOM 快照、组件代码、可访问名称、角色和 data 属性 | 语义缺失要标出 |
| 测试代码 | 定位器、动作、断言、页面状态和辅助函数 | 不要只从选择器推断意图 |
| 变更证据 | diff、定位历史、失败截图和重跑 | 没有运行时证据就保持未验证 |
| 边界 | 浏览器、语言、响应式模式和 Owner 约定 | 范围要保留 |

可以这样调用：

~~~text
请使用 ui-test-selector-review Skill。

任务：复核设计系统按钮重构后的结账 UI 选择器。
输入材料：[组件代码、DOM 快照、可访问角色与名称、测试代码、失败截图和 diff]
范围：[结账提交、优惠券和错误控件]
限制：[不执行测试、不修改选择器]

输出 USR-## 发现，包含对象、问题、来源、证据状态、影响、负责人、关闭条件和验证方式。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：复核组件重构后的结账按钮

测试按第三个 `.btn` 元素定位提交按钮，但组件已经暴露可访问名称和稳定测试 ID。这个 Skill 应指出位置和样式依赖，建议验证语义定位器，并保留尚未执行测试这一事实。

复核可以从已有材料识别选择器质量候选，不能证明运行时稳定、覆盖完整或 UI 套件通过。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“选择器发现”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和选择器发现的具体对象 |
| 发现 | 选择器发现的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 选择器发现 | 定位器为何稳定、歧义或脆弱 | USR 编号与来源 |
| 语义依据 | 角色、可访问名称、测试 ID 或无依据结构 | 适用性 |
| 维护影响 | 标记变化或本地化如何影响它 | 优先级与证据 |
| 验证动作 | 替换定位器前的最小检查 | 负责人与 NOT_RUN 边界 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供组件和 DOM 证据、可访问名称与角色、测试代码、定位约定、变更历史、失败产物、浏览器和语言范围。语义缺失时保持未评估。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 只因为选择器短或当前 DOM 能通过就选它。
2. 使用可见文本，却不考虑本地化和重复名称。
3. data-testid 看起来稳定，就把它当成测试有行为价值的证明。

## FAQ

### data-testid 总是最好吗？

不一定。唯一且有意设计的用户语义优先；当组件需要明确自动化契约时再使用测试 ID。

### 这个 Skill 会修改测试代码吗？

不会。它提供复核发现和验证动作，实现属于单独的变更。
