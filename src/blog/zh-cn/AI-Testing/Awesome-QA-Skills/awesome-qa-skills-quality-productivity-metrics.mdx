测试用例数和关闭工单数可以让忙碌的团队看起来很高产，但用户风险可能正在上升。生产力指标要先问：什么有价值的质量信号变了，条件是什么，代价又是什么？

## 为什么需要这个 Skill

Quality Productivity Metrics Skill 把质量指标与交付指标放在一起看，帮助团队区分流程证据和个人活动，暴露归因限制，并设计更难被刷数的复核方式。

## Skill 用来做什么

本文关注指标是否描述系统结果，不把可见动作数量当成结论。

当团队要评估流程或工具变化后的 QA 流程、设计工程记分卡，或者复核生产力结论是否有质量结果支撑时，使用这个 Skill。它不负责给个人排名，也不把活动数量直接变成发布决定。

结果要写清质量指标、交付指标、分母、归因限制、刷数风险、证据状态，以及分析之外仍需人工决定的事项。

当团队想知道执行更快、自动化更多或分诊更短，是否改善交付且没有增加线上逃逸风险时，使用这个 Skill。

## 它不做什么

质量生产力指标 Skill 可以组织质量信号的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 团队学习，不是排名 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“质量信号”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕质量信号，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

在请求判断前先列出已有材料。缺口可以保留，但状态必须可见。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 评估变化 | 一次让两个产品团队排队时间缩短的 CI 改造 | 不要把所有后续变化都归因给它 |
| 质量与交付事件 | 反馈时长、线上缺陷、flaky 重跑、发布和返工 | 没有的事件保留为未评估 |
| 分母与队列 | 运行、发布、变更文件、用户或固定团队周期 | 拒绝不匹配的分母 |
| 使用边界 | 团队学习、计划还是薪酬场景 | 草稿指标不能直接惩罚个人 |

可以这样调用：

~~~text
请使用 quality-productivity-metrics Skill。

任务：评估 CI 并行化是否改善结账和商品目录团队的 QA 生产力，同时没有增加线上逃逸风险。
输入材料：[前后窗口、运行事件、排队时间、重跑、发布、缺陷和变更范围]
范围：[两个团队和指定流水线]
限制：[缺少事故关联、发布量不同、隐私要求]

分开质量指标、交付指标、分母、归因限制、刷数风险和人工决策。不要把活动数量变成员工分数。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：评估 CI 变快，不要庆祝重跑数量增加

并行化后反馈中位数从 28 分钟降到 12 分钟，但重跑翻倍，线上缺陷也没有关联到发布。这个 Skill 可以报告流程速度改善已有证据，同时把质量影响标为未评估；下一步应检查 flaky 原因和发布关联，再判断改造价值。

结果只能说明给定队列和事件支持了什么，不能证明个人努力、单一改造的因果影响，也不能证明更短反馈一定有价值。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“质量信号”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和质量信号的具体对象 |
| 发现 | 质量信号的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 团队学习，不是排名 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供可比前后窗口、流水线和发布标识、事件定义、变更范围及混杂因素。说明结果用于计划、团队学习还是受治理的其他决策。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、提交数或关闭工单数直接当作生产力分数。
2. 比较风险、发布量或分母定义不同的团队。
3. 忽略 flaky 重跑、人员变化和范围缩减，就把工具改造认定为因果原因。

## FAQ

### 这个 Skill 能输出团队排名吗？

它可以整理可比证据，但排名是另外的治理决定。先暴露不确定性和刷数风险，再由负责人决定是否用于评价。

### 如果质量数据缺失怎么办？

保留生产力和质量信号的区分，把缺失部分标为未评估，并给出最小的关联或抽样动作。
