测试用例数和关闭工单数可以让忙碌的团队看起来很高产，但用户风险可能正在上升。生产力指标要先问：什么有价值的质量信号变了，条件是什么，代价又是什么？

## 为什么需要这个 Skill

质量生产力指标 Skill 把质量结果和交付流程放在同一份分析里，帮助团队区分系统表现与个人活动，记录归因限制，并检查指标是否容易被刷高。

## Skill 用来做什么

本文关注指标是否描述系统结果，不把可见动作数量当成结论。

当团队评估流程或工具变化、设计工程记分卡，或想确认更快执行、更多自动化和更短分诊是否影响交付质量时，可以使用这个 Skill。它不会给个人排名，也不会把活动数量直接变成发布决定。

结果要写清质量指标、交付指标、分母、归因限制、刷数风险、证据状态，以及分析之外仍需人工决定的事项。

## 它不做什么

它可以整理质量与交付指标、证据来源和下一步检查，但不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

复核重点是质量结果、交付速度和统计口径能否对应起来，不能把动作量直接折成分数。可以先按源 Skill 的输出字段整理一张检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 团队学习，不是排名 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始比较前，先把材料按六种证据状态整理。缺少发布关联或可比时间窗口不等于流程没有改善，但会限制质量结论。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

不要把观察到的结果、因果推断、建议和人工决策写成同一句结论：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

在请求判断前先列出已有材料。缺口可以保留，但状态必须可见。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 评估变化 | 一次让两个产品团队排队时间缩短的 CI 改造 | 不要把所有后续变化都归因给它 |
| 质量与交付事件 | 反馈时长、线上缺陷、不稳定测试重跑、发布和返工 | 没有的事件保留为未评估 |
| 分母与队列 | 运行、发布、变更文件、用户或固定团队周期 | 拒绝不匹配的分母 |
| 使用边界 | 团队学习、计划还是薪酬场景 | 草稿指标不能直接惩罚个人 |

可以这样调用：

~~~text
请使用 quality-productivity-metrics Skill。

任务：评估 CI 并行化是否改善结账和商品目录团队的 QA 生产力，同时没有增加线上逃逸风险。
输入材料：[前后窗口、运行事件、排队时间、重跑、发布、缺陷和变更范围]
范围：[两个团队和指定流水线]
限制：[缺少事故关联、发布量不同、隐私要求]

分开质量指标、交付指标、分母、归因限制、刷数风险和人工决策。不要把活动数量变成员工分数。
~~~

### 分析

先根据输入、检查矩阵和证据状态整理判断，再进入发现；缺失材料保留为缺口。

### 发现

#### 聚焦例子：评估 CI 变快，不要庆祝重跑数量增加

假设输入给出一个前后对比：并行化后反馈中位数从 28 分钟降到 12 分钟，重跑次数翻倍，但线上缺陷没有关联到发布。若原始 CI 记录支持这些数字，流程速度变化可以报告为已有证据；质量影响仍应标为未评估。下一步要查明重跑原因并补齐发布关联，再判断这项改造带来的整体价值。本例是分析方法示意，不代表本站实际测量结果。

这组数据只能支持对给定队列和事件的判断，不能衡量个人努力，也不能单独证明并行化造成了变化。若更短反馈伴随更多误报或重跑，是否有价值仍要结合后续成本判断。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

沿用上面的示例，若只提供了前后汇总数字，没有原始运行记录或缺陷与发布的关联，发现可以这样写。它说明结论还缺哪类依据，不把“未关联”直接说成质量恶化。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 两个团队、指定流水线，以及前后对比窗口；实际版本和范围以输入材料为准 |
| 发现 | 反馈时间缩短、重跑增加，但现有汇总无法说明质量是否受影响 |
| 证据状态 | 若未提供 CI 运行记录和发布/缺陷关联，流程汇总与质量影响应分别标注证据状态；质量部分保持 `unassessed` |
| 影响 | 更快反馈可能减少等待，但重跑增加会带来额外排查成本；不能据此给个人或团队排名 |
| 负责人和待决策项 | 流水线负责人核对运行口径，质量负责人确认缺陷归属和结果用途 |
| 动作与关闭条件 | 提供可比队列、重跑原因和发布关联；结论能回到来源，未解释的质量缺口单独保留 |
| 验证 | 用同一服务范围和可比较窗口复算反馈时长与重跑情况，保留来源查询及发布关联检查结果 |

记录的目的，是让接手的人知道还缺什么材料、谁来确认，以及哪项检查可能改变当前判断。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 团队学习，不是排名 |

每条结论都要能回到来源和证据状态，并指出下一步。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补空白。

### 下一步路由

按缺口安排后续工作：

| 缺口 | 下一步负责人 | 要解决的问题 |
| --- | --- | --- |
| 前后队列或窗口不可比 | 流水线负责人 | 对齐范围、事件定义和统计窗口，再重算交付指标 |
| 质量结果未关联到发布或变更 | 质量或数据平台负责人 | 补上可追溯关系，或明确质量影响暂时无法评估 |
| 结果准备进入团队评价 | 业务与治理负责人 | 审核用途、隐私和刷数风险；分析结果本身不是排名批准 |

交接时保留来源、证据状态和验证动作，不能让下一阶段把相关性当成因果结论。

## 怎样准备更好的输入

提供可比前后窗口、流水线和发布标识、事件定义、变更范围及混杂因素。说明结果用于计划、团队学习还是受治理的其他决策。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、提交数或关闭工单数直接当作生产力分数。
2. 比较风险、发布量或分母定义不同的团队。
3. 忽略不稳定测试重跑、人员变化和范围缩减，就把工具改造认定为因果原因。

## 常见问题

### 这个 Skill 能输出团队排名吗？

它可以整理可比证据，但排名是另外的治理决定。先暴露不确定性和刷数风险，再由负责人决定是否用于评价。

### 如果质量数据缺失怎么办？

保留生产力和质量信号的区分，把缺失部分标为未评估，并给出最小的关联或抽样动作。
