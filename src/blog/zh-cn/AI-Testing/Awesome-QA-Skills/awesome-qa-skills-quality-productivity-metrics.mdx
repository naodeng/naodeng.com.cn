测试用例数和关闭工单数可以让忙碌的团队看起来很高产，但用户风险可能正在上升。生产力指标要先问：什么有价值的质量信号变了，条件是什么，代价又是什么？

## 为什么需要这个 Skill

质量生产力指标 Skill 把质量结果和交付流程放在同一份分析里，帮助团队区分系统表现与个人活动，记录归因限制，并检查指标是否容易被刷高。

## Skill 用来做什么

本文关注指标是否描述系统结果，不把可见动作数量当成结论。

当团队评估流程或工具变化、设计工程记分卡，或想确认更快执行、更多自动化和更短分诊是否影响交付质量时，可以使用这个 Skill。它不会给个人排名，也不会把活动数量直接变成发布决定。

结果要写清质量指标、交付指标、分母、归因限制、刷数风险、证据状态，以及分析之外仍需人工决定的事项。

## 它不做什么

它可以整理质量与交付指标、证据来源和下一步检查，但不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

复核重点是质量结果、交付速度和统计口径能否对应起来，不能把动作量直接折成分数。可以先按源 Skill 的输出字段整理一张检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 可用于团队学习；排名需另行治理审批 |
| 输出格式 | 是否需要表格、CSV、JSON 或工单字段 | 保留发现字段；机器读取前确认 schema、枚举值、必填字段和证据来源 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始比较前，先把材料按六种证据状态整理，并检查材料是否完整、来源是否可信、时间是否有效、样本是否可比。发布关联或可比时间窗口缺失会限制质量结论。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

每个质量信号都要分开写清四层内容：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

源 Skill 附有一组合成样例，用来比较投入、已验收产出、质量和可比性。它只用于演示，不代表真实团队测量结果。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 基线 | 100 小时完成 100 项已验收任务，出现 1 个逃逸缺陷 | 明确队列范围和任务单位 |
| P-1 候选结果 | 拆分后有 200 行用例，但仍是 100 小时完成 100 项已验收任务，出现 5 个逃逸缺陷 | 不要把行数当成已验收产出 |
| P-2 候选结果 | 80 小时完成 100 项已验收任务，出现 1 个逃逸缺陷；返工情况可比，验收证据完整 | 没有提供的质量或投入证据保留为缺口 |
| P-3 对比 | 只按用例数给支付团队和文案团队排名 | 没有匹配任务和背景时标为 `NOT_COMPARABLE` |
| 样例边界 | 基线、P-1 和 P-2 在团队、窗口和复杂度上匹配；样例为合成数据 | 不要推广到其他团队，也不要据此排名 |

可以这样调用：

~~~text
请使用 quality-productivity-metrics Skill。

任务：复核这组匹配的 QA 工作样例是否支持生产力提升结论。
输入材料：[已验收任务、投入小时、逃逸缺陷、拆分用例、返工和验收证据]
范围：[匹配的团队、时间窗口和任务复杂度]
限制：[仅为合成样例、因果背景不完整、不用于个人排名]
成功标准：[结论不超出匹配样例能够支持的范围]
排除事项：[个人排名或未经授权的奖励决定]

计算每小时已验收任务数，对照质量证据，标出没有依据或不可比较的结论，并说明仍然未知的内容。不要把用例行数或活动量变成员工分数。
~~~

### 分析

先平衡投入、已验收产出、逃逸缺陷和返工，再写发现。缺失证据要保留为缺口，并且只比较样例中匹配的队列。

### 发现

#### 计算示例：对照已验收产出、投入和逃逸缺陷

基线的已验收任务吞吐量为 **100 / 100 = 每小时 1 项任务**。P-1 也在 100 小时内交付 100 项已验收任务，所以把用例拆成 200 行没有让已验收产出或吞吐量翻倍。它有 5 个逃逸缺陷，基线是 1 个；这也与“质量更好”的说法不符。

P-2 用 80 小时完成相同的 100 项已验收任务，吞吐量是 **100 / 80 = 每小时 1.25 项任务**，在这组匹配样例中高出 25%。样例还显示两个队列都出现 1 个逃逸缺陷、返工情况可比且验收证据完整，因此可以说这组样例观察到工时效率改善。P-3 只按用例数比较支付和文案工作，无法支持排名。

这些计算不能证明某个工具或流程变化造成了结果，也不能据此给个人或团队排名。

| 候选结论 | 复核结果 |
| --- | --- |
| P-1 因为拆分出 200 行用例，所以生产力翻倍 | `UNSUPPORTED`；投入和已验收产出仍是 100 小时完成 100 项任务，逃逸缺陷从 1 个增加到 5 个 |
| P-2 支持观察到工时效率改善 | `SUPPORTED`；80 小时完成 100 项已验收任务，1 个逃逸缺陷、返工可比且验收证据完整 |
| P-3 按用例数给支付团队和文案团队排名 | `NOT_COMPARABLE`；比较依据没有匹配工作，也没有建立有效分母 |

#### 示例发现：交接一项缺少依据的结论

| 字段 | 示例写法 |
| --- | --- |
| 发现 | `QPM-01`：P-1 没有显示生产力翻倍；已验收任务吞吐量未变，样例中的逃逸缺陷增加 |
| 来源与触发条件 | 匹配团队、窗口和复杂度的脱敏合成样例；当结论依据拆分后的用例行数时触发复核 |
| 预期问题 | 按行数而非已验收工作计数，可能虚增产出，同时掩盖质量信号变差 |
| 证据状态 | 样例计算为 `known`；这组数据是合成样例，不是真实团队的测量结果 |
| 影响与优先级 | 该结论可能误导计划或评价；没有业务影响分级依据，优先级保持 `NOT_SCORED` |
| 负责人和待决策项 | 质量与交付指标负责人确认任务验收、逃逸缺陷定义和结果用途 |
| 动作与关闭条件 | 对拆分用例去重，按每小时已验收任务数计算，并为匹配队列保留缺陷与返工证据 |
| 验证 | 用有版本的记录重新计算，并追溯已验收任务和逃逸缺陷来源；不要比较或排名不匹配的工作 |
| 停止条件 | 任务验收、复杂度或质量证据不可比时，不将结果用于排名或奖励；结果用途交由相应负责人确认 |

这条 QPM 发现把来源、触发条件、预期问题、证据状态、影响、负责人、关闭条件和验证方式放在一起。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

真实项目的发现关闭前，按写明的方式执行验证并保留原始产物。合成样例只演示计算，不能验证团队的线上数据链路。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 质量信号 | 变化是否影响用户风险或缺陷发现 | 证据与来源 |
| 交付信号 | 可比队列下反馈是否变快 | 窗口与分母 |
| 归因限制 | 还可能解释变化的其他因素 | 候选混杂因素 |
| 使用边界 | 结果怎样安全使用 | 可用于团队学习；排名需另行治理审批 |

每条结论都要能回到来源和证据状态，并指出下一步。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补空白。

### 下一步路由

按缺口安排后续工作：

| 缺口 | 下一步负责人 | 要解决的问题 |
| --- | --- | --- |
| 前后队列或窗口不可比 | 流水线负责人 | 对齐范围、事件定义和统计窗口，再重算交付指标 |
| 质量结果未关联到发布或变更 | 质量或数据平台负责人 | 补上可追溯关系，或明确质量影响暂时无法评估 |
| 结果准备进入团队评价 | 业务与治理负责人 | 审核用途、隐私和刷数风险；分析结论不能单独授权排名 |

交接时保留来源、证据状态和验证动作，不能让下一阶段把相关性当成因果结论。

## 怎样准备更好的输入

提供可比前后窗口、流水线和发布标识、事件定义、变更范围及混杂因素。说明结果用于计划、团队学习还是受治理的其他决策。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把测试数、提交数或关闭工单数直接当作生产力分数。
2. 比较风险、发布量或分母定义不同的团队。
3. 忽略不稳定测试重跑、人员变化和范围缩减，就把工具改造认定为因果原因。

## 最佳实践

- 只比较任务、产品风险、复杂度、工具和时间窗口相匹配的样本。把投入或成本与已验收产出、缺陷或逃逸、等待时间和返工放在一起看。
- 对拆分或合并的用例去重，并核实验收情况。用例数或提交数不等于交付价值。
- 检查高难度测试是否被移除、缺陷是否漏报、工作是否延期以及测试重跑情况。缺少质量或返工证据时，生产力结论应保持未评估。
- 指标变化用于触发调查或最小可验证实验，并记录实验条件、版本、来源和证据；不能自动变成因果结论、奖励或排名决定。

## 新手入门：复核一项流程改动

1. 选一项改动，并准备任务、复杂度和时间窗口可比的基线。
2. 提供投入、已验收产出、质量结果、等待或返工，以及对应的来源记录。
3. 请 Skill 检查分母、归因限制和刷数风险，再给出最小验证动作。先用于团队学习，再考虑是否进入受治理的其他用途。

## 把生产力指标放进质量循环

![生产力证据循环：在可比范围内检查验收产出、投入和质量，调查其他影响因素，调整流程后重新测量](/images/blog/ai-testing-quality-loops/quality-productivity-metrics-quality-loop-zh.svg)

日常 QA 中，AI 生成的用例先是候选项，不能直接算作已验收产出。先按需求复核、去重并确认验收，再记录它在哪个构建上运行。比较节省的投入与逃逸缺陷、被移除的高难度测试、重跑、延期工作和返工。把发现带入下一轮测试集或流程实验，不要只凭生成行数宣称生产力提高。

## 常见问题

### 这个 Skill 能输出团队排名吗？

它可以整理可比证据，但排名是另外的治理决定。先暴露不确定性和刷数风险，再由负责人决定是否用于评价。

### 如果质量数据缺失怎么办？

保留生产力和质量信号的区分，把缺失部分标为未评估，并给出最小的关联或抽样动作。

### AI 生成更多测试用例，是否代表团队生产力提高？

不代表。生成结果要经过复核、去重、验收和执行才是有效产出。衡量时还要把这部分投入与已验收任务、质量结果、重跑和返工一起看，不能只数生成的行数。
