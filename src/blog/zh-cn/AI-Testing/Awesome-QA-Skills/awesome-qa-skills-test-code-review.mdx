测试通过，不代表它真的保护了产品。弱断言、共享夹具、隐藏的时间依赖和意外网络调用，都会让绿色结果难以信任。

## 为什么需要这个 Skill

Test Code Review Skill 根据提供的测试代码和证据识别断言、隔离、夹具、确定性和可维护性风险，产出 TCR-## 发现；它不执行测试，也不把候选数量叫作覆盖。

## Skill 用来做什么

本文会追问：这个测试真的会在它声称保护的缺陷出现时失败吗？

在测试代码变更、flaky 调查、夹具重构或 CI 复核中，如果团队需要有证据的测试工程问题和最小验证动作，使用这个 Skill。

TCR 发现要写清测试对象、前置条件、问题、来源证据、验证、影响、优先级、负责人、关闭条件和证据状态。

当测试套件发生变化，需要在相信新的绿色运行前复核可靠性、隔离性或维护成本时，使用这个 Skill。

## 它不做什么

测试代码评审 Skill 可以组织断言发现的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 断言发现 | 断言是否能发现目标缺陷 | TCR 编号与来源 |
| 隔离发现 | 共享状态、网络、时间或顺序依赖 | 证据状态 |
| 确定性发现 | 夹具、随机性、时钟或重试不稳定 | 需要复现 |
| 验证动作 | 相信测试前的最小安全检查 | 负责人和方法 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“断言发现”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕断言发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 测试代码与 diff | 断言、夹具、初始化、mock、依赖和改动行 | 未提供的代码标出范围外 |
| 行为契约 | 需求、预期结果、错误规则和数据边界 | 缺失预期不要自推 |
| 运行证据 | 失败日志、重跑、耗时、环境和 CI 配置 | 静态复核与运行分开 |
| 维护上下文 | Owner、重复、辅助 API 和历史失败 | 未知历史要记录 |

可以这样调用：

~~~text
请使用 test-code-review Skill。

任务：复核一个新结账 API 测试：它使用共享数据库夹具，并且只断言 HTTP 200。
输入材料：[diff、需求、夹具代码、mock 配置、CI 运行日志和失败历史]
范围：[合并前 API 测试套件]
限制：[不执行测试、不修改代码]

输出 TCR-## 发现，包含问题、来源证据、影响、负责人、关闭条件、验证方式和证据状态。不要把候选发现写成覆盖或通过结论。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：质疑只断言 200 的绿色 API 测试

接口即使响应体有错误码也返回 200，共享夹具还把记录留给后续测试。这个 Skill 应指出弱断言和隔离风险，要求确认契约中的错误语义，并建议验证夹具清理。不能直接运行或宣布套件失败。

复核可以从已有材料中产出测试工程候选，不能在没有执行证据时证明缺陷存在、测试通过或覆盖完整。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“断言发现”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和断言发现的具体对象 |
| 发现 | 断言发现的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 断言发现 | 断言是否能发现目标缺陷 | TCR 编号与来源 |
| 隔离发现 | 共享状态、网络、时间或顺序依赖 | 证据状态 |
| 确定性发现 | 夹具、随机性、时钟或重试不稳定 | 需要复现 |
| 验证动作 | 相信测试前的最小安全检查 | 负责人和方法 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供变更测试、夹具与辅助代码、行为契约、CI 配置、相关运行记录和失败历史。没有运行证据时，运行结论标记 NOT_RUN。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 把方法名或测试数量当成目标行为已被检查的证明。
2. 没有需求或 API 契约就只复核断言。
3. 每个测试使用不同标签，就假设共享夹具已经隔离。

## FAQ

### 这个 Skill 会直接修改测试代码吗？

不会。它识别可追溯复核发现和验证动作，代码修改需要单独的实现请求。

### 静态断言复核能证明测试能抓住缺陷吗？

不能。它可以发现弱断言并提出检查，带有实际失败条件的执行是另一类证据。
