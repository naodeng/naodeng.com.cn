Agent 完全按照用户要求执行，也可能是错的——如果用户本来就没有权限查看那份文档。

Agent 权限测试用于验证 Agent 在读取数据或调用工具前，是否同时判断身份、角色、租户、资源和动作。

当团队需要围绕“身份绑定、最小权限、资源范围、拒绝行为和可审计性”工作时，使用 Agent 权限测试 Skill。它把模糊的测试请求变成有来源、有假设、有输出字段和下一步动作的受限分析。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦 Agent 权限测试。

## Agent 权限测试 Skill 用来做什么


它适合这些场景：团队需要重复检查身份绑定、最小权限、资源范围、拒绝行为和可审计性；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

好的结果会把身份绑定、最小权限、资源范围、拒绝行为和可审计性接回来源和验证动作。设计清单不能直接写成通过结论。

## 用一份项目材料开始

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 身份矩阵 | 用户、角色、租户、资源和允许动作 | 策略含糊时指定负责人 |
| Agent 表面 | Prompt、工具 Schema、授权中间件和回退路径 | 不要把 Prompt 当作权限系统 |
| 证据 | 允许与拒绝日志、资源 ID、策略版本和用户可见响应 | 只有礼貌拒绝而没有审计记录仍不完整 |

可以这样调用：

```text

请使用 agent-permission-testing Skill。

任务：HR 助手收到导出薪资记录的请求，但调用者只有团队级员工信息权限
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。

```

## Agent 权限测试 要交付什么

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 授权判断 | 身份、资源、动作、策略和结果 | allowed、denied 或 unresolved |
| Agent 行为 | 是否停止、解释或尝试更低权限路径 | 不能出现越权绕过 |
| 审计要求 | 必须记录和保留什么 | 负责人和保留边界 |

没有运行记录、查询结果或原始产物时，不要写“已通过”。好的权限测试会独立改变身份和资源，并检查拒绝后的下一步——安全拒绝、澄清还是升级，而不只看 HTTP 状态码。

## 在项目里跑一轮

先从一个边界清楚的小回合开始：HR 助手收到导出薪资记录的请求，但调用者只有团队级员工信息权限。用团队经理、HR 管理员和外包人员三种身份发送同一个薪资导出请求，保持资源 ID 不变，再比较策略判断、工具调用、响应文本和审计事件。外包人员不应该因为“过滤后导出”而意外拿到数据，操作应在取数前被拒绝。

交接产物要同时保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

## 如何把初版做得更好

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从“看起来完整的清单”推进到可用评审。


## 容易踩的坑

1. 依赖模型记住角色规则。
2. 只测试允许访问。
3. 拒绝后允许调用另一个没有日志的替代工具。

## 常见问题

### 有拒绝响应就够了吗？

不够。还要确认没有取回受保护数据，并且拒绝可以追溯到身份和策略版本。



### 角色矩阵缺失怎么办？

停在策略缺口处，指定决策负责人，不要擅自补一个默认允许或默认拒绝规则。
