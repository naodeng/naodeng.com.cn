开始编码前，团队往往已经能指出哪些行为可能受影响，但还没有 Diff 可以证明影响范围。编码完成后，真实改动又可能与最初设想不同。回归分析需要保留这两个时间点的区别。

change-to-regression 支持两个阶段：编码前根据提案列出回归护栏和待验证假设，编码后根据实际 Diff 或 base/head 提交分析回归范围。前一阶段的结论是候选，后一阶段要对应真实差异；两类结论的证据来源应分开。

## 编码前：记录护栏和待验证假设

提供变更目标、已知行为、需求或设计材料，以及可能受影响的契约。没有 Diff 或提交 SHA 是正常情况。输出应标记为编码前分析，区分项目事实、候选影响和待验证假设。

可先约定一组观察项：预期行为、可能受影响的调用方、应保持不变的行为、需要新增或补跑的测试。待代码完成后，再逐项核对哪些假设被实际改动支持。

## 编码后：从真实差异追到测试

提供精确的 base/head、完整 Diff 和可访问的项目证据。分析应从改动符号、数据或接口追到消费者、业务行为和现有测试，再按风险划分：

| 结论 | 含义 |
| --- | --- |
| 必须执行 | 风险或契约要求较高，当前证据支持执行 |
| 可以延后 | 有理由暂缓，但要注明残余风险、负责人或补测条件 |
| 排除 | 本轮不执行，并说明排除依据 |

缺少调用关系、测试映射或运行证据时，应保留未知项或扩大候选范围，不能只看文件名就断言影响结束。计划列表也不等于已经执行；要运行并报告结果，需要单独的执行证据。

## 让 AI 帮你比较两个时间点

AI 可以帮助梳理提案里的风险，并在代码变化后找出与之相符或不符的路径。每次都要保留输入版本和证据来源。

~~~text
请使用 change-to-regression 评估这次变更。

阶段：[PRE_CHANGE 或 POST_CHANGE]
变更目标与已有行为：[需求或设计材料]
代码证据：[编码前写“尚无 Diff”；编码后给 base/head 和完整 Diff]
测试映射与限制：[已有用例、环境、时间和权限]

编码前请输出候选护栏、假设和待验证项。
编码后请依据实际差异输出必须执行、可延后和排除的回归范围。
每项结论附来源、状态与理由；区分分析计划和真实运行结果。
不要执行对外写入，除非我明确授权。
~~~

改动完成后，回看编码前记录：哪些风险兑现了，哪些被实际实现排除，哪些需要新增测试。这个对照还能暴露最初分析中遗漏的依赖。

### 没有 Diff 时能开始吗？

可以，作为编码前护栏。需将影响标成候选或假设，不应声称这是完整回归范围。

### 什么时候可以说测试通过？

只有拿到对应版本、环境、命令或测试记录及真实结果后，才能报告实际执行状态。静态分析或测试计划不能证明通过。

### 这个 Skill 可以直接改动项目吗？

它默认只读，主要产出风险分析与测试范围。任何对外写入或改变项目状态的操作都需要明确授权。
