PR 审查看起来像检查改动，但真正能帮助团队决策的结果还要回答：哪些行为有风险、测试是否覆盖这些变化、哪些结果有实际证据、剩余问题由谁处理。

pr-quality-review 把代码、测试影响、测试有效性和质量证据放在同一份审查里。它默认只读；没有运行记录时，不会把静态推断写成测试通过。

## 先把审查输入固定下来

提供 PR 链接或材料、base/head、完整 Diff、相关需求和已有测试记录。还要说明审查范围、团队严重度定义和本次权限边界。输入不全时可以做受限审查，但缺口要保留在报告里。

按证据逐步检查：

1. 改了哪些行为、接口或数据约束，代码变更是否符合预期。
2. 哪些调用方和用户路径可能受影响，测试选择有没有覆盖这些行为。
3. 断言是否真正验证预期，负向路径、边界和依赖替身是否可信。
4. CI 或本地测试有哪些运行记录、版本和结果，哪些检查没有证据。
5. 尚存风险、阻塞项和下一步分别由谁跟进。

## 区分分析判断和运行状态

如果没有提供测试或 CI 结果，执行状态应保持 UNKNOWN；只有材料明确说某项没有执行时，才标记 NOT_RUN。尝试过但结果异常、记录失效或无法判断时，不能把它改写成通过。

每个发现都应能回到 PR 或仓库材料。不要引用内部记忆、对话日志或没有交给审查者的来源。若检查点已过期，保留标准状态 STALE。静态代码分析可以帮助发现风险，但不等于运行证据。

| 报告内容 | 应包含 |
| --- | --- |
| 发现 | 位置、严重度、行为影响和证据 |
| 测试影响 | 受影响路径、覆盖情况及选择依据 |
| 执行证据 | 版本、命令或 CI 记录、结果和来源 |
| 信息缺口 | 当前无法判断的内容与需要补充的材料 |
| 交接 | 下一步、负责人或需人工接受的风险 |

## 让 AI 做证据导向的初审

AI 可以先读 Diff、测试和 PR 描述，列出需要复核的地方。审查者仍需核对每条发现的代码位置和运行记录，尤其避免把“看起来合理”升级为“已验证”。

~~~text
请使用 pr-quality-review 审查这个 PR。

PR 和版本：[链接、base/head 或提交 SHA]
材料：[完整 Diff、需求、测试和 CI 记录]
审查范围：[本次包含与排除项]
团队严重度定义：[提供规则；没有时请说明未知]

按代码风险、测试影响、测试有效性和证据输出发现。
每项判断引用可访问的材料。没有运行记录时标为 UNKNOWN；
只有明确未执行时才标 NOT_RUN。区分事实、推断和待办。
保持只读，不要修改 PR 或外部系统。
~~~

使用前把源文件和必要材料提供给 AI。没有明确的写入授权时，审查结果应停留在分析和建议。

### 它和 PR 测试影响分析有什么区别？

pr-test-impact-analysis 重点把代码变化映射到受影响行为和测试范围；pr-quality-review 还检查代码风险、测试断言有效性、运行证据和最终交接。两者可以串联，但职责不同。

### CI 绿了，PR 就可以合并吗？

CI 结果只是证据的一部分。还要核对构建与 PR 版本一致、相关检查实际执行、风险和团队规则得到处理。

### AI 可以替我批准 PR 吗？

不能。它可以整理发现和证据，合并、风险接受和发布决定仍由有权限的负责人作出。
