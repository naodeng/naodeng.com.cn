会话安全经常在状态转换中失败：登录之后、改密之后、第二台设备出现时，或者会话应该过期却仍然保留权限。

## 为什么需要这个 Skill

Session-Security Testing Skill 为会话创建、固定、过期、撤销、并发和跨设备边界准备有证据边界的场景，同时把设计声明与执行后的安全结果分开。

## Skill 用来做什么

本文关注的会话规则只有在生命周期和失效边界可观察时才真正有用。

当你要在隔离环境使用合成账号复核会话行为时，使用这个 Skill。它识别安全问题和验证动作，不会登录生产、读取凭证或宣布系统安全。

结果要写清会话状态、角色与设备、触发条件、预期 token 或权限变化、证据、负责人、关闭条件和安全验证方式。

当认证改造、刷新 token 行为变化、退出或改密流程重做，或者跨设备策略不明确时，使用这个 Skill。

## 它不做什么

会话安全测试 Skill 可以组织生命周期场景的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 生命周期场景 | 会话状态、触发、角色和设备 | 来源与适用性 |
| 安全关注 | 意外权限、固定、旧权限或跨设备泄露 | 证据状态 |
| 预期边界 | 什么应过期、轮换、撤销或保留 | 策略与负责人 |
| 验证动作 | 安全重放和所需证据 | 合成账号与清理 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“生命周期场景”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕生命周期场景，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 会话模型 | 创建、刷新、过期、退出、改密和撤销规则 | 未文档化的转换保留问题 |
| 角色与设备 | 用户角色、浏览器/设备类型、并发和租户范围 | 缺失边界要标出 |
| Token 证据 | 脱敏声明、Cookie 标志、ID、时间戳和服务端记录 | 不要提供真实 token |
| 验证环境 | 合成账号、隔离 staging、日志和清理方案 | 不登录生产 |

可以这样调用：

~~~text
请使用 session-security-testing Skill。

任务：复核改密是否撤销 Web 和移动端会话，同时保留一个批准的恢复设备。
输入材料：[会话策略、token 元数据、改密流程、设备规则、staging 日志和合成账号]
范围：[Web 与移动端 staging]
限制：[不使用真实凭证、不访问生产]

覆盖创建、固定、过期、撤销、并发和跨设备边界，没有依据的安全结论保持 pending。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：检查 Web 和移动端的改密撤销

改密撤销了 Web Cookie，却让移动端 refresh token 继续可用。这个 Skill 应记录跨设备撤销缺口，保留已批准的恢复设备例外，并建议使用合成账号重放，同时记录 token 时间戳和服务端撤销证据。

复核可以准备安全场景和证据检查，不能在没有授权运行前证明漏洞利用成功、不存在漏洞或发布安全。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“生命周期场景”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和生命周期场景的具体对象 |
| 发现 | 生命周期场景的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 生命周期场景 | 会话状态、触发、角色和设备 | 来源与适用性 |
| 安全关注 | 意外权限、固定、旧权限或跨设备泄露 | 证据状态 |
| 预期边界 | 什么应过期、轮换、撤销或保留 | 策略与负责人 |
| 验证动作 | 安全重放和所需证据 | 合成账号与清理 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供会话生命周期、token 类型、Cookie 和存储策略、角色/设备矩阵、改密/退出规则、环境、合成账号和清理方案。Token 值必须脱敏。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 只在一个浏览器测试退出，漏掉 refresh token 或移动端会话。
2. 只看 token 过期时间，不检查服务端撤销和资源授权。
3. 用真实账号或线上 token 证明安全边界。

## FAQ

### Token 生命周期短就够安全吗？

不够。过期、轮换、撤销、存储、并发和资源检查共同决定会话安全。

### 可以把生产账号拿到 staging 复用吗？

不可以。使用明确角色的合成账号并清理，不要跨环境搬运真实凭证。
