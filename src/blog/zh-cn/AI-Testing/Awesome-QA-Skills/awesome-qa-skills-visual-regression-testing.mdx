截图差异只是观察，不是缺陷结论。字体、视口、数据、动画、浏览器渲染和有意设计变化，都会决定比较是否有意义。

## 为什么需要这个 Skill

Visual Regression Testing Skill 围绕基线、视口、字体、数据、差异阈值、有意变化和历史差异设计 VRT-## 候选，不执行视觉测试，也不把基线文件当成通过证据。

## Skill 用来做什么

本文关注的是有意义的差异：它需要受控基线，以及对有意变化的明确决定。

当你要为页面或组件定义视觉回归候选和比较条件时，使用这个 Skill。它让选择理由、适用性、证据缺口和最小验证动作可见。

VRT 发现要写清视觉对象、基线版本、视口和浏览器、字体与数据条件、预期变化、差异问题、负责人、关闭条件和验证方式。

当设计系统、响应式布局或本地化发生变化，或者截图流水线需要有依据的视觉比较时，使用这个 Skill。

## 它不做什么

视觉回归测试 Skill 可以组织视觉候选的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 视觉候选 | 页面/组件、状态、变体和风险 | VRT 编号与来源 |
| 比较条件 | 基线、视口、浏览器、字体、语言和数据 | 适用性 |
| 差异判断 | 预期、未解释或未评估变化 | 意图与证据 |
| 验证动作 | 最小截图或复核检查 | 负责人与 NOT_RUN 状态 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“视觉候选”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕视觉候选，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 页面与组件清单 | 关键页面、状态、主题和组件变体 | 缺失状态保持未评估 |
| 基线条件 | 修订、视口、浏览器、字体、语言、时区和数据 | 不同条件不要直接比较 |
| 预期变化 | 设计改动、批准意图和影响范围 | 有意与未知分开 |
| 差异证据 | 截图、阈值、区域、历史和复核人 | 差异文件不是结论 |

可以这样调用：

~~~text
请使用 visual-regression-testing Skill。

任务：为仪表盘主题改造准备视觉回归候选，覆盖浅色、深色、紧凑视口和中文语言。
输入材料：[页面清单、基线截图、设计 diff、字体、数据夹具、浏览器矩阵和阈值策略]
范围：[仪表盘卡片、表格、空状态和错误状态]
限制：[不执行截图、不批准差异]

输出 VRT-## 发现，包含对象、条件、预期变化、问题、证据状态、负责人、关闭条件和验证方式。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：复核主题改造，不要先怪字体

深色模式差异显示仪表盘表格换行，但基线使用了不同字体回退和不同长度数据。这个 Skill 应把字体与夹具差异和主题改造分开，要求受控基线条件匹配，在输入一致前保持差异未评估。

产物可以设计视觉比较候选，不能在没有受控截图和人工复核前证明视觉缺陷、像素级质量、无障碍或发布就绪。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“视觉候选”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和视觉候选的具体对象 |
| 发现 | 视觉候选的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 视觉候选 | 页面/组件、状态、变体和风险 | VRT 编号与来源 |
| 比较条件 | 基线、视口、浏览器、字体、语言和数据 | 适用性 |
| 差异判断 | 预期、未解释或未评估变化 | 意图与证据 |
| 验证动作 | 最小截图或复核检查 | 负责人与 NOT_RUN 状态 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供基线修订、页面状态、视口和浏览器、字体、语言、时区、数据夹具、阈值策略、有意设计范围和复核人。条件缺失时标为 blocked 或未评估。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 比较字体、数据、视口或语言不同的截图。
2. 把每个像素差异都当成产品缺陷。
3. 还没理解变化，就先更新基线让流水线变绿。

## FAQ

### 差异阈值应该全局只用一个数字吗？

不一定。阈值取决于渲染噪声、区域、组件和漏掉视觉变化的代价。

### 批准的设计变化可以自动接受吗？

只有在范围和复核规则明确时才可以。有意变化仍需要基线更新证据。
