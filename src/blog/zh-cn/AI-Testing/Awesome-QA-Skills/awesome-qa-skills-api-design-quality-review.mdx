一个 API 的 OpenAPI 文件可以看起来很整洁，却仍然让每个消费者猜测部分失败后会发生什么。

API 设计质量评审用于在实现或版本演进前检查 API 契约，把输入、输出、错误、权限、生命周期和消费者影响写到足够可验证。

当团队需要围绕“操作契约、错误模型、授权、幂等、兼容性和消费者影响”工作时，使用 API 设计质量评审 Skill。它把模糊的测试请求变成有来源、有假设、有输出字段和下一步动作的受限分析。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦 API 设计质量评审。

## API 设计质量评审 Skill 用来做什么


它适合这些场景：团队需要重复检查操作契约、错误模型、授权、幂等、兼容性和消费者影响；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

好的结果会把操作契约、错误模型、授权、幂等、兼容性和消费者影响接回来源和验证动作。设计清单不能直接写成通过结论。

## 先回到源 Skill

完整执行契约位于 [API 设计质量评审 提示词](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/api-design-quality-review/prompts/api-design-quality-review.md)。调用 Skill 前先阅读它；提示词定义了详细流程和输出契约。[源目录](https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/api-design-quality-review) 中还包含入口文件以及实际存在的配套资料。

入口文件重点约束操作契约、错误模型、授权、幂等、兼容性和消费者影响。写结论前先阅读配套提示词，并保留这个 Skill 的决策边界。

## 用一份项目材料开始

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 契约材料 | OpenAPI、请求与响应示例、状态码和版本策略 | 未定义字段列为缺口，不要猜 |
| 消费者上下文 | 移动端、Web、计费、重试行为和发布顺序 | 写出尚未咨询的消费者 |
| 风险边界 | 授权、幂等、状态变化和向后兼容 | 发布批准仍由负责人决定 |

可以这样调用：

```text

请使用 api-design-quality-review Skill。

任务：在移动端、Web 端和计费服务接入前，评审订阅取消 API
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。

```

## API 设计质量评审 要交付什么

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 契约发现 | 缺失、冲突、过期或不可验证的 API 规则 | API-##、影响和来源 |
| 消费者影响 | 客户端哪些行为会变得模糊或不安全 | 受影响消费者和版本 |
| 就绪动作 | 需要明确的字段、错误、策略或迁移决定 | 负责人和关闭证据 |

没有运行记录、查询结果或原始产物时，不要写“已通过”。好的评审会走一遍消费者主流程、一条失败路径和一次版本变化。它不会用接口数量来批准设计。

## 在项目里跑一轮

先从一个边界清楚的小回合开始：在移动端、Web 端和计费服务接入前，评审订阅取消 API。对取消订阅，需要定义订阅已经取消、计费服务不可用和请求重复时的行为。契约应该告诉消费者是重试、轮询、展示最终状态，还是请求人工介入。

交接产物要同时保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

## 如何把初版做得更好

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从“看起来完整的清单”推进到可用评审。


## 容易踩的坑

1. 只看 Schema，不走消费者流程。
2. 把 200 响应当成完整成功契约。
3. 把版本和重试行为留给实现者自行猜测。

## 常见问题

### 代码还没写可以评审吗？

可以，这正是它的用途：在契约选择变成兼容性负担之前发现不可验证或冲突的地方。



### 这个 Skill 会替团队决定 API 版本吗？

不会。它展示取舍与证据缺口，版本决定仍由负责人做。
