Skill 改一处，影响可能不止措辞：触发范围、输入要求、输出字段、限制条件和失败处理都可能改变。Skill 变更验证从实际 diff 出发，为受影响的行为选择检查，并明确证据能支持什么结论。它不会把配置检查说成运行时证明。

## 先按改动面选择检查

根据实际改动文件及其消费者分类。即使跑了全量检查，也要单独覆盖本次改动触及的路径。

| 改动范围 | 最少考虑的证据 | 证据能支持的结论 |
| --- | --- | --- |
| 入口、元数据、链接或目录 | 相关静态与结构检查；适用时检查独立安装副本 | 包结构有效、引用资源可解析；未验证实际行为 |
| Prompt、流程或输出契约 | 实际运行成功、缺材料和边界用例，并保留 judge 结果 | 仅限已运行的用例、版本、宿主和环境 |
| 解析、生成或安装脚本 | 原故障回归、有效对照，以及目标格式或工具执行 | 仅限实际覆盖的路径 |
| 发布建议 | 变更证据、版本、残余风险和授权决策记录 | AI 建议与正式批准分别报告 |

证据等级也要分开写：**Static** 检查文件和 frontmatter；**Structural** 检查配对、索引和 Eval 结构；**Configuration** 检查 `skill-up validate` 这类配置；**Evaluation** 记录实际 `skill-up run`、选中用例、运行元数据和 judge 结果；**Runtime** 记录 Skill 或 Prompt 在目标宿主上的实际行为；**Human review** 负责语义和风险判断。配置命令成功不代表 Evaluation 或 Runtime 已完成。

## 示例：修改 Skill 的触发描述

假设改动目标是让某个 Skill 用于 API 兼容性审查。先记录新旧版本与实际 diff，再用固定请求集验证：一条属于兼容性审查的请求、一条相邻的 API 任务，以及一条无关请求。如果宿主可以观察 Skill 选择结果，也要保存选择记录和最终输出。若新指令依赖接口规范或版本，再加入缺少这些材料的用例。

如果只检查了 frontmatter 并运行 `skill-up validate`，报告配置检查结果，同时把 Evaluation 和 Runtime 标为 `NOT_RUN`。没有对应运行和人工决策时，不要声称触发变准、Skill 已可靠，或改动可以用于生产。

如果改动涉及输出契约，测试样本要覆盖正常、缺材料和冲突三种输入。核对新版本是否仍输出必需字段、是否把未知状态保留下来、是否会把互相冲突的来源合并成一个确定答案；再用一条相邻但不适用的请求检查触发边界。记录旧版本与新版本在相同样本上的差异，避免只证明新增行为，却漏掉原有约束被删掉。

## 让报告可以复核

保留所选命令、版本、环境、Eval 用例、原始输出和 judge 状态。每个未执行的检查都写明原因及留下的风险。超时、认证缺失、过滤掉相关用例或 judge 失败，都不能当作全套通过。

```markdown
# 验证报告
## 变更分类
## 已执行检查
| 命令 | 证据等级 | 结果 |
## 未执行检查
| 项目 | 原因 | 风险 |
## 可以声称
## 不能声称
## 残余风险
```

明确写 `NOT_RUN` 能让下一位审查者看到未知项，不会把配置检查的绿灯误读成行为证明。

## 按任务交接

若改动本身存在歧义或规则冲突，先看 Skill 文案契约审查: https://inaodeng.com/zh-cn/qaskills/skill-prose-review/；若本次任务是清理过程残留，使用过程性文案清理: https://inaodeng.com/zh-cn/qaskills/skill-prose-trim/。完成获准的编辑后，再用 Skill 变更验证检查相应契约和示例是否仍成立。

安装命令：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/skill-engineering/skill-change-verification -g
```
