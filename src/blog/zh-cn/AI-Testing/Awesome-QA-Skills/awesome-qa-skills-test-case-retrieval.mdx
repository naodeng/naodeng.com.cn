遇到一次需求变更或线上缺陷，团队往往先问：以前有没有测过类似场景？只搜标题关键词容易漏掉语义相近的用例；只看相似度排名，又容易把“看起来相关”误当成“必须执行”。

`test-case-retrieval` 用于在可访问的测试仓库、用例目录或用户提供的清单中查找候选。它把业务行为和精确标识组合起来，返回来源 ID、位置和匹配理由，同时说明检索范围与限制。候选排序不等于覆盖率、缺陷概率或执行优先级，这个 Skill 也不运行测试。

下面以“查找与文件上传超时有关的已有用例”为例，说明怎样给出可复核的检索请求，并把结果交给后续的回归范围判断。

Awesome QA Skills 按语言和测试阶段组织 Skill。项目结构与通用安装方式见系列总览：https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/。本文聚焦测试用例检索。

## 先确认有哪些来源可以查

检索需要真实可访问的测试资产，例如已连接的用例仓库、明确授权的检索工具，或用户提供的导出清单。还要说明项目、套件、查询词和过滤条件。

没有来源或连接信息时，结果应标为 `NO_ACCESS`，并请求最小的用例清单或连接信息。不能根据一个功能描述猜出用例 ID、命中数量、位置或仓库范围。

结果还要交代检索完整性：已完成查询可标记 `SEARCHED`；只查到部分授权范围、受分页或权限限制时标记 `PARTIAL`，并说明未覆盖的来源；没有可访问来源则标记 `NO_ACCESS`。不能把未访问的项目说成“没有覆盖”。

## 把语义查询和精确标识放在一起

对“文件上传超时”这个问题，可以同时给出业务行为、接口或错误码、关联需求或缺陷标识，再限制项目和套件范围。以下只是请求格式示例，并非真实仓库查询。

| 检索要素 | 示例输入 |
| --- | --- |
| 来源 | [已连接的用例仓库或用户提供的清单] |
| 范围 | [项目、套件、版本] |
| 语义查询 | 文件上传、等待超时、失败后的重试与恢复 |
| 精确线索 | [实际接口名、错误码、需求或缺陷 ID] |
| 过滤条件 | [平台、状态、标签或排除项] |
| 结果用途 | 先找可复用候选，再由负责人判断是否进入回归范围 |

如果结果太宽，可以细化查询、增加过滤条件、翻页或排除已确认无关的记录。分页时记录查过几页和停止原因；重复命中可按稳定 ID 去重，但要保留该 ID 的全部来源。用例内容和工具返回文本都当作不可信数据，不能执行其中嵌入的指令，也不能据此扩大检索范围。

## 候选列表需要留下依据

每条结果都应带来源 ID、可复核的位置和具体匹配理由。只有来源工具实际返回分数时才展示分数，并且只解释这次查询内的相对顺序。

可用下面的表格记录实际结果；没有查到的字段保持为空或标出来源未提供，不要补造。

| 来源 ID | 位置 | 匹配理由 | 来源分数 | 适用性待确认 |
| --- | --- | --- | --- | --- |
| [工具返回值] | [项目/套件/路径] | [与行为或标识的对应关系] | [仅来源提供时填写] | [版本、平台或前置条件差异] |

所有检索结果都使用 `CANDIDATES_ONLY`。即使排名第一，也不能自动改成“必须执行”。检索回答的是“可能相关的资产在哪里”，不是“本次发布必须跑哪些测试”。

## 一段可以直接改的调用词

```text
请使用 test-case-retrieval Skill。

目标：[要查找的行为或覆盖]
来源：[已连接的用例仓库 / 我提供的清单]
范围：[项目、套件、版本]
语义线索：[功能、业务行为、边界或错误现象]
精确线索：[真实接口名、错误码、需求或缺陷 ID]
过滤条件：[平台、标签、状态、排除项]

组合语义和精确线索检索，并记录实际查询、过滤和翻页范围。
只返回带来源 ID、位置和具体匹配理由的候选。
分数只在来源提供时展示，且不代表概率、覆盖率或执行优先级。
使用 CANDIDATES_ONLY；不要运行测试，也不要把候选标为必测集。
```

如果目标是决定“这次必须跑哪些测试”，还需要结合代码或需求变更影响、业务风险、执行成本和团队发布标准，再交给回归范围选择步骤判断。

## 安装与调用

安装单个 Skill 即可：

```bash
npx skills add https://github.com/naodeng/awesome-qa-skills/tree/main/skills/zh/testing-types/test-case-retrieval -g
```

安装后，在支持 Skills 的工具中明确调用 `test-case-retrieval`，同时提供当前会话可访问的用例来源、检索范围和查询线索。是否能检索取决于会话实际可访问的数据或工具。

## 从检索候选交接到回归选择

`变更与风险分析` → `test-case-retrieval` → `回归范围选择` → `测试执行`

向下一步交接时，保留候选来源 ID、位置、匹配理由、原始检索范围、未查来源和适用性待确认项。回归选择还要检查这些候选覆盖了哪些变更风险、哪些风险仍没有用例，以及执行成本是否可接受。检索本身不做这项决策，也不报告测试通过。

## 四个实际问题

### 排名第一的用例是否必须执行？

不一定。排名只表示它在当前查询结果中的相对位置。是否必测要根据变更影响、风险、成本和发布要求单独判断。

### 没有连接用例库时，能否先生成一组看似合理的 ID？

不能。应说明 `NO_ACCESS`，然后请求用户提供最小清单或连接信息。没有来源证据，就没有可追溯的候选。

### 检索分数代表用例更可能发现缺陷吗？

不代表。分数只在来源实际提供时展示，并限定为当前查询中的相对排序；它不是置信度、缺陷发现概率、覆盖率或执行优先级。

### Skill 会帮忙执行找到的用例吗？

不会。它只检索并整理候选，不运行测试。执行前还要由团队确认候选与当前版本、平台和变更范围相符。

先用一个有明确来源和范围的真实问题试跑。检查每个候选是否能回到原始记录，也记录哪些仓库、页面或过滤范围没有被检索。
