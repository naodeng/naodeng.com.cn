混沌测试是围绕明确假设设计的受控故障实验。在提出故障注入前，方案需要有可测稳态、有边界的爆炸半径、有来源的停止条件，以及负责回滚的人。

## 为什么需要这个 Skill

混沌测试用于设计受控故障实验，把假设与稳态信号、爆炸半径、停止条件和恢复证据连接起来。

## Skill 用来做什么

当团队需要围绕“假设、稳态、故障注入、爆炸半径、护栏、恢复和学习”工作时，使用混沌测试 Skill。

[Awesome QA Skills](https://github.com/naodeng/awesome-qa-skills) 按语言和测试阶段组织 Skill。[系列总览](https://inaodeng.com/zh-cn/blog/ai-testing/introduction_of_awesome_qa_skills/) 解释通用安装方式，本文只聚焦混沌测试。

好的混沌测试具体得有点无聊。它知道稳态、最重要的第一个信号、最大爆炸半径，以及停止实验的准确条件。

它适合这些场景：团队需要重复检查假设、稳态、故障注入、爆炸半径、护栏、恢复和学习；多个证据来源互相矛盾；交接时必须说明哪些内容仍未验证。

## 它不做什么

混沌测试 Skill 可以准备和评审实验设计，但不能授权注入故障、访问真实依赖，也不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 假设与稳态 | 哪些不变量必须成立、采用什么有来源的时间窗、与哪个基线或对照比较 | 可证伪的假设 |
| 注入与爆炸半径 | 故障、目标、持续时间、流量或实例比例、依赖、隔离和排除项 | 有边界的实验卡 |
| 停止与回滚 | 可测停止规则、监测频率、停止责任人和恢复动作 | 准备阻塞项与负责人 |
| 前/中/后证据 | 与基线和对照比较功能、数据及恢复信号 | 证据状态与剩余风险 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

设计故障注入场景前，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕每条混沌测试发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入、分析、发现、决策和验证展开；材料不足时保留 `missing`、`conflicting` 或 `assumptions` 状态，不把它们改写成通过。

### 输入

| 材料 | 这次提供什么 | 缺失时怎么处理 |
| --- | --- | --- |
| 实验假设 | 预期降级、用户影响和恢复条件 | 不要从没有边界的故障开始 |
| 实验护栏 | 流量范围、终止阈值、权限和沟通计划 | 指定可以停止实验的人 |
| 信号 | 延迟、错误、回退率、业务转化和恢复日志 | 注入前先定义基线 |

可以这样调用：

```text
请使用 chaos-testing Skill。

任务：测试推荐服务的特征存储不可用时，结算流程是否仍然可用
输入材料：[需求、版本、链接、日志、报告或数据路径]
范围：[本次包含和排除的对象]
未知项：[缺失的环境、账号、数据或权限]
期望输出：[按风险排序的发现、证据状态和下一步动作]

先审计输入。分开写事实、假设和待确认问题。没有运行记录时不要声称已经执行。
```

### 分析

以下只是设计示例：假设任务要求评估特征存储超时时推荐服务能否继续工作，并把结算流程排除在实验范围外。材料没有提供目标流量比例、持续时间、基线、可测停止阈值、测试环境或回滚责任人，应标记为 `missing`，不能随手填入一个百分比。负责人提供这些值并授权隔离、可回滚的验证前，执行准备仍为 blocked。后续运行应按来源定义的基线或对照，在故障前、中、后比较推荐和结算不变量。本文没有记录任何实际执行或结果。

交接产物要保留输入版本、时间窗口、证据索引、负责人和下一次验证动作。Skill 可以整理不确定性，不能制造缺失的产物。

### 发现

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

按源 Prompt 的 `CHS-##` 合同记录发现。以下示例只标出执行准备缺少的证据，不表示系统已经失败。

| `CHS-01` 字段 | 有边界的示例 |
| --- | --- |
| 对象/规则与来源 | 推荐路径；需附上示例任务及其版本 |
| 触发条件/适用范围 | 特征存储超时；须确认目标和排除在外的结算流程 |
| 预期关注点/理由 | 按示例目标检查推荐行为及结算隔离 |
| 证据状态 | `missing`：未提供流量比例、持续时间、基线、停止阈值、环境和回滚责任人 |
| 影响/优先级与负责人 | 仅凭此材料不评分；需确认服务负责人和实验停止责任人 |
| 关闭条件 | 范围、来源阈值、监测频率、停止责任人及回滚/恢复步骤均可复核 |
| 验证方法 | 先评审实验卡；获准后仅在隔离环境执行并保留前/中/后证据；此处不声称已经执行 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 输出字段 | 它要回答什么 | 示例状态 |
| --- | --- | --- |
| 假设/对照 | 有来源的不变量及基线或对照组 | 设计状态 |
| 注入/边界 | 故障、目标、持续时间、暴露范围、依赖和排除项 | 范围与授权 |
| 停止/恢复 | 阈值、频率、停止责任人、回滚和恢复证据 | 准备阻塞项 |
| 学习结果 | 前/中/后证据支持什么、仍缺少什么 | 负责人和下一步动作 |

没有运行记录和原始证据时，不要写“已通过”。实验卡只是准备材料，不是实验结果。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

如果第一次调用只有一行目标，输出就应该保持受限。补充来源版本、受影响对象、环境、已知缺陷和决策负责人，才能从看起来完整的清单推进到可用评审。

这里补充信息会改变结果，因为假设、稳态、故障注入、爆炸半径、护栏、恢复和学习必须接回证据，不能只靠熟悉的测试套路推断。

## 和其他 Skill 怎么配合

- [韧性测试](https://inaodeng.com/zh-cn/qaskills/resilience-testing/)：把故障假设转成韧性检查。
- [恢复测试](https://inaodeng.com/zh-cn/qaskills/recovery-testing/)：聚焦恢复到安全状态。
- [生产验证](https://inaodeng.com/zh-cn/qaskills/production-verification/)：检查实验后的真实信号。

## 容易踩的坑

1. 没有稳态基线就注入故障。
2. 因为第一个指标没问题就扩大爆炸半径。
3. 技术指标恢复就立刻宣称用户和业务已恢复。

## 常见问题

### 混沌实验可以在生产运行吗？

只有在有明确授权、护栏、沟通和可逆故障机制时才可以。

### 没有业务指标怎么办？

标出缺口，使用最小可靠代理指标，不要声称用户影响已知。
