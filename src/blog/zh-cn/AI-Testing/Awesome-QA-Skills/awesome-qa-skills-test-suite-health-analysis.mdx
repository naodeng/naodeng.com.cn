测试套件可以很大、全绿，却并不健康。flaky 重跑、不断增长的隔离清单、重复意图、长尾耗时和 Owner 不清，都会降低信号可信度。

## 为什么需要这个 Skill

Test Suite Health Analysis Skill 根据 CI 历史、时长分布、重跑、隔离清单、重复测试、维护记录和缺陷证据检查套件健康，产出 TSH-## 治理候选，不是执行结果。

## Skill 用来做什么

本文关注的健康状态由多个可观察条件组成，不是一个绿色百分比。

当你要了解套件是否足够可信、可维护，能否承担预期反馈职责时，使用这个 Skill。它不执行测试，不从数量推断覆盖，也不替人工接受风险。

TSH 发现包含对象、前置条件、问题、来源证据、验证、影响、优先级、负责人、关闭条件和证据状态。

当套件变慢或变 flaky、隔离清单增长、怀疑测试重复，或者 CI 健康需要有证据复核时，使用这个 Skill。

## 它不做什么

测试套件健康度分析 Skill 可以组织健康发现的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 健康发现 | flaky、时长、重复、隔离或维护问题 | TSH 编号与证据 |
| 影响 | 问题如何影响信任或反馈 | 优先级与边界 |
| 验证动作 | 改变套件前的最小检查 | 负责人和方法 |
| 残余状态 | 仍未评估或 NOT_RUN 的内容 | 不是覆盖结论 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“健康发现”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕健康发现，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 运行历史 | 时长分布、重试、失败、环境和版本 | 窗口缺失要保持可见 |
| 套件清单 | 测试、Owner、隔离、标签和重复意图 | 不要按文件数算覆盖 |
| 维护与缺陷 | 修复记录、变更区域、逃逸和失败聚类 | 相关性与因果分开 |
| 决策边界 | 反馈角色、负责人、停止条件和验证动作 | 不要批准发布 |

可以这样调用：

~~~text
请使用 test-suite-health-analysis Skill。

任务：复核结账合并前套件在三周内重跑增加、隔离清单变长后的健康度。
输入材料：[CI 历史、时长数据、隔离记录、测试清单、Owner 和缺陷链接]
范围：[结账合并前套件]
限制：[不执行测试、不把候选数量叫覆盖]

输出 TSH-## 发现，包含来源、证据状态、影响、负责人、关闭条件和最小验证动作。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：区分 flaky 重跑和真实产品失败

浏览器升级后重跑增加，但产品缺陷稳定，大多数失败集中在一个夹具。这个 Skill 应提出环境或隔离假设，把产品风险推断分开，并要求受控重放；不能直接删除测试，也不能因为一次重跑变绿就叫套件健康。

分析可以说明已有套件健康证据，不能证明执行覆盖、根因或发布就绪。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“健康发现”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和健康发现的具体对象 |
| 发现 | 健康发现的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 健康发现 | flaky、时长、重复、隔离或维护问题 | TSH 编号与证据 |
| 影响 | 问题如何影响信任或反馈 | 优先级与边界 |
| 验证动作 | 改变套件前的最小检查 | 负责人和方法 |
| 残余状态 | 仍未评估或 NOT_RUN 的内容 | 不是覆盖结论 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供固定时间窗口、运行 ID、时长和重试数据、隔离历史、套件和 Owner 清单、缺陷关联、环境变化及套件反馈职责。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 容易踩的坑

1. 用测试数量或绿色百分比代表整体健康。
2. 没有记录保护风险，就把隔离测试直接删除。
3. 没有环境或复现证据，就把失败聚类叫根因。

## FAQ

### 隔离测试一定要删吗？

不一定。先记录隔离原因、保护风险、负责人，以及关闭或升级条件。

### 套件健康就代表全覆盖吗？

不代表。健康关注信号可信度和可维护性，覆盖是另一条可追踪问题。
