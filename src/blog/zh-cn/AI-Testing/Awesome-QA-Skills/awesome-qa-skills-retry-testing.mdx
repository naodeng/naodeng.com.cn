当第一次请求可能已经成功时，重试会把临时故障变成业务风险。要问的不是客户端会不会再试，而是再试时会不会产生重复副作用。

## 为什么需要这个 Skill

Retry Testing Skill 把重试触发、退避、幂等性、次数限制和重复副作用作为一个受控行为来复核，同时区分策略描述和已经执行的重试结果。

## Skill 用来做什么

本文关注的关键边界是客户端无法确定第一次请求是否已经生效的那段时间。

当支付、通知、任务或 API 流程在超时和瞬态错误下可能重复请求时，使用这个 Skill。它帮助准备安全隔离的验证，不会调用生产系统。

好的复核要写清可重试条件、退避规则、幂等键、尝试上限、副作用预期、证据来源、停止条件和人工边界。

当服务要新增重试、事故暴露重复写入，或者超时路径没有明确的未知成功处理规则时，使用这个 Skill。

## 它不做什么

重试测试 Skill 可以组织触发判断的材料、证据和下一步动作，但它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

这个 Skill 的价值不在于把关键词再列一遍，而在于把每个关注点接到可观察的输入、判断和收口动作。先用源 Skill 已定义的输出字段整理一张小矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 触发判断 | 哪些失败应该或不应该重试 | 策略与证据 |
| 时间行为 | 退避、抖动、顺序和尝试上限 | 预期时间线 |
| 副作用安全 | 如何阻止重复写入或通知 | 幂等性与数据检查 |
| 验证边界 | 什么可以安全运行、何时停止 | 负责人与回滚 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

围绕“触发判断”开始分析时，先把输入分成六种状态。缺口不会自动变成失败，但也不能被隐藏在结论里。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化 Finding

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

围绕触发判断，不要把四种语气揉成一句“建议通过”：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| Fact | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| Evidence-backed Inference | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| Recommendation | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| Human Decision | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

本节按输入（Input）、分析（Analysis）、Finding、决策（Decision）和验证（Validation）展开；材料不足时保留 missing、conflicting 或 assumptions，不把它们改写成通过。

### 输入（Input）

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 重试策略 | 错误类别、超时处理、退避、抖动和上限 | 未说明的行为保留 pending |
| 操作契约 | 读写语义、幂等键和副作用 | 不要只根据 HTTP 方法推断安全 |
| 故障场景 | 超时、连接重置、429、5xx 或 Worker 重启 | 选择一个受控触发 |
| 证据与环境 | 日志、请求 ID、mock 依赖、数据检查和回滚 | 不要使用生产凭证 |

可以这样调用：

~~~text
请使用 retry-testing Skill。

任务：为第一次请求发生连接重置后的支付捕获客户端准备验证。
输入材料：[重试策略、API 契约、幂等语义、请求日志、mock 供应商和数据断言]
范围：[隔离的 staging 流程]
限制：[不产生真实扣款、限制次数、明确清理]

覆盖触发、退避、幂等、限制和重复副作用，分开计划与执行/通过结论。
~~~

### 分析（Analysis）

先根据输入、检查矩阵和证据状态整理判断，再进入 Finding；缺失材料保留为缺口。

### Finding

#### 聚焦例子：重试支付捕获，但不要扣款两次

供应商可能已经捕获支付后连接被重置。这个 Skill 应要求幂等键、有限重试，以及能区分一次和两次捕获的查询或供应商 mock。第二次 HTTP 返回成功，不等于已经证明没有重复副作用。

分析可以准备受控重试验证，不能在隔离运行产生请求和数据证据前证明幂等、扣款正确或没有重复效果。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

假设当前材料无法证明“触发判断”已经满足要求，发现可以这样写。它既不替团队补写规则，也不把缺失证据伪装成失败。

| 字段 | 示例写法 |
| --- | --- |
| 来源与范围 | 记录本轮使用的需求、版本、环境和触发判断的具体对象 |
| 发现 | 触发判断的判断条件或结果仍缺少可追溯依据 |
| 证据状态 | missing / assumptions；如果来源相互矛盾则改为 conflicting |
| 影响与优先级 | 说明会影响哪个用户、链路或交付决定，不凭感觉扩大等级 |
| Owner 与 Human 决策 | 由业务、开发、安全或测试负责人确认规则和风险取舍 |
| 动作与关闭条件 | 补齐最小证据；关闭条件是来源、判断和责任人都能复核 |
| 验证 | 指定一次可重复的检查、查询或运行，并保存原始产物 |

这类记录的重点是让下一位同事能从发现回到来源，再执行一项能改变结论的动作。

### 决策（Decision）

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证（Validation）

关闭前按 Finding 中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## Finding 怎么进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 触发判断 | 哪些失败应该或不应该重试 | 策略与证据 |
| 时间行为 | 退避、抖动、顺序和尝试上限 | 预期时间线 |
| 副作用安全 | 如何阻止重复写入或通知 | 幂等性与数据检查 |
| 验证边界 | 什么可以安全运行、何时停止 | 负责人与回滚 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时使用 pending、blocked、未评估或 NOT_SCORED，不要用自信填空。

### 下一步路由

至少交付来源、证据状态、负责人、关闭条件和验证动作；下一阶段的结论仍受证据状态约束。

## 怎样准备更好的输入

提供错误分类、超时语义、API 契约、幂等行为、次数上限、退避规则、请求 ID、mock 或沙箱、数据断言和清理方式。缺一项就让对应结论保持 pending。

交接时至少保留输入版本、范围、时间窗口、证据索引、假设、人工决策边界和最小验证动作。

## 和其他 Skill 怎么配合

- [超时测试](https://inaodeng.com/zh-cn/qaskills/timeout-testing/)：隔离未知完成和超时行为。
- [熔断器测试](https://inaodeng.com/zh-cn/qaskills/circuit-breaker-testing/)：检查连续失败何时应停止调用。

## 容易踩的坑

1. 不检查操作是否安全，就对所有 4xx 和 5xx 重试。
2. 只检查最终响应，不检查写入、消息或扣款次数。
3. 不明确退避和最大次数，让故障演变为请求风暴。

## FAQ

### 有幂等键就一定够了吗？

不够。幂等键、服务端行为、保留时间、响应语义和副作用证据都要符合操作契约。

### 可以对生产测试重试吗？

默认不可以。使用 mock、沙箱或隔离环境，限制次数并清理；生产验证需要明确授权。
