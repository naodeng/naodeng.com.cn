测试执行时间只是一个潜在瓶颈。共享环境、评审队列、缺少数据、专业交接和容量规则也会限制流程。

## 为什么需要这个 Skill

测试瓶颈分析 Skill 检查等待队列、依赖、容量、交接和测试约束证据，把延迟抱怨变成有证据边界的改进路径。

## Skill 用来做什么

本文关注的产物应指出下一个可测量的约束，而不是只指出看起来最长的队列。

当你要复核测试为什么等待、流程停在哪里，以及什么证据能区分需求、容量、依赖或交接约束时，使用这个 Skill。它不自造根因，也不批准流程变化。

结果要写清队列、依赖、容量或交接信号、时间窗口、证据状态、优先级、负责人、关闭条件和最小验证。

当测试工作反复等待环境、数据、评审、专家或 CI 容量，需要可决策诊断时，使用这个 Skill。

## 它不做什么

测试瓶颈分析 Skill 可以整理队列、依赖、容量和交接证据，并提出下一步检查；它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

分析时要定位等待发生在哪个阶段，再判断现有事件能否说明延迟来自排队、服务时间、依赖还是交接。可以先按源 Skill 的输出字段整理检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 阶段与约束 | 哪个队列、依赖、容量或交接环节出现等待 | 对应事件、来源和证据状态 |
| 影响范围 | 延迟影响哪些发布、验证范围或风险 | 影响对象和优先级依据 |
| 验证方案 | 哪项最小变化可以区分候选原因 | 对照窗口、观察指标和停止条件 |
| 决策边界 | 哪些容量或流程选择需要负责人批准 | 决策人、权限和残余风险 |
| 输出契约 | 结果是否要进入表格、CSV、JSON 或工单 | 确认 schema、枚举值、必填字段和证据来源 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始分析前，先标出六种证据状态，并检查材料完整性、来源可信度、时效性和可比性。时间戳缺失或互相冲突会限制因果判断，不能据此认定流程失败。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

整理结果时，把事实、证据支持的推断、建议和人工决策分开：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

下面的源样例拆分了依赖等待、执行和返工，并用可比观察检查并发相关说法。缺少材料时保留 `missing`、`conflicting` 或 `assumptions` 状态。

### 输入

源 Skill 附有一组脱敏合成样例，仅用于演示，不代表真实团队的流转数据。

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| T1 时间线 | 第 0 分钟到达，0–40 分钟等待环境，40–50 分钟执行，50–60 分钟返工，第 60 分钟完成；等待期间 runner 空闲 | 明确每个阶段和事件边界 |
| 同日同复杂度任务 | 并发 2 时每小时完成 10 项、WIP 为 4；并发 4 时每小时完成 6 项、WIP 为 8，DB 锁等待增加 | 只比较样例中匹配的窗口和任务范围 |
| 待复核的说法 | B1 判断耗时最长阶段；B2 认为并发越高越好；B3 把 40 分钟等待当作人手不足证明；B4 提出 DB 争用假设，需受控验证 | 分开记录支持的判断、不成立的说法和待验证假设 |
| 决策边界 | 观察窗口、负责人、实验和回滚信号 | 取舍与授权由负责人确认 |

可以这样调用：

~~~text
请使用 testing-bottleneck-analysis Skill。

任务：拆分样例中的依赖等待、执行和返工，并复核并发相关说法。
输入材料：[T1 事件时间线、完成吞吐、WIP、DB 锁等待观察]
范围：[同日、同复杂度任务和给定并发水平]
成功标准：[结论不超出样例证据，实验有可测量的停止信号]
排除事项：[只凭等待时间判断人手不足]

计算每个阶段耗时，区分 WIP 与吞吐量，并判定 B1–B4。提供证据状态、优先级或 `NOT_SCORED`、负责人角色、关闭条件和最小验证动作。
~~~

### 分析

T1 的周期共 **60 分钟**，其中 **40 分钟**等待环境，**10 分钟**执行，**10 分钟**返工。runner 在等待环境时空闲。按样例，最长阶段是 `DEPENDENCY_WAIT`；60 分钟周期不等于 60 分钟人工投入。

同日同复杂度任务在并发 2 时每小时完成 10 项，WIP 为 4；并发 4 时每小时完成 6 项，WIP 为 8，DB 锁等待也增加。样例不能证明 DB 争用导致吞吐下降，但已足以反驳“并发越高越好”的普遍说法。runner 等环境时空闲，40 分钟等待也不能证明人手不足。

### 发现

#### 源样例判定

| 说法 | 样例判定 |
| --- | --- |
| B1 判断环境等待是耗时最长的阶段 | `DEPENDENCY_WAIT`；等待 40 分钟，执行 10 分钟，返工 10 分钟 |
| B2 认为并发越高越好 | `UNSUPPORTED`；样例中的高并发吞吐更低，WIP 更高 |
| B3 把等待环境 40 分钟当成人手不足的证明 | `UNSUPPORTED`；runner 等待期间处于空闲状态 |
| B4 提出 DB 争用可能是原因 | `HYPOTHESIS`；锁等待观察还需受控对照 |

## 把假设变成可比较的实验

选择能区分假设的最小受控变化。保留现有测试与发布控制，一次只改一个条件；实验前由负责人确认停止或回滚信号，并记录其他可能影响结果的变化。

| 假设 | 最小验证方式 | 观察与边界 |
| --- | --- | --- |
| 环境依赖造成等待 | 对照相似任务的环境可用时间和预约记录 | 观察环境等待和总周期；任务范围、复杂度和窗口需可比 |
| 更高并发降低了流转效率 | 在授权的受控比较中记录各并发水平下的完成项、WIP 和 DB 锁等待 | 并发变化前与负责人约定回滚信号；样例没有给出通用阈值 |
| 人手不足 | 按阶段比较到达、完成、利用率和空闲原因 | 单凭等待不足以证明人手不足；runner 可能在等材料或环境 |
| 事件数据不足 | 补齐到达、环境可用、执行开始/结束、返工、完成和阻塞原因 | 时间线可复核前保持未评估，不补造缺失时长 |

WIP 统计窗口内尚未完成的工作；吞吐量统计相同窗口内已完成的工作。周期和各阶段时间分开计算，并明确时间戳含义、时区和观察窗口。保留原始事件、计算规则、实验条件、停止信号和未解释差异。平均等待时间本身不能证明根因；验证前也不能声称吞吐量提升或已具备发布条件。

#### 示例发现：把环境等待变成可复核事项

| 字段 | 示例记录 |
| --- | --- |
| 发现 | `TBA-01`：样例中的 T1 等环境 40 分钟，是时间线里最长的阶段；这不能证明人手不足 |
| 来源与触发条件 | 脱敏样例时间线；当环境等待反复发生，或只凭耗时作出容量结论时触发复核 |
| 预期问题 | 总周期可能被当成人工投入，依赖等待也可能被误判为人手不足 |
| 证据状态 | 样例中的阶段拆分为 `known`；它不是线上测量，DB 争用仍是待验证假设 |
| 影响与优先级 | 等待会延迟完成；没有项目风险和影响分级规则时，优先级保持 `NOT_SCORED` |
| 负责人和待决策项 | 环境负责人确认可用时间和预约事件；流程负责人确认任务窗口以及是否批准实验 |
| 动作与关闭条件 | 保留工作项 ID 和阶段时间；当瓶颈阶段和获准变更的效果可复算后再关闭 |
| 验证 | 用匹配任务对照到达、环境可用、执行、返工和完成事件，保留原始记录及计算规则 |
| 停止条件 | 事件定义或任务可比性缺失时，原因保持未评估；未确认回滚信号和权限前，不改变并发量 |

这条发现把观察到的依赖等待与人手或数据库根因假设分开。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 约束发现 | 观察到的队列、依赖、容量或交接问题 | 来源与证据状态 |
| 影响 | 延迟如何影响验证或风险 | 优先级与范围 |
| 实验 | 区分假设的最小变化 | 预期观察 |
| 决策边界 | 需要人工做容量或流程选择的内容 | 负责人和残余风险 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补证据空白。

### 下一步路由

按缺口交给能补齐证据或批准改变流程的人：

| 缺口 | 下一步负责人 | 交付目标 |
| --- | --- | --- |
| 到达、开始或完成时间缺失 | CI、环境或评审系统负责人 | 补齐事件定义、时间戳和关联发布的方式 |
| 排队时间与服务时间混在一起 | 流程负责人和数据分析者 | 分阶段计算等待与处理时间，指出未覆盖部分 |
| 交接时间不清楚 | 相关阶段的负责人 | 补齐交接的开始和结束事件；保留现有审批要求 |
| 需要新增环境或人员 | 获授权的工程管理负责人 | 根据证据决定容量投入、范围和复核日期 |

后续结论仍受证据状态约束；诊断结果本身不授权流程或容量变更。

## 怎样准备更好的输入

提供固定发布窗口、队列和服务时间戳、阻塞原因、依赖图、容量排期、交接负责人和分析要支持的决定。时间戳缺失时保持未评估。

交接时保留输入版本、范围、观察窗口、事件定义、证据位置、假设和人工决策边界，并指定最小验证动作。

## 容易踩的坑

1. 不检查下游等待或服务时间，就把最长队列叫瓶颈。
2. 把利用率或抱怨当成容量饱和证明。
3. 没有定义实验和成功证据就先改流程。

## 最佳实践

- 比较前先固定观察窗口、工作项 ID、任务复杂度、到达和完成事件。
- 分开记录排队或依赖等待、执行、返工、交接和阻塞。总周期时间不等于人工工时。
- 在同一窗口统计 WIP 和吞吐量，并结合阶段时间、到达、完成和利用率定位约束；平均等待本身不能证明根因。
- 一次只验证一项改动，用可比的前后指标，并提前和负责人确认停止或回滚信号。保留实验条件、版本、来源和结果。

## 新手入门：追踪一项延迟工作

1. 选一个阶段和固定观察窗口。
2. 收集工作项 ID、复杂度、到达、可开始、开始、交接、返工和完成时间，并记录 WIP 与完成项。
3. 请 Skill 把等待和执行拆开，标出证据缺口，提出最小受控检查。证据不足时，不要下人力或根因结论。

## 把瓶颈分析放进质量循环

![测试流转质量循环：验收关联需求的用例，测量等待和完成量，定位约束，进行受控实验后再次测量](/images/blog/ai-testing-quality-loops/testing-bottleneck-analysis-quality-loop-zh.svg)

AI 生成的用例数量本身不能说明有效吞吐。先复核、去重并验收，再关联需求并执行，随后一起观察完成量、等待、返工和质量结果。新增工作也可能推高 WIP 或造成资源争用，因此要把结果带回下一轮测试计划。

## 常见问题

### 这个 Skill 会自动建议增加人员吗？

不会。它识别证据和取舍，容量变化属于人工计划决定。

### 时间戳不完整怎么办？

返回受限诊断，把因果发现标为未评估，并请求最小缺失事件时间戳。

### 并发越高，吞吐量一定越高吗？

不一定。源样例中并发较高时吞吐量更低、WIP 更高，DB 锁等待也增加。这组观察足以质疑“并发越高越好”，但不能单独证明变化由哪个因素造成。

### AI 生成的用例应该算作已完成工作吗？

不能只按生成数量计算。还要复核、去重并验收用例，再结合完成量、等待、返工和质量证据评估。
