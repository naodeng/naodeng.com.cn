测试瓶颈不一定是慢测试，也可能是共享环境、评审队列、缺少数据、专业交接，或仪表盘没有记录的容量规则。

## 为什么需要这个 Skill

测试瓶颈分析 Skill 检查等待队列、依赖、容量、交接和测试约束证据，把延迟抱怨变成有证据边界的改进路径。

## Skill 用来做什么

本文关注的产物应指出下一个可测量的约束，而不是只指出看起来最长的队列。

当你要复核测试为什么等待、流程停在哪里，以及什么证据能区分需求、容量、依赖或交接约束时，使用这个 Skill。它不自造根因，也不批准流程变化。

结果要写清队列、依赖、容量或交接信号、时间窗口、证据状态、优先级、负责人、关闭条件和最小验证。

当测试工作反复等待环境、数据、评审、专家或 CI 容量，需要可决策诊断时，使用这个 Skill。

## 它不做什么

测试瓶颈分析 Skill 可以整理队列、依赖、容量和交接证据，并提出下一步检查；它不能替代：

- 业务或领域负责人对规则、范围和风险的确认。
- 真实环境、账号、数据、日志或运行结果；静态分析不会自动升级为运行证据。
- 发布、合规、生产操作和残余风险接受等授权决定。
- 在输入相互冲突时替团队选择一个未经确认的事实。

## 它主要检查哪些内容

关键不是找出最长的队列，而是确认等待发生在哪个阶段、现有事件能否说明延迟来自排队、服务时间、依赖还是交接。可以先按源 Skill 的输出字段整理检查矩阵：

| 检查关注点 | 开始前要问 | 结果应留下什么 |
| --- | --- | --- |
| 阶段与约束 | 哪个队列、依赖、容量或交接环节出现等待 | 对应事件、来源和证据状态 |
| 影响范围 | 延迟影响哪些发布、验证范围或风险 | 影响对象和优先级依据 |
| 验证方案 | 哪项最小变化可以区分候选原因 | 对照窗口、观察指标和停止条件 |
| 决策边界 | 哪些容量或流程选择需要负责人批准 | 决策人、权限和残余风险 |

如果某一行只有经验判断、没有来源或验证方法，就把它留在待确认项里，不要提前写成通过。

## 开始之前先审计输入

开始分析前，先给材料标出六种证据状态。时间戳缺失或互相冲突会限制因果判断，但不会自动证明流程失败。

| 状态 | 含义 | 本 Skill 的处理方式 |
| --- | --- | --- |
| known | 材料直接证明的事实 | 标出来源、版本和时间，允许进入判断 |
| missing | 本轮需要但尚未提供的材料 | 列出最小补证动作，结论保持受限 |
| conflicting | 来源之间互相矛盾 | 并列来源和冲突点，交给负责人裁决 |
| stale | 材料存在但版本或时间已经过期 | 标出新鲜度，不把旧结论当当前事实 |
| out_of_scope | 有关但不在本轮范围内 | 明确排除，避免分析悄悄扩大 |
| assumptions | 为继续分析而暂时采用的假设 | 写出验证方式和失效条件 |

至少把输入版本、范围、环境、证据位置和负责人放在一起。没有运行记录时，只能交付分析、设计或验证计划，不能写执行通过。

## 从问题到结构化发现

先把来源、范围、证据状态、分析判断、责任角色、动作、关闭条件和验证方式连起来，再写结论。下面的案例保留这个 Skill 的专属编号和领域语境。

### 分层写法

整理结果时，把事实、证据支持的推断、建议和人工决策分开：

| 层次 | 写法 | 本文应用 |
| --- | --- | --- |
| 事实 | 材料直接显示了什么 | 引用来源中的重点、版本、输入或运行记录 |
| 基于证据的推断 | 多个事实共同支持的判断 | 说明推断链，并保留不确定性 |
| 建议 | 下一步最小动作是什么 | 指定补证、复核、执行或回归路径 |
| 人工决策 | 谁需要决定什么 | 由负责人确认范围、风险接受、资源和发布含义 |

## 一个完整案例

下面用结账发布等待预发布环境和安全评审的示例，说明如何从时间线走到待验证假设。缺少材料时保留 `missing`、`conflicting` 或 `assumptions` 状态。

### 输入

| 材料 | 这次提供什么 | 缺失时的处理 |
| --- | --- | --- |
| 流转证据 | 到达、等待、服务、交接、排队和完成时间戳 | 缺时间戳要明确 |
| 依赖 | 环境、数据、审批、服务和专家约束 | 观察到的依赖与假设分开 |
| 容量 | 工作进程、环境、评审槽位、窗口和利用率 | 不要从抱怨推断饱和 |
| 决策边界 | 负责人、实验、停止条件和变更权限 | 取舍由人工决定 |

可以这样调用：

~~~text
请使用 testing-bottleneck-analysis Skill。

任务：诊断结账发布验证为什么要等待两天的共享 staging 环境和安全评审。
输入材料：[队列时间戳、环境预约、评审交接、容量、阻塞原因和发布日历]
范围：[最近四次发布]
限制：[不自造根因、不承诺吞吐改善]

分开等待队列、依赖、容量、交接和证据发现，给出优先级、负责人、关闭条件和可测量的下一步。
~~~

### 分析

对照到达、排队、服务、交接和完成时间，分别计算各阶段的等待。只有当事件定义、时间窗口和发布范围可比时，才能比较前后变化；缺少这些数据时，根因仍待验证。

### 发现

#### 聚焦例子：区分预发布环境稀缺和安全评审交接

假设示例时间戳显示，发布要等待预发布环境，而安全评审总在手工交接后才开始。环境容量和交接顺序是两个不同的候选原因，需要分别验证；队列较长本身不能证明环境容量不足。

## 把假设变成可比较的实验

先选能区分假设的最小变化。实验要遵守现有安全评审和发布门禁；只有相关负责人确认允许并行时，才改变交接顺序。每次只改一个条件，并记录其他可能影响等待时间的变化。

| 假设 | 最小验证方式 | 观察与边界 |
| --- | --- | --- |
| 预发布环境容量不足 | 在授权范围内增加一个隔离环境时段，比较相近发布窗口的预约等待 | 同时看环境等待和总周期；若工作量、测试范围或发布时间不同，不能只归因给环境 |
| 安全评审被交接顺序拖后 | 若策略允许，让评审者在环境准备期间预审同一证据包 | 比较评审开始、结束和总等待；不能省略必需评审或把准备时间记成审批完成 |
| 实际是测试运行时间过长 | 先拆分排队时间与服务时间，再对慢执行步骤做单独分析 | 只有服务时间占主要部分时，才转交运行时优化；不能拿队列长度代替测试耗时 |
| 容量或事件数据不足 | 补齐到达、可开始、实际开始、完成和阻塞原因时间 | 在时间线可复核前将原因标为未评估，不通过增加人员来填补未知数 |

比较前先统一每个时间戳的含义和时区，固定发布范围与观察窗口。结果至少应保留原始事件、计算规则、实验条件、停止条件和未解释的差异。诊断可以提出改进方案，不能在验证前证明根因、吞吐提升或发布就绪。

#### 示例发现：把一次问题写成可交接动作

下面的字段示例只展示记录方式，不代表真实环境已经执行。

沿用上面的交接场景，假设现有摘要显示评审在手工交接后才开始，但没有完整的预约和服务时间，发现可以这样写：

| 字段 | 示例记录 |
| --- | --- |
| 来源与范围 | 最近四次结账发布的预约、评审交接和 CI 时间线；以实际提供的版本为准 |
| 发现 | 当前时间线显示评审晚于手工环境交接，但没有分阶段等待和服务时间，无法判断主要约束 |
| 证据状态 | 若只有汇总时间、缺少到达与开始事件，根因标为 `missing` / `unassessed`；不要推断容量饱和 |
| 影响与优先级 | 可能延长发布验证周期；按受影响发布范围和待验证风险确定优先级 |
| 负责人和待决策项 | 流水线负责人补齐时间线；安全负责人确认预审能否与环境准备并行 |
| 动作与关闭条件 | 先核对时间戳定义，再选择一项获准实验；关闭时应能说明哪一段等待变化、哪些因素仍未排除 |
| 验证 | 对照相近发布窗口的预约、评审开始/结束、环境可用和验证完成记录，保留原始事件与计算规则 |

这份记录把剩余问题、负责人和可验证的下一步放在一起，接手人可以据此判断还缺什么证据。

### 决策

责任角色和待决策问题应由对应负责人确认；Skill 不替他们做风险取舍。

### 验证

关闭前按发现中的验证方式执行，并保留原始产物；没有执行记录时，状态仍然保持未验证。

## 发现如何进入下一阶段

### 交接产物

| 产物 | 要回答的问题 | 示例状态 |
| --- | --- | --- |
| 约束发现 | 观察到的队列、依赖、容量或交接问题 | 来源与证据状态 |
| 影响 | 延迟如何影响验证或风险 | 优先级与范围 |
| 实验 | 区分假设的最小变化 | 预期观察 |
| 决策边界 | 需要人工做容量或流程选择的内容 | 负责人和残余风险 |

每条结论都应该能回到来源、证据状态和下一步动作。材料不足时保留 `pending`、`blocked`、未评估或 `NOT_SCORED`，不要用肯定语气填补证据空白。

### 下一步路由

按缺口交给能补齐证据或批准改变流程的人：

| 缺口 | 下一步负责人 | 交付目标 |
| --- | --- | --- |
| 到达、开始或完成时间缺失 | CI、环境或评审系统负责人 | 补齐事件定义、时间戳和关联发布的方式 |
| 排队时间与服务时间混在一起 | 流程负责人和数据分析者 | 分阶段计算等待与处理时间，指出未覆盖部分 |
| 交接顺序可能造成延迟 | 安全评审与发布负责人 | 确认是否允许并行准备，并保留必需审批边界 |
| 需要新增环境或人员 | 获授权的工程管理负责人 | 根据证据决定容量投入、范围和复核日期 |

后续结论仍受证据状态约束；诊断结果本身不授权流程或容量变更。

## 怎样准备更好的输入

提供固定发布窗口、队列和服务时间戳、阻塞原因、依赖图、容量排期、交接负责人和分析要支持的决定。时间戳缺失时保持未评估。

交接时保留输入版本、范围、观察窗口、事件定义、证据位置、假设和人工决策边界，并指定最小验证动作。

## 容易踩的坑

1. 不检查下游等待或服务时间，就把最长队列叫瓶颈。
2. 把利用率或抱怨当成容量饱和证明。
3. 没有定义实验和成功证据就先改流程。

## 常见问题

### 这个 Skill 会自动建议增加人员吗？

不会。它识别证据和取舍，容量变化属于人工计划决定。

### 时间戳不完整怎么办？

返回受限诊断，把因果发现标为未评估，并请求最小缺失事件时间戳。
