AI 编码 Agent 可以连接需求单、查看设计、编写测试用例和自动化代码、运行测试，最后准备好拉取请求。听起来很高效，直到它开始自行补全缺失需求，或一次生成几十个质量一般的场景。

在 Ministry of Testing 的分享《测试人员工作流中的日常 AI 编码：Skills 与插件》中，Maneesh Maddala（测试领域高级软件工程师，Principal Software Engineer in Testing）提出了更稳妥的做法：把 Agent 的职责拆小、明确，谨慎开放工具权限，并在关键审批点保留人工判断。分享于 2026 年 7 月 31 日举行。下文把其中的案例整理成团队可以检查和调整的工作流。

## Skill 是路线图，不是魔法

可复用的 Skill 像一张路线图，能把完成任务所需的指引、上下文和方法整理出来，帮助团队复用做法。它可以提升一致性，却不能保证 Agent 会遵守每条规则，也不能替它补上缺失的信息。

在测试任务中，Skill 可以要求先取得证据再创建测试；Agent 仍需要权限边界、有代表性的评估样本，以及在需求不清楚时安全停止的方式。Skill 是工程工作流的一部分，不能替代整个工作流。

## 命令、Skill、插件、MCP 和 Agent 有什么区别

分享用厨房做比喻，帮助听众区分这些概念。这个比喻有助于理解，但不是技术规范。

| 概念 | 厨房比喻 | 实际作用 |
| --- | --- | --- |
| 斜杠命令 | 一个快捷操作 | 按需启动已知任务 |
| Skill | 一份菜谱或工作方法 | 提供任务所需的说明和上下文 |
| 插件 | 厨房里的功能扩展 | 在特定宿主中打包或提供能力 |
| MCP 服务器 | 连接外部供应商 | 通过约定接口让模型访问外部数据或执行操作 |
| Agent | 实际做事的厨师 | 使用指引和工具完成任务 |

Skill 不会取代 MCP。Skill 可以说明怎样使用已经连接的系统，MCP 则可以提供这条连接。工作流是否需要 MCP，取决于是否必须读取外部数据或执行外部操作。

## 为什么一个超长提示词效果不好

分享中回顾了一次早期的端到端尝试：一个提示词要串起 Asana 需求、Jira、Figma、TestRail、Playwright 和拉取请求评审。Agent 最后生成了大约 50 至 60 个测试场景，但其中不少质量薄弱，甚至虚构了行为；即便可以使用浏览器，它也编造了定位器。

这个超长提示词把太多决策、系统、权限和输出类型塞进同一项任务，却没有提供足够的项目上下文和检查机制。团队把场景数量误当成覆盖率；用例增多，评审负担也可能随之上升。

## 按职责拆分工作流

给每个 Skill 一个范围明确的任务和交接条件。规划 Skill 可以只读需求并提出场景，不获得创建测试用例或代码的权限。场景编写 Skill 在获批后创建用例。编码 Skill 实现页面对象和测试。执行 Skill 运行并汇报。评审 Skill 可以准备拉取请求，但除非负责人明确授权，否则应在合并之前停止。

限制应结合任务复杂度设置。分享中的示例大致是：小改动提出 3 至 5 个场景，较大的任务提出 10 至 12 个场景。这些数字是演示中的起点，不是通用上限；每个场景仍要说明为什么需要它。

## 保留人工审批的五阶段工作流

| 阶段 | Agent 负责的工作 | 人工决策或交接 |
| --- | --- | --- |
| 规划 | 阅读需求，在 scenarios.md 中提出有数量边界的场景清单 | 评审范围并批准场景 |
| 测试管理 | 将获批场景映射到已有 TestRail 用例，提出新增或修改建议 | 批准测试用例变更 |
| 实现 | 创建或更新页面对象和自动化测试 | 评审代码并确认符合仓库约定 |
| 执行 | 运行已批准的测试集，附证据总结失败 | 判断失败来自产品、测试、数据还是环境 |
| 评审 | 整理变更、执行结果和已知限制，准备拉取请求 | 工程师评审并决定是否合并 |

不同工具的实际能力和权限边界各不相同。这张表只是把分享中的流程拆开整理；每次交接仍要说清产出物是什么、谁来评审，以及满足什么条件才能进入下一步。

例如，测试场景可以记录来源需求、用户意图、前置条件、预期行为、风险和待澄清问题。相比自由文本，简洁的结构化格式更容易检查。没有获得相应审批之前，不要让 Agent 写入 TestRail、修改仓库文件或创建拉取请求。

自主循环也需要自己的边界：重试次数、超时时间、费用预算、失败分类和成功条件。“一直重试到变绿”不是安全的完成标准。

## 为什么仍然需要人工评审

人工审批应放在假设即将变成受管理的测试资产、代码变更、外部写入或发布决定的节点，而不能只留到流程末尾。

评审者应检查输出是否符合需求、场景是否彼此独立且覆盖风险、定位方式是否使用稳定语义、页面对象是否只封装操作而没有藏入断言，以及是否有对应的真实执行记录。Agent 能访问浏览器，不代表它一定正确使用了浏览器。

审批要明确，也要有范围。一个人批准了场景意图，并不等于同时批准仓库修改、外部系统变更或合并拉取请求。

## SauceDemo 对比演示说明了什么

现场演示使用 SauceDemo 创建了约 8 至 10 个检查，覆盖登录、购物车和结账。缺少充分说明时，Agent 没有主动澄清项目假设，生成的测试也留有本可避免的缺口。

加入 grill-me Skill 后，Agent 开始询问项目是否使用 TypeScript、npm、代码检查和 GitHub Actions，也询问认证方式、测试类型、浏览器范围和仓库约定，再提出夹具、页面对象和测试方案。这里可借鉴的是先澄清再实现；这段演示并非受控基准测试，不能据此断言某个 Skill 在所有项目里都会让测试更好。

## Guardrails 和 Evals 解决的是不同问题

Guardrails（权限护栏）规定 Agent 可以做什么：只读访问、允许执行的命令、受保护文件、外部写入权限、费用上限和审批要求。Evals（评估集）则通过有代表性的输入检查它是否按预期行动。

可以从三个层面评估：

1. **结构：** 输出是否符合格式要求，必需字段是否齐全？
2. **行为：** Skill 是否遵循指引、只用获准工具，并在审批边界前停止？
3. **质量：** 场景是否能追溯到真实验收条件，是否重复，是否虚构功能或使用了薄弱断言？

评估样例可以简单到下面这样：

```yaml
case: missing_acceptance_criteria
input: "Create tests for an unspecified checkout change"
expected:
  ask_for_clarification: true
  fabricate_requirements: false
  create_testrail_cases: false
```

“输出看起来不错”不是足够的通过条件。把真实失败样本保留下来作为回归集；每次修改 Skill 后，记录通过率、越权情况、人工修改量和回归结果。

## 效率提升的数据应怎样理解

分享中的一个团队案例是：一条 Jira 需求从分析到拉取请求，原本约需 8 小时；半自主工作流将它缩短到 2 至 2.5 小时。按这组案例数字计算，耗时减少约 69% 至 75%。这个结果不能直接外推到其他团队。

分享者还提到，使用 Skill 可能消耗更多模型词元（Token）：演示约为两倍，某些场景可能达到两至三倍。因此要一起衡量端到端耗时、评审时间、有效场景比例、代码返工、不稳定测试比例、错误的外部写入和模型费用。生成更快，不一定意味着总成本更低。

分享中还提到，过去六个月生产缺陷有所下降，但没有把变化全部归功于 AI。团队成熟度和风险管理的变化也可能产生影响。讨论效果时应保留这一区分。

## 从个人提示词走向组织能力

分享把组织采用 AI 的成熟过程大致分为四个阶段：

1. 个人把 AI 当聊天机器人使用。
2. 团队为日常工作创建可复用的 Skill。
3. 团队之间共享 Skill，并组合跨团队的 Agent 工作流。
4. 组织建立中央目录和统一管理的访问方式。

采用范围扩大后，Skill 需要有负责人、版本、输入和输出契约、权限边界、评估集、变更记录和弃用流程。除了共享文件，还要管理这项能力的版本和使用规则。同一个 Skill 在不同 IDE、模型和 Agent 中可能表现不同，因此要分别检查触发条件和工具权限，不能直接假定它可以无差别迁移。

## 分享中的五个常见问题

**Skill 会不会取代 MCP？** 不会。它们承担不同职责：一个可以描述工作方法，另一个可以连接外部数据或操作。

**为什么不让整个流程完全自主运行？** 因为停止条件、重试、费用限制和失败恢复需要先可靠。把多个 Skill 串起来，并不会自动得到安全的自主系统。

**AI 会不会取代测试人员？** 分享中的回答是否定的。人仍要确定目标、评审推理、识别风险、维护标准，并把节省的时间用于更高价值的质量工作。

**Claude 太贵怎么办？** 可以在企业安全评审后评估 Copilot 或其他模型，再用同一套行为与质量评估重新检查。模型可以替换，不表示效果天然相同。

**怎样证明价值？** 先做范围有限的单条需求耗时对比，再加入质量、成本和复用情况。没有证据时，不要把生产缺陷趋势归因于 AI。

## 让 Skill 成为可测试的工程资产

整场分享梳理出一套工程纪律：职责保持精简、契约明确、工具受限、人工审批到位，并针对真实失败做回归评估。

团队可以给每个 Skill 维护一张小型质量卡：触发是否准确、是否遵守工具边界、是否编造测试、是否符合输出契约、在支持的模型间是否表现一致、遇到缺失信息时能否安全停止？这样才能把好用的提示词变成可维护的工程资产。

Skill 能减少团队重复解释工作方式的时间，却不会取代工程判断。评估 AI 编码工作流时，重点应放在它是否减少重复沟通，并交付可验证、可追溯、可评审的结果，而不是生成了多少代码。
