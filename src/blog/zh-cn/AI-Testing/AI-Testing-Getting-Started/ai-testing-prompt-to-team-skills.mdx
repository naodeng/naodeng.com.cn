一个人用 Prompt 辅助 AI 分析需求，是个人实践的一步；团队能否把这套方法稳定地用在相似任务上，则是另一回事。把提示词复制到共享文档，并不会自动形成可维护的工作流程。

先回看真实工作，再决定是否要写 Skill：哪些任务重复发生？哪些判断步骤确实有效？有哪些失败案例值得以后避免？

## 从一次成功走到可重复

可以先把做过的需求分析保存下来，连同输入版本、已确认规则、AI 输出、人工修订和最后发现的问题一起记录。多做几次后，再辨认哪些步骤重复出现、哪些内容只适用于某个项目。

适合先整理的通常是重复频率高、输入范围较清楚、结果也能核对的任务，例如验收标准审查或测试用例评审。探索性测试、业务方向不明确的讨论仍需要留出弹性，不宜硬塞进固定流程。

| 沉淀阶段 | 要回答的问题 | 可留下的资产 |
| --- | --- | --- |
| 个人试用 | 任务是否真的受益？ | 原始需求、对话、人工修订记录 |
| Prompt 固定 | 哪些要求反复有效？ | 模板、输入字段、输出约定 |
| Skill 封装 | 哪些步骤需要每次照做？ | Skill 说明、参考资料、模板或脚本 |
| 团队试点 | 不同成员能否用好？ | 使用说明、评估样本、反馈与版本记录 |

> 配图待补：可画一张从真实任务、Prompt 迭代、Skill 封装到团队试点的横向流程图，并用真实工作产物替换示意内容。

## 一个 Skill 至少要让人看懂这些事

以需求缺口分析为例，团队版本要说明适用场景、必要输入、执行步骤、输出格式、不能替代的人工判断，以及如何处理信息不足。比如可以要求 AI 提取规则、标注缺失与冲突、给出证据位置和风险，再把无法确认的行为列成问题，而非替业务直接补规则。

说明至少列出名称与适用场景、必需输入、执行步骤、输出格式、人工确认点和维护版本。不是每个 Skill 都需要脚本；若任务只需要一份清晰说明和参考模板，就不要为了看起来完整而增加不必要的文件。

同时要明确维护责任：谁更新参考资料，谁确认业务规则，谁审查 Skill 变更。若其中包含脚本、文件写入或外部访问，也要说明授权范围和禁止操作。不要让一份“为了方便”的流程默认拿到超出任务需要的权限。

以“需求缺口审查”为例，个人 Prompt 可以先沉淀成一份评估样本，再整理成 Skill 的输入输出约定：

| 项目 | 示例约定 |
| --- | --- |
| 输入 | 带版本的需求、适用范围、已有验收条件和相关接口约定 |
| 步骤 | 抽取规则，逐条关联来源；将缺失、冲突和过期信息分开标记 |
| 输出 | 规则 ID、引用位置、风险影响、待确认问题和最小补证动作 |
| 边界 | 不替产品补写业务规则；没有来源的预期保持待确认 |
| 回归样本 | 需求完整、关键字段缺失、两份来源冲突三类脱敏输入 |

该表只展示一种结构，没有提供实际评测结果。试用时要保存输入版本、输出、人工修订和评审结论；如果模型把缺失信息补成事实，应将该样本留作失败用例，修改说明后再回归。

## 评估不能只收集成功截图

准备 3～5 份脱敏样本，覆盖规则完整、信息缺失、规则冲突和边界复杂等情况。评估关键问题是否被发现、未知项有没有被误写成事实、输出是否符合约定、人工修订是否减少。把失败样本加入回归集合，每次修改 Prompt 或 Skill 后重新检查。

这一步能避免只保存看起来漂亮的案例。真实价值来自在有挑战的输入上表现如何；若暂时没有足够数据，就把结论写成待验证，而不是宣称已经提升团队效率。

## 可以用四周做一次小范围试点

| 周次 | 重点 | 交付物 |
| --- | --- | --- |
| 第一周 | 选一个高频任务，收集脱敏需求与失败样本 | 样本集、已知问题清单 |
| 第二周 | 固定 Prompt、必要输入和输出格式 | 可评审的模板 |
| 第三周 | 根据使用平台封装 Skill，并做回归 | Skill 初版、评估记录 |
| 第四周 | 邀请小组成员试用，收集问题并决定是否推广 | 使用说明、改进事项、推广决定 |

四周只是一个便于讨论的试点节奏，不是所有团队都必须遵守的标准。若样本不足、输出不稳定或维护者缺席，先暂停推广可能比仓促扩大使用更合适。

## 从工具使用回到质量责任

Prompt 和 Skills 都只是承载方法的形式。团队真正需要维护的是输入是否可信、步骤是否适用、输出是否可追溯，以及失败后如何修正。Skill 可以降低重复交代的成本，却不能替人确认需求、判断风险或承担发布决策。

团队版的质量闭环要把这些工作连起来：记录每轮任务的输入、Agent 和模型版本、输出、发现的问题与人工调整；验证修正是否有效；再把确认过的规则、案例和做法更新到共享上下文、Prompt、Skill 与回归样本中。业务流程变了，或者团队换了工具和模型，都要重新评估并继续迭代。团队沉淀的不是一份永远正确的模板，而是一套能根据证据持续修正的方法。

本系列依次讨论了直接对话、Prompt、Skills、效果对比、用例审查、自动化和团队复用。是否引入更复杂的智能体，应由实际任务和证据决定；自动化程度本身不是目标。
