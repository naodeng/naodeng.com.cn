直接提问、Prompt 和 Skills，哪种方式更适合做测试？只看几段输出很难回答。模型版本、需求材料、对话历史、运行设置都可能影响结果；如果每组条件不一样，最后比较的就不是三种方法，而是三个不同实验。

这篇先给出一套对比方法。学习资料中没有真实跑分，所以这里不声称哪种方式胜出。等用同一份样本完成实验后，再把结果填进记录表。

## 先准备评审参照

对比手机号验证码登录需求时，先由了解业务的人整理一份参考清单：已确认规则、重要风险、待确认问题和可接受的输出要求。比如已确认验证码 5 分钟有效，但“恰好 300 秒”如何判定仍未确定；模型提出这个问题可以算发现缺口，擅自选定答案则应记为无依据结论。

参考清单需要在查看三组模型输出之前完成，否则评审者容易把模型提到的内容误当成“标准答案”。它也不必穷尽所有可能，只需标出团队认为重要、且能说明依据的条件。

如果需求材料包含真实手机号、令牌或其他敏感信息，先脱敏，再用于三组对比。

## 控制输入，只改变使用方式

准备三组：

- 直接对话：用简短自然语言提出相同的测试任务；
- Prompt：使用前一篇 Prompt 测试设计文章中的结构化模板；
- Skills：调用一个经过检查的需求分析或测试设计 Skill。

三组都使用同一份需求和上下文资料、同一模型版本与参数，并尽量使用同一个宿主工具及相同工具设置；组间只改变直接对话、Prompt 或 Skill 的指令方式。若工具或设置无法保持一致，应在报告中说明，此时比较的是整套工具配置，不能把差异单独归因于 Prompt 或 Skill。每次从干净会话开始，避免某组继承前一轮的提示。

记录工具、模型、Prompt 或 Skill 的版本，以及从开始到结果可交付的总时间。建议每种方式至少重复运行三次，观察结果是否稳定，而不是只挑最好的一次展示。三次只是初步观察，不能证明统计显著，也不能代表其他需求；如果预算或时间不允许，也要在报告中说明运行次数和限制。

## 不按用例数量给分

| 观察项 | 怎么记录 |
| --- | --- |
| 关键缺口发现 | 识别出多少条预先标注的重要未知项 |
| 无依据结论 | 把多少未确认规则写成确定事实 |
| 风险覆盖 | 是否触及重要状态、边界、失败路径和副作用 |
| 可执行性 | 前置条件、步骤、结果是否能在项目中落实 |
| 格式合规 | 是否满足约定的输出字段和追溯要求 |
| 结果稳定性 | 多次运行是否反复发现相似的问题，评分波动多大 |
| 人工成本 | 补充对话、审查和修订分别花了多久 |

如果团队想计算比例，要先说明分母是什么。例如“关键缺口召回率”可以按发现的已标注关键缺口除以参考清单中的关键缺口计算。它只衡量这份清单中的内容，不代表所有未知风险都已经被找出。

如果要把完整度也纳入评分，可以先约定每项的判定依据，再让评审者独立打分。例如 0 表示未发现，1 表示提到了但缺少来源或行动条件，2 表示引用依据并说明下一步。无依据结论应单独计数，不能被其他项目的高分抵消。这个刻度只是实验团队可调整的示例，正式运行前要写入评审规则。

## 结果需要结合任务解释

假如直接对话很快就找到了主要问题，而 Prompt 和 Skill 只让格式更统一，那么简单任务可能没必要增加模板维护成本。若 Skill 明显减少了遗漏和返工，也要检查它是否依赖更多资料、是否更难维护。若三种方式分数接近，选择更轻、团队更能持续使用的方式也很合理。

比较时还要留意评审偏差。可以先隐藏结果来源，由两名评审者按同一标准打分，再讨论分歧。把“看起来专业”与“有证据、能执行”分开，避免熟悉某种工具的人天然给它更高评价。

对有分歧的条目，先回到需求和参考清单，记录双方引用的证据，再决定评分规则是否需要补充。不要先取平均分掩盖分歧；若评审者对关键缺口的定义不同，应先修订清单或标明判断未达成一致，再比较三种方式。

对比结果还要用于质量改进循环：记录哪些输入导致遗漏、哪些上下文减少了猜测、人工修订集中在哪里；据此调整 Prompt、Skill 或使用流程，再用同一组样本复核。更换 Agent、模型或业务场景后，应重新检查适用性，不能沿用旧排名。实验要回答的是：对这类任务，哪种方式在质量、时间、重复使用和维护成本之间更合适？下一篇会转向生成结果本身，检查测试用例是否覆盖需求和风险。
