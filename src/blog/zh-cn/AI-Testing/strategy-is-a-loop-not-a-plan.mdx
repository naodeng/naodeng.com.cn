多数战略并非一开始就错了，而是曾经正确，后来却再没人回头检查。管理层花一个季度写方案，汇报时大家鼓掌，之后文件就被归档。半年后，市场变了，组织也调整了，关键假设悄悄失效。战略仍原封不动地放在内网，团队却开始各自做决定，因为那份文件已经无法描述他们面对的现实。

问题不一定出在最初分析，而在于把战略当成一份待执行的文档，而不是需要持续运转的纪律。

Ragan McGill 将 John Boyd 的 OODA 循环与 Richard Rumelt 的战略内核放在一起。Boyd 曾是美国空军战斗机飞行员和军事战略家；他的模型面向竞争激烈、局势不确定的环境，强调比对手更快、更准确地完成判断循环。Rumelt 说明好战略应包含什么，Boyd 则说明如何让战略保持鲜活。

## 两个模型为战略循环补上不同部分

Boyd 的 OODA 循环包含 **Observe（观察）、Orient（理解局势）、Decide（决策）、Act（行动）**。这不是四个地位相同的方框。Boyd 把 **Orient 视为循环的重心**：经验、思维模型、组织文化和新信息共同构成对当前局势的理解。这种理解会影响人们注意什么、认为有哪些选项，以及采取什么行动。局势判断错了，后续每一步都可能出错，速度再快也无济于事。

Rumelt 在《好战略，坏战略》中提出的战略内核包含三部分：

- **诊断**：解释正在发生什么，找出关键挑战。
- **指导方针**：选择应对挑战的总体路径。
- **连贯行动**：安排彼此协调、相互增强的具体步骤。

McGill 将两种模型映射为四阶段循环：

| 战略阶段 | Boyd 的 OODA | Rumelt 的战略内核 | 产物 |
| --- | --- | --- | --- |
| 收集信号 | Observe | — | 事实、变化和意外 |
| 提炼洞察 | Orient | 诊断 | 对关键约束的可检验解释 |
| 建立指导方针 | Decide | 指导方针 | 做什么，以及明确不做什么 |
| 安排连贯行动 | Act | 连贯行动 | 有顺序、能彼此支撑的行动 |

这里有一个重要区分：**识别真正的问题属于 Orient，而不是 Decide。**诊断是在理解局势；Decide 应专注于选择应对方式，而不是还在寻找问题是什么。

## 观察真实工作，不只看仪表盘

战略应从诚实观察现实开始，不只是看季度报告里的情况，也要看团队每天实际经历的工作。

工程组织的信号可能来自：

- **系统数据**：流动指标、DORA 指标、事故、成本和可靠性；
- **人员**：认真倾听工程师、产品经理和管理者的开放式反馈；
- **客户**：他们使用什么、抱怨什么、在哪一步放弃；
- **外部环境**：市场变化、法规、技术和竞争者；
- **工作本身**：任务在哪里等待、在团队间来回退回，或卡住不动。

仪表盘只呈现过去有人决定测量的内容；对话能揭示没人想到要计数的问题。最好的观察往往来自工作现场，亲眼看看流程如何运行。

观察阶段需要广泛收集信号，也要对现有判断保持谦逊。Boyd 的观点提醒我们，既有判断会影响观察：如果管理层已经认定问题是人手不足，就可能到处都看到人手不足。要有意识地寻找能够推翻当前看法的证据。

**找到症状背后的关键约束。**

原始观察只是数据。洞察来自不断追问“为什么”，直到解释触及结构性原因。目标不是列出二十个问题，而是找到一两个关键约束：如果它们得到解决，其他问题也会随之松动。

设想交付速度慢，团队提出要增加工程师。

**观察**：交付很慢，大家认为需要更多人手。

**诊断**：团队边界横切价值流，几乎每个重要变更都要三个或更多团队协调，所以工作的大部分时间花在等待，而不是实际推进。继续招聘可能只增加交接次数，并不会让流动更快。

同一组信号可以导向完全不同的战略，差别就在诊断如何塑造了团队对现实的理解。

好的诊断能简化复杂情况但不歪曲事实，解释症状而非罗列症状，让一些应对方式显得更有希望，并且**可以被证据推翻**。例如，跨团队等待时间明显下降，交付周期却没有改善，就说明诊断可能需要修正。

Cynefin 这类情境判断框架也能帮助团队选方法。繁复问题（complicated，因果关系可分析）适合专家分析；复杂问题（complex，因果关系会随互动而涌现）则可能需要小范围试探，再观察结果。应由问题的性质决定应对方式，而不是先选好方法再强套给问题。McGill 在另一篇文章中进一步解释了组织为什么会误判问题类型。

不要从“我们交付慢”直接跳到“要成立平台团队”“要采用 SAFe”或“要全面引入 AI”。这些都可能是还没有问题定义的答案。如果组织无法用几句话说清诊断，就还没准备好做战略选择。

## 选择一条有代价的指导方针

指导方针处于总体目标与具体项目计划之间。它能收窄选择、引导精力。针对上面的例子，方针可以是：

- 按价值流组织团队，而不是按技术组件划分；
- 团队对自己构建和运行的系统承担端到端责任；
- 平台能力采用自助服务，不建立排队等审批的工单流程。

每一种选择都有成本。按价值流组队，可能会失去部分专家集中管理带来的效率。代价不是需要掩饰的麻烦，而是战略取舍的一部分。战略既要说明做什么，也要说明不做什么。

可以用一个问题判断这是否真是选择：**一个理性的人会不会支持相反做法？**“交付高质量软件”不是战略选择，因为没人主张低质量；“优先优化流动效率，而不是每个团队的利用率”才是选择，因为不少组织会主动优先考虑利用率。

“成为世界级团队”“交付速度翻倍”“转型为 AI 优先组织”都只是目标，不是指导方针。它们说了希望到哪里，却没有说明如何到达、愿意接受什么代价。

**让行动彼此支撑。**

如果指导方针到了周一早上却什么都没改变，它就只是一句好听的话。连贯行动需要把方针转化为彼此协调的工作：

| 一组互不关联的倡议 | 相互支撑的行动 |
| --- | --- |
| 发起开发者体验调查 | 先为价值最高的两个团队重划边界 |
| 更换工单工具 | 提供这些团队马上能用的标准化部署路径 |
| 安排敏捷培训 | 把环境配置改为自助服务 |
| 举办创新周 | 每月测量等待时间和流动情况，验证诊断 |
| 招聘平台负责人 | 停止资助依赖旧组织结构的项目 |

右侧的行动都来自同一指导方针，彼此推动，合在一起比单项相加更有力量。注意，其中一项是停止做某些事。战略既要投入资源，也要释放容量。好的行动有明确顺序、有真实人员和预算，也能观察是否有效。

二十个只拿到一半资源的倡议，往往说明组织在逃避选择，而不是拥有战略。

## 把每次行动的结果带回下一轮

采取行动会改变系统。团队和客户会回应，竞争环境也可能变化，原来的诊断因此会过时。战略循环就是一个持续学习过程：

- **诊断是一项假设**，是当前最好的解释，不是永远不变的真理；
- **指导方针是一场押注**，组织押注这条路径能解决关键约束；
- **行动是一组实验**，会产生新的证据；
- **新证据进入下一轮观察**，用来确认、修正或推翻原假设。

在复杂系统中，因果关系往往要行动之后才看得清。组织无法只靠事前分析消除不确定性，而要通过行动、观察反馈和回应来学习。循环的价值，就在于承认不确定性，而不是假装它不存在。

**共同理解让团队可以自行行动。**

Boyd 完整的 OODA 图中，Orient 还可以直接连接 Act，这通常称为**隐含引导与控制**。如果团队对局势和行动意图有共同理解，就不必把每个局部决定都送到中央审批，而能在共识范围内迅速、协调地行动。

如果团队理解“我们优先优化流动，而不是利用率”，就可以自行决定先做什么、是否承担某项依赖、何时拆分工作，而不必逐项升级审批。指导方针本身就能协调日常选择。

这正是**对齐与控制**的区别。控制依赖集中决策，组织越大越容易变慢；共同理解则更容易扩展。

**按学习节奏安排复查。**

Boyd 所说的速度，不只是做事更快，而是更快、更准确地完成一个循环：缩短发现变化到作出有效回应之间的时间。在组织里，这种竞争优势转化为更快的学习循环。如果战略一年只复盘一次，组织也就只有一次集中检验和修正的机会；持续运行循环，则能积累多轮学习。时间一长，一个组织依赖去年的地图，另一个组织已经根据上周看到的情况调整方向。

这不意味着每个星期五都要重写战略。循环不同阶段可以有不同节奏：

| 阶段 | 建议节奏 | 重点 |
| --- | --- | --- |
| 观察 | 每周或持续进行 | 流动指标、事故、对话、客户信号 |
| 理解局势 | 每月 | 诊断仍能解释现状吗？有什么意外？ |
| 决策 | 每季度 | 指导方针还合适吗？要改动或停止什么？ |
| 行动 | 持续进行 | 团队在方针范围内推进连贯行动 |
| 全面重审 | 每年或重大变化后 | 重新检视整个战略内核 |

这只是建议节奏，不是统一标准。指导方针应足够稳定，让团队可以依赖；行动应灵活调整；对局势的理解则要持续更新。

## 把战略写在团队用得上的一页里

McGill 建议用一页纸呈现战略，每个阶段各有一个用白话写成的区域。如果一页仍讲不清楚，战略可能还没有真正想透。

| 区域 | 提示问题 |
| --- | --- |
| 观察 | 我们看到什么？什么出乎意料？哪些内容没有测量？ |
| 提炼洞察 | 实际发生了什么？关键约束是什么？什么证据会推翻诊断？ |
| 指导方针 | 采用什么路径？明确选择不做什么？由谁作出决策？接受哪些取舍？ |
| 连贯行动 | 先做什么？行动如何彼此增强？每项行动由谁负责、分配多少产能？要停止什么？用什么指标衡量结果、何时复查？ |

**哪些做法会让循环失效。**

| 陷阱 | 表现 | 改进方向 |
| --- | --- | --- |
| 把目标当成战略 | “成为世界级工程组织” | 说清选择与代价 |
| 跳过诊断 | 一上来就推熟悉的方案 | 先用简短、可证伪的陈述说明关键问题 |
| 只列症状 | 二十个问题，没有优先级 | 找出能解释多数症状的结构性原因 |
| 堆叠倡议 | 行动很多，却彼此无关 | 检查每项行动是否符合指导方针 |
| 定完不管 | 年度战略再也不回顾 | 建立持续观察和重新理解的节奏 |
| 固守既有判断 | “问题我们早就知道了” | 邀请质疑，主动寻找反证 |

## 把循环用于质量工程

以下内容是把 McGill 的框架应用到质量工程，并非原文直接观点。

测试策略也可能变成一份归档文件：列出界面、接口、性能、工具和执行周期，却很少根据证据调整。更有效的 QA 战略应联系线上逃逸缺陷、反馈时间、故障诊断成本、用户影响和交付风险变化。

例如，回归时间从 35 分钟涨到 95 分钟，重试越来越多，关键缺陷仍然逃逸。诊断不一定是“测试数量不够”，也可能是界面端到端测试重复、共享环境争用和不稳定测试掩盖了可信信号。指导方针可以转向可靠反馈：保留少量关键 E2E 流程，把适合的规则下沉到 API 或组件测试。行动则包括去重、隔离数据、治理不稳定测试、按风险选择回归范围、停止奖励单纯的测试数量，并每月复查反馈时间和逃逸缺陷。

目标不是把测试组合改造成某个预设形状，而是根据真实成本和风险持续调整。

建设技能、智能体、评估或测试审查工具的 AI 原生 QA 团队也可以运行同一个循环：观察真实项目中的失败、误报、审查投入和实际采用情况；诊断当前的信任瓶颈；选择适用范围清楚的指导方针；再投入能够检验诊断的行动。不要只因 AI 成为热点，就同时铺开一堆方向。真实项目验证、质量结果，以及有意暂缓的方向和原因都应留有记录；最后一项能说明团队确实在作取舍，而不只是在堆功能。

**结语。**

Rumelt 说明了战略的内容，Boyd 让这些内容持续运转。最好的战略不是声称永远正确的文件，而是能够发现自己何时开始失效，并及时调整的机制。

**诚实观察，谨慎理解，清楚决策，连贯行动，然后再跑一轮。**
