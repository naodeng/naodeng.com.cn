危险的定时智能体故障，往往不是程序明显崩溃，而是**失败看起来像成功**：GitHub 凭据过期后，报告却说“没有待处理的 PR”；Slack 返回结果不明确，系统却把消息记为已发送，之后再也不处理那条更新。

本文依据 Lance Martin 与 CJ Avilla 的分享《Building Effective Agent Automations》整理。原文以 Claude Managed Agents（测试版）生成每日简报为例。下文的质量工程检查与落地建议是本文延伸，不是演讲者报告的验证结论。

原文：Building Effective Agent Automations: https://claude.dev/blog/building-effective-agent-automations/
参考实现：Daily Brief: https://github.com/anthropics/claude-quickstarts/tree/main/managed-agents/daily-brief

## 一、把定时智能体看成有状态的分布式工作流

这类自动化至少包含六个部分：**数据来源**（如 Slack、GitHub）、**输出目标**（允许写入的目标位置）、**智能体**（有版本记录的指令与工具）、**调度器**（何时启动）、**记忆**（偏好与运行状态），以及**护栏**（权限和预算）。

每次运行都可能从全新的沙箱开始，不能假定上一次会话还在。需要明确保存状态。一轮可靠的处理大致是：读取用户偏好和各来源的书签，获取新增内容、去重并筛选可行动事项，再次确认事项状态，核对输出位置，发布并验证是否成功，最后才更新书签和处理记录。

## 二、书签比固定时间窗口可靠

“读取最近 24 小时”看似简单，却会在任务延迟、重试或时区变化时漏掉更新，或重复处理旧内容。更稳妥的方式是给每个来源分别保存书签，从上次确认处理到的位置继续读取。时间戳不唯一时，可以用稳定标识符辅助排序；读取时稍作重叠，再通过去重抵御时间粒度较粗和数据延迟可见的问题。

关键在于：**读取成功，不代表内容已经处理完成。**只有对应输出得到确认后，才能推进书签。某个来源读取失败，也不能把它当成“没有新内容”；应保留原书签，在条件允许时继续处理其他来源，并明确说明本次覆盖不完整。

## 三、发布是副作用，必须确认结果

发布之前，先用当天简报的唯一标识检查目标频道里是否已有相同内容。对于 Slack，只有响应中同时出现 `ok: true` 和消息时间戳 `ts`，才能作为明确的成功回执。得到回执后，再更新处理记录和来源书签。

若请求超时，系统并不知道消息究竟有没有发出去。此时应进入“可能已发布”状态，回查 Slack；确认前不要再次发送，也不要提前提交进度。

参考实现会由定时智能体自动发布；Slack 回执只能证明消息送达，**不代表有人审核过内容**。如果流程要求发布前审核，就应把审批设计成明确的状态；否则，应严格限制机器人的写入范围，并让依赖简报的人清楚知道它会自动产生发布副作用。

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| posting | 正在尝试发布或等待结果 | 检查目标位置并确认发送 |
| posted | 已收到明确的远端回执 | 更新处理记录和书签 |
| maybe_posted | 响应不明确 | 先回查，再决定是否重试 |
| source_partial | 部分来源不可用 | 清楚说明缺少哪些来源 |

发布前查重属于应用层的幂等保护，**不等于系统获得了原子性的“恰好一次”保证**。两个任务并发时仍可能同时通过查重。生产实现还可能需要持久化运行标识、互斥锁、发布意图记录和恢复流程。

## 四、相关性与新鲜度比数量重要

只有确实需要今天采取行动，或会改变近期决策的事项，才值得进入简报。“有 12 个未合并 PR”本身并不说明读者该做什么；反复出现但仍未解决的事项，可以压缩成“仍在等待，已第 3 天”。

发布前，应重新读取每个候选事项的当前状态：移除已解决事项，更新状态已变更的事项，无法核实的内容则不发布。链接应直接复制来源返回的地址，不要根据猜测拼接标识符。少报一条低优先级内容，通常比发出一条过时的行动提醒更不伤信任。

## 五、把用户偏好与运行状态分开

用户维护的 preferences 应对智能体只读，内容包括频道、仓库、排除项、篇幅上限和输出位置；书签、处理记录、运行日志和来源专属备注，则放在可写的 state 存储中。

每次运行都重新读取偏好。如果读取不到，就明确停止或报告失败，不要悄悄退回旧提示词里的默认值。为偏好记录版本，便于解释某条内容为什么被排除。简洁的处理记录至少应包括报告日期、来源、稳定标识符、当前状态和上次报告时间。

## 六、最小权限与预算也是可靠性控制

GitHub 凭据尽量只读；密钥通过保险库提供；输出主机使用允许列表。来源消息属于不可信内容，可能包含提示注入指令，不能因此改写用户偏好或触发仓库修改。Slack 机器人也只应获得目标频道所需的写入权限。

原分享建议先把单次运行预算设为平常成本的约 3 至 5 倍，再根据真实消耗收紧。这只是起步经验，不是通用上限。预算耗尽应成为独立、可见的暂停状态，不能被误报为“没有更新”。

## 七、从故障注入中验证质量

不要只检查正常路径。可以主动制造故障，并事先写清系统该如何响应：

| 注入情况 | 预期行为 |
| --- | --- |
| GitHub 令牌过期 | 显示来源读取失败，书签保持不变 |
| Slack 超时，但消息实际上已发出 | 标为结果不明确，回查后避免重复发布 |
| Slack 明确拒绝消息 | 不提交已发布记录或书签 |
| 调度延迟三小时 | 不漏读更新，日期按配置的时区计算 |
| 两次运行重叠 | 通过锁或去重阻止重复简报 |
| 起草时 PR 已合并 | 最终核验时移除过期提醒 |
| 用户修改排除项 | 下一轮读取新版本偏好 |
| 来源消息含恶意指令 | 不产生未授权写入或偏好修改 |
| 达到预算上限 | 明确暂停并告警，不伪装成成功 |

这些检查还能变成可验证的不变量：来源读取失败时书签不变；状态为已发布时必须有远端回执；交付结果不明时不能提交进度。另应分别跟踪上次成功读取、上次成功发布和上次健康检查时间，避免把它们混成一个“运行正常”指标。

## 八、分阶段落地

先从单一来源、持久书签和明确失败状态开始；随后加入处理记录与发布回执；再增加实时状态核验、隔离存储的用户偏好和最小权限；最后系统化故障注入，并观察成本与内容新鲜度。

可信的每日简报不需要一开始就引入多智能体编排。相同的可靠性要求也适用于 QA 汇总、PR 风险提醒、持续集成失败摘要和每周质量报告。真正可复用的不是某个模型，而是这份契约：**状态准确、失败可见、权限受限、输出可核验。**
