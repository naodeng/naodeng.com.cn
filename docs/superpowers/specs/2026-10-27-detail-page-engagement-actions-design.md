# 详情页赞助与互动入口设计

## 意图

让读者能从详情页快速访问本站赞助页，以及跳到文章点赞和评论区域；入口保持克制，不打断正文阅读。

## 目标与边界

### 目标

- 在目标详情页目录区域提供低调的“支持 / Support”入口，跳转到当前语言的 `/sponsor/`。
- 提供“评论 / Comments”快捷入口，跳至该页 Giscus 区域；无障碍名称说明目标包含点赞和评论。
- 不在标题区或正文上新增悬浮条；操作入口跟随既有目录，不遮挡阅读内容。
- 保留目标页 Giscus 现有的评论输入框顺序（位于讨论列表下方）。
- 保持中英文标签、键盘可用性、窄屏阅读体验和减少动态效果偏好。

### 不在范围内

- 不改站点全局导航、文章正文、分享、点赞/评论服务或 Giscus 的页面映射规则。
- 不增加弹窗、营销横幅、外部依赖或新的数据存储。
- 不覆盖不在本次范围内的每周简报等其他 Giscus 页面。

## 方案比较

1. **仅在标题区放入口**：最克制、实现最简单，但读者滚动后无法直接使用。
2. **全程固定操作栏**：随时可用，但会持续占用屏幕空间，并增加移动端遮挡和与“回到顶部”按钮冲突的风险。
3. **将两个入口并入既有目录区域（选定）**：桌面放在 TOC 列表之后、目录卡片底部；窄屏在目录展开时跟在完整目录列表后，折叠时跟在摘要后。QA Skill 使用自有的“本页导航”横栏，因此入口并入该导航并位于章节列表之后。标题区和正文保持原有阅读顺序，不显示固定浮动入口。

用户确认采用目录区域方案，覆盖所有 Guild 教程，并保留 Giscus 当前的输入框顺序。

## 页面范围

- 博客详情页。
- QA Skill 详情页。
- Prompt 详情页与 Prompt 工作流详情页。
- 所有 Guild 教程详情页；博客中的自动化测试文章也由“博客详情页”覆盖。
- 测试 Wiki 与 AI Wiki 详情页。

这些页面使用不同的详情布局，但已共用 Giscus 组件；实现应复用一个操作入口组件，并在对应页面模板中接入，不改列表页。

### 入口位置

- 博客：放在右侧 TOC 面板的目录列表之后；窄屏展开目录时位于完整目录列表后，折叠时位于摘要后。
- QA Skill：并入自有的“本页导航”横栏，位于章节导航链接之后。
- Prompt 与 Prompt 工作流：放在右侧 TOC 面板的目录列表之后；窄屏展开目录时位于完整目录列表后，折叠时位于摘要后。
- Guild、Wiki、AI Wiki：复用 Docs 布局的右侧 TOC 面板，入口放在目录列表之后；窄屏展开目录时位于完整目录列表后，折叠时位于摘要后。
- 无目录标题的短详情页仍需提供入口：共享 TOC 面板显示操作入口；博客和 Prompt 详情回退到页面说明区之后。
- Wiki / AI Wiki 的 H1 模板迁移仍按原设计执行：模板 H1 保留原可见文字及旧 `id`，`pageTitle` 继续供 SEO、面包屑、侧栏和结构化数据使用。保留源 Markdown、其他标题 ID 和目录行为，不通过客户端脚本重排 DOM。

### 页面范围说明

博客详情路由已覆盖所有博客文章，包括自动化测试分类文章。用户另外确认纳入 Guild 的所有教程详情；该路由按测试类型和框架组织，范围也包括 API、UI 和性能测试教程。

## 交互设计

- 目录卡片底部提供两个并排、低权重的链接：“支持 / Support”与“评论 / Comments”；不使用主色大按钮。
- “支持 / Support”通过项目的 locale URL helper 链接到当前语言的 `/sponsor/`。
- “评论 / Comments”是跳转链接，不会直接点赞、打开评论输入框或绕过登录；链接的无障碍名称说明目标是点赞和评论区域。Giscus 是跨域 iframe，外层页面不能操作 iframe 内的控件；发表评论可能需要访客通过 GitHub OAuth 授权。[Giscus 配置与登录说明](https://giscus.app/zh-CN)
- 给目标 Giscus 外层 `<section>` 增加统一 `id="page-discussion"`、`tabindex="-1"` 和 sticky-header 滚动偏移。目录入口使用 `href="#page-discussion"`。点击跳转后将键盘焦点交给讨论区外层；遵守 `prefers-reduced-motion`。锚点仍然指向外层区域，不宣称可聚焦 iframe 内部。
- 保留目标页当前的 `inputPosition="bottom"`，不更改 Giscus 共享默认值。讨论区跳转将定位到反应和评论区域开头；已有评论较多时，访客仍需在 Giscus 内滚动到列表下方的输入框。Giscus 文档说明将输入框放在列表上方可省去这一步，但用户选择保留现有顺序。[Giscus 配置说明](https://giscus.app/zh-CN)
- 保留每个详情页当前的 Giscus 加载策略（包括 QA Skill 页的 eager）。快捷跳转可能先到达一个仍在加载的 iframe 区域；页面文案和验收不得把“滚到讨论区”写成“评论框已立即可用”。
- 目标 Giscus 外层在 iframe 加载期间提供双语 `role="status"` / `aria-live="polite"` 状态；iframe 加载成功后移除加载提示，脚本失败或超时则显示暂不可用提示。即使 Giscus 配置缺失，显式目标页也保留 `#page-discussion` 锚点并说明不可用，避免 CTA 指向不存在的元素。
- Giscus 配置缺失时只渲染目标页锚点与不可用提示，不下载客户端或主题同步脚本；非目标 Giscus 页面保留原有输出和“评论 / Comments”无障碍名称。若 15 秒超时后 iframe 才加载，状态提示恢复为已加载。
- 目录入口触控高度至少 44px，使用清晰的焦点样式。入口随 TOC 面板折叠或重排，不固定在视口上。

## 响应式与可访问性

- TOC 底部入口使用项目的次要文字和轻边框样式；窄屏下两个链接仍可见、可触达，不与横向滚动的 QA Skill 章节导航混成一组。
- 所有操作使用明确的中英文可见文案、真实链接和可见焦点样式；图标仅作辅助。
- 评论跳转后焦点落在 Giscus 外层锚点；减少动态效果设置仍由页面滚动行为遵守。

## 已确认决策

- Wiki / AI Wiki：将标题提到模板中，保留现有标题 ID 与深链。
- Wiki / AI Wiki：模板标题沿用 Markdown 首个 H1 的实际可见文字；metadata `pageTitle` 保持现状。
- Guild：覆盖所有教程详情页。
- 移动端：目录展开时入口放在完整目录列表之后，折叠时放在摘要之后；不保留固定浮动讨论入口。
- Giscus：保留评论输入框位于讨论列表下方的现有顺序。

## 验收标准

- 所有目标详情页在既有 TOC 或本页导航区域显示一次两个入口；入口有正确的双语文案，Support 链接使用当前语言路径，评论链接指向本页 `#page-discussion`。
- 桌面、834px 平板和 390px 手机宽度下，入口位于目录卡片底部且不引起页面横向溢出；展开目录时排在完整列表之后，折叠时排在摘要之后，QA Skill 排在自有章节导航之后。
- 不显示固定浮动讨论按钮；“回到顶部”控件维持自身行为。
- 评论链接跳转后焦点移到讨论区外层；目标具有可见焦点反馈且不被 sticky header 遮住。
- Giscus 加载中或不可用时，讨论区锚点仍然存在且状态可被屏幕阅读器读到；成功加载后移除状态提示。目标页面各自原有的 `data-loading` 策略仍保留，页面不承诺 iframe 已立即可用。
- Giscus 反应保持启用，`inputPosition="bottom"` 保持不变；检查无评论、已有较长讨论、未授权 GitHub 用户和窄屏状态，并确认评论输入框仍位于讨论列表下方。加载/失败状态需可见；实际 iframe 内容和 GitHub 授权只在外部服务可访问时人工检查。
- 博客、Skill、Prompt、工作流、所有 Guild 教程、Wiki、AI Wiki 各抽取中英文代表页验证；检查桌面、平板和手机宽度，不遮挡正文或移动端导航。Wiki / AI Wiki 模板 H1 保持原有可见文字和 `id`；测试 frontmatter 标题与正文 H1 不同、重复标题、显式标题 ID 及缺少 H1 的回退场景。现有标题深链仍可定位，目录和其余 H2/H3 锚点不变。
- 在 1440px、834px 和 390px 下检查不同详情布局的目录入口位置、触控尺寸、键盘顺序、标签换行和页面宽度；正文长段落、代码块和移动导航状态不应被固定入口遮挡。
- 运行相关构建检查及上述入口的 E2E 验证；检查页首入口双语路径与锚点目标。
